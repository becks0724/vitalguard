> 규칙: 모듈에 손대는 모든 작업(모델·코드·문서·검증)을 날짜와 함께 기록한다. 최신이 위.

## 2026-08-28 — v6.2.0: 경보 게이트(2.8G) 신설 + trace 계약 고정
- 배경: 관제·통합 트랙 결정요청서(낙상ML_결정요청_2026-08-28) — ML 경보 경로에 충격 게이트가
  없어 수집용 게이트(1.8/1.5)가 그대로 경보 게이트였다(섀도 7일 오탐 11.2~13.8건/h). ML 담당
  회신: 결정 1=게이트 신설 승인하되 수집·경보 분리, 결정 2=work_veto 재학습(하향 기각),
  결정 3=recovery 음성 커버리지 부족 확인, 결정 4=trace 계약 additive-only 고정.
- 값 선정 근거: 트랙A 임계스윕(8/1, 낙상 189윈도)의 피크 P50=2.76G — 2.8 은 매트(완충 최악
  하한) 기준 낙상 절반이 미달이라, 수집 게이트는 유지해 미달 danger 를 계속 기록(사후 실측)하고
  경보만 게이트. 증량 재학습(v6.2.x 후속) 뒤 2.0~2.2 하향 검토.
- 구현: `ALERT_GATE_G`(모듈 상수·양 플랫폼) + `Verdict.alertGatePassed` + trace 키 2종
  (`alert_gate_g`·`alert_gate_passed`). 리포터는 게이트 미달 danger 를 not_alerted 로 확정.
- 검증: wear 246건 전체 통과(게이트 시험 2건 신규 · 팀원 진단 시험 FallCountdownOutcomeTest 는
  게이트 위 피크로 정정) · Swift typecheck ✅. 모델·임계·판정 규칙 무변경.
- 배경: handoff ⓒ·DB 실측(실효 52~54Hz) — 갤럭시 센서 지원 주기에 50 이 없어 slice 150표본이
  3초가 아닌 ~2.8초가 되고 주파수 피처가 ~8% 뒤틀림. ML 담당 결정 = 단기 리샘플(현행 모델 보호),
  장기 = 갤럭시 증량 데이터로 네이티브 재학습.
- 구현: 모듈 소속 선형보간 리샘플러(20ms 격자·공백 무보간·totalG 재계산), CollectorService 는
  리샘플러 경유로 배선(워치독은 원시 콜백 유지). 시험 4건 + wear 전체 통과.
- 판정·모델 무변경, 버전 6.1.3. 배포 판별 = trace effective_hz ~50.0.

## 2026-08-27 — v6.1.2: 갤럭시 결말(prompt_result) 유실 수정
- 발견 경로: 섀도 데이터 분석 — 갤럭시 danger 후보 54건 전부 결말 미기록(애플은 59건 정상 갱신).
  간격 실측으로 재시작 루프 기각 → 서버 코드 추적 → store.hasMonitorableSignal(빈 샘플 게이트)이
  원인. 결말 항목에 실측 신호가 없어 낙상 갱신 분기 도달 전에 폐기됨.
- 수정: prompt_result 에 fallCandidate=true 동봉(애플 폰 확장과 동일 와이어 형식). 시험도 교정 —
  v6.1.1 시험은 "결말엔 fallCandidate 없음"을 정답으로 못박아 결함을 통과시켰다(계약 출처를
  워치 축약키만 보고 폰 확장을 안 본 것이 원인). 모델·판정 무변경, 버전 6.1.2.
- 교훈: 와이어 계약 미러링은 **수신 서버가 실제로 받는 최종 형태** 기준으로 검증할 것.
