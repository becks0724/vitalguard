# VitAlGuard DB — 전체 그림

> 정리 2026-08-17 · **갱신 2026-09-26** · 기술 용어를 몰라도 읽히도록 쓴 것. 세부는 [신규 스키마 ERD](./신규_스키마_ERD.md) 참조.

---

## 한 문장으로

**현장 작업자의 안전 데이터를 받아 저장하는 DB를 새로 만들었고, 지금은 "그릇도 뚜껑도 다 만들었으니 옮겨 담는 날짜만 남은" 상태다.**

2026-08-17 에 이 노트를 쓸 때 비어 있던 **생체 데이터 그릇은 채워졌다**(워치 표 4개 · 2026-09-08~15). 시험용 사본(재현본)과 학원 서버의 새 DB가 **같은 상태로 맞춰져 있고**(설계 변경 95개 전부 적용), 앱도 새 DB만 보고 돌아간다. 남은 것은 **실제 서비스를 갈아끼우는 작업**이지 설계가 아니다.

## 1. 왜 새로 만드나

지금 돌아가는 DB(구 DB, `vitalguard`)가 있다. 그런데 급하게 만들어져서 이런 문제가 있다.

| 문제 | 무슨 뜻인가 |
|---|---|
| 시각이 **글자**로 저장됨 | `"2026-08-17"`이 날짜가 아니라 **문자열**이다. 그래서 "8월 것만 골라줘"가 위험하다 |
| 표끼리 **연결이 안 됨** | 작업자가 지워져도 그 사람 측정값이 남는다. 주인 없는 데이터가 생긴다 |
| **중복이 25%** | 같은 데이터가 두 번 들어왔는데 구분할 방법이 없다 |
| **현장 격리 없음** | A현장 관리자가 B현장 데이터를 볼 수 있다 |
| 설계도가 **코드 안에** | 문서와 실제가 다르다. 문서를 믿으면 틀린다 |

그래서 **새 DB(`VITALGUARD2`)를 처음부터 제대로** 만들고 있다.

> ⚠ 구 DB는 지금도 서비스 중이다. 새 DB가 완성되면 갈아탄다. **구 DB의 문제를 정답지로 삼으면 안 된다** — 그걸 그대로 베끼는 꼴이 된다.

## 2. 데이터가 어디서 오는가

우리 시스템은 **다섯 갈래**로 데이터를 받는다.

```
가스포드(ESP32)  ──▶ 산소·일산화탄소·황화수소·온습도     ──▶ gas_reading
CCTV AI(젯슨)    ──▶ 안전모 착용 여부 · 낙상 판정        ──▶ ppe_minute_stat · vision_fall_event
                 ──▶ 화면에 띄울 사진 한 장(5초마다)     ──▶ cctv_frame          ← 2026-09-25 추가
AED 알람(라파)   ──▶ 제세동기 자가진단                   ──▶ aed_self_test
워치·태블릿 앱   ──▶ 심박 · 산소포화도 · 위치 · 낙상      ──▶ watch_vital · watch_location · watch_fall_event   ← 채워졌다
기상 API         ──▶ 온도 · 습도 · 미세먼지              ──▶ weather_reading
```

**가장 큰 구멍이던 생체 데이터는 메워졌다.** 2026-09-07 에 워치가 실제로 무엇을 읽어 보내는지(앱 사양)를 받아 설계했고, 표 4개(`wearable`·`watch_vital`·`watch_location`·`watch_fall_event`)로 들어갔다. 설계 갈림길 W-1~W-9 도 전부 닫혔다([신규 스키마 ERD](./신규_스키마_ERD.md) §17).

> ⚠ 옛 DB의 **57개 항목을 그대로 베끼지 않았다.** 워치가 실제로 내는 것만 받는다 — 워치가 계산한 심부체온·스트레스 같은 값은 **받지 않고 서버가 다시 계산한다**(계산식이 바뀌면 과거까지 다시 판정할 수 있어야 하기 때문이다). 낙상 학습용 원시 신호는 일반 표와 섞지 않고 `ml` 스키마로 따로 뺐다.).**

## 4. 데이터를 지키는 세 겹

이게 핵심이다. **층이 다르고, 막는 것도 다르다.**

### 1층 — 제약(CHECK): "값이 말이 되는가"

들어오는 값의 범위를 못 박아 둔다.

```
산소 농도   0 ~ 100 %          습도    0 ~ 100 %
일산화탄소  0 ~ 10,000 ppm     기압    800 ~ 1200 hPa
온도       -50 ~ 100 ℃         배터리  0 ~ 10 V
```

관계까지 본다 — **낙상자 수는 전체 인원보다 클 수 없다.**

> 침입자가 없어도 생기는 문제를 막는 층이다. 센서 고장, 앱 버그, 계산 실수.

### 2층 — RLS: "남의 것을 못 보게"

**RLS(Row Level Security, 행 수준 보안)** = DB가 조회에 조건을 **자동으로 덧붙여** 볼 권한이 없는 줄을 안 보이게 하는 기능.

앱이 이렇게 써도 —

```sql
SELECT * FROM 위치기록;          -- 조건 없음
```

DB가 알아서 이렇게 바꿔 실행한다.

```sql
SELECT * FROM 위치기록 WHERE 본인 것이거나 관리자;
```

**앱이 실수로 조건을 빠뜨려도 남의 데이터가 안 나간다.** 통제가 사람의 기억력이 아니라 DB 구조에 들어간 것이다.

현재 **74개 표 전부에 켜져 있고**(그중 73개는 표 주인에게도 적용되는 강제 모드) **정책이 275개**다.

> ⚠ **RLS의 한계 세 가지**
> ① **줄 단위지 칸 단위가 아니다** — 동료 줄이 보이면 그 줄의 비밀번호 칸까지 딸려 나온다. 그래서 민감한 칸은 따로 암호화한다.
> ② **세션 설정으로 우회된다** — 정책이 `지금 접속한 사람이 누구인가`를 세션 변수로 판단하는데, 그 변수는 아무나 바꿀 수 있다.
> ③ 따라서 **"RLS가 있으니 해킹당해도 안전하다"는 계산은 성립하지 않는다.** RLS는 *앱의 실수*를 막는 층이지 *침입자*를 막는 층이 아니다.

### 3층 — 트리거: "서버가 강제로 덮어쓴다"

**트리거** = 데이터가 들어오거나 바뀔 때 DB가 자동으로 실행하는 코드.

두 가지로 쓴다.

**① 시각·행위자를 서버가 정한다**

기록을 남길 때 "언제, 누가"를 **보내는 쪽이 정하게 두지 않는다.** 서버가 덮어쓴다.

> 그래서 *"내가 아니라 관리자가 2001년에 했다"* 는 기록을 심을 수 없다.

**② 원천 측정값은 아예 못 고치게 한다** *(2026-08-17 추가)*

가스 측정값·낙상 이벤트·안전모 통계는 **수정도 삭제도 안 된다.**

> 사고가 났다. 당시 산소 농도가 17%였다. 누군가 19.5로 고치려 하면 **DB가 거부한다.**
> 값을 바로잡아야 하면 원본을 고치지 말고 **정정 줄을 새로 추가**한다. 원본이 남아야 "무엇을 잘못 쟀는지"가 보존된다.

**이 층이 RLS보다 강한 이유** — RLS는 세션 설정 한 줄로 우회되지만, 트리거는 그렇지 않다. 끄려면 **설계 변경 명령(DDL)**을 써야 하고 그건 흔적이 남는다.

## 5. 법이 요구하는 것

### 위치정보법 — 의무가 **둘로 갈린다**

여기를 섞으면 판단이 통째로 틀린다.

|        | 누구에게                    | 어기면                    |
| ------ | ----------------------- | ---------------------- |
| **동의** | **누구든지** — 사업자든 아니든 무조건 | 3년 이하 징역 또는 3천만원 이하 벌금 |
| **신고** | **사업으로 할 때만**           | 같은 처벌                  |

**동의**는 프로토타입이라고 빠져나갈 수 없다. 조문 주어가 "누구든지"다.
예외는 **119·경찰이 요청한 경우**와 다른 법에 특별 규정이 있는 경우 **셋뿐**이다.
⚠ **우리 낙상 감지는 여기 해당 안 된다.** 119가 요청한 경우를 말하는 것이지 우리 자체 판단이 아니다.

**신고**는 실증 단계면 아직 아닐 여지가 있다. 유상으로 제공하거나 계속·반복하면 그때부터 사업이다.

### 확인자료 — **위치값을 담지 않는 기록**

법은 "언제 누가 위치를 수집·제공했는지"를 **자동으로 기록**하라고 한다. 그런데 그 기록에는 **위치값 자체를 넣지 않는다.**

> 왜? 법이 "개인위치정보는 목적 달성 시 즉시 파기하라"고 하면서 "확인자료는 보존하라"고 한다.
> **한 줄에 둘 다 있으면 지워야 할 것과 남겨야 할 것이 충돌한다.**

그래서 새 표 두 개를 만들었다 — 수집 확인자료 · 제공 확인자료. **둘 다 위경도 칸이 없다.**

### 영상 (CCTV)

- 근거는 "시설의 안전 및 관리" — 성립한다
- **안내판 필수** (설치 목적·장소·촬영 범위·시간·관리책임자 연락처)
- **녹음 금지** — 카메라에 마이크가 있으면 꺼야 한다
- 운영 방침은 개인정보 처리방침에 포함시키면 갈음된다

### 놓치기 쉬운 것 — 노사협의회

> **근로자참여법 제20조** — *"사업장 내 **근로자 감시 설비의 설치**"* 는 노사협의회 협의 사항

우리 시스템이 정확히 그것이다. **상시 30명 이상 현장이면 협의를 거쳐야 한다.** 개인정보 동의를 다 받아도 **별개 절차**다.

### 보호자 정보 — 주인은 보호자다

작업자가 보호자 연락처를 입력한다. 그런데 그 정보의 **주인은 보호자**이지 작업자가 아니다.

문자·알림톡이 막혀 있어(사업자등록 없음) 이렇게 우회한다.

```
① 작업자가 입력 → "동의 대기" 상태로만 저장 (알림 안 감)
② 작업자가 보호자에게 동의 링크를 직접 전달   ← 우리가 안 보내는 게 핵심
③ 보호자가 열어서 동의 → 그 접속이 증적
④ 동의 후에야 알림 대상이 됨
```

⚠ **한계** — 링크를 연 사람이 진짜 그 보호자인지 확인할 수단이 없다. **"동의를 받았다"고는 해도 "본인임을 확인했다"고는 못 한다.**

## 6. 통신 구간 암호화 (TLS)

DB로 오가는 데이터가 도청되지 않게 하는 것.

| 단계 | 도청 | 사칭 | 상태 |
|---|---|---|---|
| 평문 | ✕ | ✕ | 2026-08-12까지 이랬음 |
| **검증 없는 암호화** | **○** | ✕ | **← 지금. 여기가 상한** |
| 신원 검증까지 | ○ | ○ | 학원 협조 필요 → **불가** |

위로 못 가는 이유 — 서버 인증서를 바꾸거나 파일을 받아야 하는데 **학원에 요청할 수 없다.**

**구멍은 소스에서 막았다.** 접속 설정 파일에 암호화를 못 박아서, **코드가 실수해도 평문으로 못 간다.**

> 실제로 오늘 발견한 문제였다 — 구축 도구 3개가 평문으로 붙고 있었고, 그 상태로 새 DB를 만들고 있었다. 접속도 되고 쿼리도 되니 **아무 신호가 없었다.**

## 7. 오늘까지 한 것

| | 2026-08-17 | **2026-09-26** |
|---|---|---|
| 마이그레이션 | 56개 | **95개** 적용 완료 |
| 표 | 58개 · 컬럼 554개 | **74개 · 컬럼 797개** |
| 제약 | CHECK 221 · 외래키 185 · 기본키 114 · 고유 85 | CHECK 174 · 외래키 118 · 기본키 74 · 고유 34 |
| 보호 | RLS 정책 164개 · 트리거 92개 | **RLS 정책 275개 · 트리거 145개** |
| 자동 검사 | 17종 | **18종** — 돌려서 **0행이면 정상** |

> ⚠ **제약 숫자가 줄어든 것처럼 보이는 건 세는 법을 바꿔서다.** 8월 수치는 월별로 쪼갠 조각표(파티션)까지 하나씩 세었고, 9월 수치는 **원표만** 센다. 같은 제약이 조각 13개에 복제돼 있어 8월 방식은 한 제약을 14번 세었다. 줄어든 것이 아니라 중복을 뺀 것이다.

**자동 검사기가 핵심이다.** 사람이 매번 눈으로 볼 수 없으니, DB가 스스로 점검하게 만들었다.

```
DB 구조가 온전한가 · 외래키 정책이 맞는가 · RLS가 읽기/쓰기를 구분하는가
평문 접속이 있는가 · 위치 제공 통보를 빠뜨렸는가 · 원천 기록이 불변인가 · …
```

> **0행이 기본 상태여야 한다.** 매번 뜨는 항목이 있으면 사람이 "원래 뜨는 것"으로 넘기게 되고, 그 사이에 진짜 결함이 섞이면 사라진다. 이 원칙 때문에 오늘도 오탐 7건을 걷어냈다.

### 2026-08-18 — 바깥 눈으로 감사하고 12개를 고쳤다

우리 검사기 17종이 **전부 0행인데도** 뚫려 있는 곳이 있었다. 구조는 맞는데 **의미가 틀린** 경우를 검사기가 못 잡기 때문이다. 그래서 다른 AI(Grok)에게 스키마 전체를 주고 **정합성·추적성·보안성** 세 축으로 감사를 맡겼고, 나온 발견을 **하나씩 라이브에서 재현**해 봤다.

**재현된 것 12개.** 몇 가지만 옮기면:

| 무엇이 가능했나 | 왜 위험한가 |
|---|---|
| 작업자가 같은 회사 동료 계정을 **삭제** | 그 사람의 **동의 증적이 함께 사라진다.** 에러도 안 난다 |
| 작업자가 **경보의 severity 를 clear 로 변경** | 사고 당사자가 자기 SOS 를 지울 수 있다 |
| 같은 회사 작업자가 **남의 초대 이메일·전화번호를 평문 조회** | 변경이력에도 복제되고 있었다 |
| 작업자가 **안전관리비 계상액 수정** | 조달 산출물의 근거 금액이다 |
| **한 번 철회하면 다시 동의 불가** | 위치 동의를 껐다 켜는 것은 법이 보장한 권리다 |
| 가스포드로 등록한 뒤 **유형만 camera 로 바꾸면** 노사협의 게이트 통과 | 전날 만든 게이트가 무력해진다 |

**고치는 코드는 다른 AI 둘에게 맡기고, 검토와 판정만 우리가 했다.** Codex 가 052·054, Grok 이 053·055 를 썼다. 판정은 눈으로 보는 대신 **검사 스크립트로 고정**했다 — 재현했던 공격이 막히는가, 정상 동작이 죽지 않았는가(비회귀), 기존 함수를 고치면서 옛 검사를 빠뜨리지 않았는가.

**053 은 두 번 돌려보냈다.** 처음엔 적용 자체가 실패했고(타입 오류), 두 번째는 통과했지만 "경보 종료는 관리자만"이라는 기존 결정이 직접 UPDATE 경로로 새고 있었다.

> **검토에서 배운 것** — RLS 가 막으면 **에러가 아니라 「0행」**이 돌아온다. 그래서 판정 기준에 "조용한 0행도 실패"를 넣었다. 계정 삭제 차단은 그 때문에 **문장 트리거**로 만들어졌다 — 대상 행이 0개로 걸러져도 트리거는 반드시 한 번 실행되므로 사람이 알아챌 수 있다.

## 8. 남은 것

> 2026-08-17 판의 이 절은 **"설계가 덜 됐다"** 는 목록이었다. 지금은 설계가 아니라 **"갈아끼우는 날 할 일"** 목록이다.

### ✅ 그때 비어 있었는데 지금은 찬 것

| 2026-08-17 에 남은 일이라고 적은 것 | 지금 |
|---|---|
| 생체 측정 표가 없다 (가장 큰 공백) | `watch_vital` 등 표 4개로 들어갔다 |
| 작업자 위치 표가 없다 | `watch_location`(월별로 쪼갠 표) |
| 생체 데이터에 보호자 이름·전화가 5초마다 딸려 온다 | **서버가 받자마자 버린다.** 보호자 정보는 계정에만 있다 |
| 이름·사번·직급이 매번 실려 와 표기가 갈라진다(`장우진`/`장 우진`) | **번호표(계정 id)로 바꿨다.** 생체 표에 이름 칸이 아예 없다 |
| 앱이 052~055 때문에 고쳐야 할 규칙 7가지 | 전부 반영됐다(앱이 옛 DB 표를 보는 곳 0곳) |

### 🔜 갈아끼우는 날 해야 하는 것

설계가 아니라 **운영 작업**이다. 순서와 명령은 `DB재구축/15_라이브_전환_런북` 에 있다.

- **파기 크론 붙이기** — 049 위치정보 동의서에 *"7일이 지나면 자동으로 파기합니다"* 라고 적었다. 지우는 함수(`purge_watch_location` 등 6개)는 있는데 **정해진 시각에 불러 주는 주체가 아직 없다.** 앱이 새 DB로 넘어오는 순간 반드시 붙여야 한다 — 안 붙이면 동의서 문구와 실제가 어긋나고 그것 자체가 위치정보법 위반이다. ⚠ 첫 단계로 `CRON_SECRET` 회전(8/17 노출분).
- **첫 데이터 넣기** — 회사·현장·현장 좌표·담당자 계정·최고관리자 계정. 새 DB는 **비어 있는 상태로 정상**이다(시험 사본에만 시험용 행이 있다).
- **장치 등록** — 가스포드·카메라(CAM-01·CAM-03). 등록 전에는 장치를 못 찾아 거부한다.
- **키 등록** — 개인정보 암·복호 키 2개, 카메라 전송 토큰. 없으면 2단계 인증·아이디 찾기·카메라 전송이 막힌다.
- **태블릿 앱을 같은 날 배포** — 경보 확인 번호 형식이 정수에서 새 형식으로 바뀐다. 서버만 바꾸면 앱이 400 을 받는다.
- **학습 데이터 옮기기** — 낙상 학습용 734줄(도구 검증 완료).

### ⏳ 부품·측정을 기다리는 것 (설계는 끝)

- **이산화탄소 센서** — 법정 기준은 1.5%(15,000ppm)인데 흔한 모듈은 5,000~10,000ppm 에서 교정이 끝나 그 위 정확도를 주장할 수 없다. 부품 선정은 미정이고, **DB 자리는 미리 만들어 둔다**(097 · 승인 대기). 임계값은 센서가 정해진 뒤 근거와 함께 넣는다.
- **일산화탄소 전기화학 센서(ZE15-CO)** — 자리는 이미 있다(078). 부품이 오면 실측값 한 줄만 넣으면 된다.

### 🚪 우리 손을 떠난 것

- 통신 암호화를 더 올리는 것 — 학원 협조 필요
- 백업·복구 확인 — 서버 관리 권한 필요. **미확인으로 남김**
- DB 접속 기록 — 서버 설정. 지금은 **누가 접속했는지 기록이 안 남는다**
- 노사협의회 협의 — 상시 30명 이상 현장 도입 시 **사람이 하는 절차**다(DB 게이트는 만들어 뒀다)

## 자주 헷갈리는 것 정리

**"이거 전부 보안 얘기인가?"** — 아니다. **셋으로 갈린다.**

| | 묻는 것 | 예 |
|---|---|---|
| **정합성** | 데이터가 **말이 되는가** | 산소 농도가 −5%로 들어옴 |
| **추적성** | 나중에 **누가 뭘 했는지 알 수 있는가** | 사고 조사 · 분쟁 대응 |
| **보안** | 권한 없는 접근을 **막는가** | 남의 현장 데이터 열람 |

그리고 **가장 큰 문제였던 "생체 표가 없다"는 셋 중 어디도 아니었다** — 막는 게 아니라 **받는** 이야기였고, 그냥 **설계가 덜 된 것**이었다. (2026-09 에 표 4개로 메워졌다.)

**"보호자 정보를 매번 받는 것"도 보안이 아니다** — 암호화를 아무리 잘해도 *"왜 5초마다 받나"* 라는 질문에는 답이 안 된다. 그건 **개인정보 최소수집** 문제다.
