## 1. 캔버스

### 1-1. [관측] 인셋 원문

```
$ adb shell dumpsys window        (세로 · 크롬 전체창 · IME 표시 상태에서의 관찰값)
statusBars      frame=[0,0][1840,83]
navigationBars  frame=[0,2912][1840,2944]
systemGestures  frame=[0,0][63,2944]          좌
systemGestures  frame=[1777,0][1840,2944]     우
ime             frame=[0,2162][1840,2944]
```
`devicePixelRatio = 2.125` (density 340) · 전체 1840 × 2944 px

> ⚠ **이 값은 "이 창·이 방향·이 IME"의 관찰값이다.** 가로·분할창·플로팅/필기 IME·탐색 모드에서
> 달라진다. **앱은 런타임 인셋을 읽어야 하며 이 상수를 하드코딩하지 않는다.**

### 1-2. [계산] 유도값

| 값 | 산식 | 결과 |
|---|---|---|
| 전체(세로) | 1840/2.125, 2944/2.125 | 866.0 × 1385.4 dp |
| 상태바 | 83/2.125 | 39.1 dp |
| 네비바 | 32/2.125 | 15.1 dp |
| 좌/우 제스처 | 63/2.125 | 29.6 dp 각각 |
| **안전 높이** | (2944−83−32)/2.125 | **1331.3 dp** |
| **IME 위 높이** | (2162−83)/2.125 | **978.4 dp** |
| **IME로 인한 추가 손실** | 1−978.4/1331.3 | **26.5 %** |

> ⚠ **정정(코덱스 R1-4).** 이전 개정의 "29% 소실"은 **전체 높이와 안전 영역 기준을 섞은 오류**였다.
> 안전 영역 대비는 **26.5%** 다.
> ⚠ **`ime` 782px 에는 하단 네비바 32px 이 이미 포함**된다. **둘을 중복 차감하지 않는다.**
> "SafeArea 적용 후 15.1dp 를 또 더한다"는 이중 차감이다.

### 1-3. 규칙

- **C-1 [가설]** 드래그 시작점·펜 시작점·주 실행 버튼은 좌우 가장자리 **29.6dp 안쪽**으로 들인다.
  ⚠ 이 띠는 **뒤로가기 제스처 경합 영역**이지 **모든 내용의 금지 구역이 아니다.** 목록 내용·배경은
  가장자리까지 그려도 된다. "실질 조작 폭 806dp"를 정답 수치로 부르지 않는다(같은 산식으로 806.6dp).
- **C-2 [계산+가설]** 측정한 키보드가 뜨면 **세로** 안전 높이의 **26.5%**, **가로는 43.5%** 가 사라진다.
  → **키보드를 띄우는 동선을 기본값으로 두지 않는다**(요구사항 13·14의 물리적 근거 중 하나).
- **C-3 [관측된 규격]** Android 16 은 **targetSdk 36 + sw600dp 이상**에서 앱의 방향·크기 제한을
  기본적으로 무시한다. 예외·임시 옵트아웃이 있으나 **거기에 의존하지 않고 적응형으로 만든다.**
  ⚠ "세로=1단 / 가로=2단"만으로는 부족하다 — **좁은 가로 분할창은 1단, 넓은 세로는 2단**이어야 한다.
  판단 기준은 방향이 아니라 **창 크기 클래스**다.
- **C-4 [가설]** 인셋은 **시스템 바 / 디스플레이 컷아웃 / IME / 제스처**를 구분해 **한 계층에서만 소비**한다.
  회전·리사이즈 중 **선택한 사진·원본 좌표계의 스트로크·댓글 초안·대기 큐를 보존**한다.
- **C-5 [관측]** **가로에서 키보드를 띄우는 흐름을 피한다** — P4 실앱 측정에서 안전 높이의 **43.5%**가 사라졌다.
  근거는 IME **368.0dp**, 가로 안전 높이 **811.8dp**다. IME에 포함된 네비바 **15.1dp**를 중복 차감하지 않은
  추가 손실 비율은 **(368.0 − 15.1) / 811.8 ≈ 43.5% [계산]**다.
  세로 C-2의 **26.5%**는 유지한다. 이 기기·Gboard 측정 조건이며 실제 앱은 런타임 인셋을 읽는다.

P4 창·IME 근거: [device-facts.md의 실앱 측정](../research/device-facts.md) 「앱을 실제로 띄워 잰 값」.

## 2. 색 — 대비

### 2-1. [계산] 배경·전경 쌍별 대비

WCAG 상대휘도로 계산. 색 값은 관제웹 `globals.css` 토큰 그대로다.

| 배경 | **흰 글자 `#FFF`** | **잉크 글자 `#171717`** | 쓸 수 있는 전경 |
|---|---|---|---|
| 정상 `#10B981` | 2.54:1 ❌ | **7.07:1 ✅** | 잉크만 |
| 주의 `#F59E0B` | 2.15:1 ❌ | **8.35:1 ✅** | 잉크만 |
| 위험 `#EF4444` | 3.76:1 ❌ | **4.76:1 ✅** | 잉크만 |
| primary `#0D74CE` | **4.77:1 ✅** | 3.76:1 ❌ | **흰색만** |
| 흰 배경 `#FFF` | — | 17.93:1 ✅ | 잉크·body(5.94)·primary(4.77) |

> ⚠ **정정(코덱스 R1-6).** 이전 개정의 "색 배경 위 잉크 **또는 흰색**"은 틀렸다. **흰 글자는 상태색
> 3종 배경에서 전부 실패**한다. 그리고 위험 배경 위 잉크는 **4.76:1** 이지 7~8.4:1 이 아니다.
> primary 는 정반대로 **흰 글자만** 통과한다. **배경·전경은 쌍으로 고정해 계산**한다.

### 2-2. [관측] 흰 배경 위 텍스트로 쓸 수 없는 색

`정상 2.54:1` · `주의 2.15:1` · `muted 2.85:1` · `primary(다크) 2.01:1` — **본문 4.5:1 미달**.
`위험 3.76:1` 은 큰 글자 기준(3:1)만 통과.

> ⚠ 이것은 **실내·야외 공통**이다. "실내에서는 통과하는데 야외에서만 실패"라고 말할 수 없다(코덱스 지적).
> 500nit 는 **디스플레이 보고값**이지 야외 반사 측정이 아니다.

### 2-3. 규칙

- **V-1 [가설 · 2026-09-12 개정]** 상태는 **색 + 모양**으로 말한다. **모양이 곧 라벨이므로 글자를 덧붙이지 않는다.**
  글자는 **내용**(무엇이·얼마나)에만 쓴다. 접근성은 `title`·`aria-label` 로 보장한다(화면에는 안 보임).
  ```
  정상  ✓   둥근 사각      주의  !   둥근 사각      위험  !!  원형
  ```
  ⚠ **개정 사유(태곤 님 지적)** — 종전 규칙 `면 + 모양 + 한글 라벨` 3중은 **같은 말을 두 번 하게** 만들었다.
  `[✓정상] 현장 기상 — 특보 없음` 처럼 배지 글자와 옆 문장이 겹쳐 **시각적으로 번잡**했다.
  특히 입력 칩은 `[정상] 이상 없음` 으로 **3중**이었다(정상 = 이상 없음).
  ⚠ 단, **녹색·주황 면 자체가 흰 바탕 대비 3:1 미달**이므로 **면 색만으로 구분이 보장되지 않는다.**
  그래서 **글자 수(✓ / ! / !!)와 테두리 모양을 모두 다르게** 해 색 없이도 갈리게 한다.
  테두리·아이콘의 **비텍스트 대비(3:1)** 는 별도 확보한다.
- **V-2 [정책]** 관제웹 의미색 토큰을 그대로 쓴다 — **브랜드·표기 일관성 정책**이다.
  ⚠ **정정.** "색을 바꾸면 판정이 어긋난다"는 인과는 틀렸다. **판정은 서버 규칙·상태가 정하고 색은 표현**이다.
  색 유지가 판정 일치를 증명하지 않는다. 토큰 유지 정책과 **가독 대비 확보는 별개 문제**로 다룬다.
- **V-3 [가설]** 본문은 **밝은 배경 + 잉크로 4.5:1 이상**, 중요한 수치·지시는 **7:1 목표**.
  **위험색으로 핵심 문장을 크게 키워 3:1 예외를 얻으려 하지 않는다.** 위험색은 **배지·띠·아이콘 강조**로.
- **V-4 [규격]** WCAG 큰 글자 = 일반 **18pt(24 CSS px)** / 굵은 **14pt(18.67 CSS px)**, CJK 는 동등 크기.
  **dp 로 단정하지 않는다.** HTML 시안은 보수적으로 **일반 24px 또는 bold 20px 이상**을 쓰되
  실제 글꼴·두께·배경으로 검사한다. Flutter 는 **사용자 `textScaler`·Android sp 대응까지 검증**하고
  "24dp 니까 준수"라고 쓰지 않는다.
- **V-5 [가설]** 밀도 — 큰 카드 4장이 아니라 **한 패널 안 64~72dp 행 4개**. 글자 확대 시 **줄바꿈·스크롤 허용**,
  한 화면에 억지로 압축하지 않는다.

근거: [contrast-minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) ·
[non-text-contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

## 3. 터치·파지

### 3-1. [계산] 물리 크기

56dp × (25.4/160) × ... → 이 기기 밀도(340dpi, 2.125x)에서 **56dp ≈ 11.1mm**.

### 3-2. [관측] 터치 정확도와 손가락 축

P4 진단 화면 `app/vitalguard_field/lib/glove_screen.dart`에서 타깃 **40→48→56→64→72dp**를
순환시켰다. 위치 난수는 **고정 시드 7**이며, 두 조건은 같은 위치 순서를 사용했다.

**조건과 한계:** ‘천’은 실제 장갑이 아니라 **면 95% 의류 원단을 손에 감싼 상태**다.
원본 측정 기록에는 **겹수·두께가 기록되지 않았다.** 이 결과는 현장 장갑을 대표하지 않는다.

| 타깃 | 맨손 | 천(면 95%) |
|---|---|---|
| 40dp | **2/4 (50%)** · 오차 18.5 | 3/4 (75%) · 오차 12.5 |
| 48dp | 4/4 (100%) · 12.7 | 4/4 (100%) · 13.1 |
| 56dp | 4/4 (100%) · 11.5 | 4/4 (100%) · 9.5 |
| 64dp | 4/4 (100%) · 15.2 | 3/3 (100%) · 14.3 |
| 72dp | 3/4 (75%) · **69.1 — 이상치** | 3/3 (100%) · 15.4 |
| 평균 오차 벡터 | **(3.3, 12.7)** · 크기 **13.2** | (2.7, 7.7) · 크기 8.1 |
| 접촉반경 · 압력 | **0.2 · 1.000** | **0.1 · 1.000** |
| 표본 | **20** | **18** |

오차 거리와 오차 벡터의 단위는 dp다. 크기당 표본은 **3~4개**이며 **4/4는 네 번 중 실패가 없었다**는 뜻이다.
실패율 0%나 실제 장갑에서의 성공률로 일반화하지 않는다. **72dp 맨손 오차 69.1**은 원본 기록에서
측정 사고로 분류한 이상치다. 타깃 반지름 36dp에서 3/4 적중했으므로 빗나간 한 번의 영향이 크다.
이상치를 숨기거나 제외 후 통계를 새로 만들지 않는다.

**[관측] 아래 방향 편향:** 맨손 평균 벡터의 세로 성분은 **12.7dp**, 크기는 **13.2dp**다.
천 조건의 세로 성분 **7.7dp**보다 커서, 이번 기록의 아래쪽 쏠림은 천 조건에서만 나타난 현상이 아니다.
소재별 우열이나 모든 사용자의 조준 특성까지 확정하지 않는다.

**[관측] 손가락 축:** 두 조건 모두 압력은 **1.000 고정**, 접촉반경은 **0.1~0.2**였다.
펜 필압 **0.041~0.917**과 달리 유효한 손가락 압력·접촉면적 변화를 얻지 못했으므로,
**이 측정 경로의 압력·접촉면적으로 장갑 착용을 자동 감지할 수 없다.**

**[미검증] 실제 장갑:** 면 목장갑·PU 코팅장갑으로 재측정해야 한다.
코팅장갑에서는 터치가 아예 안 될 수 있다는 설명은 **[가설]**이다.
원본 수치·조건: [device-facts.md](../research/device-facts.md) 「터치 정확도 — 맨손 vs 천」.

### 3-3. 규칙

- **T-1 [관측]** 주 실행 **64dp** / 일반 **56dp**를 유지하고 **40dp는 금지**한다.
  위 실측에서 40dp 맨손은 **2/4 (50%)**였고, 48·56·64dp는 해당 소표본에서 실패가 없었다.
  이는 56dp 최소 유지의 근거이며 실제 장갑의 성공률이나 안전성을 보장하지 않는다.
- **T-2 [가설]** 자주 쓰는 실행 묶음은 **한 벌만** 둔다. 파지 쪽 하단 안쪽에 놓고 **좌/우 배치는 선택**.
  ⚠ **주 실행(저장·전송·대응확인)을 양쪽에 복제하지 않는다** — 손바닥 터치·중복 실행 면적이 늘어난다.
  (이전 개정의 "좌우 양쪽에 같은 액션" 원칙은 **철회**한다.)
- **T-3 [가설]** 손가락/펜을 **화면 영역으로 나누지 않고 입력 종류별 역할**로 나눈다.
  캔버스에서 **펜 = 그리기 / 손가락 = 허용된 이동·확대**. 도구판은 이동 가능하되 **겹치거나 갑자기
  위치를 바꾸지 않는다.**
- **T-4** 길게 누르기·스와이프**만**을 유일한 실행 수단으로 두지 않는다(항상 대체 경로).
- **T-5 [관측]** **세로로 붙은 타깃 사이 간격을 조준 편향(약 13dp)보다 크게** 둔다.
  이번 측정은 아래쪽 쏠림을 보였으며 **2026-09-12 `vgGapTap = 16dp`로 반영**했다.
  16dp는 실측 편향 크기 **13.2dp를 넘는다.** 히트박스만 아래로 옮겨 인접 항목과 겹치게 하지 않는다.
- **T-6 [가설]** **모든 핵심 동작에 펜으로 도달하는 경로**를 둔다.
  코팅장갑에서는 손가락 터치가 아예 안 될 수 있다. 펜의 입력 신호를 사용할 수 있도록
  버튼·현장 전환·기록·전송·오류 복구를 손가락 전용 제스처에만 묶지 않는다. 실제 장갑 착용 조건은 재검증한다.
- **T-7 [관측]** 실행 묶음 **한 줄에 56dp 버튼은 9개가 한계**다.
  `ActionDock` 이 가용 폭의 **90%만** 쓰고(왼손·오른손 이동 여백 · `action_dock.dart:48`),
  좌우 패딩 20+20 과 `systemGestureInsets` 가 더 빠지기 때문이다.
  세로 논리 폭은 **866dp**(1840px ÷ DPR 2.125 · `wm density` 340), 레일 80dp 를 빼면 786dp 다.
  10개(56×10 + 8×9 = **632dp**)는 들어가지 않는다. 2026-09-15 펜 툴바에서 실측했다.
  ⚠ 버튼을 더 넣어야 하면 **줄을 나누되 의미 묶음을 쪼개지 마라.**
  색 3개가 두 줄로 갈라지면 무엇이 한 벌인지 읽히지 않는다.
  ⚠ 위젯 테스트가 통과해도 실기기와 다를 수 있다 — 테스트의 화면 크기부터 이 실측값으로 맞춘다.
- **[미검증]** 620g 을 한 손으로 얼마나 드는지, 어떤 파지가 실제 다수인지 **측정 없음.**
  특정 자세를 정답으로 고정하지 않는다. 첫 터치 성공률·인접 오터치·재입력·파지 변경을 별도 기록한다.

## 5. 입력

| 수단 | 근거 등급 | 상태 |
|---|---|---|
| 레노버 OS 손글씨 | **[관측]** | **기각** — `네이버 구글` → `네ㅇ뻐7ㄱㅜ그리`(음절 조합 실패·숫자 혼입) |
| ML Kit Digital Ink | [문서] | **채택 불요** — 순정 STT로 요구 14의 수단을 정했다. 기존 동적 다운로드 조사는 보존하며 사용 불가 판정은 아님. ML Kit 인식률은 미실측 |
| 순정 STT | **[관측]** | **채택** — `createOnDeviceSpeechRecognizer`·`ko-KR`, 비행기모드 ON·Wi-Fi OFF·활성 네트워크 OFF에서 인식 확인. 후보 선택·확인 필수 |
| sherpa_onnx | [문서] | **채택 불요** — 순정 STT 사용 결정으로 폴백·설치 요청 취소 |

- **I-1 [관측]** 입력 우선순위 = **① 정형 선택지 → ② 펜 주석(변환 없이 잉크 저장) → ③ 순정 STT**.
  자유 기록은 **펜 잉크를 그대로 저장하는 경로가 1순위**, STT는 보조다. 이번 오프라인 최종 결과는
  **5건 중 1건이 1순위에서 원문과 일치**, 후보 목록에는 **5건 중 3건**의 원문이 있었다.
  이 소표본의 오인식·의미 반전이 후보 선택과 확인을 거치는 보조 입력 설계의 근거다(I-4·I-5).
- **I-2 [미검증]** 현장 소음 조건은 **측정되지 않았다.** 이전 개정의 "80~100dB·어떤 STT 도 급락"은
  이 현장의 실측도, 보편 벤치마크도 아니다. **실제 장소·거리·마이크·문장으로 평가**한 뒤에 쓴다.
- **I-3 [가설]** 기록·댓글·일정 입력을 음성 전용으로 만들지 않는다. **정형 선택지·펜 잉크 경로를 함께** 둔다.
- **I-4 [관측]** **STT 결과를 1순위 한 줄로 확정해 넣지 않는다. 최대 5개 후보를 보여주고 고르게 한다.**
  요청한 후보 상한은 5개이며 이번 실제 반환은 **3~5개**다. 반환된 후보만 원래 순서대로 보여주고,
  없는 후보를 만들거나 1순위를 미리 선택하지 않는다. 정답이 없으면 다시 말하기·수정·펜 기록 경로를 제공한다.
  오프라인 **1순위 원문 일치 5건 중 1건 / 후보 포함 5건 중 3건**은 선택 기회의 근거이며,
  사용자의 선택 성공률·보편적 정확도·향상 배수를 실측한 값은 아니다.
- **I-5 [관측]** **STT 결과를 확인 없이 저장하지 않는다.** 후보 선택 후 문장을 보여주고 사용자가
  확인·수정한 뒤 명시적으로 저장한다. 선택 자체로 저장하지 않으며, 미확인 후보·부분 결과를 업무 기록이나 전송 큐에 넣지 않는다.
  실측에서 **`작업자 두 명 안전대 미착용` → `작업자 두 명 안전띠 적용`**으로 부정이 사라졌다.
  입력 칩의 **‘이상 없음’ 기본 선택 금지**와 같은 원칙이다. 연결된 화면 규칙은
  [app_uIuX_plan.md의 R-06](../app_uIuX_plan.md)이다. 진단용 원시 로그 보존과 업무 기록 저장은 구분한다.

근거 정본: [원시 로그 251 이벤트](../research/raw/p4-stt-2026-09-12.jsonl).
결과 표: [device-facts.md §5-4](../research/device-facts.md).
비교는 **조건당 5문장 최종 결과를 문장별 1회씩**이며 온라인 오류 1건·취소 1건은 별도 보존한다.
같은 ‘미착용’ 문장이 오프라인에서는 일치했으므로 네트워크 상태가 의미 반전의 원인이라고 단정하지 않는다.

| 게이지 % 하락 속도 | 1.30 A 상당(설계용량 환산) | **약 102% 상당 — 선형 외삽 약 7.8시간** |

두 값은 **밝기 121·이번 부하의 단기 외삽**이며, 완전 방전까지 잰 사용시간이나 모든 현장 조건의 상한이 아니다.
화면 꺼짐 시간·밝기·실제 작업 부하를 포함한 장시간 실측이 필요하다.

**추가 1시간 측정 계획:** 같은 조건에서 전류값을 설계용량으로 환산하면 **7.2~7.6%/시간**, 기존 게이지 기울기는 **12.8%/시간**이다.
기존 세션의 안내 `4~5% vs 8%`는 계산 오류이므로 폐기한다. USB 분리 후 안정화 시간을 두고 전류·잔량·전압·온도·전원 연결 상태를 함께 기록한다.
한 번의 1시간 측정은 장기 기울기를 비교하는 자료이며 **센서 정확도나 불일치 원인을 자동으로 확정하지 않는다.**
인계 중 기기 읽기 확인: 밝기 217·자동밝기 OFF·기존 로거 종료·파일 보존, 외부전원 연결(AC true, USB false).
`/sys/class/power_supply/usb/online`은 없어 옛 로그의 마지막 열은 전부 `?`다. 다음 측정에서 이 열로 USB 분리를 판정하지 않는다.

9/26 추가 — 게이지 불일치 확인용 1시간 자연 방전을 시작했으나 41분에 중단(태곤 님: Compose 재작성 결정으로 불필요).
남은 기록: 19:29:55 79%(8,058mAh) → 20:11:23 72%(7,344mAh), 2,488초 동안 714mAh = **게이지 기준 1.03 A**(같은 CCTV 5초·밝기 121 조건).
current_now 평균은 로그를 지우기 전에 계산하지 않아 없다. 불일치는 그대로 "확인 필요".

절차 메모: USB 재연결 뒤 `adb devices` 가 몇 분씩 비어 있으면 `adb kill-server` 로 즉시 잡힌다(오늘 두 번).
`adb shell 'pkill -f vg_batt.sh'` 는 자기 셸을 먼저 죽여 뒤 명령이 안 돈다 — pid 로 `kill`.

### 11-1. CCTV 가 가스포드·AED 와 다른 이유 — **경로가 둘로 갈린다**

태곤 님 질문: *"가스포드나 AED는 서버에 엔드포인트를 만들고 물린 형태인데 그건 왜 그렇지?"*

**CCTV 도 서버에 엔드포인트가 있다.** 갈리는 것은 **무엇을 보내느냐**다.

| 무엇 | 경로 | 근거 | 왜 |
|---|---|---|---|
| 낙상 **이벤트**(JSON) | 젯슨 → **서버** → DB | `app/api/cctv/event/route.ts` POST | 작고, **저장해야 한다**(산업재해 자료) |
| **영상 픽셀**(MJPEG) | 브라우저 ↔ **젯슨 직결** | `CctvQuadView.tsx:14,195` `NEXT_PUBLIC_AI_CCTV_API` | 크고, **저장하지 않는다** |

`cctv/event` 는 `gaspod/telemetry` 와 **구조가 같다** — 같은 `ingestAuthStatus` · `consumeToken` ·
soft 토큰 방식. 가스·AED 는 데이터가 전부 작고 전부 저장 대상이라 **나눌 이유가 없어** 전부 서버로 간다.
CCTV 만 "저장할 것"과 "보기만 할 것"이 갈려서 경로가 둘이다.

⚠ **앱 함의** — 영상을 보려면 **태블릿이 젯슨 엔드포인트에 직접 닿아야** 한다.
→ **해소(2026-09-13, §11-4).** 사설 대역이 아니라 **공인 DDNS 주소 + 8443** 이다.
현장 Wi-Fi 밖에서도 닿는다 — 다만 **지금은 그 포트가 안 열려 있다.**

### 11-4. [확정] CCTV 측정이 404 로 막힌 원인 — 세 겹이었다 (2026-09-13 · Claude 실측 + astra 교차검증)

측정 화면에 `<cctv-ai 오리진>/cctv/stream3` 과 티켓을 넣고 5초 주기로 GET → **`HTTP 404`** 만 나왔다.
**경로 조합은 처음부터 맞았다**(`CctvGateStream.tsx:117` · `CctvQuadView.tsx:195` 둘 다 `/cctv/stream{suffix}`).
404 는 경로 문제가 아니었다.

| # | 원인 | 근거 |
|---|---|---|
| ① | **내가 넣은 호스트가 존재하지 않는 주소였다.** 실제 `cctv-ai` URL 은 옛 형식(`…a.run.app`)인데 새 형식으로 조합했다 | `gcloud run services describe` 실측 |
| ② | **실제 주소를 넣었어도 404다.** `ingress=internal` 이라 바깥에서는 `/` 조차 404 | 실측: 모든 경로 404 · 본문은 Google `404 Page not found` HTML |
| ③ | **CAM-03 은 애초에 cctv-ai 가 아니라 젯슨 게이트 직결이다** | `_CAM03_GATE` 가 최근 빌드(9/12 14:20)에 주입됨 |

#### ★ ②는 고장이 아니라 **의도된 OFF 상태**다

`cctv-ai/README.md:183-194` 에 과금 토글 절차가 있다.

```bash
# OFF (하드 — 외부 접근까지 차단)
gcloud run services update cctv-ai --region asia-northeast3 --min-instances 0 --ingress internal
# ON (재개)
gcloud run services update cctv-ai --region asia-northeast3 --min-instances 1 --ingress all
```

> 문서 원문: *"검증: 외부에서 `/`·`/cctv/*` 가 404 면 OFF 성공"*

**내가 본 404 가 정확히 그 OFF 성공 신호였다.** `--min-instances 1 --no-cpu-throttling` 은 상시 과금이라
발표·테스트가 아닐 때 내려 둔 것이다. 켜면 과금이 다시 시작된다.

⇒ **CAM-01·CAM-02 는 지금 안 나온다. CAM-03 만 젯슨에서 직접 와서 나왔던 것이다** — 게이트를 만든 이유가
"영상이 클라우드를 안 지난다"(`CctvQuadView.tsx:32`)이므로 cctv-ai 가 꺼져 있어도 CAM-03 은 산다.

#### 젯슨 게이트는 지금 닫혀 있다

| 확인 | 결과 |
|---|---|
| DNS 해석 | **성공** (레코드 존재) |
| TCP 8443 | **무응답** (30초 타임아웃) |
| 대조군 google:443 · portquiz:8443 | 둘 다 연결됨 → **내 쪽 네트워크 문제 아님** |

원인 후보 3 — ⑴ 젯슨 전원·`cctv_gate.py` 미기동 ⑵ 공유기 8443 포트포워딩 ⑶ DDNS IP 가 낡음(동적 IP 변경).
**바깥에서는 이 셋을 구분할 수 없다. 젯슨 쪽 확인이 필요하다.**

### ⛔ 11-5. 측정 설계 자체의 결함 — 주소를 고쳐도 안 됐다 (astra 지적)

**티켓은 1회용이다.**

```
cctv-ticket.ts:77   // jti 는 게이트가 1회 소비한다 — 같은 티켓을 두 번 쓰지 못한다.
cctv_gate.py:131    if consume and not _consume_jti(p.get("jti", ""), p["exp"]):
cctv_gate.py:132        return None, (jsonify({"error": "ticket already used"}), 401)
```

`_consume_jti` 는 SQLite 기본키로 사용 이력을 남긴다 — 중복 INSERT 실패 = 재사용 거절.
**측정 화면은 티켓 1장을 받아 주기마다 반복 전송한다**(`cctv_probe_screen.dart:50-70`).
⇒ 첫 요청만 통과하고 나머지는 401 이다. (정확히는 검증 전 요청률 제한이 먼저 걸리면 429 다.)

#### 앱이 스스로 티켓을 받을 수도 없다 — **서명키가 분리돼 있다**

| | 서명 | 근거 |
|---|---|---|
| 관제웹 세션 | `session-jwt.ts:33-37` | 티켓 발급 API 가 `getSession()` 으로 이것을 본다 |
| 앱 모바일 세션 | `app-jwt.ts:114-120` | 앱에는 로그인·갱신·Bearer 전송이 **있다** |

**둘의 서명키가 다르다.** 앱 토큰을 `/api/cctv/ticket` 에 그대로 넣어도 통과하지 못한다
(`ticket/route.ts:30-34` · `admin-auth.ts:141-150`). 앱에서 티켓을 자동 재발급하려면 **서버 작업이 따로 필요하다.**

#### 그리고 **잴 대상이 아직 없다**

astra 확인 — **본 앱에 V-01 CCTV 수신 구현이 없다**(`field_shell.dart:196-210` 화면 목록에 CCTV 없음).
지시서의 "앱은 스냅샷 갱신"(`TASK-cctv-probe.md:39`)은 **계획이지 코드 근거가 아니다.**

⇒ 남은 길은 둘이고, **둘은 서로 다른 값을 준다.**

| 안 | 방법 | 얻는 것 | 대가 |
|---|---|---|---|
| **A** | 젯슨 게이트 · 티켓 1장으로 **스트림을 끊지 않고 유지** (TTL 300초 = 5분 측정) | **연속 스트림 = 상한값.** 관제웹 1.550 A 와 직접 비교 가능 | 젯슨 8443 복구 필요 · 측정 화면을 "첫 파트만 읽고 끊기"에서 "계속 읽기"로 고쳐야 함 |
| **B** | cctv-ai 를 잠깐 ON 하고 `/cctv/snapshot3` 반복 GET | **스냅샷 = 하한값.** 티켓 불필요 → 주기별 곡선이 바로 나옴 | **과금 재개** · 측정 후 OFF 필수 · 게이트와 서버·인증 경로가 다름(astra 반대 근거) |

★ **A 와 B 를 둘 다 재는 것이 이 측정의 목적에 맞다.** 정할 것이 "CCTV 를 넣을까"가 아니라
**"넣는다면 연속이냐 스냅샷이냐"** 이기 때문이다. 두 값의 간격이 곧 그 선택의 대가다.

⚠ `/cctv/snapshot3` 은 **게이트에 없다**(`cctv_gate.py:9-13` 경로 4개뿐). 그래서 B 는 게이트로 못 잰다.
⚠ 대시보드 `/ai-cctv` 프록시도 지금 죽어 있다 — 실측 `503 {"ok":false,"error":"ai backend unreachable"}`
(`AI_CCTV_ORIGIN` 미설정 또는 internal 차단). `snapshot` 은 프록시 허용목록 밖이라 **403** 이다
(`app/ai-cctv/[...path]/route.ts:12`).
