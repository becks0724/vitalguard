### ★★ 사진 위변조 방지 — 원본과 잉크본을 **둘 다** 남긴다 (2026-09-13 · 태곤 님)

> 원문: *"원본에 펜 잉크를 바로 해버리고 사진 전송이 되면 그것은 편집이 되어 사진의 위변조가
> 가능해진다는 것. 이는 막아야함"*

**서버 캘린더에 2장이 올라간다.**

| | 무엇 | 성격 |
|---|---|---|
| 1 | **원본** — 촬영 그대로 + 각인 | 증빙. 손대지 않는다 |
| 2 | **잉크본** — 원본 위에 담당관이 펜으로 표시한 것 | 메모 |

**관제웹 표시** — 기존처럼 사진을 보다가 **한 번 더 클릭하면 카드가 한 바퀴 뒤집혀** 잉크본이 나온다.

⛔ **서버에 둘을 묶을 칸이 없다.** `calendar_media` 전체 컬럼을 확인했다 —
`id · date_key · captured_at · media_type · title · storage_provider · storage_key · media_url ·
thumbnail_url · ocr_text · description · site_id · uploader · worker_id · latitude · longitude ·
road_address · created_at`. **"이 사진은 저 사진의 잉크본이다"를 적을 곳이 없다.**
지금 구조로 2장을 올리면 캘린더에 **사진 2장이 따로** 뜬다.

→ 필요한 변경은 컬럼 하나다.
```sql
ALTER TABLE calendar_media ADD COLUMN IF NOT EXISTS annotation_of TEXT;
```

### ★★ [확정] 잉크는 **벡터로 따로** 올린다 (2026-09-13 · 태곤 님)

> 원문: *"사진 픽셀이나 크기 이런거 잘 맞춰서 원본 사진 1장 + 현장 안전 담당관이 메모한 것만
> 따로 띄워서 원본 사진 위에 호버링처럼 메모한 내용만 띄워서 매칭 시키면 사진 1장 분의 크기를
> 줄일 수 있지 않나?"*

**앱은 이미 벡터를 들고 있다** — `record_editor.dart:15-36 InkStroke`.
`width` 는 *"원본 너비 대비 비율. 회전·확대와 무관하다"*, `points` 는 *"정규화 x,y와 압력"* 이고
`toJson`/`fromJson` 도 있다. 어떤 크기로 띄워도 원본 위에 정확히 얹힌다.

그런데 `:353-354` 는 원본 해상도로 **합성해 PNG** 로 만들어 올린다.
**사진을 PNG 로 저장하면 JPEG 원본보다 3~10배 크다.**

| | 지금 (A 합성) | 확정 (B 벡터) |
|---|---|---|
| 원본 | JPEG | JPEG |
| 잉크 | **합성 PNG — 원본 해상도 전체** | JSON (획 데이터) |

### ✅ [실측] 잉크 JSON 크기 — 2026-09-13 (`test/ink_stroke_test.dart`)

```
INK_SIZE strokes=10  pointsPerStroke=100  bytes=60,472     KB=59.05
INK_SIZE strokes=100 pointsPerStroke=100  bytes=604,207    KB=590.05
INK_SIZE strokes=100 pointsPerStroke=400  bytes=2,398,275  KB=2,342.07  ← 2MB 한도 초과
```

**내 초판 주장("수 KB")은 틀렸다. 열 획만 그려도 59KB 다.**
astra 반박이 옳았고, 실측으로 확정한다.

| 쓰임 | 크기 | 판단 |
|---|---|---|
| 메모 몇 줄 (10획) | **59 KB** | 사진(JPEG 1~5MB)보다 훨씬 작다 — **버전을 쌓아도 된다** |
| 빽빽한 주석 (100획) | **590 KB** | 아직 사진보다 작다 |
| 100획 × 점 400 | **2.29 MB** | **한도 초과.** 전송이 막힌다 |

⚠ **`record_editor.dart:272` 가 점 수 제한 없이 `points.add` 한다.**
천천히 그으면 한 획의 점이 폭증한다 — 위 셋째 줄이 그 경우다.
지금은 **한도 초과 시 사용자에게 알리고 기기에는 저장**하는 것으로 막아 뒀다(전송만 중단).
**근본 해결은 점 단순화(Douglas–Peucker 등)다. 아직 하지 않았다 — 미해결로 남긴다.**

<details><summary>철회 기록 (초판에 근거 없이 적었던 것)</summary>

⛔ **용량 수치를 아직 적지 마라 — 2026-09-13 astra 반박으로 철회.**
초판에 *"잉크 JSON 수 KB · 합계 1/10 이하"* 라고 적었으나 **근거가 없었다.**
`record_editor.dart:272` 는 펜이 움직일 때마다 `points.add(p)` 를 하고 **점 수 제한도 단순화도 없다.**
한 버전의 직렬화 크기를 **잰 적이 없다.**
→ **버전 보존은 기록 원칙으로 결정하고, 용량은 실측으로 따로 검증한다.**

사진 배경을 버전마다 중복 저장하지 않는 절감 효과 자체는 분명하다. 배수는 재고 나서 적는다.

</details>

이것은 D-2 의 **B 벡터** 안이다. 계획서가 이미
*"공통 로컬 원본+벡터를 보관해 A/B/D 게시를 모두 가능하게 설계한다"* 고 적어 둬서 전환 비용이 거의 없다.

### ★ [확정] 재편집 — **버전을 쌓는다. 덮어쓰지 않는다** (2026-09-13 · 태곤 님)

재편집은 **이미 로컬에서 작동한다**(`record_editor.dart:160-180` · `published:<원본id>` 별칭).
안 되는 것은 **다른 기기**다 — 서버에 벡터가 없어서다. 벡터를 올리면 R-05 의 4상황이 함께 풀린다.

| 항목 | 결정 |
|---|---|
| 저장 방식 | **버전 추가.** 덮어쓰기 금지 |
| 편집 권한 | **작성한 담당관만** |
| 화면 | 프론트는 **갈아끼운 것처럼** 최신만 보인다. 옛 버전은 저장해 둔다 |
| 동시 편집 | **있을 수 없다** — 담당관 한 사람만 고친다 |

⛔ **왜 덮어쓰면 안 되나 — 이 이유를 코드 주석에 남길 것.**
산업재해 기록이다. 현장에서 `균열 있음` 으로 적었다가 나중에 `이상 없음` 으로 고쳤을 때
**이전 기록이 사라지면 그 자체가 위변조다.** 원본 사진을 지키려고 잉크를 분리한 것과 같은 이유다.
이 프로젝트는 담당관 확정 원장에 이미 **정정 사유 컬럼**을 뒀다 — 같은 원칙이다.
벡터라 한 버전이 수 KB 이므로 **열 번을 고쳐도 사진 한 장보다 작다.** 남기지 않을 이유가 없다.

### ✅ [해소] 지우개 — **획 통째 삭제로 바꾼다** (2026-09-13 · 태곤 님 결정)

아래 문제를 **지우개 동작 자체를 바꿔** 없앤다. 지우개가 닿은 획을 `strokes` 목록에서 **제거**한다.
지우개 획은 저장되지 않는다.

| | |
|---|---|
| 얻는 것 | 지운 내용이 데이터에 **아예 남지 않는다** · 웹 렌더 규칙이 단순해진다(`saveLayer`·`BlendMode.clear` 불필요) |
| 잃는 것 | **선의 일부만 지우기가 안 된다.** 그은 선이 통째로 사라진다 |

벡터 필기 앱들이 쓰는 방식이고, 현장 안전 메모에는 정밀한 부분 지우기가 필요 없다.
⇒ **서버가 알아야 할 것은 하나 — 잉크 JSON 에 `eraser` 획이 오지 않는다.**

<details><summary>원래 무엇이 문제였나 (2026-09-13 astra 발견)</summary>

```dart
// record_editor.dart:63
if (stroke.tool == InkTool.eraser) paint.blendMode = BlendMode.clear;
```

지우개는 **또 하나의 획으로 저장**되고, 그릴 때 `BlendMode.clear` 로 덮어 지워진 것처럼 보이게 한다.
**원래 획 데이터는 그대로 남아 있다.** (합성 PNG 로 올릴 때는 결과 픽셀만 가므로 드러나지 않았다.)

**벡터를 그대로 서버에 보내면:**
- 한 번도 게시할 생각이 없던 **초안의 지운 낙서까지** 서버로 간다
- 웹이 지우개 획을 빼고 그리면 **지운 내용이 다시 보인다**

이것은 확정한 "게시본 보존" 보다 **훨씬 넓은 범위**다. 전송 전에 정리할지, 어떻게 정리할지 **미정.**

</details>

### ✅ [결정] 원본 삭제 — **유예 10분 안에서만. 잉크본은 같이 지운다** (2026-09-13 · 태곤 님)

> *"어차피 원본 사진을 잘못올려서 삭제하는 경우일텐데 잉크본만 남으면 뭐해.

**10분**(`DB재구축/db-build/VITALGUARD2/plan-061.md:294` · 061 리허설 실측 통과).
설계 주석: *"현장 오업로드는 10분 안에 본인 경로로 정정하고, 그 뒤는…"*

⚠ **라이브(구 DB)에는 이 규칙이 없다.** `deleteCalendarMedia`(`lib/db.ts:4790`)는 소유권만 본다.

라이브 DB 에 트리거를 직접 넣지 않는 이유 — 스키마 정본이 `ensureSchema` 이기 때문이다.

### ⚠ 그 밖에 남는 것 (2026-09-13 astra)

| | 내용 |
|---|---|
| 렌더 규칙 | 웹이 필압 굵기·형광펜 투명도(0.35)·지우개 순서를 재현해야 한다. **저장 형식과 렌더 규칙의 버전 관리 필요** |
| 원본 삭제 | 서버에 원본 삭제 경로가 있다 → **이력은 있는데 볼 사진이 없는 상태**가 가능 |
| 응답 유실 | 원본 저장은 됐는데 응답을 못 받으면 앱이 id 를 모른다(`uncertain`). 확정 6 의 큐가 이걸 확인할 방법이 필요 |
| 최신만 표시 | 확정 4 의 대가 — 화면만 보는 사람은 `균열 있음` 이 사라진 경위를 모른다 |

★ 정정 — `published:<원본id>` 별칭의 방향은 **발행본 ID → 로컬 초안 ID** 다.
다른 기기에는 이 별칭이 없으므로 **서버의 원본·버전 식별자로 복원**해야 한다.

### ✅ [해소] 잉크를 언제 그을 수 있나 — **오프라인에서도 즉시**

이전 개정의 ⓐ/ⓑ 미결은 **벡터 분리로 사라졌다**(태곤 님 2026-09-13).

> *"원본 사진 따로 펜 잉크 벡터 따로 하면 원본은 보장이 되는거니까
> 펜 잉크 기능을 그대로 편집 가능하게 해도 상관없지 않나?"*

ⓐ(서버 저장 후에만 잉크)를 두려던 이유는 **원본에 그려 편집본이 원본으로 둔갑하는 것**을 막기
위해서였다. 잉크가 벡터로 따로 나가면 **그 픽셀 위변조 경로는 사라진다.**

⚠ **다만 "위변조 위험이 없다" 는 과장이었다** (2026-09-13 astra 반박).
막히는 것은 **사진 바이트를 바꾸는 경로**뿐이다. 아래는 그대로 남는다.
- 잘못된 **원본 ID** 에 잉크를 붙이는 것
- **남의 이름으로** 주석을 게시하는 것
- ⛔ `mediaWriteScope` 는 **사진 업로더·owner** 규칙이라 확정 3(주석 작성자만 편집)에 **그대로 못 쓴다**

⚠ **남는 것 하나 — 잉크가 고아가 되지 않게 순서를 묶는다.**
잉크는 원본 id 를 가리킨다. 원본 전송이 실패하면 가리킬 대상이 서버에 없다.
```
원본 전송 성공 → 받은 id 를 잉크에 박아 전송
원본 실패      → 잉크는 큐에서 대기 (혼자 올라가지 않는다)
```
그리는 것은 오프라인에서 자유롭고, **올라가는 순서만** 묶는다. `O-01` 전송 상태가 다룬다.

### R-06 입력 — **칩을 뺀다** (2026-09-13 · 태곤 님)

**철회된 것** — 하루 전 확정했던 조치수준 4단계 칩

| 용도 | 실제 경로 | 방식 | 근거 |
|---|---|---|---|
| **영상** | `{aiApi}/cctv/stream{suffix}?t={tick}` | **MJPEG `<img>` 장기연결** | `:195` |
| **통계** | `{aiApi}/cctv/stats{suffix}` | 폴링 | `:429` |

`docs/progress.md` 의 `00006-svz` 스냅샷 엔드포인트(`/cctv/snapshot[|2|3]`)는 **관제웹 코드에서 호출되는 곳이 없다.**
계획이었거나, 만들어 두고 안 쓰거나 둘 중 하나다. **[미검증] 실제로 응답하는지 확인 안 됨.**

**ⓐ 경로·인증·suffix — 확인 완료**

| CAM | suffix | 인증 |
|---|---|---|
| CAM-01 정문 출입구 (객체감지) | **없음** | 없음(공개) |
| CAM-02 지하 기계실 (낙상) | **`2`** | 없음(공개) |
| CAM-03 현장 작업구역 GoPro (PPE) | **`3`** | ★ **Ed25519 티켓** — `POST /api/cctv/ticket` → `Authorization: Bearer <ticket>` (`:441-442`) |

⚠ **8분할이다**(CAM-01~08). 라이브 AI 는 **01·02·03 셋뿐**이고 04~08 은 샘플 placeholder 다(`:37-44`).

**ⓑ 갱신 간격 — 확인 완료**

| | 값 | 근거 |
|---|---|---|
| AI 통계 폴링 | **8초** (`AI_POLL_MS`) | `:413` |
| 오래됨 판정 | **30초** (`AI_STALE_MS`) | `:414` |

> 주석: *"생체 연결끊김 게이트 `STALE_MS` 와 같은 이유"* — **같은 기준을 쓴다.**

**ⓒ CAM-03 사설 IP — 구조는 확인, 값은 미확인**

```ts
const CAM03_GATE_API = process.env.NEXT_PUBLIC_CAM03_GATE_API || "";   // :18
```
CAM-03 **만** 자기 주소를 갖는다. 주석의 이유:
> `AI_CCTV_API` 를 통째로 바꾸면 **CAM-01·02 와 서버 낙상 폴러까지 젯슨을 보게 되어 함께 멈춘다.**

가드 테스트(`lib/2026-09-09-cctv-gate-wiring.guard.test.ts`)가 이 분리를 **구조적으로 고정**한다.
→ **[미검증] 사설 대역인지는 환경변수 값에 달렸다.** `.env` 는 읽기 차단이라 태곤 님 확인이 필요하다.

**ⓓ 실패 표시 — 재료 있음**

```ts
const fresh = rx !== null && probedAt - rx.at <= AI_STALE_MS;   // :463
```
**"응답 없음" 과 "오래됨" 을 구분한다.** `V-03`(왜 안 되는지 말한다)에 그대로 쓸 수 있다.

### ★★ 태블릿에 그대로 옮기면 안 되는 것

**MJPEG 장기연결은 모바일에 맞지 않는다.**
- 배터리·데이터를 계속 먹는다
- Wi-Fi 가 끊기면 복구가 지저분하다(현장에서 정상 시나리오다)
- Flutter 에서 multipart 파싱 + 프레임 조립을 직접 해야 한다

→ **스냅샷 폴링이 맞다.** 다만 위에 적었듯 **그 엔드포인트가 실제로 응답하는지 확인 안 됐다.**
없으면 `V` 영상은 **서버 작업이 선행**돼야 한다.

> **남은 확인** — ⓐ `/cctv/snapshot[|2|3]` 이 실제로 응답하는가 ⓑ `NEXT_PUBLIC_CAM03_GATE_API` 가 사설 대역인가 ⓒ VIGI C340S 교체 후 어느 경로로 물릴지
