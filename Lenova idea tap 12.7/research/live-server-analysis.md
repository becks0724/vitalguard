## 2. ★ 인증 구조 — 태블릿 앱 설계의 최대 제약

서버에 **인증 주체가 3종**이고, 각 API가 받는 주체가 다르다.

| 주체 | 검증 함수 | 발급 경로 | 성격 |
|---|---|---|---|
| **관제 세션** | `verifyBasicAuth` / `getSession` | 웹 로그인(쿠키) | 관제웹 전용 |
| **앱 JWT(공통)** | `verifyAppJwt` | `POST /api/app-auth/login` | 30일 · 워치/수집 단말용 |
| **모바일 세션 v2** | `verifyMobileAccessJwt` | `POST /api/mobile/v1/session/login` | 단기 access + 회전 refresh · 로그인 시 TOTP 단계 |

#### ★ 두 검증 함수의 실제 포함관계 (2026-09-12 코드 실측 · 코덱스 지적으로 정정)

```
verifyAppJwt(token)          → 서명 + 만료만 검사
verifyMobileAccessJwt(token) → verifyAppJwt() 를 호출한 뒤
                               aud=="vitalguard-mobile" && tokenUse=="access"
                               && v==2 && sessionId 非공백  을 추가로 요구
```

**즉 `verifyMobileAccessJwt` ⊂ `verifyAppJwt` 다.** 여기서 두 가지가 따라온다.

1. **v2 토큰은 `verifyAppJwt` 를 쓰는 아래 12개 API를 그대로 통과한다.** 태블릿 앱이 v2 세션
   경로로 로그인해도 캘린더·사진·업로드·배치챗은 **서버 변경 없이** 쓸 수 있다.
2. ⚠ **"v2 토큰 = 2단계 인증 완료 + 즉시 폐기 보장" 이라고 읽으면 안 된다.**
   `verifyMobileAccessJwt` 는 **세션 DB를 조회하지 않는다** — 로그아웃으로 세션 행을 폐기해도
   이미 발급된 access 토큰은 **만료 전까지 유효**하다. 2단계 인증도 *로그인 시점의 절차*이지
   토큰이 그 사실을 들고 다니며 증명하는 것이 아니다.
   → 관제 데이터를 열 때는 **토큰 수용 여부**와 **관제 권한 검증**을 반드시 따로 설계한다.

> 서버 측 API 인증 확장이 필수다.** 앱이 손댈 수 있는 현재 범위는 캘린더·사진·현장정보·본인생체·배치챗뿐이다.

> *"관리자 조회는 이 토큰(`verifyMobileAccessJwt`)만 받도록 만든다"*.
> 즉 **모바일 세션 v2 토큰을 관제 조회 API에 받아들이는 작업**이 설계된 채 미구현이다.
> 태블릿 앱은 이 경로를 타는 것이 맞다 — 다만 위 2-1의 경고대로, 그 작업은 "v2 토큰을 받는다"로
> 끝나지 않고 **세션 유효성 재확인 + 역할(admin/owner) 검증**을 같이 붙여야 한다.
>
> ⚠ 레거시 `/api/app-auth/login` 에 2단계 인증을 걸면 **워치 수집이 즉시 멈춘다**(가드 테스트 존재).
> 태블릿 앱이 레거시 경로를 쓰면 안 되는 이유이기도 하다.

## 3. ★ 캘린더 + 현장 사진 — 요구사항 13의 핵심 대상

### 3-1. 현재 흐름

> ⚠ **정정 (태곤 님 2026-09-12)** — 종전 기록의 **"작업자 앱"은 틀렸다.**
> **OCR 기능이 들어간 휴대폰 앱은 `현장 담당관 앱`이다. 작업자용 앱은 없다.**
> 작업자용으로 존재하는 것은 팀원이 만든 **워치 앱**뿐이다.
> (옛 기록이 남아 "작업자 앱"으로 보였던 것으로 추정된다.)
>
> **이 정정이 D-2 설계를 좌우한다** — 캘린더 사진은 **담당관 본인이 올린 것**이므로
> 담당관이 주석본을 다시 올려도 **귀속이 바뀌지 않는다.** 아래 3-3 참조.

```
현장 담당관 휴대폰 앱(카메라·OCR)      ← 작업자 앱이 아니다
  └ POST /api/app-media  (multipart: 파일 + capturedAt/GPS/도로명/촬영자/ocrText)
      └ 서버: 네이버 Object Storage 업로드 + calendar_media 행 등록
          └ 관제웹 캘린더: 촬영 날짜 셀에 배지 → 클릭 시 사진 + 메타 + 댓글 스레드

(별개) 워치 앱 = 작업자용 — 생체·수집 경로. 캘린더 사진과 무관하다.
```

### 3-2. 사진 1건이 들고 있는 데이터 (`CalendarMedia`)

| 필드 | 내용 |

| `date_key` / `captured_at` | 캘린더 배치 날짜 / 촬영 시각(**KST 로컬 ISO 필수**, `Z`로 보내면 9시간 어긋남) |

| `ocr_text` | 앱 OCR 원문 (관제웹은 "원문 보기" 토글로 접어둠) |

### 3-3. ★ 펜 주석(그림·표시)을 어디에 저장할 것인가 — 미해결 설계 결정

현재 서버에는 **텍스트 댓글만** 있다. 펜 스트로크를 담을 자리가 없다.

| 안 | 방법 | 서버 변경 | 장단 |
|---|---|---|---|
| **A** | 원본+주석을 **합성한 새 이미지**를 `POST /api/app-media` 로 업로드 | **불필요** | 당장 가능·관제웹에서 바로 보임 / 원본과 주석 분리 불가·되돌리기 불가 |
| **B** | 주석을 **벡터 스트로크(JSON)** 로 별도 저장 | 신규 API 필요 | 편집·삭제 가능·원본 보존 / 관제웹도 렌더러 추가 필요 |
| **C** | 주석만 **투명 PNG 레이어**로 저장 | 신규 API 필요 | 원본 보존·합성 단순 / 벡터 편집 불가 |
| **D** | A + 댓글에 "주석본" 표시를 남겨 원본과 연결 | 불필요(관례만) | A의 약점을 운용으로 보완 |

> **설계 단계에서 결정할 1순위 항목.** cmux-duo-build 토론 주제로 올린다.

### 3-4. ★ [관측] `POST /api/app-media` 소스 확인 (2026-09-12)

근거: `기존_조달청모듈/safetymonitor/apps/dashboard-web/app/api/app-media/route.ts` (170행)

| 확인 | 답 | 근거 행 |
|---|---|---|
| **역할(role) 검사** | **없다.** `verifyAppJwt` 통과 또는 공유 `APP_UPLOAD_TOKEN` 하나면 업로드된다. **403 으로 막히지 않는다** | `:79-87` |
| **`dateKey` 우선순위** | **폼 값이 우선.** 형식(`DATE_RE`)만 맞으면 그대로 쓴다. 안 맞으면 `capturedAt` 의 앞 10자, 그것도 없으면 `todayKst()` | `:120-123` |
| **`title` 필드** | **`TEXT` · 길이 제한 없음.** 라우트는 `.trim()`만 하고 자르지 않는다 | `lib/db.ts:956-975`, `app-media/route.ts:125,154` |
| ★ **귀속(uploader/workerId)** | **JWT 신원으로 강제 덮어쓴다. 폼 값은 무시된다.** 주석에 의도가 명시돼 있다 — *"폼 workerId 가 JWT 보다 우선하면 인증된 사용자가 미디어를 타인에게 귀속시킬 수 있음"* | `:127-133` |

```js
// 귀속 위조 방지 — 로그인 JWT 로 인증했으면 JWT 신원(name/workerId)을 강제하고 폼 값은 무시한다.
const uploader = jwtClaims?.name ?? pick(form, [...]) ?? null;
const workerId = jwtClaims?.workerId ?? pick(form, [...]) ?? null;
```

**여기서 나오는 D-2 판정**

- 이 서버는 **"누가 올렸는지"를 위조할 수 없게 설계돼 있다.** 담당관이 올리면 담당관으로 기록된다.
- **§3-1 정정으로 이 제약이 문제가 되지 않는다.** 캘린더 사진은 **담당관 본인이 올린 것**이고
  "한 현장 = 담당관 1명 = 태블릿 1대"(D-2 근거)이므로 **원본 업로더와 주석본 업로더가 같은 사람**이다.
  → **A안(합성본 재업로드)은 귀속 문제를 일으키지 않는다.**
- **`dateKey` 를 원본 날짜로 보내는 보완 2 도 실제로 동작한다**(폼 값이 우선하므로).
- ⚠ **[미검증] 남은 잔여 리스크** — **담당관이 교체된 현장**에서는 이전 담당관이 올린 사진에
  새 담당관이 주석본을 올리게 된다. 그때는 업로더가 바뀐다.
  `title` 에 원본 식별자를 남기는 보완 2가 이 경우의 유일한 연결 고리다.
- `calendar_media.title`은 **`TEXT`**이고 라우트도 자르지 않으므로,
  `현장 이미지 (주석) — 원본 … · <id>`의 원본 식별자를 그대로 보존한다.

**[관측] 없는 것:** 현장 배정 상태와 첫 로그인 비밀번호 변경 필요 여부는 두 응답 어디에도 없다.
없는 상태를 `false`로 가정할 수 없어 기존 라이브 경로는 `AuthStage.contractPending`에서
멈추게 했다. 그 판단은 서버 계약을 그대로 반영한 것이었다.

**[확정 2026-09-12] 해소 방향:** 서버를 확장하지 않고 `A-06`·`A-12`를 앱 라이브 경로에서 제외한다.

- `A-06` 현장 선택은 삭제가 아니다. `getLatestSiteInfo()`가 사용자·현장 필터 없이
  `site_info_daily`의 전역 최신 1행만 주므로(`lib/db.ts:3626-3631`),
  **배정 1개면 건너뛴다**는 기존 규칙이 발동한다. 다중 현장을 위한 화면 정의는 보존한다.
- `A-12` 첫 비밀번호 변경은 앱에서 제외하고 관제웹이 담당한다.

⚠ **[미검증 · 잔여 리스크] 첫 비밀번호를 바꾸지 않은 계정도 앱에 로그인된다.**
앱은 그 상태를 알 방법이 없다(`/login`·`/me` 응답에 필드가 없다).
관제웹에서 강제 변경을 거치지 않은 계정이 앱으로 먼저 들어올 수 있다.
이 제품 결정으로 라이브 로그인은 기록 화면까지 진행하며, 사이트 응답이 `null`이면
현장명을 만들지 않고 **`현장 정보 없음`**으로 상태를 드러낸다.

### 6-2. ★ 현장 통합 안전 신호등 — 담당관이 **가장 먼저 보는 것**

4행 고정(현장 기상 / 작업자 / 가스 감지 / AED) + 우상단 **종합 판정**. 각 행은
`● 상태배지 + 한 줄 요약 + 펼침(⌄)`. 실측된 문구 예:

| 행 | 상태 | 요약 문구(실물) |
|---|---|---|
| 현장 기상 | 정상 | 특보 없음 · 광주 · 발효 특보 — 현장 영향 점검 |
| 작업자 | 정상 | 정상 1명 · 대기 3명 · 대기 작업자는 생체 미수신 — 판정 대상 아님 |
| 가스 감지 | **위험** | CO 52ppm · 탱크 야드 · 산소운반 방해 — 두통·어지러움, **즉시 환기·대피** |
| AED | 주의 | AED 배터리 교환 임박 · 지하 주차장 B1 · 외 1건 |

> **태블릿 1순위 화면.** 이 4줄 + 종합 판정만으로 "지금 현장이 어떤가"가 끝난다.
> 한 손으로 들고 볼 때 이 블록이 첫 화면이어야 한다.

### 6-3. ★ 알림 이력 모달 — 담당관의 **실제 처리 업무**

헤더 🔔 → 모달. 제목 `SOS·낙상·생체·이탈 알림 이력  미대응 10건` · 우상단 `[미대응 모두 확인]`.

카드 1건 = `아이콘 + 종류·작업자명 + 발생시각(+대응시각·사유) + [✓ 대응 확인]`

| 알림 종류(실물) | 예시 |
|---|---|
| **구획 이탈** | 구획 이탈 · 장우진 / 발생 09.12 오전 11:36:45 → **미대응(주황 카드 + 빨간 [대응 확인])** |
| **absence**(미수신) | 발생 09.12 10:20:02 · 대응 09.12 11:35:03 (**자동해제 · 수집이 멎어 있었음**) → 대응완료 |
| **생체 위험** | 발생 09.11 02:01:47 · 대응 02:18:06 (**관제자**) → 대응완료 |
| 생체 위험(미대응) | 발생 09.11 01:19:31 → **빨간 카드 + [대응 확인]** |

- 미대응은 카드 배경색으로 구분(주황=이탈, 빨강=생체), 대응완료는 회색 `✓ 대응완료` 배지.
- **담당관의 핵심 동작 = [대응 확인] 버튼 누르기.** 터치 1회로 끝나는 업무다.
- ⚠ 이 모달의 소스 `GET /api/alerts` · `POST /api/alerts/ack` 는 **앱 토큰을 안 받는다**(§2-2).

### 6-8. 화면 실물에서 새로 확인된 설계 제약

| 관찰 | 태블릿 설계 영향 |
|---|---|
| 상위 6탭 + 하위 4탭 **2층 탭** | 태블릿에서 2층 탭은 손가락 이동이 크다 → 한 층으로 접거나 레일/바텀바로 재편 필요 |
| 지표 바의 긴 진행 막대 2개 | 866dp 세로에서 가로로 2개는 안 들어감 → 스택 또는 요약 수치로 |
| 작업자 표 12컬럼 | 카드형 필수 |
| 가스 표 7컬럼 × 11행 | 위험/주의만 상단 고정하는 방식 검토 |
| 캘린더 3단(사이드+격자+패널) | 태블릿 세로에서 3단 불가 → 날짜 선택 → 시트(bottom sheet) 전환 |
| 알림 모달이 화면 대부분을 덮음 | 태블릿에선 전체화면 시트가 자연스러움 |
| 대형 시계·공정률 등 **관제실 벽면용 표시** | 현장 순찰에서는 가치가 낮음 → 태블릿에서는 접거나 제거 대상 |
