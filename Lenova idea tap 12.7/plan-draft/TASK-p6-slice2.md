## ★★★ 반드시 먼저 읽어라 — **서버에 멱등키가 없다**

`POST /api/app-media` 를 소스로 확인했다:

```
app-media/route.ts:139   const key = `calendar-media/${dateKey}/${crypto.randomUUID()}.${ext}`
app-media/route.ts:150   id: crypto.randomUUID()
```

**저장소 키도 DB id 도 서버가 요청마다 새로 만든다.**
`Idempotency-Key` 도, `ON CONFLICT` 도, dedup 도 **없다.**

### → **재전송은 무조건 중복을 만든다.**

`screen-inventory.md:131` 의 `O-03` 은 **"N-3 중복방지 계약 선행"** 을 전제로 적혀 있다.
**그 계약은 서버에 존재하지 않는다.** 그러니 `O-03` 을 원안대로 만들 수 없다.

**대신 이렇게 간다 — "멱등키로 안전하게 재시도" 가 아니라 "재조회로 확인한 뒤 사람이 결정".**

1. **결과 불명(`uncertainWrite`)이면 절대 자동 재전송하지 않는다.**
   슬라이스 1 이 이미 이렇게 돼 있다(`ApiFailure.uncertainWrite` · 테스트
   「업로드 결과 불명은 자동 재전송하지 않는다」). **그 계약을 전송 상태까지 이어라.**
2. **`서버에서 확인` 버튼**을 준다 — `GET /api/calendar/media?from=&to=` 로 그 날짜를 다시 읽어
   **`title` 에 원본 ID 가 들어간 항목이 있는지** 본다(주석본 제목 형식은
   `record_origin.dart` 의 `annotationFields()` 가 만든다).
3. 있으면 **완료로 바꾼다.** 없으면 **사용자가 명시적으로 재시도**한다.

### ⚠ 이 방법의 한계를 화면이 **숨기지 마라**

**같은 원본 사진을 두 번 주석하면 제목이 똑같다.**
`annotationFields()` 의 제목은 **원본 ID 기준**이라 "내 재시도가 도착한 것" 과
"예전에 한 번 더 주석한 것" 을 **구분할 수 없다.**

- 화면에 **`같은 사진의 이전 주석과 구분되지 않을 수 있습니다`** 라고 적어라.
- **"중복 없음" 이라고 단정하지 마라.** 확인한 것은 **"그 날짜에 원본 ID 가 든 항목이 있다"** 까지다.
- ⛔ **제목 형식을 네 마음대로 바꾸지 마라.** 제목은 **D-2 보완 2 의 유일한 연결 고리**다.
  고유 토큰을 넣으면 해결되지만 **그건 제품 결정이라 태곤 님께 올린다.** 아래 ⑤ 참조.

## 할 일

### ① `lib/data/contracts/field_contracts.dart` — 전송 상태 계약 추가

- 큐 항목 상태는 **5가지**: `대기` · `진행` · `실패` · **`결과 불명`** · `완료`
  ⚠ **`결과 불명` 을 `실패` 에 합치지 마라.** 둘은 **행동이 정반대**다 —
  실패는 재시도해도 되고, 결과 불명은 **재시도하면 중복이 난다.**
- 항목이 들고 있어야 할 것: **작성 당시 현장**(`O-04`) · 계정 · 원본 ID · 만든 시각 · 마지막 시도 시각 · 실패 사유
- ⚠ **서버가 안 주는 필드를 만들지 마라.** 이건 **기기 로컬 상태**이므로
  `server_models.dart` 가 아니라 **별도 로컬 모델**로 둬라. 슬라이스 1 의 분리를 지켜라.

### ② `O-01` 전송 상태 화면

- **`기기에 저장됨` 과 `서버 전송 완료` 를 절대 같은 말로 쓰지 마라**(`screen-inventory.md:129`).
- 각 항목에 **작성 당시 현장**과 **계정**을 보여라. 다른 계정 항목은 **보이지 않는다.**
- `O-02` 재로그인 필요 — `ApiFailure.action == 'reauth'` 인 항목을 묶어 보여라.
- 목록 행 탭이 **재전송이 되면 안 된다.** 상세에서 명시적으로 누른다.
  (`L-02` 에 적힌 원칙과 같다 — 목록 탭을 파괴적 동작으로 만들지 않는다)

### ③ ★ `경보` 탭이 **왜 비어 있는지** 화면이 말해라

지금 `_NextSlice('경보')` 는 "다음 슬라이스" 라고만 한다. **그건 사실이 아니다.**
다음 슬라이스에 만들 수 있는 게 아니라 **서버가 앱에 안 열려 있다.**

- 문구 예: **`경보는 아직 이 앱에서 볼 수 없습니다. 관제 화면에서 확인해 주세요.`**
- ⛔ **"준비 중" 이라고 쓰지 마라.** 우리가 안 만든 게 아니라 **못 받는 것**이다.
- ⛔ 경보 **개수·배지를 0 으로 표시하지 마라.** 0 건이 아니라 **모르는 것**이다.
  이건 `N-1`(조용히 실패하지 않는다)과 슬라이스 1 검증에서 잡은
  **⑫ "일어나지 않은 일을 일어났다고 말하지 않는다"** 의 연장이다.

### ④ 테스트 — 기존 것을 고치지 말고 **추가**해라

최소 이만큼은 검사로 남겨라:

```
· 결과 불명 항목은 자동 재전송하지 않는다
· 결과 불명과 실패를 한 상태로 합치지 않는다
· 전송 상태 항목은 작성 당시 현장을 유지한다 (현장이 바뀌어도)
· 다른 계정의 전송 상태 항목이 보이지 않는다
· 서버 재조회는 제목에 원본 ID 가 든 항목만 일치로 본다
· 경보 탭은 건수를 0 으로 표시하지 않는다
```

### ⑤ ★ 문서 — `research/live-server-analysis.md` §3-6 신설

위 **앱 JWT 전수표**와 **멱등키 부재**를 근거 행과 함께 기록해라. 그리고 **결정 대기**로 두 가지를 적어라:

**(가) `L` 경보를 열려면 서버가 얼마나 바뀌나 — D-4 의 최소안**

이미 **같은 패턴의 선례가 있다.** `admin/site-info` GET 이 앱 JWT 를 받도록 확장돼 있고
주석까지 달려 있다(`:29-31`):
> `조회(GET) = 대시보드 관리자 세션 또는 앱 로그인 JWT(owner/admin/worker) 수용 — 현장 앱이 현장정보 표시.`
> `저장(PUT)은 관리자 전용 유지.`

→ **`alerts` GET 과 `alerts/ack` POST 에 같은 3줄을 넣는 것**이 최소안이다.
  **읽기만 여는 것과 ack 까지 여는 것은 무게가 다르다** — ack 는 쓰기이고
  **"누가 대응했는가" 가 기록에 남는다.** 나눠서 판단할 수 있게 두 줄로 적어라.

**(나) 주석본 제목에 고유 토큰을 넣을 것인가**

넣으면 재시도 중복을 정확히 가릴 수 있다. 대신 **제목 형식이 바뀐다** —
D-2 보완 2 의 연결 고리라 **관제웹에서 사람이 읽는 문자열**이기도 하다.

⚠ **(가)·(나) 어느 것도 네가 정하지 마라. 근거만 정리해라.**

# 추가 범위 — `L` 경보 (2026-09-12 결정분)

서버 계약은 `SPEC-d4-alerts-app-jwt.md` 가 정본이다. 앱이 기대할 모양:

```
GET  /api/alerts            → { ok, alerts: AlertRow[] }      최근 100건
POST /api/alerts/ack        → { ok, acked: boolean }
     body: { id } 또는 { workerId, type }     ⚠ ackBy 를 보내지 마라 (서버가 JWT 신원으로 덮는다)
```

`AlertRow` 실제 컬럼(`lib/db.ts:543-553`) — **없는 필드를 만들지 마라**:
```
id(serial) · worker_id · worker_name · type · ts · created_at · ack_at · ack_by
type 은 sos | fall | vital | geofence  (lib/alert-type.ts)
```

### ⑥ `L-01` 경보 목록

- ⛔ **"이 현장 경보" 라고 쓰지 마라.** `alerts` 테이블에 `site_id` 가 **없고**
  `listAlerts()` 에 현장 조건이 **없다**. 실제로 오는 건 **전체 최근 100건**이다.
  화면 문구는 **"최근 경보"** 다. (`screen-inventory.md:87` 의 "배지는 이 현장 기준" 은 **지금 불가**)
- **미대응 / 대응완료**로 가른다 — `ack_at` 이 `null` 인지로만 판단한다.
- 종류 4가지만 온다(`sos`·`fall`·`vital`·`geofence`). **`absence` 는 이 표에 없다.**
  ⚠ `screen-inventory.md:87` 이 5종을 적고 있는데 **서버가 4종만 준다.** 문서와 다르면 **서버가 옳다.**
- ⛔ **건수를 0 으로 단정하지 마라.** 못 받았으면 **"확인 못 함"** 이다(`N-1`).

### ⑦ `L-02` 경보 상세 + 대응 확인  **★ 여기가 가장 위험하다**

- ⛔ **목록 행 탭 = 확인 처리로 만들지 마라**(`screen-inventory.md:88`).
  **상세에서 대상·시각을 본 뒤 명시적으로 1회** 누른다.
- **`ackBy` 를 body 에 넣지 마라.** 서버가 JWT 신원으로 강제한다. 보내봐야 무시되고,
  보내는 코드가 남아 있으면 **다음 사람이 "앱이 대응자를 정한다" 고 오해한다.**
- **ack 는 멱등하다** — `WHERE ack_at IS NULL` 조건이고 자연키 방식도 `LIMIT 1` 이다
  (`lib/db.ts:2619-2643`). 두 번 눌러도 덮어쓰지 않는다.
  ⚠ **그렇다고 자동 재시도를 넣지 마라.** 사람이 누르는 동작이다.
- ★ **`ack_by` 는 산업재해 자료 CSV 에 "대응자" 로 실린다**(`AdminExportModal.tsx` 첫 줄).
  **되돌리는 API 가 없다.** 그러니 **확인 단계를 반드시 둔다**(`I-5` 와 같은 이유).

### ⑧ `L-03` 오프라인 · `L-04` 결과 불명

- `L-03` — 오프라인이면 **"연결 후 가능"** 만 말하고 **완료·예약 상태를 만들지 마라**(`N-2`).
- `L-04` — 결과 불명이면 **`GET /api/alerts` 재조회가 정답이다.**
  ack 는 멱등하고 재조회하면 `ack_at`·`ack_by` 로 **사실을 확인할 수 있다.**
  ⚠ **사진 업로드와 정반대다** — 거긴 멱등키가 없어 재시도가 중복을 만든다.
  **두 경우를 같은 코드로 묶지 마라.**
- `L-05` 다른 관리자가 이미 처리 — `acked: false` 가 오면 **이미 처리됐다는 뜻**이다
  (`ackAlert` 가 `ack_at IS NULL` 일 때만 바꾸고 변경 행 수를 돌려준다).
  **실패로 표시하지 마라.** 재조회해서 **누가 처리했는지 보여줘라.**

### ⑨ `L-07` 전역 경보 스트립

- **비차단.** ⛔ **자동 모달·자동 초점 이동 금지.** **펜으로 쓰는 중에 끼어들면 안 된다.**
- 실측 근거: 팜 리젝션이 사후 취소 방식이라 **작성 중 화면 전환은 획을 잃게 만든다.**

### ⑩ 테스트 추가

```
· 경보 목록에 "이 현장" 이라고 표시하지 않는다
· ack 요청 본문에 ackBy 를 넣지 않는다
· acked:false 를 실패가 아니라 "이미 처리됨" 으로 다룬다
· 오프라인에서 대응확인이 완료 상태를 만들지 않는다
· 경보를 못 받았을 때 건수를 0 으로 표시하지 않는다
· 경보 스트립이 펜 작성 화면의 초점을 빼앗지 않는다
```
