# 1. 목적과 완료 기준

## 1.1 담당관이 겪는 문제

현장 안전관리자는 지금까지 **데스크톱 앞에 앉아** 관제웹을 봤다. 그런데 현장에 문제가 생기면
자리를 떠야 하고, 떠나는 순간 **관제 정보가 끊긴다**. 현장 순찰 중에 무엇이 일어나는지 모르고,
현장에서 본 것을 기록하려면 다시 자리로 돌아와야 한다.

## 1.2 요구사항 원문 (태곤 님 · 축약 없이 보존)

부록 A 에 15개 원문을 그대로 둔다. 이 절은 그것을 대체하지 않는다.

## 1.3 출동·순찰 시나리오

```
[사무실]  관제웹으로 현장을 본다
   ↓      이상을 발견한다 / 순찰 시각이 된다
[이동]    태블릿을 들고 나간다  ← 이 순간부터 관제 정보가 끊기면 안 된다
   ↓
[현장]    ① 지금 현장이 어떤가 (신호등)
          ② 문제 대상을 확인한다 (작업자·가스·AED·영상)
          ③ 대응을 확인 처리한다
          ④ 본 것을 남긴다 (사진·펜 주석·메모)   ← 태블릿에서만 되는 일
          ⑤ 사무실/관제웹과 공유된다
```

## 1.4 인수 기준 (완료를 무엇으로 판정하는가)

| # | 기준 | 검증 방법 |
|---|---|---|
| 1 | 현장에서 **신호등 4행을 보고 상태를 안다** | 실기기 시나리오 실행 |
| 2 | **경보를 대응 확인**할 수 있다 | 서버 반영까지 확인 |
| 3 | **사진에 펜으로 남긴 것**이 관제웹에 도달한다 | 웹에서 눈으로 확인 |

## 3.3 [관측] API 인증 — 메서드별로 다르다

서버에 **인증 주체가 3종**이다.

| 주체 | 검증 함수 | 발급 |
|---|---|---|
| 관제 세션 | `verifyBasicAuth` / `getSession` | 웹 로그인(쿠키) |
| 앱 JWT | `verifyAppJwt` | `POST /api/app-auth/login` (30일) |
| 모바일 세션 v2 | `verifyMobileAccessJwt` | `POST /api/mobile/v1/session/login` (단기 + 회전 refresh) |

**★ 두 함수의 포함관계** (`lib/app-jwt.ts:180`·`:186`)

```
verifyAppJwt(token)          → 서명 + 만료만 검사
verifyMobileAccessJwt(token) → verifyAppJwt() 호출 후
                               aud=="vitalguard-mobile" && tokenUse=="access"
                               && v==2 && sessionId 非공백 을 추가 요구
```

**즉 `verifyMobileAccessJwt` ⊂ `verifyAppJwt`.** 유효한 v2 토큰은 `verifyAppJwt` 를 쓰는
아래 12개 API 를 **그대로 통과**한다.

### 앱 토큰이 닿는 API (12개)

`GET /api/admin/site-info` · `GET /api/calendar/media` · `POST|PATCH|DELETE /api/calendar/media/comment` ·
`GET /api/calendar/events` · `/labels` · `GET /api/inspection-schedule` · `POST /api/app-media` ·
`GET|POST /api/app/vital` · `/me/vitals` · `/wearable/register` · `/app/address` ·
`POST /api/assignment/chat` · (`GET /api/radar` 는 공개)

### 앱 토큰이 **닿지 않는** 관제 기능

`monitor/vital`·`/history` · `monitor/track`·`slots`·`site-coord` · `alerts`·`alerts/ack` ·
`gaspod/*` · `aed/*` · `cctv/*` · `weather`·`kma-warning`·`typhoon`·`disaster-msg` · `kosha/*` ·
`admin/workers` 등 — **전부 관제 세션 전용**

> ⚠ **"v2 = 2단계 인증 완료 + 즉시 폐기 보장" 이 아니다.**
> `verifyMobileAccessJwt` 는 **세션 DB 를 조회하지 않는다** — 로그아웃으로 세션을 폐기해도
> 발급된 access 토큰은 만료 전까지 유효하다. 또 **v2 로그인도 `twoFactorPending` 계정을 막지 않는다**
> (`mobile/v1/session/login/route.ts:153`). **토큰 수용과 관제 권한 검증은 따로 설계한다.**

# 4. 제품 범위와 출시 묶음

## 4.1 [확정 2026-09-12] 주 사용자

ERD 「사용자 4부류」 기준 **`org_type=contractor` / `role=site_manager`**, 현장 범위 **배정된 1~2개**.

| 부류 | org_type | role | 표지 | 태블릿 로그인 |
|---|---|---|---|---|
| 어드민 | `platform` | `platform_admin` | — | ✅ 허용 |
| 조달청 담당관 | `owner` | `owner_officer` | — | ❌ **거부** |
| **현장 관리자** | `contractor` | **`site_manager`** | — | ✅ **주 사용자** |
| **시공사 법인 계정** | `contractor` | **`site_manager`** | **`is_company_account=true`** | ✅ 허용 |
| 작업자 | `contractor` | `worker` | — | ❌ **거부** |

### [관측] 시공사 법인 계정은 별도 역할이 아니다 (ERD 073)

```
app_user.is_company_account : boolean NOT NULL DEFAULT false
  · 소속 = 그 현장의 시공사 (site.contractor_company_id)
  · 역할 = site_manager          ← 4역할 모델을 유지하고 표지가 성격을 더한다
  · 현장 묶음 = site_member
  · contractor 소속·site_manager 가 아니면 트리거 fn_guard_company_account 가 거부
  · 스스로 바꿀 수 없다 (fn_guard_privileged_columns)
```

> ERD 원문 — 별도 표를 두지 않은 이유: *"이 사람이 이 현장을 볼 수 있는가"의 답이 둘로 갈린다.*

**[확정] 발급·운영 규칙 (태곤 님 2026-09-11)**
- **현장별 발급** — A 현장 ↔ A 현장 담당관 ↔ A 시공사 법인 계정
- 계약서는 **시스템 밖**에서 확인한 뒤 발급 · **초기 비밀번호는 메일**
- **[확정 2026-09-12] 첫 로그인 전 비밀번호 변경은 관제웹 담당** → `A-12`는 앱에서 제외한다.
  `/login`·`/me`가 변경 필요 여부를 주지 않아 앱은 차단할 수 없다.
  ⚠ **[미검증 · 잔여 리스크] 미변경 계정도 앱에 로그인될 수 있다.**
- 사업자등록증 적재 · 열람은 **`platform_admin` + 그 회사 활성 법인 계정만**
  (같은 회사의 담당관·작업자도 불가 — ERD 075).
  ⚠ **이 기능은 태블릿 범위 밖이다**(§4.3) — 서버·관제웹에만 둔다.

> **그래서 허용 목록이 단순해진다** — 법인 계정도 `site_manager` 이므로 **역할 검사 하나로 둘 다 통과**한다.

> **[확정]** 태곤 님: *"태블릿에 로그인 할 수 있는 사람은 현장 안전 담당관과 시공사 법인 계정 +
> 우리 어드민 계정만 로그인할 수 있게 해놓아야함."*
> **[확정] 허용 목록** — `role IN ('platform_admin', 'site_manager')`. 그 밖은 **기본 거부**.
> ⚠ **허용 목록(allowlist) 방식**으로 구현한다. 차단 목록이면 **새 역할이 자동 통과**한다.
> ⚠ **서버가 막는다.** 앱에서 화면만 가리면 API 는 그대로 열려 있다.
> 현장 범위가 1~2개이므로 **다현장 전환 UI 는 과설계**다. 단일 현장 기본.

### ★ 제외 판단 기준 (앞으로 새 기능을 넣을지 정할 때 먼저 던지는 두 질문)

둘 중 하나라도 걸리면 **태블릿에 넣지 않는다.** 관제웹에서 하면 된다.

# 5. 서비스화면 설계 연결

화면 상세는 `app_uIuX_plan.md` 가 소유한다. 여기서는 **구조와 규칙만** 적는다.

## 5.1 [확정] 정보 구조 — 4목적지

```
[ 현장 ]  [ 경보 ② ]  [ 기록 ]  [ 전송함 ]
   └ 상세에서 → 영상 보기 (스냅샷 갱신 · 단일 채널)
공통 상단: 현장명 · 마지막 수신 시각 · 비차단 경보 스트립
```

  **자동 모달·자동 초점 이동을 하지 않는다** — 펜으로 쓰는 도중 확인 버튼이 손끝 아래
  삽입되면 오조작한다.
- **전송함이 목적지인 이유** — 지연 전송(§8)을 채택한 이상 "무엇이 서버에 올라갔는가"를
  볼 곳이 없으면 신뢰를 얻지 못한다.

> 펜 축은 표준 `PointerEvent`로 확인됐으며 잉크 지연의 정량 검증은 별도로 남아 있다.

## 6.4 의존성 방침

# 7. 현재 라이브 인증·API 연동

## 7.1 로그인 경로

**모바일 세션 v2**(`POST /api/mobile/v1/session/login`)를 쓴다. 요청 모양은 관제웹과 같다 —
1단계 `{id,password}`, 서버가 `twoFactorRequired` 로 되물으면 **비밀번호를 그대로 쥔 채 `totpCode` 만 더해** 다시 보낸다.

> ⚠ **레거시 `/api/app-auth/login` 에 2단계 인증을 걸면 워치 수집이 즉시 멈춘다**(가드 테스트 존재).
> 태블릿이 레거시 경로를 쓰면 안 되는 이유이기도 하다.

## 7.2 토큰 수명·회수

- access 는 단기, refresh 는 회전. **[미검증]** 실제 수명과 회전 동작은 라이브에서 확인해야 한다.
  ⚠ 과거 사고 이력 — 토큰 수명 15분인데 단말이 만료본을 22시간 재전송하고 **리프레시 회전이
  동작하지 않은** 사례가 있다(세션 32건 중 29건 미회전).
- **`verifyMobileAccessJwt` 는 세션 DB 를 조회하지 않는다** → 즉시 폐기가 보장되지 않는다.

## 7.3 역할·현장·소유권

- **[확정] 허용**: `role IN ('platform_admin','site_manager')`
  — 시공사 법인 계정은 `site_manager` + `is_company_account=true` 이므로 **같은 검사로 통과**한다.
- **거부**: `owner_officer` · `worker` · 그 밖의 모르는 역할(**기본 거부**)
- **[관측] CCTV 는 서버 함수가 판정한다** (ERD 073)
  ```sql
  can_view_site_cctv(p_user, p_site) → boolean
   = active AND ( platform_admin
                OR ( site_manager AND company_id = site.contractor_company_id
                     AND site_member(left_on IS NULL) ) )
  ```
  담당관·법인 계정은 true, **작업자·발주기관 담당관·다른 회사·미배정 관리자는 false**.
  송출 on/off(젯슨 게이트 `enabled`)는 **`platform_admin` 전용**이고 **CCTV 는 항상 ON 이 기본**이다.
  → **앱이 판정하지 않는다.** 서버 결과만 반영한다.
- **[관측]** `mediaWriteScope` 는 **소유자 또는 본인(workerId)** 만 수정하도록 되어 있다.
  "admin·owner 수정 가능"은 부정확하다. **타인 사진에 주석을 다는 권한은 별도 검사**가 필요하다.
- **[관측]** ERD §RLS — *"조달청 담당관(`owner_officer`)은 생체 열람 대상이 아니다"*.
  태블릿 허용 목록과 일관된다.

## 7.4 서버 확장 범위 (D-4 · **미확정**)

담당관 주 업무 API 가 앱 토큰을 받지 않는다(§3.3). 선택지:

| 안 | 방법 | 트레이드오프 |
|---|---|---|
| ⓐ | 필요한 기존 라우트에 **공통 v2 인가 추가** | 적은 라우트 / **웹·워치 회귀 면적이 넓다** |
| ⓑ | **모바일 전용 관제 경로** + 업무 로직 공유 | 계약 분리가 쉽다 / 래퍼·버전 관리 증가 |
| ⓒ | 명시 기준에 따른 혼합 | |

> ⚠ 조사의 "108개"·"12개"를 **그대로 수정 개수로 계산하지 않는다.**
> endpoint + HTTP method 별로 **허용 역할·현장·소유권·응답**을 정해야 한다.
> **워치 로그인은 유지**한다.

## 7.5 워치 호환

레거시 경로와 워치 수집은 **건드리지 않는다**. 태블릿 작업이 워치를 멈추게 해서는 안 된다.

# 8. 오프라인과 데이터 수명

## 8.1 [확정 2026-09-12] 오프라인 범위

**조회 캐시 + 기록 초안 + 댓글·사진·일정 지연 전송.**

| 상태 | 되는 것 | 안 되는 것 |
|---|---|---|
| 끊김 | 마지막 수신 화면 열람 · **사진 촬영 · 펜 주석 · 메모 작성** | 최신 현장 상태 · 영상 · **경보 대응 확인** |

> **경보 '대응 확인'은 오프라인 예약하지 않는다.** "연결 후 가능"을 표시하고
> **완료·예약 상태를 만들지 않는다** — 누가 언제 확인했는지가 안전 기록이기 때문이다.

## 8.2 영속화

로컬 DB 후보는 **채택 전 재확인**한다. 보관 대상 = 조회 캐시 · 기록 초안 · 전송 큐 · **펜 벡터**.

## 8.3 전송 큐 최소 상태 (9종)

`로컬 저장` / `전송 대기` / `전송 중` / **`서버 결과 확인 중(응답 유실)`** / `완료` / `실패` /
`재로그인 필요` / `권한 회수` / `수정 충돌`

> **"로컬 저장됨" 과 "전송 완료" 는 다른 문구**로 쓴다.
> **연결 아이콘이 켜져도 POST 는 실패할 수 있다** — `처리 중`/`서버 확인됨`/`실패`를 구분하고,
> **결과 불명이면 재전송이 아니라 서버 상태 재조회가 먼저**다.

## 8.4 ★ 중복 방지 (선행 조건)

**[관측]** `app/api/app-media/route.ts` 핸들러에서 **클라이언트 작업 ID 중복방지 계약을 찾지 못했다.**
(DB·트리거 전체 감사 결론은 아니다.)

> **지연 전송을 채택한 이상 이것은 선택이 아니다.**
> **전송 결과 불명에서 새 작업 ID 로 재전송하면 안 된다.** 서버가 **작업 ID 로 결과를 조회**하거나
> **같은 ID 재시도를 중복 없이 처리**하는 계약이 필요하다.

## 8.5 계정 전환

- 세션 만료 시 **미전송 기록을 삭제하지 않는다.** 잠금·보존.
- **재로그인 계정이 이전과 다르면 이전 큐를 발송하지 않는다.**
- 재인증 후에도 **작성 현장·대상 권한을 다시 확인**한다.
- **미전송 초안은 작성 당시 현장으로 고정**한다.

## 8.6 보존

⚠ 개인정보·안전 기록 보존 정책은 **이 문서가 정하지 않는다.** 서버 정책을 따른다.

# 9. 캘린더 · OCR 사진 · 펜 기록 — 요구사항 13의 핵심

## 9.1 [관측] 현재 흐름

> ⚠ **정정 (태곤 님 2026-09-12)** — 종전 기록의 **"작업자 앱" 은 틀렸다.**
> **OCR 이 들어간 휴대폰 앱은 `현장 담당관 앱` 이고, 작업자용 앱은 없다.**
> 작업자용은 팀원이 만든 **워치 앱**뿐이며 생체·수집 경로라 캘린더 사진과 무관하다.
> **이 정정이 D-2 를 살렸다** — 사진이 담당관 본인 것이라 주석본을 올려도 **귀속이 안 바뀐다**.

```
현장 담당관 휴대폰 앱(카메라·OCR) → POST /api/app-media → Object Storage 업로드 + calendar_media 등록
                                              → 관제웹 캘린더 날짜 셀에 배지 → 사진 + 메타 + 댓글

(별개) 워치 앱 = 작업자용 — 생체·수집. 캘린더 사진과 무관.
```

**[관측] `POST /api/app-media` 소스 확인** (`app-media/route.ts` · 상세는 `research/live-server-analysis.md` §3-4)

| 확인 | 답 | 행 |
|---|---|---|
| 역할(role) 검사 | **없다** — `verifyAppJwt` 또는 `APP_UPLOAD_TOKEN` 하나면 업로드된다 | `:79-87` |
| `dateKey` | **폼 값이 우선** → **D-2 보완 2 가 동작한다** | `:120-123` |
| 귀속(`uploader`/`workerId`) | **JWT 신원으로 강제 덮어쓴다. 폼 값 무시**(위조 방지) | `:127-133` |

> ⚠ **[미검증] 잔여 리스크** — **담당관이 교체된 현장**에서는 업로더가 바뀐다.
> 그때 `title` 의 원본 식별자가 **유일한 연결 고리**다. `title` 길이 제한은 **미확인**.

사진 1건이 들고 있는 것 — `date_key`·`captured_at`(**KST 로컬 ISO**)·`media_url`(**만료형 프리사인**)·
`ocr_text`·`road_address`·`latitude/longitude`·`worker_id`·`description`·`comments[]`·`coordGapM`

> ⚠ **프리사인 URL 과 이미지 바이트 캐시는 별개다.** 만료 URL 을 영속 ID 로 삼지 않는다.
> ⚠ **KST 날짜와 촬영 시각을 분리한다.** "Z 로 보내면 항상 9시간 오류"로 일반화하지 않고
> 자정·명시 `dateKey`·지연 업로드를 **따로 시험**한다.

## 9.2 주석 대상

사진 위 주석을 1순위로 한다. 일정·날짜 칸 필기는 **범위 밖**(필요하면 별도 결정).

## 9.3 [확정 2026-09-12] 저장 방식 — **A안 + 보완 2**

**신규 스키마(`media`·`media_comment`)에도 펜 주석을 담을 자리가 없다.** 어느 안이든 설계가 필요하다.

| 안 | 방법 | 서버 변경 |
|---|---|---|
| **A** | 주석 합성본을 **새 사진으로 업로드** | 불필요 |
| **B** | **벡터(스트로크)를 분리 저장** | **주석 저장소 신설** |
| **D** | A + 댓글로 **원본 연결 표시** | 불필요(관례) |

**차이가 나는 지점** — ⒜ 합성 게시본의 스트로크를 **편집할 수 있는가** ⒝ **다른 단말이 벡터를 받는가**
⒞ **원본 관계가 서버에 보장되는가**

> ⚠ **A/D 도 "수정 불가"가 아니다** — 로컬에 벡터를 보관하므로 **그 단말에서는** 재편집된다.
> ⚠ **B 도 레이어 토글·히스토리·웹 편집이 자동으로 생기지 않는다.** 구현해야 생긴다.
> ⚠ **D 의 댓글 연결은 관례이지 참조 무결성이 아니다** — 원본 삭제·권한 상실·댓글 삭제로 끊긴다.
>
> **[확정] 어느 안이든 앱 안에는 벡터를 보관**한다. 단 **로컬 보관만으로 전환이 보장되지 않는다** —
> 원본 ID·버전·좌표계·작성자·작업 ID·스키마 버전이 함께 있어야 한다.
>
### ★ 결정 — **A안(합성본 업로드) + 보완 2가지**

**[확정] 근거 (태곤 님 2026-09-12)**
> *"한 현장 하나에 한명의 현장 안전 담당관이 배치됨. 이에 따라 태블릿도 한 현장 하나당 한 태블릿만 제공이됨"*

→ **"다른 기기에서 열기"가 구조적으로 발생하지 않는다.** B안의 결정적 이점(다른 단말 재편집)이
무의미하므로 **서버에 주석 저장소를 신설하지 않는다.**

**보완 2가지 — A안의 약점을 서버 변경 없이 막는다**

| A안 약점 | 보완 | 방법 |
|---|---|---|
| 캘린더 날짜가 어긋난다(주석본이 *주석 단 날*로 들어가 원본과 멀어짐) | **`dateKey` 를 원본 날짜로 지정해 업로드** | `POST /api/app-media` 가 이미 `dateKey` 를 받는다 |
| 어느 사진의 주석인지 모른다 | **`title` 에 원본 식별자를 박는다** | 예: `현장 이미지 (주석) — 원본 08-28 14:38 · <id>` |

→ **같은 날짜 칸에 원본과 주석본이 나란히** 놓이고, 제목만으로 관계가 보인다.

**D안보다 나은 점** — D 는 `사진 + 연결 댓글` **2건**을 보내야 해서 *사진만 성공하고 댓글이 실패*할 수
있다. 그러면 연결이 없는데 **사용자는 연결됐다고 믿는다.** A+보완은 **전송이 1건**이라 이 실패가 없다.

**로컬 벡터는 그대로 보관한다** — 담당관 본인 기기에서는 주석만 지우거나 이어서 고칠 수 있고,
나중에 B 로 옮길 여지도 남는다.

> ⚠ **남은 검증** — ⓐ `dateKey` 를 원본 날짜로 보냈을 때 캘린더 배치가 실제로 그렇게 되는지
> ⓑ `title` 길이 제한 ⓒ **타인 사진에 주석을 덧붙일 권한**을 서버가 어떻게 검사하는지(§7.3).
>
> 비교 근거 화면 — `artifacts/ui-mock/annotation.html` (A/B/D × 4상황).

## 9.4 원본·버전

**타인이 올린 사진에 주석을 다는 것은 원본을 고치는 것과 다르다.** 서버가 "내 주석을 덧붙일 권한"을
별도로 검사해야 한다(§7.3).

## 9.5 시간·위치·OCR

메타 표시 우선순위 = ① 앱 구조화 필드 → ② `ocr_text` 말미 스탬프 파싱(best-effort).

## 9.6 공유

관제웹에서 **어느 사진의 주석인지** 보여야 하는지가 D-2 선택의 핵심 기준 중 하나다.

# 10. 현장 관제 기능

## 10.1 안전 신호등 · 작업자

- 4행(기상·작업자·가스·AED) + 종합 판정. **각 행은 상세로 진입**한다.
- 작업자 표 12컬럼은 **카드형으로 재설계**한다.
- ⚠ **대기 작업자는 생체 미수신이라 판정 대상이 아니다** — 이 구분을 화면이 말해야 한다.

## 10.2 가스 · AED

- **실연동 3 / 데모 8** 구분을 유지한다. **[관측]** 실연동은 `raw` 값, 데모는 `ppm` 으로 **단위가 섞여 있다.**
- AED 교환주기·점검 예정일은 캘린더 자동 마커와 같은 소스다.

## 10.3 경보 수신 · 대응

- **목록 행 탭 = 확인 처리로 만들지 않는다.** 상세에서 대상·시각을 본 뒤 **명시적 1회**.

- **[미확정]** 푸시(FCM)는 미구현. 오프라인 복귀 시 **놓친 경보 따라잡기** 규칙이 필요하다.
- ⚠ **이 기기는 전화를 걸 수 없다.** 관제웹 SOS 모달의 통화 버튼을 그대로 옮길 수 없다 —
  **연락처 복사·공유** 등 대안을 쓰고, **화면이 그 사실을 말한다.**

# 11. 신규 스키마 수용성 · 전환 호환

## 11.1 전제

**신규 DB 는 아직 라이브에 연결되지 않았다.** 라이브 관제웹은 구 DB 를 쓴다.
전환은 별도 트랙이고, **태곤 님 명시 허락 전까지 main·라이브·Cloud Run env 를 신 DB 에 물리지 않는다.**

> **신규 스키마를 구 DB 기준으로 매핑하지 않는다.** 자체 설계 의도로 읽고
> "이 기능을 감당하는가"로만 평가한다.

## 11.2 [관측] §7 증빙·일지

```
media        { id, site_id, user_id, captured_at, ocr_text, latitude,
               road_address, date_key, title, description }
media_comment{ id, media_id, author_id, updated_at }
```

**펜 주석을 담을 자리가 신규 스키마에도 없다.** → A 안은 구·신 양쪽에서 스키마 변경 없이 동작하고,
B·C 안은 **신규 스키마에도 추가가 필요**하다.

## 11.3 역할·RLS

§4.1 의 4부류 + `site_member` 로 현장 범위가 정해진다.
**[관측]** `watch_vital`·`watch_location` RLS = **본인 + 배정 현장 관리자**.

## 11.4 경보

`kind`/`detail_key` 분리 · `source_kind`(누가 판정했나) · `dedup_key`(중복 방지).
**[미검증]** 오프라인 복귀 시 **변경 경보 조회·커서**가 가능한지.

## 11.5 세션·감사

**[미검증]** §8 세션·감사 구조가 "v2 토큰이 세션 DB 를 조회하지 않는" 문제를 해결하는지.

## 11.6 API 호환 게이트 (전환 차단점)

| 앱이 하는 일 | 전환이 보장해야 하는 것 |
|---|---|
| HTTPS 업무 API 만 사용 | **DB 연결·테이블명·SQL 에 의존하지 않는다** |
| API 응답을 안정된 업무 모델로 해석 | 식별자는 **불투명 값** · 시각·권한·오류 의미를 명시한 계약 |
| 사용자·현장별 캐시와 미전송 큐 보존 | **ID·인증 주체·큐 작업 ID 의 연속성** |
| 라이브와 독립적으로 문서·시안 시험 | 신규 백엔드 독립 시험 환경에 같은 계약 시험 |

> **아직 "전환해도 안 깨진다"고 증명한 것이 아니다.** 이를 인수 조건으로 둔다.
> **DB 전환은 이 앱 계획의 선행조건이 아니다.**
