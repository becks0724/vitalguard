**여기서 나오는 설계 결론 3가지**

1. **`SafeArea` 는 좌우 제스처 띠를 막아주지 않는다.**
   `padding.left/right` 가 **0.0** 인데 `systemGestureInsets.left/right` 는 **29.6 dp** 다.
   둘은 다른 인셋이다. 좌우 끝 29.6 dp 에 **주 실행(밀기·스와이프 삭제·캔버스 끝 획)을 두면
   OS 제스처와 경합**한다. → `MediaQuery.systemGestureInsets` 를 **명시적으로 읽어서** 피한다.
2. **상태바·네비바는 회전해도 위/아래에 그대로 있다.** 가로에서도 `left/right` 가 0 이고
   `top 39.1 / bottom 15.1` 이 유지된다. 측면으로 옮겨 간다고 가정한 레이아웃은 틀린다.
3. **가로에서 키보드를 띄우면 안전 높이의 43.5% 가 사라진다**(세로 26.5%의 1.6배).
   `IME 368.0 dp` 는 방향과 무관하게 같은데 **안전 높이가 811.8 dp 로 줄기 때문**이다.
   → **가로에서는 키보드를 띄우는 흐름을 더 강하게 피해야 한다.** 펜·음성·선택지를 우선한다.

> ⚠ `viewInsets.bottom` 에는 **하단 네비바(15.1 dp)가 이미 포함**돼 있다.
> `padding.bottom` 을 또 빼면 중복 차감이다. 위 26.5% / 43.5% 는 중복 차감 없이 계산한 값이다.
>
> ⚠ IME 368.0 dp 는 **Gboard 한글 기본 상태** 값이다. 다른 입력기·이모지 패널·추천줄 설정에
> 따라 달라진다. **고정 상수로 쓰지 말고 런타임 인셋을 읽는다.**

### ★★★ [관측] 팜 리젝션 · 손가락 구분 — 2차 측정 (2026-09-12)

1차 측정은 **폐기했다.** 진단 화면이 **호버 포인터를 접촉과 같이 세는 버그**가 있었다
(`Listener` 에는 exit 콜백이 없어 호버가 유령으로 남았고, 펜을 뗀 뒤에도 "동시 포인터 1" 이
유지됐다). 호버를 분리하고 **`PointerCancel` 횟수**를 세도록 고친 뒤 다시 쟀다.

손바닥을 캔버스에 얹은 채 펜으로 긋고, 손가락으로도 그은 결과다.

| 판정 | 결과 | 실측값 |

| **포인터 취소(팜 리젝션)** | ✅ 동작 | **2 회** · 마지막 취소 종류 **`touch`(손가락)** |
| 필압 (2차 표본 200) | ✅ | `min 0.220 → max 0.782` · `pressureMin 0.000` |

> 오염 검증: 이때 오른쪽 패널을 `adb` 로 스크롤했지만 **`Listener` 는 왼쪽 캔버스에만** 걸려 있다
> (`lib/diag_screen.dart:262` — 패널은 `:289` 로 별개). 취소 2회는 **전부 캔버스에서 난 것**이다.

**★ 팜 리젝션은 "차단" 이 아니라 "사후 취소" 다**

손바닥이 **일단 `touch` 포인터로 들어온 뒤**(그래서 동시 접촉이 2가 된다)
시스템이 **`PointerCancel` 로 거둬간다.** 그리고 취소된 것은 `touch` 이지 `stylus` 가 아니다 —
**펜 획은 살아남았다.**

**여기서 나오는 구현 규칙 3가지**

1. **잉크는 `PointerDeviceKind.stylus` 만 그린다.** `touch` 로도 그리면 **손바닥이 점을 남긴다.**
   취소가 오기 전까지의 몇 프레임이 이미 화면에 찍히기 때문이다.
2. **`onPointerCancel` 을 반드시 처리한다.** 취소된 포인터가 남긴 획을 **되돌려야** 한다.
   `onPointerUp` 만 처리하면 손바닥 흔적이 영구히 남는다.
3. **동시 접촉 2를 전제로 설계한다.** 손바닥과 펜이 **동시에 잡히는 구간이 실제로 존재한다.**
   포인터를 하나로 가정한 코드는 여기서 깨진다.

**아직 못 잰 것**

- **잉크 지연**(펜 끝과 획 사이 거리) — 눈으로만 봐서는 수치가 안 나온다. 별도 측정 필요.
- **호버 거리의 단계 수** — `max distance 1.000` 만으로는 **연속값인지 0/1 이진인지 모른다.**
- **장갑 낀 손의 터치 인식** — **부분 측정**(바로 아래 절). ⚠ 진짜 장갑이 아니라
  **면 95% 옷을 감싼 상태**였다. **면 목장갑 · PU 코팅장갑으로 재측정해야 닫힌다.**

### ★★ [관측] 터치 정확도 — 맨손 vs 천 (2026-09-12)

진단 화면의 `장갑 측정`(`lib/glove_screen.dart`)으로 쟀다. 타깃을 40→48→56→64→72 dp 로
순환시키며 랜덤 위치에 띄우고, 탭 지점과 타깃 중심의 **오차 벡터**를 기록한다.
위치 난수는 **고정 시드(7)** 라 두 조건이 **같은 자리 순서**를 밟는다.

> ⚠⚠ **측정 조건을 먼저 읽을 것.** "장갑" 열은 **진짜 장갑이 아니다.**
> 장갑이 없어서 **면 95% 의류 원단을 손에 감싼 상태**로 쟀다(겹 수·두께 미기록).
> 면은 전도성이 없지만 **얇은 천은 정전용량을 완전히 차단하지 못한다.**
> 따라서 이 열은 **"가장 유리한 조건"의 하한선**이고 **현장 장갑을 대표하지 않는다.**

| 타깃 | 맨손 | 천(면 95%) |
|---|---|---|
| **40 dp** | **2/4 (50%)** · 오차 18.5 | **3/4 (75%)** · 오차 12.5 |
| 48 dp | 4/4 (100%) · 12.7 | 4/4 (100%) · 13.1 |
| 56 dp | 4/4 (100%) · 11.5 | 4/4 (100%) · **9.5** |
| 64 dp | 4/4 (100%) · 15.2 | 3/3 (100%) · 14.3 |
| 72 dp | 3/4 (75%) · **69.1** ⚠이상치 | 3/3 (100%) · 15.4 |
| **평균 오차 벡터** | **(3.3, 12.7)** dp · 크기 **13.2** | (2.7, 7.7) dp · 크기 **8.1** |
| 접촉 반경 · 압력 | **0.2 · 1.000** | 0.1 · 1.000 |
| 표본 | 20 | 18 |

> ⚠ **72dp 맨손 오차 69.1 은 이상치다.** 반지름 36dp 타깃에서 3/4 가 적중했으므로
> 빗나간 1회가 200dp 넘게 떨어졌다는 계산이 나온다. 타깃이 바뀐 걸 못 보고 이전 자리를
> 누른 **측정 사고**다. 평균에서 빼고 본다.
>
> ⚠ **표본이 크기당 3~4개다.** `4/4 = 100%` 는 **"실패율 0%" 가 아니라 "4번 중 실패가 없었다"** 다.
> 40dp 의 50% vs 75% 도 표본 4개 차이라 **우연 범위**다.

**확정할 수 있는 것 4가지**

1. **40 dp 는 쓰지 않는다.** **맨손조차 50%** 다. 48dp 부터 실패가 없었다.
   → 계획서의 **56dp 최소**는 여유를 둔 값으로 유지할 근거가 있다.
2. **★ 오차의 대부분이 "편향" 이다 — 랜덤이 아니다.**
   맨손 평균 오차 벡터의 **크기가 13.2** 인데 평균 오차 **거리가 11.5~15.2** 다. 거의 같다.
   즉 빗나감이 사방으로 흩어진 게 아니라 **아래쪽으로 쏠려 있다.**
   손가락이 타깃을 가려 **위쪽 가장자리를 보고 조준**하기 때문으로 보인다(원인은 [가설]).
3. **그 편향은 천 때문이 아니다.** **맨손(12.7)이 천(7.7)보다 오히려 크다.**
   소재와 무관한 보편적 조준 특성이다.
4. **손가락은 압력도 접촉 면적도 보고하지 않는다.** 두 조건 모두 **압력 `1.000` 고정**,
   반경 0.1~0.2. 펜은 `0.041~0.917` 로 변하는데 손가락은 안 변한다.
   → **접촉 면적으로 장갑 착용을 자동 감지하는 방식은 불가능하다.**

**★ 2번에서 나오는 처방 — "타깃을 키워라" 가 아니다**

랜덤 오차라면 타깃을 키우는 게 답이지만 **편향이라면 위치가 답**이다.
그렇다고 히트박스를 아래로 옮기면 **그 아래 항목과 겹쳐 오탭이 늘어난다.** 그래서 실제 처방은:

> **세로로 붙은 터치 타깃 사이 간격을 편향(약 13dp)보다 크게 둔다.**
> 현재 `vgGapTap = 12dp` 는 **편향보다 작다 — 부족하다.**

**아직 못 잰 것 — 실제 장갑**

| 장갑 | 이 측정 대비 예상 | 등급 |
|---|---|---|
| 면 목장갑 | 더 두껍고 짜임이 여러 겹 → **더 나쁨** | [가설] |
| **PU · NBR 코팅장갑** | 코팅면이 **절연체** → **아예 안 될 수 있음** | [가설] |
| 가죽 · 방한장갑 | 두껍고 절연 → **아예 안 될 가능성 높음** | [가설] |

→ **면 목장갑 + PU 코팅장갑** 두 종으로 재측정해야 `[미검증] 7` 이 닫힌다.
   가능하면 **현장 담당관이 실제로 끼는 것**으로 잰다.

**★ 이것이 "펜 우선" 설계에 주는 더 강한 근거**

코팅장갑에서 터치가 **아예 안 되면 펜이 유일한 입력 수단**이 된다.
펜은 자체 신호를 내므로 **장갑과 무관하게 동작한다.**
→ 계획서의 "펜 우선" 은 *편해서* 가 아니라 **"장갑을 끼면 터치가 아예 안 될 수 있어서"** 다.
→ **모든 핵심 동작에 펜으로 도달하는 경로가 있어야 한다.**
   장갑을 벗어야만 되는 기능은 현장에서 안 쓰인다.

### 5-1. ★ 레노버 OS 손글씨 인식 — **실측으로 기각** (2026-09-12 12:00)

`com.lenovo.penservice/...HandwritingIme` 는 정식 Android IME 로 **실존**하고, 설정 문구도

**시험 절차(전부 실행 완료)**

| # | 단계 | 결과 |
|---|---|---|
| 1 | `설정 → 펜 → 손글씨 → 인식 언어` 에서 **한국어 팩 다운로드** | ✅ 완료 (⚠ 버튼을 누르자 **Wi-Fi 설정으로 튕김** — 네트워크 필수) |

| 쓴 글자 | 결과 | 실패 유형 |
|---|---|---|
| 네 | `네` | 정상 |
| 이 | `ㅇ` | 중성 `ㅣ` 누락 — **음절 조합 실패** |
| 버 | `뻐` | 자음 오인식 (ㅂ→ㅃ) |
| 구 | `7ㄱㅜ` | **숫자 혼입** + 자모 분리 |

**원인** — 설정 화면이 스스로 말한다:
> *"필기 기능은 **영어, 숫자 및 구두점 기호와 함께** 선택한 언어를 인식할 수 있습니다."*

**한글 음절 조합(초성·중성·종성)을 수행하지 못한다**(`글`→`그리`).

> **판정 — 플랜A(레노버 OS 손글씨 위임)는 주력 입력 수단으로 부적격.**

→ 설계 제약: **앱은 IME 를 강제하지 않고 사용자 기본 IME 를 존중**해야 한다.

### 5-4. [관측] P4 순정 온디바이스 한국어 STT 실측 완료

Codex는 **원시 로그 251 이벤트 전체**를 읽어 엔진·환경·원문 결과를 대조했다.
**비행기모드 ON·Wi-Fi OFF·활성 네트워크 OFF에서도 한국어 인식이 동작한다.**
온라인 조건에서도 같은 온디바이스 엔진을 사용했다.

**[확정] 사용자 결정:** `[미검증] 5` 온디바이스 한국어 STT는 **닫힘**이다.

#### 엔진·모델·환경과 비교 범위

`isOnDeviceRecognitionAvailable=true`, 설치 모델 `installed=["ko-KR"]`, `pending=[]`,
`online=[]` 보고를 확인했다. 오프라인 지원 조회는 원시 로그 138~140행이며,
오프라인 최종 결과 5건의 시작·종료 환경도 모두 비행기모드 ON·Wi-Fi OFF·활성 네트워크 OFF다.
중간 설정 전환에 아직 활성 네트워크가 남은 조회(134~136행)는 이 5건과 구분한다.

| 항목 | 온라인 조건 | 오프라인 조건 |
|---|---|---|
| 엔진·언어 | `createOnDeviceSpeechRecognizer` · `ko-KR` | 동일 |
| 설정 | 비행기모드 OFF · Wi-Fi ON · 활성 네트워크 ON | **비행기모드 ON · Wi-Fi OFF · 활성 네트워크 OFF** |
| 비교 대상 최종 결과 | 5문장, 문장별 1건 | 5문장, 문장별 1건 |
| 1순위 원문 일치 | **5건 중 1건** | **5건 중 1건** |
| 후보 목록에 원문 포함 | **5건 중 2건** | **5건 중 3건** |
| 별도 인식 오류 | **1건 · code=7 · ERROR_NO_MATCH** | **0건** |
| 첫 부분결과 평균, ms 정수부 | **2,506 ms** | **2,246 ms** |

평균은 **최종 결과가 있는 각 조건 5건**의 `firstPartialMs`를 대상으로 지시서처럼
**소수점 이하를 버린 ms 정수부**로 표시했다. 지연은 `startListening` 직전부터 첫 부분결과 콜백까지이며
발화 시작 기준이 아니다. 준비·발화 타이밍도 포함되므로 두 평균으로 온라인/오프라인의 성능 우열을 단정하지 않는다.

원시 로그에는 **started 12건·final 10건·error 1건·cancelled 1건**이 있다.
온라인의 취소 1건(20행)과 오류 1건(72행)은 위 5개 최종 결과의 비교·지연 평균에서 제외하되,
원시 로그와 이 설명에 그대로 남긴다. 온라인 ‘가스 농도’는 오류 뒤 재시도한 최종 결과가 표에 실려 있다.

#### 이번 표본에서 확인한 실패와 설계 규칙

- 조건당 **5문장 최종 결과를 문장별 1회씩** 비교했다. **5건 중 1건**은 이 표본의 원문 일치 건수이며
  일반적인 정확도로 환산하지 않는다. 띄어쓰기·숫자 표기를 정규화해 맞는 건수를 늘리지 않는다.
- `크레인`→`그린`/`크린`, `초과`→`추가`, `3번`→`3분`을 관측했다. 이 문장들에서의 실패이며
  전문용어 전체에 대한 성능을 확정하지 않는다.
- 온라인 `작업자 두 명 안전대 미착용`이 **`작업자 두 명 안전띠 적용`**으로 바뀌었고,
  같은 목록의 4순위도 **`작업자 두 명 안전띠 착용`**이었다. 부정이 사라져 안전 기록 의미가 뒤집히는 실패다.
  같은 문장의 오프라인 결과는 원문과 일치하므로 온라인 연결이 원인이라고 단정하지 않는다.
- **I-4:** STT를 1순위 한 줄로 확정하지 않는다. **최대 5개 후보를 보여주고 사용자가 고르게** 한다.
  실제 반환은 **3~5개**였으므로 없는 후보를 생성해 채우지 않는다. 오프라인에서 1순위 일치는 5건 중 1건,
  후보 포함은 5건 중 3건이다. 이는 선택 기회이며 사용자의 선택 성공이나 향상 배수를 실측한 값은 아니다.
- **I-5:** 선택·수정한 STT 결과를 **사용자가 확인하기 전 저장·전송하지 않는다**.
  정답 후보가 없으면 다시 말하거나 펜 잉크로 기록할 수 있어야 한다.
  입력 칩의 ‘이상 없음’을 기본 선택하지 않는 규칙과 같은 이유다.
