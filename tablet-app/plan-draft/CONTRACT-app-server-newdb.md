# 앱–서버 계약 (신 DB 이행 기준)

> **담당관 태블릿 앱(`vitalguard_field`)이 서버에 요구하는 것**을 한 곳에 적는다.
> 신 DB(VITALGUARD2)를 설계·이행할 때 **이 계약이 깨지면 앱이 죽는다.**
>
> 작성 2026-09-15 · 기준 앱 커밋 `dbbff451` 이후 · 라이브 리비전 `00388-5dm`
> 근거는 **앱 코드에서 뽑았다**(`lib/data/live/live_gateway.dart`). 추정이 아니다.
> 관련 — [[SPEC-d4-app-admin-routes]] · [[신규 스키마 ERD]] · [[newdb-cutover-track]]

> **9/25 인수 기준:** [최종 인수 기록](../태블릿_최종_인수기록_20260925.md). 현재 설치본(main `8b9a071c`)과 신 DB 준비본(`9fb95dd5`)을 구분한다. 본문의 작성 당시 계약과 후속 개정은 날짜별로 읽는다.

## 0. 이 문서를 쓰는 이유

신 DB 는 **기존 기능 기준으로** 판단한다(구 스키마 매핑 프레임 금지 — 2026-09-04 결정).
그런데 "기능"이 어디까지인지가 문서마다 흩어져 있어, **앱이 실제로 부르는 것**을 기준선으로 고정한다.

⚠ 이 문서는 **앱이 요구하는 최소 계약**이다. 서버가 더 줘도 되지만 **덜 주면 앱이 깨진다.**

## 2. 신 DB 가 반드시 만족해야 할 것

### C-1. 현장 식별자가 DB 에 있어야 한다 ★

2026-09-15 에 구 DB 에서 고친 것이다. **같은 실수를 반복하지 마라.**

구 DB 는 이랬다:
- 현장 목록 9개 = **코드 상수**
- 담당관이 고른 현장 = **브라우저 localStorage**
- 현장 이름·주소 테이블에 **`site_id` 컬럼이 없음**
- 현장 마스터 `t_site` 는 **0행·미사용**

→ **앱이 현재 현장을 알 방법이 없어** `calendar_media` 51행 중 49행(96%)이 `site_id` NULL 이었다.

신 DB 요구:
1. **현장 마스터 테이블**이 있고 실제로 채워져 있을 것
2. **담당관 ↔ 현장** 관계가 DB 에 있을 것(현재 선택 `user_current_site` + 배정 `user_site_assignment` — **2026-09-17 구 DB 에 신설**, 협력업체(`org_type=contractor`)는 배정 현장만 본다 · `SPEC-d5-site-assignment.md`)
3. `GET /api/admin/site-info` 응답에 **`site_id` 가 포함**될 것
   — 앱은 `controller.site?.site_id` 를 읽어 사진에 붙인다(`capture_screen.dart:249`)
4. 현장 정보 스냅숏은 **현장별로** 남을 것
   — 구 DB 는 `UNIQUE(snapshot_date)` 라 하루 1행이어서 담당관 여럿이 서로 덮어썼다.
     `UNIQUE(snapshot_date, site_id)` 로 고쳤다

✅ **다중 현장 담당관 — 2026-09-17 결정: 합집합이 아니라 현재 현장 1개.** 앱은 `siteId` 를 보내지 않고
`site-info` 가 주는 `user_current_site` 한 곳을 쓴다. **site-status 다섯 행(작업자 행 포함)도 같은 현장 기준**이어야
헤더와 상태 행이 어긋나지 않는다(`actor.siteIds[0]` 가 아니라 `user_current_site`, 없으면 첫 배정).
발주처 담당관(`owner_officer`)은 태블릿을 쓰지 않는다. **9/25 호환 보완:** 앱 허용 role 은 `platform_admin`·`owner`·`site_manager`·`admin`이다.
신 DB 모바일 로그인·me 응답은 구 어휘를 유지하여 `platform_admin → owner`, `site_manager/owner_officer → admin`으로 보낸다.
앱은 응답 role을 그대로 읽으므로 `owner` 별칭이 필요하다. **`admin`만으로 현장 관리자와 발주처를 구별할 수 없으며 최종 접근 판정은 서버가 한다.**
상세 — `~/Desktop/태블릿앱_계약_질문지_회신_20260917.md` Q1·Q2.

### C-2. 멱등키 — 중복 업로드를 막는다 (N-3)

`POST /api/app-media` 와 댓글은 **`client_operation_id`** 를 받는다.

- 컬럼: `calendar_media.client_operation_id` · `calendar_media_comment.client_operation_id`
- **부분 유일 인덱스**: `WHERE client_operation_id IS NOT NULL`
  (기존 NULL 행을 보호한다 — 전체 UNIQUE 로 만들면 옛 행이 충돌한다)
- 서버 순서: **`BEGIN → INSERT → 스토리지 PUT → COMMIT`**
  멱등키를 확보한 요청만 업로드한다(고아 파일 방지).
  경쟁 패자는 `23505` 를 잡아 롤백하고 **기존 행을 200 으로 돌려준다**

### C-3. 결과 불명을 해소할 조회 (N-4)

`GET /api/app/admin/operation-status` — 작업 ID 로 **등록 여부**를 묻는다.

앱 규칙(바꾸면 안 된다):
- 자동 조회는 **전송 상태 탭 진입·전경 복귀 시 1회**(30초 제한)
- **503·통신 실패는 "결과 불명" 을 유지**한다(성공으로 간주하지 않는다)
- `not_registered` 여도 **자동 재전송하지 않는다.** 재시도는 같은 작업 ID 로만

### C-4. 경보 종류는 **5종**이다

`sos` · `fall` · `vital` · `geofence` · **`absence`**

⚠ 2026-09-14 에 내가 "4종" 이라고 명세에 단언해 **`absence` 131건이 앱에서 누락**됐다.
`ALERT_TYPES` 단일 소스로 고쳤다. 신 DB 에서도 **한 곳에서만 정의**해라.
`danger_zone`(1건·08-19 이후 없음·타입 정의에도 없음)은 계속 제외한다.

### C-5. PII — 앱에 보내는 것과 보내지 않는 것

**보내지 않는다**: 워치 **생체 원시값**(개인정보·민감정보 보호)
**보낸다**: 가스포드 측정값(개인정보가 아니다) — `value`·`unit` 포함
  · O₂ 는 `%`, CO·H₂S 는 **raw ADC 그대로**(ppm 환산은 가스 임계 v2 과제)
**보내지 않는다**: 가스 이력 720행 · 펌웨어 state

⚠ 2026-09-14 정정: "서버가 원시값을 앱에 보내지 마라" 는 지침의 **취지는 워치 생체 데이터**다.
가스포드까지 막는 것이 아니다.

### C-6. 시각은 KST 로 통일

앱은 `asKstIso()` 로 정규화해 표시한다. 서버가 주는 시각에 **오프셋이 없으면 `+09:00` 으로 간주**한다.
적재 시각이 전부 `text` 인 것은 구 DB 의 사실이다([[vitalguard-live-db-facts]]) —
신 DB 에서 타입을 바꾸면 **앱의 파싱 경로를 함께 확인**해라.

### C-8. 기기 캐시는 7일, 전송 완료 원본은 웹 전용 (2026-09-17 결정)

앱은 기록 목록 캐시(`calendar:*`)·전송 완료 항목을 **7일** 지나면 지운다(049·055 파기 고지와 같은 값).
전송이 끝난 사진 원본은 **웹에서만 본다** — 완료 즉시 기기 원본·미리보기·`photo:<id>` 를 지우고
태블릿에서 그 사진에 추가 메모를 붙이지 않는다. 서버는 이 전제로 **원본·잉크·음성을 잃지 않아야 한다**
(기기에 사본이 없다). 현장 상태(작업자 생체·위치·경보)는 원래 캐시하지 않는다.

### C-7. 조회 0행을 정상 0건으로 만들지 않는다

앱 화면 원칙이다. 서버도 **"없음" 과 "못 가져옴" 을 구분해** 응답해야 한다.
`site-status` 는 `Promise.allSettled` 로 **행별 실패를 격리**하고 실패한 행만 표시한다.

## 3. 앱이 의존하는 DB 컬럼 (신 DB 대응표)

앱이 직접 읽는 필드다. 이름이 바뀌면 **서버 응답에서 맞춰주면 된다** —
앱은 DB 를 직접 보지 않는다. 다만 **의미가 사라지면 화면이 죽는다.**

| 화면 | 필요한 것 | 구 DB 위치 |
|---|---|---|
| 현장 요약 | 현장명·주소·`site_id` | `site_info_daily` + `site`(9/15 신설) |
| 작업자 | 이름·직급·심박·SpO₂·체온·상태 | `wearable_*` |
| 가스 | 가스종·위치·값·단위·심각도 | `gas_*` |
| AED | 장비 수·점검 예정일·남은 일수 | `aed_*` |
| 기상 | 기온·체감·습도·풍속(**m/s**)·특보 | 기상 캐시 |
| 경보 | 종류(5종)·작업자·시각·대응여부 | `alerts` |
| 기록 | 사진·잉크·음성·댓글·`site_id` | `calendar_media*` |
| 전송 상태 | 작업 ID·상태·멱등키 | `calendar_media.client_operation_id` |

⚠ **풍속은 m/s 로 통일**했다(2026-09-14). 안전보건규칙 §37② 의 설치·해체 10m/s ·
운전 15m/s 가 법적 강제라 단위를 섞으면 안 된다.

## 4. 이행 시 확인 절차

신 DB 로 바꾼 뒤 **이 순서로** 확인한다. 하나라도 건너뛰면 오늘 같은 일이 난다.

1. `GET /api/admin/site-info` 응답에 **`site_id` 가 실리는가**
2. 앱에서 **사진을 새로 찍어** `calendar_media.site_id` 가 채워지는가
   (기존 행은 소급되지 않는다 — 새로 찍어야 확인된다)
3. `site-status` 5행이 전부 오는가, 한 행이 실패해도 **나머지가 오는가**
4. 경보 목록에 **`absence` 가 포함**되는가
5. 같은 작업 ID 로 두 번 업로드해도 **행이 하나인가**(멱등키)
6. 통신을 끊고 업로드한 뒤 `operation-status` 로 **결과 불명이 해소되는가**

⚠ **앱 APK 를 다시 빌드·설치했는지 먼저 확인해라.** 2026-09-15 에 커밋만 하고
빌드를 빠뜨려 "서버가 안 준다" 고 한참 오진했다.

## 5. 하지 말 것

- **앱을 고쳐서 DB 변경을 흡수하지 마라.** 서버 응답에서 맞춘다(앱은 배포가 느리다)
- **워치 생체 원시값을 앱 응답에 넣지 마라**(C-5)
- **경보 종류를 여러 곳에 정의하지 마라**(C-4)
- **`client_operation_id` 를 전체 UNIQUE 로 만들지 마라** — 부분 유일 인덱스다(C-2)
- **스키마를 DDL 파일이나 직접 SQL 로 바꾸지 마라** — 정본은 `ensureSchema` 다

- **C-9 (2026-09-23 실측) 태블릿 사용 조건**: 서버 앱 게이트(`lib/app-admin-auth.ts`)는 `users.status='approved'` **and** (`role='owner'` or `admin_access=true`). 앱 쪽 `_allowed` 역할 집합과 별개로, 시공사 현장 관리자 계정도 관제웹 사용자 관리에서 **관리자권한(admin_access)** 을 켜야 현장 상태·경보·CCTV 가 열린다. **9/23 결정(태곤 님, 권장안 수용)**: 지금은 A — 승인 + 관리자권한 수동 부여 2단계 유지(자동 부여 B 는 관제웹 관리 메뉴·API 까지 열려 권장하지 않음). 신 DB 전환 설계에 C — 태블릿 전용 비트(예: `tablet_access`) 신설·앱 게이트 `owner | admin_access | tablet_access`·사용자 관리 토글·승인 시 현장 관리자 자동 부여 — 를 포함한다. 현장 배정은 `user_site_assignment` + `site.active=TRUE` 조인으로만 인정되고, `user_current_site` 는 site-info 조회 때 서버가 첫 배정으로 만든다.

> **9/25 최종 정정:** 위 C-9 비트 신설 제안은 **미채택**으로 종료했다. 현장당 관리자 1명 운영 전제에서 Q2 역할 제한과 현장 배정을 사용하며, `tablet_access`·관리 화면 토글·기기 시리얼 등록을 추가하지 않는다. 위 9/23 문장은 당시 검토 이력이다.

### 9/25 인계 갱신 — Q2 유지, C-9 미채택

- 신 DB Q2는 `feat/newdb-cutover` **83dd1b78**로 로컬 커밋 완료(미push·미배포, 담당 피어 인계 및 커밋 확인).
  앱 관리 API는 **DB 현재 role의 `site_manager`·`platform_admin`만** 허용하고 `owner_officer`는 403이다.
  담당 피어 검증: tsc/ESLint 통과, 전체 2346개 중 2333 통과·0 실패·13 기존 skip.
