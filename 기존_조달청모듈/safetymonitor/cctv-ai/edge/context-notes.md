# CAM-03 전송률 개선 — 컨텍스트 노트

## 2026-09-01 — 발단과 원인 확정

사용자 보고 = "Jetson 엣지 구동 시 CCTV 영상이 끊긴다 → MSI 랩탑(RTX 2060)으로 대체 검토".
실측 결과 **대체 불요** — 병목은 하드웨어가 아니라 전송 구조였다.

### 기각된 가설 (전부 실측)
- **연산 부족** ❌ — MSI 2060 PyTorch 24.7ms ≈ Jetson TRT 23.4ms. 요구는 83ms(12fps) 주기라 둘 다 3.5배 여유.
- **GoPro UDP 불안정** ❌ — 정상 운영 90초간 재연결 0 · 30fps 안정. 로그의 재연결 5.6만 회는 **18일 GoPro 분리 기간**의 재시도 루프였다(정상 운영 지표가 아님).
- **네트워크** ❌ — 유선 전환(enP8p1s0 1Gbps · 기본 경로) 후 rx/tx err 0. ※ 종전엔 와이파이가 기본 경로였다.
- **"PUSH_FPS 올려도 소용없다"(작업 중 중간 결론)** ❌ — POST 실측 93ms 로 반증. 6→10 변경으로 5.0→8.33fps 실제 상승.

### 단계별 천장 (전부 실측, 2026-09-01)
```
캡처(GoPro)        30 fps
추론               37 ms  → 27 fps
렌더(PIL+JPEG)     ~35 ms → 29 fps   ← ARM CPU 비용. 폰트는 캐시돼 있음(범인 아님)
추론+렌더 직렬      72 ms  → 13.9 fps ← 현 생산 상한
POST 왕복          93 ms  → 직렬 푸시 10.7 fps  ★ GET 바닥 82ms 라 페이로드 축소 무의미
```
- 6/12 → 10/20 설정 변경 실측: 전송 5.0 → 8.33fps · **429 등 푸시 오류 0**("429 회피" 주석은 예방적 설정이었음).
- 부작용 발견: 읽기·추론·렌더가 한 스레드라 INFER_FPS 를 올리면 **원본 읽기가 30→13.9fps 로 하락**(UDP 버퍼 적체 위험).

### 결정
- **D1. CCTV 는 Jetson 유지, MSI 는 예비.** 연산이 병목이 아님이 확정돼 이전의 근거 소멸. MSI 에는 스택 구축 완료(예비 경로 — memory `msi-laptop-remote`).
- **D2. 동시 푸시 = A안 채택(사용자 승인 09-01).** 워커 2개, 각자 **보낼 때 최신 프레임을 선점**. 도착 순서 역전 가능하나 둘 다 최신이라 체감 ≤1프레임. B안(시퀀스 번호 + 서버 폐기)은 cctv-ai 서버 수정이 필요해 보류.
- **D3. 2단계 분리.** 1단계 = 캡처 분리 + 동시 푸시(→~12fps), 2단계 = 추론/렌더 파이프라인(→~20fps, GIL 로 이론치 미달 가능). 한 번에 하면 어느 변경이 효과인지 분리 불가.
- **D4. PUSH_FPS 의미 유지** — 워커 합산 목표율. 워커당 주기 = PUSH_WORKERS/PUSH_FPS, 위상 어긋내기로 균등 간격.

### 함정 (재발 방지)
- **`pkill -f gopro_ppe_edge.py` 자기 매칭** — SSH 원격 명령줄에 같은 문자열이 있으면 자기 셸을 죽인다(레포 기록 3회차 재현). `[g]opro_ppe_edge` 브래킷 + kill/start 별도 호출.
- **`stream_fps` = 원본 읽기 속도**(cap.read 계수)이지 추론률이 아니다. 추론률은 `infers` 증분으로 잰다.
- **08-29 "CAM-03 라이브 확인"은 오판 가능성** — 오버레이 시각 14:51 이 마지막 GoPro 프레임 시각(08-13 14시대)과 일치. cctv-ai 캐시 프레임이었을 공산. 다음 ON 때 1분이면 확정 가능.
- Windows(MSI) 쪽: PowerShell 인라인 따옴표는 ssh 경유 시 깨진다 → **스크립트 파일 scp 후 실행**. `Start-Process` detach 는 실행 안 됨 / 동기 실행은 SSH 가 끊겨도 살아남았다(실측).

### 운영 메모
- 기동 env: `INFER_FPS=20 PUSH_FPS=12 PUSH_WORKERS=2` (코드 기본값은 12/6/2 유지 — 재부팅 시 기본값으로 돌아가므로 Phase 3 에서 기동 명령에 박는다).
- cctv-ai ON/OFF 는 기존 런북 그대로(ON=min 1·ingress all / OFF=min 0·internal · max 1 절대 유지).

## 2026-09-01 (이어서) — 1단계 구현 중 발견 2건

### ★ 발견 1 — 캡처 스레드 분리는 GIL 때문에 불가능하다 (py-spy 실측)
계획했던 ③(캡처 스레드 분리)을 구현하자 **추론이 13.2 → 0.5fps 로 폭락**했다. CPU 80% 유휴·스왑 0·캡처는 30fps 정상 — 자원 문제가 아니었다. sudo py-spy 8회 샘플링으로 확정 — `cap.read()` 가 **GIL 을 쥔 채 UDP 프레임을 대기**해(캡처 스레드가 172행 read 에 상주) 추론 스레드가 87% 유휴로 굶었다.
- **결론: cv2 UDP 캡처와 추론은 같은 스레드여야 한다.** 원래 코드가 한 스레드였던 것이 정답이었다.
- 대체 구현 = 한 스레드 + `grab()`(소비만)/`retrieve()`(추론 프레임만 디코드 변환). 추론 13.30fps 복원 확인.
- 진단 도구: Jetson 에 py-spy 설치됨(`~/.local/bin/py-spy` · **sudo -n 가능**). `pgrep -f` 로 python PID 잡을 때 bash 래퍼(-c 명령줄)도 걸리므로 `awk '$2=="python3"'` 필터 필요.

### ★ 발견 2 — INFER_FPS 를 올리면 스트림 소비가 무너진다 (구조적 트레이드오프)
작업(추론+렌더 72ms)이 루프를 점유하면 grab 할 짬이 사라진다.
```
INFER_FPS=12 → 작업 점유 86% → 남는 짬에 30fps 전부 소비 (실측 30.30)
INFER_FPS=20 → 작업 점유 포화 → 소비 = 추론률 13fps ← 유입 30 과의 차이가 FIFO(5MB≈7초분)에 쌓여 화면 지연
```
⚠ `age` 지표는 이 지연을 못 본다(렌더 시각 기준이지 장면 시각이 아니다). **운영값 = INFER_FPS 12 유지.** 20 의 실이득은 +1.3fps 뿐이고 대가가 지연 누적이라 불리하다. 추론률 자체를 올리려면 2단계(렌더 분리)가 아니라 **프로세스 분리**(GIL 밖)가 필요하다 — 발견 1 때문에 스레드로는 안 된다.

### 1단계 종결 (09-01) — 최종 실측과 재개 런북
- **실전송 5.0 → 9.7fps (1.94배)** · 정상 구간 푸시 오류 0(켠 직후 "Remote end closed" 는 콜드스타트 잡음) · 재연결 0 · FIFO 완전 소비(지연 없음). 관제웹 육안 확인 완료(사용자).
- 정리 완료: cctv-ai OFF(`00073-56f`·ingress internal·외부 404) · 엣지 종료 · GoPro 웹캠 STOP.
- **재개 런북** (두 줄).
  ```
  gcloud run services update cctv-ai --region asia-northeast3 --min-instances 1 --max-instances 1 --ingress all
  ssh jetson@yahboom-1 'cd ~/vg_edge_poc && CCTV_BASE=https://cctv-ai-569797426568.asia-northeast3.run.app PPE_ENGINE=/home/jetson/ppe_yolo26s_640_v5_nc.engine PPE_CONF=0.30 INFER_FPS=12 PUSH_FPS=12 PUSH_WORKERS=2 setsid nohup python3 gopro_ppe_edge.py < /dev/null > live_cam03.log 2>&1 &'
  ```
  (GoPro 웹캠은 스크립트가 자동 START · 종료 시 역순 — pkill 은 `[g]opro_ppe_edge` 브래킷 필수)
- 2단계(10→~20fps)는 **프로세스 분리**(GIL 밖)가 전제 — 별도 결정 전 착수하지 않는다.
