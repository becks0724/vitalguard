# 젯슨↔관제웹 직결 계획 (v4 · 확정본)

2026-09-09 · codex 적대적 검증 2라운드 반영 + 사용자 결정 3건 반영 · 근거 = red-1 / red-2 (scratchpad, 미커밋)

> 이 문서는 **계획**이다. 아직 아무것도 구현·배포하지 않았다.
> 착수 전에 §1 의 미결 결정 두 건에 사용자 승인이 필요하다.

## 0. 조건과 판정

사용자가 건 조건 여섯. 적대 검증 결과 **원문 그대로는 셋이 불가**라서 두 건을 재정의해야 한다.

| | 조건 | 원문 판정 | 처리 |
|---|---|---|---|
| ① | 젯슨↔관제웹 직결 | 조건부 | CAM-03 만 별도 주소로 분리하면 가능 |
| ② | 기존 cloudrun 미사용 | **불가** | 관제웹 자신이 Cloud Run · **재정의 필요** |
| ③ | 과금 0 | **불가** | 잔존비가 CCTV 와 무관하게 존재 · **재정의 필요** |
| ④ | 보안 | 조건부 | 공개 표면 분리 + 인증 게이트로 가능 |
| ⑤ | 인가받은 해당 관리자만 | 조건부 | 세션에 현장 개념 신설 필요 |
| ⑥ | 관제웹 로그인해야 영상 | 조건부 | 현재는 UI 게이트뿐 · 서버 강제 필요 |

### ★ 착수 전 확인이 끝난 사실 — 과금 전제가 바뀌었다

```
gcloud run services describe cctv-ai --region=asia-northeast3
→ minScale 없음(기본 0) · ingress=internal · 트래픽 태그 없음
```

**CCTV 클라우드 과금은 이미 0 이다.** 「4vCPU/4GiB 상시 과금을 끈다」는 절감 근거는 성립하지 않는다.
직결의 과금 동기는 **절감이 아니라 회피**다 — 심사 시연을 하려면 `cctv-ai` 를 다시 public +
minScale 1 로 올려야 하는데, 직결이면 올릴 일이 없다.

## 1. 사용자 결정 (2026-09-09 · 확정)

```
결정 1 · 조건 ②  → (a) CAM-03 영상 바이트만 Cloud Run 미경유          [승인]
                    로그인·티켓 발급은 관제웹(Cloud Run)에 그대로 둔다

결정 2 · 조건 ③  → 증분 기준으로 측정한다                              [승인]
                    세는 것 = 티켓 발급 요청 · 로그 인제스트 · Cloud Build 분
                    안 세는 것 = dashboard minScale=1 · Artifact 14.3GB · VPC/NAT
                                (CCTV 와 무관하며 이 계획으로 줄지 않는다)

결정 3 · 공개 경로 → ★ Tailscale 을 쓰지 않는다                        [지시]
                    젯슨의 직접 이더넷으로 공개한다
                    Tailscale 은 사용자가 젯슨을 제어할 때만 쓰는 운영자 전용 경로다
```

### 결정 3 이 바꾼 것 — 실측으로 확인

```
공인 IP      125.244.144.225      ← CGNAT 대역(100.64/10) 아님 · 포트포워딩이 원리상 가능
게이트웨이    192.168.219.1
인터페이스    유선 enP8p1s0 192.168.219.46 (metric 100) · 무선 wlP1p1s0 .191 (metric 600) — 둘 다 UP
:8444        0.0.0.0 리스닝 (pt_main_thread pid 39572)

상향 대역     37.6 MB/s · 43.7 MB/s   (25MB 업로드 ×2회 · Cloudflare 종단)  ≈ 300~350 Mbps
필요량        57 KB × 12 fps = 684 KB/s = 5.47 Mbps / 시청자 1명
여유          약 50명분
```

★ **최대 미해결 위험이었던 「길이 영상을 감당하는가」가 크게 줄었다.** Tailscale Funnel 의
문서화되지 않은 대역 제한이 빠지고, 회선 상향이 필요량의 약 50배로 실측됐다.

⚠ 다만 이 값은 **짧은 버스트 측정**이고 종단이 Cloudflare 다. 실제 시청자 경로와 30분 지속
거동은 다르다. 병목은 이제 회선이 아니라 **젯슨의 단일 파이썬 루프(현재 9.6/s)** 일 가능성이 크다.

### 결정 3 이 새로 만든 위험 — 노출면이 커졌다

```
① 공인 IP:포트 직접 노출   인터넷 스캐너가 몇 시간 안에 인덱싱한다.
                          Tailscale Funnel 보다 노출면이 크다 → 게이트 인증이 더 중요해진다
② 공유기 UPnP / DMZ        켜져 있으면 의도하지 않은 포트가 열린다.
                          ★ 포워딩 전에 반드시 확인하고 끈다. DMZ 모드는 절대 금지
③ 유선·무선 이중 UP        포워딩 대상 IP 가 흔들릴 수 있다 → 유선 .46 을 DHCP 예약으로 고정
④ 공인 IP 가 동적이면      바뀌는 순간 화면이 죽는다 → DDNS 필요
⑤ 인증서                   공인 IP 만으로는 표준 경로로 공인 인증서를 못 받는다.
                          ★ 도메인이 필요하다 (예: cam.<팀 도메인> → DDNS → 젯슨 → Let's Encrypt)
                          팀 도메인 보유 여부 = 미확인
```

★ **red-1 의 CRITICAL 이 더 심각해졌다.** 터널 대신 포트포워딩이면 **무엇을 포워딩하는지가 곧
공개 표면**이다. 기존 `:8444` 를 포워딩하면 그 순간 비로그인자가 영상·`/config`·`/reset` 을 얻는다.
**포워딩 대상은 신규 게이트 포트 하나뿐이다.**

## 2. 설계

### 2-1. 공개 표면을 기존 `:8444` 와 분리한다

```
기존 :8444    /  /stream  /snapshot  /health  /config  /mark  /reset
              현재 0.0.0.0 바인딩 · 인증 전무 → 공개 터널이 절대 여기를 향하지 않는다
              ★ loopback 으로 내리기 전에 §3 0-B 를 먼저 끝낸다 (아래 경고)

신규 게이트    별도 프로세스 · loopback 포트 · 아래 표 밖은 전부 404 · 상태 변경 GET 없음
              터널 upstream = 이 게이트 하나
```

**경로 계약 (이 표가 유일한 정본)**

| 메서드 | 경로 | 필요 티켓 | 비고 |
|---|---|---|---|
| GET | `/cctv/stream3` | `scope=read` · 연결 단위 | 연결 시 1회 소비 + 매 프레임 `exp` 검사 |
| GET | `/cctv/stats3` | `scope=read` · 요청 단위 | |
| GET | `/cctv/connection3` | `scope=read` | 조회만 |
| POST | `/cctv/connection3` | `scope=control` | 토글 · read 티켓으로는 403 |

그 외 전부 404. `/config` `/mark` `/reset` `/snapshot` 은 **공개 게이트에 존재하지 않는다.**

### 2-2. 티켓 — v2 에서 셋을 고쳤다

```
① URL 이 아니라 헤더로 (red-2)
   <img src="...?tk="> 를 버리고 fetch + Authorization 헤더로 MJPEG 를 읽어
   multipart 경계를 파싱해 canvas/ImageBitmap 으로 그린다.
   이유 = URL 티켓은 접근 로그·브라우저 devtools·복사된 링크로 새는 bearer 자격이고,
          탈취자가 먼저 제시하면 통과한다. 헤더로 옮기면 그 유출면이 사라진다.
   대가 = <img> 의 자동 재연결을 잃는다 → abort/재연결/backoff 를 직접 구현해야 한다.

② 공유 HMAC 이 아니라 Ed25519 비대칭 (red-2)
   젯슨에는 검증용 **공개키만** 둔다. 서명키는 Cloud Run 시크릿.
   이유 = 공유키면 젯슨을 얻은 사람이 scope=control 티켓을 임의 서명할 수 있다.
   회전 = 게이트가 old+new 공개키를 먼저 수용 → issuer 전환 → max(exp+skew)+여유 대기 → old 제거

③ 「요청마다 jti 1회 소비」 폐기 (red-2)
   stream·stats·connection 이 같은 티켓을 쓰면 한쪽이 소비하는 순간 나머지가 거절된다.
   수정 = 발급 응답에 **엔드포인트별 티켓을 묶어서** 준다.
          stream 은 연결 단위(1회 소비 + 매 프레임 exp), stats/connection 은 짧은 요청용.
          클라이언트는 single-flight 재발급 + jitter + 401 처리.
          발급 API 와 게이트에 사용자·카메라별 rate limit 과 동시 발급 상한.
```

**클레임** `aud=cameraId · siteId · scope(read|control) · sub(세션 subject) · exp(짧게) · nbf · jti · kid`
**시계** 허용 오차 ±30초. ⚠ 이 오차가 `exp` 에도 적용되면 실효 수명이 명목보다 길어진다 — hard cutoff 를 별도 시험한다.

### 2-3. 현장 단위 인가 (조건 ⑤)

```
신설    site · camera · user_site_role 표
        camera 는 지금 프런트 상수 배열이라 서버가 모른다 → 서버로 옮긴다
권한    can_view 와 can_control 을 분리된 서버 술어로 둔다
판정    발급 시 (session.sub, 요청 camera) 로 조회 · 없으면 403
        ★ 클라이언트가 보낸 cameraId/siteId 를 신뢰하지 않는다
        ★ CctvQuadView 의 canManage 는 UI 힌트일 뿐 권한 근거가 아니다
감사    발급·거절을 사용자·카메라·시각과 함께 기록
```

### 2-4. CAM-01·02 는 유지한다

셋 다 같은 `AI_CCTV_API` 를 쓰고 서버 낙상 폴러도 그 주소로 `/cctv/stats2` 를 1.5초마다 친다.
CAM-03 만 바꾸고 `cctv-ai` 를 끄면 둘과 폴러가 깨진다. `cctv-ai` 는 이미 internal/min0 이라
과금이 0 이므로 **끄지 않는다.** 이 계획에서 `cctv-ai` 중지 단계를 삭제했다.

### 2-5. 공개 경로 — 이더넷 직접 (결정 3)

```
제외    Tailscale Funnel      사용자 지시 · Tailscale 은 운영자 전용
제외    Cloudflare 무료 터널   연속 영상 운반은 TOS 상 허용 경로가 아니다
채택    공유기 포트포워딩 → 젯슨 유선 .46 의 신규 게이트 포트

포워딩 규칙
  대상    게이트 포트 하나만. `:8444` 는 절대 포워딩하지 않는다
  사전    UPnP·DMZ 를 끈다 · 유선 .46 을 DHCP 예약으로 고정
  주소    도메인 + DDNS (동적 IP 대비) → Let's Encrypt 인증서
  방어    게이트에 deny-by-default · 요청률·동시연결 상한 · 실패 반복 차단

운영 경로 (공개와 분리)
  `:8444` 는 LAN + Tailscale 에서만 닿는다 — 지금 사용자가 쓰는 방식 그대로다.
  ★ 이것이 red-2 가 지적한 0-B 문제(`/mark` 낙상 라벨 단절)를 그대로 해소한다.
     `:8444` 를 loopback 으로 내릴 필요가 없다. 포워딩만 안 하면 된다.
```

### 2-6. 기존 프록시 차단

`app/ai-cctv/[...path]/route.ts` 는 인증 없이 `stream|stats|connection` 을 중계한다.
`AI_CCTV_ORIGIN` 이 젯슨/게이트를 향하면 **로그인 없이** 관제웹 오리진으로 우회된다.
제거하거나 서버 ACL 을 넣고, 직결 경로와 프록시 경로를 **둘 다** 외부 무인증 curl 로 회귀 시험한다.

## 3. 순서

각 단계는 「됐다는 표시」로만 닫는다.

```
0-A  결정        §1 의 두 건 승인                                    [사용자]
0-B  운영 경로    결정 3 으로 해소됨 — :8444 는 LAN + Tailscale 에 그대로 둔다
                 /mark(낙상 라벨)·뷰어·진단기가 끊기지 않는다
                 확인 = 공유기 UPnP·DMZ 가 꺼져 있고, 포워딩 목록에 8444 가 없다

1    권한 모델    site/camera/user_site_role · 발급 API(세션 Bearer 검증 · ACL 판정 · scope 분리)
                 확인 = 로그아웃 401 · 타 현장 403 · 타 카메라 403 · read 로 control 요청 403

2    공개 게이트  별도 프로세스 · 전용 포트 · §2-1 표 밖 404 · 요청마다 티켓 검증
                 확인 = 무티켓 401 · /config /reset /snapshot /stream 404 · 게이트 재시작 후 replay 거절

3    만료 강제    MJPEG generator 안에서 exp 검사 · 만료 시 끊김을 HTTP 시험으로 확인
                 확인 = 만료 후 프레임이 더 오지 않는다 (hard cutoff)

4    공개 준비    공유기 = UPnP·DMZ 끄기 · 유선 .46 DHCP 예약 · 게이트 포트 하나만 포워딩
                 주소 = 도메인 + DDNS → Let's Encrypt 인증서
                 ★ 포워딩 직후 첫 외부 요청부터 무티켓이 거절되어야 한다
                 확인 = 외부 무인증 curl 로 게이트 401 · :8444 는 연결 자체가 안 됨
                        그 뒤 1·2·4 시청자 × 30분 × 12fps 지속 시험 (회선은 여유 확인됨 ·
                        이제 보는 것은 젯슨 CPU 와 프레임 드랍이다)

5    관제웹 배포  CAM-03 별도 주소 + fetch 렌더러 + 티켓 호출 (빌드타임 변경)
                 이전 revision digest 를 롤백 기준으로 기록 · 아직 승격하지 않는다

6    승격        검증된 엔드포인트를 실제 CAM-03 에 붙인다 (새 공개가 아니다)
                 확인 = 브라우저 정상 · 외부 무인증 curl 거절 · 프록시 경로도 거절

7    롤백 실측    web  = 이전 revision 트래픽 + 터널 disable
                 edge = 포워딩 해제(공유기 한 줄) — 바인딩을 안 건드리므로 재기동 불필요
                 확인 = 둘을 실제로 재 본다. 재기 전에는 시간을 주장하지 않는다

8    12fps       푸시 워커가 빠진 뒤 재측정 → 그다음 카메라 증설
```

## 4. 미해결·미확인

```
해소됨      「길이 12fps × N명을 감당하는가」
            → 상향 300~350 Mbps 실측 · 필요량 5.47 Mbps/명 · 약 50명분 여유
            남은 것은 회선이 아니라 젯슨 CPU 와 30분 지속 거동

미확인      팀 도메인 보유 여부      ★ 없으면 인증서를 못 받아 화면이 안 뜬다. 가장 먼저 확인할 것
            공인 IP 의 고정/동적 여부 (동적이면 DDNS 필수)
            공유기 관리 접근 권한 · UPnP/DMZ 현재 설정 · 이중 NAT 여부
            젯슨 실제 service unit · 부팅 시 자동 기동 여부
            live dashboard 의 AI_CCTV_ORIGIN 실제 값과 롤백 호환 revision
            실제 청구액(Cloud Build 무료 분 잔량 · Logging 인제스트)
```

## 5. 폐기된 주장 (다시 인용하지 말 것)

```
✗ "cctv-ai 4코어를 끄면 수십만 원/월이 절감된다"   → 이미 min0/internal · 과금 0
✗ "자물쇠를 먼저 달고 그다음 터널"                 → 젯슨은 인증서를 혼자 못 받는다 · 한 번에 하는 일
✗ "주소 한 줄만 되돌리면 10분"                     → NEXT_PUBLIC_* 는 빌드타임 주입 · 재빌드·재배포다
✗ "요청마다 jti 를 1회 소비한다"                   → 세 read 흐름과 정의상 충돌
✗ "공유 HMAC 키로 서명·검증"                       → 젯슨이 control 티켓을 위조할 수 있다
✗ "Tailscale Funnel 로 공개한다"                   → 사용자 지시 · Tailscale 은 운영자 전용
✗ "Funnel 대역이 최대 위험이다"                     → 이더넷 직결로 바뀌어 소멸 · 상향 300+ Mbps 실측
```
