# 워치 자동 재개 — 결정과 근거

부모 트랙 = [vital-absence-triage](../vital-absence-triage/checklist.md) §4-6·§4-7.
발단 = 2026-08-20 사용자 제보 "갑자기 워치 수집이 끊김".

## R-01 · 자동 재개는 한 번도 발동한 적이 없다 (실측)

30시간 9세션 전수에서 `session_auto_resumed` 가 **전부 0** 이다.

```
08-19 11:09:33  2863건   08-19 15:31:46  184건   08-19 16:15:53  669건
08-19 17:34:01   355건   08-19 18:40:45   97건   08-19 23:37:34   24건
08-20 07:48:46  1584건   08-20 10:13:54  352건   08-20 10:44:41  진행 중
```

코드가 없어서가 아니다 — `session_started_at` 이 도착하고 있고 그 계측(`f158861`·08-19)은
자동 재개(`f67442f`·08-18)보다 **나중**이다. 설치된 빌드에 자동 재개 코드는 확실히 있다.

## R-02 · ★ 그런데 `0` 은 두 가지를 뜻한다 — 지금 데이터로 못 가른다

`sessionAutoResumed` 는 `beginWorkout(auto:)` 한 곳에서만 정해진다.
수동 `start()` → `auto: false` · 자동 `autoResume()` → `auto: true`.
**계측 배선은 옳다.** 하지만 `0` 은 "자동 재개가 시도조차 안 됐다" 와 "사람이 [시작]을 눌렀다"
를 같은 값으로 만든다. 오늘 두 번의 재시작(10:13·10:44)도 사람이 누른 것으로 보이지만
**확인된 사실이 아니다.**

⟹ *결론을 내리기 전에 계측이 두 경우를 가르는지부터 본다.* 오늘 이 세션에서 같은 형태
(도구가 못 찾은 것을 대상이 없는 것으로 읽기)를 세 번 밟았다.

## R-03 · 가설 4개와 각자의 지문

| | 가설 | 코드 근거 |
|---|---|---|
| **H0** | 사람이 [중지]를 눌렀다 | `stop()` 이 `stopRequestedByUser = true` → 자동 재개 안 하는 것이 **정상** |
| **H1** | 델리게이트는 왔는데 `autoResume` 에 도달 못 했다 | `.ended` 처리가 `endCollection { finishWorkout { … } }` **이중 중첩 클로저 안**이다. `builder` 가 nil 이거나 콜백이 안 오면 그 안의 `autoResume` 은 영영 실행되지 않는다. 폴백이 없다 |
| **H2** | 델리게이트 자체가 안 왔다 | 세션 종료 시점에 앱이 이미 동결이면 콜백이 배달되지 않는다(§4-6 — pid 는 29시간 유지된 채 공백 넷 통과) |
| **H3** | 3연속 실패로 포기 상태 | `autoResumeBurst > 3` 이면 `"자동 재개 실패 — [시작]"` 로 멈춘다. 단 `start()` 가 리셋하므로 사람이 누른 뒤엔 풀린다 |

**`didFailWithError` 경로는 중첩이 없다**(`autoResume` 을 바로 부른다). 그쪽으로 끝났다면
발동했을 것이다 ⟹ 세션은 `.ended` 상태 변화로 끝나고 있거나(H1), 콜백이 아예 안 온다(H2).

## R-04 · 왜 로그로는 못 보나 — 계측을 만들어야 하는 이유

`autoResume` 은 `log.notice("자동 재개 N회차")` 를 남긴다. 그런데 **워치 os_log 는 회수 경로가
없다**(08-18 확정 — `log collect` 는 USB(lockdown) 전제인데 워치엔 USB 가 없고, watchOS
`sysdiagnose` 도 `DiagnoseError 0`. 폰 경유로 회수되는 것은 크래시·jetsam 리포트뿐이다).

⟹ **판정에 필요한 사실이 전부 회수 불가능한 곳에 있다.** DB 로 끌어내는 수밖에 없다.

## R-05 · 채택 방식 — 디스크 빵부스러기

메모리 상태는 프로세스가 죽으면 사라지고, 세션이 끝난 뒤엔 보낼 배치도 없다.
**UserDefaults 에 즉시 적고, 다음 세션 첫 배치에 실어 보낸다.**

기록 시점이 핵심이다 — `.ended` 를 **본 즉시**, 중첩 클로저 **바깥에서** 적는다.
클로저 안에서 적으면 H1 을 관측할 수 없다(그 자리가 바로 의심 대상이다).

| 필드 | 적는 시점 |
|---|---|
| `endSeenAt` | `didChangeTo .ended` 진입 즉시 |
| `endByUser` | 같은 시점의 `stopRequestedByUser` |
| `resumeTriedAt` | `autoResume()` 진입 즉시 |
| `resumeGaveUp` | 3연속 초과로 포기할 때 |

**네 가설이 서로 배타적인 지문을 갖는다.**

```
H0  endSeen 있음 · byUser=1 · resumeTried 없음   → 정상(사람이 중지)
H1  endSeen 있음 · byUser=0 · resumeTried 없음   → 중첩 클로저에서 끊김
H2  endSeen 없음                                 → 델리게이트 미도달(동결)
H3  resumeTried 있음 · gaveUp=1                  → 포기 상태
```

⚠ **2026-08-21 정정 — H2 는 배타적이지 않다.** `endSeen 없음`은 **동결(H2a)** ·
**프로세스 소멸(H2b)** · **객체만 재생성(H2c)** 셋 다에서 난다. 08-21 18:21 건은 기기
JetsamEvent 로 pid 연속(13616)이 확인돼 **H2b 가 반증되고 H2c 로 좁혀졌다**. 지문이 같은데 처방이 다르다(R-06 ⓐ 는 H2b 에 무효).
가르는 것은 DB 가 아니라 워치 화면의 전송 카운터다 — 상세·계측 제안은
`docs/watch-auto-resume/checklist.md` 의 "2026-08-21 18:21 사건".

## R-06 · 처방은 계측 뒤에 정한다 — 다만 H1·H2 는 처방이 같다

지금 고치면 무엇이 고쳐졌는지 모른다(발동 자체가 관측된 적 없어 대조군이 없다).
계측 먼저. 다만 결과가 H1 이든 H2 든 처방은 겹친다.

- **재개를 중첩 콜백 밖으로** — `.ended` 를 본 즉시 예약하고, 빌더 정리는 독립으로 진행.
- **깨어날 때 자가 복구** — `!isRunning && !stopRequestedByUser` 면 활성화 시 재개 시도.
  동결 중에는 아무것도 못 하지만, **손목을 들어 화면이 켜지는 순간 사람 없이 살아난다.**
  지금은 사람이 [시작]을 눌러야만 돌아온다.

⚠ H0 로 판명되면 **고칠 것이 없다.** 그때는 "왜 사람이 중지를 누르게 되는가"가 질문이 된다.

## R-07 · 계약 위험 — 필드 추가는 트리오가 함께 가야 한다

`batteryPct`·`motionVarMg` 와 같은 계약이다. **스키마·DB 컬럼·insert 매핑 셋 중 하나만
빠져도 값이 조용히 사라진다**(감사 BND-CONTRACT-01 · 이 레포가 세 번 당했다).
추가로 **스트립 허용목록에 넣어야 한다** — 안 넣으면 진단 필드 하나가 생체 샘플을 통째로
거부시킨다(mv 때 겪음). `ExportRow`(CSV 내보내기)에는 **일부러 넣지 않는다** — 진단 필드이지
사용자에게 주는 값이 아니다.

## R-08 · 설치 시점 — 서버 먼저, 워치는 설치 기회에 얹는다

워치 설치는 세션을 끊고 **자동 재개되지 않는다**(사람이 [시작]). 오늘만 두 번 설치했다.
⟹ 08-19 세션 계측 때와 같은 패턴 — **서버분(스키마·컬럼·매핑)은 먼저 배포**해 두고
워치·폰은 다음 설치 기회(재서명 창 08-24~25)에 얹는다. 그러면 추가 비용이 0 이다.
급하면 그 전에 설치해도 되지만 그때마다 사람이 [시작]을 눌러야 한다.
