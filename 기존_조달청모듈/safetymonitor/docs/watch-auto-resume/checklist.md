## 워치 재설치 — 무엇이 방아쇠이고 무엇을 리셋하나 (2026-08-21 실측)

### ★ 방아쇠는 "폰만/워치도" 가 아니라 **워치 바이너리가 바뀌었는가** 다

run-log 의 *"폰 단독 설치라 워치 세션이 안 끊겼다"* 는 **정정한다.** 폰만이라서가 아니라
그 설치의 **워치 슬라이스가 같아서** 안 끊긴 것이다. 워치 앱은 `Runner.app/Watch/` 안에
동봉돼 나가므로 폰만 설치해도 **워치 바이너리가 다르면 밀려 들어가고 세션이 끊긴다.**

08-20 의 두 설치가 정반대 결과를 낸 것이 그 증거다.

```
git log 406bcaf..b218f32 -- ios/VitalWatch/   →  0커밋 · 0diff
[통제군] 같은 구간 ios/Runner/                →  LocationProvider.swift +81/-2

15:42 설치  HEAD ≥ 406bcaf(15:13, 워치 변경)  → 워치 슬라이스 다름 → 세션 끊김
            세션 15:42:51 종료 · 15:43:19 재시작 · 종료 지문 결손      ← DB 실측
17:24 설치  HEAD = b218f32(워치 무변경)       → 밀 것이 없음 → 세션 유지
            15:43:19 세션이 17:24 을 가로질러 18:39:04 까지            ← DB 실측
```

⟹ **워치 코드를 건드린 채 폰을 설치하면 세션이 끊긴다.** "폰만이니 안전하다" 로 읽지 말 것.

### 그 경계가 `session_end_by_user` 의 의미를 가른다

`endedByUser` 는 `406bcaf`(08-20 15:13) 에서 **30초 유예 조건**이 붙었다. 그전에는 플래그가
서 있기만 하면 참이었고, `WatchStreamer.swift:105~111` 에 **사용자가 누른 적 없는데 참이었던
실측**(08-20 14:36:09)이 적혀 있다.

```
14:18:37 · 14:36:09 · 15:19:15   유예 이전 빌드 → by_user=1 을 "눌렀다" 로 못 읽는다
18:39:02                          유예 이후 빌드 → by_user=1 = "30초 안에 눌렸다"
```

⚠ `by_user = 0` 은 **전 기간 0건**이다. 유예 이후 종료 표본이 1건뿐이고 그마저 진짜 사용자
종료라 **유예가 아직 한 번도 일하지 않았다.** C-1 판정 규칙은 `docs/gps-phone-collection/checklist.md`
에 있다(중복해 적지 않는다).

### 재서명은 **항상** 재설치다 — 그래서 시점이 값이다

서명이 바뀌면 바이너리가 바뀐다. 즉 재서명은 위 방아쇠를 무조건 당긴다.

```
TimeToLive  7일        ← 무료 개인 팀 프로파일. **발급일 기준**이지 만료일 기준이 아니다
발급        08-20 10:09 KST   →  만료 08-27 10:09 KST
```

⟹ **일찍 재서명할수록 안 쓴 날을 반납한다.** 08-21 에 하면 새 만료가 08-28(+1일),
08-26 에 하면 09-02(+7일)이고 **비용은 양쪽 다 세션 리셋 1회로 같다.**

- [ ] **2026-08-26 재서명 + 설치** ← 사용자 결정(08-21). 만료 08-27 10:09 전 마지막 안전 창
      ⚠ 만료 시각이 **목요일 오전 10:09** 라 방치하면 근무 시간 한복판에 수집이 멎는다
      ⚠ 이 설치가 C-1 의 "비-사용자 종료 대기" 표본을 리셋한다 — 그 전에 한 번 나 주는 것이 최선
      ⚠ `flutter build ios --release` 는 **캐시 적중이면 아무것도 안 하고 exit 0** 을 낸다(L-97 ④).
        판정은 `embedded.mobileprovision` 의 `ExpirationDate` 가 **밀렸는지**로 한다.
        08-21 에 이 함정을 실제로 밟았다 — "✓ Built 18.3MB" 인데 바이너리 mtime 은 전날이었다
- [ ] 워치 코드를 얹을 것이 있으면 **이 설치에 함께** — 별도로 하면 세션 리셋을 한 번 더 낸다
      (08-21 검토 결과 얹을 것 **없음** — 계단 감지 `NSMotionUsageDescription` 은 불필요하다.
       워치의 CoreMotion 사용은 `CMMotionManager.deviceMotion` 뿐이고(`WatchStreamer.swift:57`·`556`)
       그건 이 권한 문구를 요구하지 않는다. 층수는 HealthKit `flightsClimbed` 에서 읽으므로
       이미 있는 Health 권한으로 충분하다.
       ⚠ grep 함정 — `CMMotionActivity` 로 찾으면 **1건**이 나오는데 `:561` 의 *"왜 안 쓰는가"*
         설명 주석이다. 호출은 0이다. 세기 전에 그 줄을 열어 볼 것(L-83·L-95②).
       ⟹ 이 문구가 필요해지는 것은 `CMAltimeter`·`CMPedometer` 를 **실제로 부를 때**이고,
         그때는 워치 재설치가 또 필요하다. 계단 감지를 할 계획이 서면 그 전 재서명에 얹는다)

## 열린 위험

- ⚠ 워치 설치는 세션을 끊고 자동 재개되지 않는다 — **매 설치마다 사람이 [시작]** 을 눌러야 한다
- ⚠ 이 트랙은 **원인 규명이지 피해 제거가 아니다.** 규명 전까지 세션이 끊기면 여전히 사람이
      알아채야 한다. 알아채는 수단 = 설정 화면 `워치 수신 끊김 — N분 전`(08-20 추가).
      그것도 사람이 열어 봐야 보인다 — **푸시 알림은 아직 없다**

### `대기` + `전송0` 이 동시에 서는 경로는 하나뿐이다

```
autoResume 포기   → "자동 재개 실패 — [시작]"        ✗
autoResume 성공   → "수집 중"                        ✗
재개 중 실패      → "수집 시작 실패…"·"세션 생성 실패…" ✗
사용자 [중지]     → "대기" ✓  그러나 batchesSent 보존(>0) ✗
새 프로세스       → "대기"(:25 초기값) ✓ + 전송0(:516 증가만, 리셋 코드 없음) ✓
```
⟹ **새 `WatchStreamer` 인스턴스다.** (`noteSent()` 가 유일한 증가처 · 리셋 코드 없음 · `deinit` 없음)
