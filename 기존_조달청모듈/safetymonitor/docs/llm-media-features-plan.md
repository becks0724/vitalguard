## 기능 #2 — 온프레미스 LLM 종합 생체 모니터링 + 보고서 (우선)

### 개념
PostgreSQL `vital_samples`(1,500+건)·`alerts` 등 작업자 생체 DB를 LLM이 인식 → **기간별 분석 → 한국어 보고서**. "데이터는 DB에 있는데 관리자가 활용할 수단이 없다"는 갭 해소.

### ★ 핵심 결정 = 온프레미스 로컬 LLM (외부 유출 0)
- 사용자 최우선 제약 = **"작업자 보고서는 어떤 경유로도 외부 유출 금지".**
- → 외부 LLM API(Claude/Anthropic 등)는 **배제**(비식별해도 데이터가 외부 서버 경유 = 위반). 오픈웨이트 로컬 모델(Llama·Qwen·Gemma 계열) 사용.
- → **Cloud Run 경유도 회피** — 관제웹이 Cloud Run(구글 외부 인프라)이므로, 민감 분석·보고서는 **온프레미스로 분리**(로컬 서버 + 로컬 LLM + 로컬망 DB 직접 읽기). 실시간 모니터링(기존 PII redaction)만 Cloud Run 유지.

### 아키텍처
```
[캠퍼스 Postgres] ──로컬망──> [온프레미스 분석 모듈]
                                ① 비식별 피처 추출 (기존 analyzers 재사용)
                                ② 로컬 LLM (Ollama/vLLM) 해석
                                ③ 보고서 = 사내망 관리자만 (export 차단·감사로그)
```
- **① 비식별 피처 추출(핵심 엔지니어링)** — 기존 `computeStressIndex`·severity·임계 재사용해 작업자별·기간별 파생 지표 산출(심박 평균/임계 초과 횟수, SpO₂ 저하 빈도, 추정체온 초과, 스트레스 추세, 낙상·SOS 건수, 활동량, 연결 품질). **이름·사원번호·보호자·GPS 제거**, 작업자 = 익명 코드(작업자 #1).
- **② 로컬 LLM** — 비식별 지표만 입력 → 한국어 해석. **원시 PII는 LLM에 절대 미투입** = "보고서에 개인정보 비공개" 충족.
- **③ 보고서** — "작업 적합성 참고 지표 + 권고"(의학 진단 아님, 최종 투입/보류 결정은 사람). 사내망 로그인 게이트 + 다운로드/공유 차단 + 감사로그.

### 가드레일 (안전 도메인)
- **임계 경로 금지** — 위험 감지·경보는 규칙·임계가 단독 권위. LLM은 조회·요약·해설만.
- **투입/보류 = human-in-the-loop** — LLM은 플래그·근거만 제시, 자동 결정 금지. fitness-for-duty는 의료·법적 민감 → 민감정보 동의·법적 근거 필요.
- **의료 진단 금지** — 기존 스트레스 칩과 동일 "참고용" 표기.

### 하드웨어 (사무용 PC 현실)
- **사무용 PC 본체로 LLM 직접 구동은 비현실적**(외장 GPU 없음·8~16GB RAM). → **추론 전용 1대(본사 GPU 서버) + 현장 사무 PC는 브라우저 클라이언트** 구조가 정답. DB가 중앙이라 분석도 중앙. 사내망/VPN = 내부 = 외부 유출 금지 충족.

| 용도 | 최소 사양 |
|---|---|
| **관제웹/보고서 열람(사무 PC)** | 최근 7년 내 PC·RAM 8GB·내장그래픽·Chrome/Edge — 거의 모두 충족 |
| **로컬 LLM 추론(최소·CPU)** | 8코어 CPU·RAM 16GB(권장 32)·GPU 없음 → 3~7B Q4, 보고서 1건 30초~1분(배치·온디맨드) |
| **로컬 LLM(권장·GPU)** | RTX 4060 Ti 16GB / 4070+·RAM 32GB → 7~14B Q4, 대화형 쾌적 |
| **고품질(32B)** | VRAM 24GB(RTX 4090 등)·RAM 32~64GB |
| **Mac 대안(발표용)** | M시리즈 16/32/64GB → 7~8B / 14B / 32B (Metal) |
- 메모리 가늠(Q4): 3B≈3GB·7~8B≈5~6GB·14B≈9~10GB·32B≈20GB.
- **발표는 발표 Mac(통합메모리 16~32GB)으로 7~14B 시연** — 별도 하드웨어 구매 불필요.

## 기능 #1 — 앱 OCR + 캘린더 미디어 메모리 (클라우드 브리지)

### 개념
iOS 앱 OCR/촬영 자료(사진대지·현장 사진/영상)를 **클라우드 경유로 관제웹 캘린더에 촬영일시 기준 자동 표기**.

### 현재 상태
- 🆕 **(2026-06-26) 캘린더 헤더 아이콘 = 클라우드+캘린더 결합으로 교체** — 미디어 캘린더 방향 신호([DemoDashboard.tsx:2186](../apps/dashboard-web/app/components/DemoDashboard.tsx#L2186), **미커밋**) + 다크모드 팝업 헤더 가독성 수정([:1230](../apps/dashboard-web/app/components/DemoDashboard.tsx#L1230) `dark:bg-*` 누락 보완). **기능(OCR 업로드·미디어 표시·설명 기입)은 아래대로 미착수** — 아이콘은 방향 신호일 뿐.
- ✅ **iOS 앱 OCR/카메라/미디어** — 독립 개발 완료(GitHub 미반영), **현재 사진첩 저장만 가능**.
- ✅ **관제웹 캘린더 UI** — `CalendarEvent`(날짜·제목·타입·라벨·시간)·추가/수정/삭제·주간 뷰([DemoDashboard.tsx:502](../apps/dashboard-web/app/components/DemoDashboard.tsx#L502), 김○○ 작업).
- ⚠️ **사진대지 업로드 라우트 존재하나 로컬디스크** — [weekly-report/photos](../apps/dashboard-web/app/api/weekly-report/photos/route.ts) + [photo-store.ts](../apps/dashboard-web/app/lib/photo-store.ts)가 `.runtime/photos/`에 저장 → **Cloud Run에선 재시작마다 휘발**. 영속 저장은 외부 클라우드 필요.
- ❌ 클라우드 저장(GCS/R2/Naver) · `calendar_media` DB 테이블 · 캘린더 미디어 자동배치·표시.

### "클라우드 브리지" = 끊긴 두 끝(앱 OCR ↔ 캘린더)을 잇는 배관
```
[앱: OCR·촬영] ─①업로드(사진/영상+메타: 촬영일시·OCR텍스트·작업자·현장)→
[GCS/R2 저장]  ─②인덱싱→ [DB: calendar_media] ─③조회→ [관제웹 캘린더 ④촬영일시로 자동 배치]
```

### 설계 결정
- **날짜 = EXIF 촬영시각, 내용 태그 = OCR.** (날짜 자동 배치는 EXIF가 정확, OCR은 사진대지 라벨 판독용 — 분리.)
- 미디어는 로컬디스크 불가(Cloud Run 휘발) → 외부 클라우드. **사진은 외부 클라우드 OK**(생체 #2와 정책 분리 = 민감도 차이, 내부 일관).
- 업로드 라우트를 **S3 호환 인터페이스**로 작성 → 저장 백엔드 교체가 설정 수준(GCS↔R2↔Naver).

### 클라우드 저장 후보 (리서치 2026-06-24)
| 서비스 | 저장 $/GB·월 | 아웃바운드 | 한국 저장 | 통합 | 적합 시점 |
|---|---|---|---|---|---|
| **GCS**(서울) | ~$0.02+ | $0.08~0.12/GB | 서울 리전 ✓ | native(이미 GCP) | **발표/MVP** |
| **Cloudflare R2** | $0.015 | **$0 무료** | 위치지정 제한 | S3 호환 | 상용화 미디어 |
| **네이버클라우드** | 저렴(추정) | 타사比 ~45%↓ | **국내 DC·공공 인증 ✓** | S3 호환 | 공공/국내 사업자 요구 |
| Backblaze B2 | $0.006 | 3배 무료+CF 무료 | 미국/EU | S3 호환 | 최저가·레지던시 무관 |

**비용 비교(1개소·저장 1TB, $1≈₩1,400 근사 / R2=확정·네이버=추정)**
| 월 아웃바운드 | R2 | 네이버(추정) |
|---|---|---|
| 0(저장만) | ~₩21,000 고정 | ~₩30,700 |
| 1TB | ~₩21,000 고정 | ~₩133,000 |
| 3TB | ~₩21,000 고정 | ~₩338,000 |
- **R2는 아웃바운드 0원이라 청구 고정**, 네이버는 열람량에 비례 증가. 미디어 반복 열람일수록 R2 유리(1TB 열람 시 ~6배, 3TB ~16배).
- **네이버 내부 전송(NCP 서버·CDN+ 경유) 무료** — 관제웹을 NCP 서버에 두거나 CDN 앞단이면 아웃바운드 크게 절감(비용 최대 레버).
- 정확 단가는 네이버 가격이 JS 렌더라 자동 추출 실패 → [요금계산기](https://www.ncloud.com/charge/calc/ko) 확정 필요(추정치).

### 권장
발표/MVP = **GCS 서울**(빠름·한국 저장·새 벤더 0) → 상용화 미디어 증가 = **R2**(zero egress) → 공공/국내 사업자 요구 = **네이버**. S3 호환이라 교체는 설정 수준.

## 관련 진단 — 현장 위치 날씨 미작동 (기존 라이브 이슈, 2026-06-24)
- **증상** — 생체값은 정상 표시되는데 GPS만 안 떠 [WeatherStrip](../apps/dashboard-web/app/components/WeatherStrip.tsx) "현장 위치 대기 중 — 0명".
- **원인 구조** — 날씨 패널은 등록 작업자 GPS 평균([DemoDashboard `fieldCoords`](../apps/dashboard-web/app/components/DemoDashboard.tsx#L1065))만으로 동작. GPS는 **3중 게이트**(① env `MOCK_VITAL_EXPOSE_PII=true` ② 유효 로그인 세션 토큰 ③ 폰이 실 GPS 전송) 모두 통과해야 노출. ①은 **라이브 env 조회로 true 확인**.
- **유력 원인** — ② 세션 토큰(세션은 인메모리·8h TTL, **rev 00007 재배포로 전부 소멸**) 또는 ③ 폰 위치 권한. 원격에선 PII 없이 둘 구분 불가.
- **조치** — 1순위 **로그아웃→재로그인**(새로고침 X, 옛 토큰 유지됨) / 2순위 아이폰 위치 "항상 허용"+GPS 획득. 재로그인 후 뜨면 ②, 안 뜨면 ③.
- **구조적** — 세션 인메모리라 Cloud Run 재배포·인스턴스 재활용마다 재발 → 근본 해결은 세션 DB/서명 토큰(스테이트리스) 전환(발표 후).
