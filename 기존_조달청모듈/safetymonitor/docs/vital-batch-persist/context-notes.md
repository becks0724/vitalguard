# 생체 배치 저장 일괄화 — 결정과 근거

2026-08-28. 장우진(애플워치) 수신이 20분간 끊긴 사고의 수리.

## 무엇이 고장났나

폰이 20초마다 265KB(500건)를 보내는데 **매번 실패**하고 있었다. 관제웹의 "연결끊김"은 정확한 보고였다.

```
① 09:26:44  DB 연결 거부(ECONNREFUSED) 다발 → 서버 503
② 폰이 큐를 안 비움(설계대로) → 큐가 배치 상한 500건에 도달
③ 서버가 건당 33ms 로 순차 INSERT → 500건 처리에 16.1~16.8초
④ 폰 타임아웃은 15초 (VitalPipeline.swift:310) → 매번 먼저 끊음
⑤ 폰은 실패로 판단 → pending.removeFirst 안 함 → 같은 500건 재전송
⑥ 서버는 끝까지 처리해 201 을 쓰지만 받는 사람이 없다
⑦ 그 500건은 이미 저장된 구간이라 ON CONFLICT 로 무시 → DB 새 행 0
```

한 번 들어가면 **스스로 못 빠져나오는 자기 고착 루프**다. 큐가 디스크 영속이라 앱 재시작으로도 안 풀린다.

### 증거

- 요청 크기가 271,742~271,744 바이트로 **±2바이트 고정**. 성공했다면 다음 배치는 내용이 달라진다.
- 서버 로그 60건 전부 201, 지연 전부 16초대.
- 대조군 갤럭시는 같은 라우트에 2~40건(1~21KB)을 보내 0.02~1.49초에 끝난다. **건당 37ms 로 속도는 같고 배치 크기만 다르다.**

## 왜 ①안(다건 INSERT)인가

건당 왕복이 무엇인지 먼저 셌다. `resolvePrimaryWorkerId` 는 15초 TTL 캐시라 500건 중 DB 를 거의 안 친다. `recordAlert`·`updateFallCandidateState` 는 SOS·낙상 때만이다. 즉 **건당 왕복은 `persistSample` 의 INSERT 하나뿐**이고, 그것을 접으면 16.5초가 통째로 사라진다.

후보였던 "루프 청크 동시 실행"은 경보 전이 판정(`prevMerged`)이 ring 순서에 의존해 검토 비용이 더 크다. 앱 타임아웃 15→60초는 계약을 맞추는 별건이고 재설치가 필요해 즉효가 아니다.

## 설계 결정

**결정 1 — 컬럼 목록을 단건과 공유한다(사본 금지).**
`vitalSampleColumns()` 를 추출해 `persistSample` 과 `persistSamples` 가 같은 것을 쓴다. 컬럼이 55개라 사본을 두면 다음 컬럼 추가 때 한쪽만 늘어난다. `persistSample` 주석이 이미 같은 사고를 기록하고 있다 — *"관문은 넷이다 — 스키마·분류·여기·컬럼"*.

**결정 2 — 출처 관문을 배치판에도 건다.**
`REAL_DEVICE_ORIGINS` 검사는 목업 격리가 목적이다. 배치 경로만 관문을 비우면 그 격리가 우회된다. 한 건이라도 위반하면 배치 전체를 던진다 — 부분 저장보다 전량 재전송이 안전하다.

**결정 3 — 파라미터 상한을 컬럼 수에서 계산한다.**
Postgres 바인드 상한은 65,535. 55컬럼 × 500건 = 27,500 이라 지금은 한 왕복이지만, 컬럼이 늘면 자동으로 청크가 쪼개져야 한다. 상수로 박지 않고 `chunkSizeFor(columnCount)` 로 계산한다.

**결정 4 — `deferPersist` 로 미루되 ring·경보는 그대로 둔다.**
`addSample` 의 순서 의존 부분(ring push, 위험 전이 판정, `recordAlert`)은 손대지 않는다. DB 저장만 뒤로 미뤄 호출부가 모은다. 경보가 저장과 분리되어 있다는 기존 계약(감사 DB-POOL-02)이 그대로 유지된다.

**결정 5 — 실패는 전량 실패로 센다.**
종전 `persistFailures` 는 건별 집계였다. 단일 문이 되면 부분 저장이 사라지므로 실패 시 배치 전체를 503 으로 돌린다. 폰이 큐를 유지하고 재전송한다 — 기존 계약과 같은 동작이다.

부수 효과로 기존 주석의 우려 하나가 해소된다 — *"부분 저장 뒤 재전송은 중복 행을 만들 수 있다"*. 청크 안에서는 전부 아니면 전무다.

## 남긴 것

- **앱 타임아웃 15초**는 그대로다. 서버가 빨라지면 당장은 안 걸리지만, 계약상 여전히 서버 최악 처리시간보다 짧다. 별건으로 올릴 것.
- 갤럭시(Wear OS)도 오프라인 후 backlog 를 몰아 보내면 같은 함정에 들어간다. 이 수리가 양쪽을 함께 막는다.
