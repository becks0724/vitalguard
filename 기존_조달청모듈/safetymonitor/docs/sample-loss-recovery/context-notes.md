# 장애 구간 샘플 보존 — 설계 결정 요청

작성 2026-08-15 · 계기 = 같은 날 DB 장애(`22:50:35Z~02:30:03Z` 3시간 39분 + `02:40:08Z~02:51:21Z` 11분).
상태 = **결정 대기**. 코드 변경 0건.

---

## 1. 지금 무슨 일이 일어나는가

DB 가 끊기면 그 구간 생체 샘플이 **조용히 사라진다.** 복구돼도 돌아오지 않는다.

```
store.ts:248   try { await persistSample(sample) } catch { console.error(...) }
               ↓ 삼키고 계속 진행
route.ts       accepted 로 세고 201 반환
VitalPipeline  2xx → 큐에서 제거          ← 여기서 원본이 사라진다
```

catch 자체는 옳다. 2026-06-30 감사 DB-POOL-02 대응으로 **"샘플은 잃어도 경보는 간다"** 를 의도해 넣었고,
이번 장애 3시간 39분 내내 SOS·낙상 알림이 살아 있던 것이 그 덕이다. 그 판단은 유지한다.

문제는 그 다음이다 — **삼킨 사실을 폰에 알리지 않는다.** 폰은 성공으로 알고 원본을 지운다.

## 2. ★ 재시도 인프라는 이미 있다

`VitalPipeline.swift` 실측.

| | |
|---|---|
| 큐 | `vital-queue.json` **디스크 영속** · 상한 **5,000건** · 배치 500건/요청 |
| 2xx | 큐에서 제거 |
| 401·403 | 5분 후 재시도 |
| **그 외(5xx 포함)** | **30초 후 재시도** ← 이미 구현됨 |
| 백그라운드 | BGTask 로 잔여 큐 소진 |

5초당 1건이면 **5,000건 ≈ 6.9시간**. 오늘 장애 3시간 39분 = 약 2,630건으로 **큐에 들어가고도 남는다.**

> **서버가 5xx 만 줬으면 오늘 유실은 0이었다.** 새로 만들 인프라가 없다.

## 3. ★★ 그런데 그대로 켜면 중복 행이 쌓인다

`ts` 가 **전송 시각**이기 때문이다. `VitalPipeline.swift:117` 의 `sentAt` 은 업로드 함수 안에서 찍히고
`:136` 이 `v["ts"] = sentAt` 으로 붙인다. 큐에는 워치 원시 샘플만 있고 변환은 전송 시점에 일어난다.

**즉 재전송할 때마다 ts 가 새로 붙는다.** 서버의 `ON CONFLICT (worker_id, ts) DO NOTHING`(`db.ts:933`)
이 무력해진다 — 같은 측정인데 ts 가 달라 중복으로 안 걸린다.

부분 실패에서 터진다. `route.ts` 는 **건별 처리**다(검증 실패를 격리하려는 의도적 설계).

```
1. 배치 500건 전송 (ts=T1)
2. 서버가 300건 저장 성공 · 200건 DB 실패
3. 전체 5xx 반환
4. 폰이 500건 재전송 (ts=T2)
5. 앞선 300건이 중복 저장 → 같은 측정이 두 행
```

측정 시각은 살아 있다 — `heartRateMeasuredAt`·`spo2MeasuredAt` 이 별도 필드로 이미 실린다(`:139`·`:149`).
**중복 판별에 쓸 값은 이미 손에 있고, 쓰지 않고 있을 뿐이다.**

## 4. 선택지

### A안 · 5xx 반환 + 배치 트랜잭션 (권고)

`persistSample` 이 실패하면 그 배치를 **503** 으로 돌려준다. 폰이 30초 후 재시도한다.
부분 저장을 없애기 위해 **DB 쓰기만 배치 단위 트랜잭션**으로 묶는다(검증 건별 격리는 그대로 둔다 —
한 샘플의 형식 오류가 배치 전체를 되돌리면 안 된다).

- 얻는 것 — 오늘 같은 장애에서 **유실 0**(6.9시간까지). 경보 경로는 지금처럼 별도 try 라 무영향.
- 대가 — 장애가 6.9시간을 넘으면 오래된 것부터 폐기(현재도 그렇다, 다만 즉시가 아니라 나중이 된다).
  재시도 트래픽이 30초마다 배치 1회 발생.
- 전제 — **3절의 중복 문제를 먼저 닫아야 한다**(아래 C안).

### B안 · 서버측 임시 버퍼

DB 실패분을 서버 메모리·디스크에 모았다가 복구 후 flush.

- **권고하지 않는다.** Cloud Run 인스턴스는 스케일 인/아웃에 휘발한다. "저장했다고 믿었는데 사라지는"
  형태가 되어 지금의 조용한 폐기보다 진단이 어렵다. in-memory ring(최근 500)이 이미 있고 그 이상은
  인스턴스 수명에 묶인다.

### C안 · `ts` 계약 정정 (A안의 전제)

중복을 막는 세 경로.

| | 방식 | 평가 |
|---|---|---|
| C-1 | UNIQUE 키를 `(worker_id, heart_rate_measured_at)` 로 | 측정 시각 없는 샘플(활동에너지 단독 등)을 못 덮는다 |
| C-2 | **폰이 큐 항목마다 고유 ID 를 붙이고 서버가 그걸로 dedup** | 가장 견고 · 폰·서버·스키마 3곳 변경 |
| C-3 | **배치를 all-or-nothing 트랜잭션으로** | 부분 실패 자체를 없앤다 · 서버만 변경 · 재전송해도 첫 시도가 통째 롤백이라 중복 없음 |

**C-3 을 권고한다.** 서버 한 곳만 바뀌고, A안이 만드는 중복 시나리오를 뿌리에서 없앤다.
C-2 는 더 견고하지만 재서명 일정(08-17)에 폰 변경을 얹는 부담이 있고, C-3 으로 충분하다.

### D안 · 현행 유지

장애 중 데이터를 포기한다. 오늘 3시간 39분이 작업 시간대(KST 07:50~11:30)를 덮었고
나흘 새 세 번 재발했다는 사실이 이 선택을 지지하지 않는다.

## 5. 권고

**A안 + C-3 을 함께.** 서버만 바뀌고 폰은 그대로다(이미 있는 재시도 경로를 쓰기만 한다).

```
① route.ts POST  — DB 쓰기를 배치 트랜잭션으로 묶는다 (검증 건별 격리 유지)
② store.ts       — persistSample 실패를 호출부에 알린다 (catch 는 유지, 삼키지만 보고한다)
③ route.ts POST  — 저장 실패 시 503 (경보 기록은 지금처럼 먼저·독립)
```

**경보 우선 원칙은 깨지지 않는다.** `recordAlert` 는 이미 별도 try 이고 503 은 폰에게 "다시 보내라"일 뿐
알림 발송과 무관하다. DB-POOL-02 가 지킨 것은 "경보가 나간다"이지 "POST 가 201 이다"가 아니다.

## 6. 미결 — 사용자 판단이 필요한 것

1. **A안 채택 여부** — 재시도 트래픽(30초마다 배치 1회)과 유실 0 의 맞바꿈.
2. **6.9시간을 넘는 장애** — 큐 상한 5,000 을 올릴지(디스크·배터리), 넘는 만큼은 포기할지.
   오늘 3시간 39분은 커버되지만 상한이 어디까지여야 하는지는 실측 근거가 없다.
3. **착수 시점** — DB 가 안정된 뒤여야 한다. 지금은 배포도 실측도 못 한다.

## 7. 검증 계획 (착수 시)

- 배치 트랜잭션 롤백 — DB 실패를 주입해 **부분 저장 0** 확인.
- 503 경로 — 폰 로그에서 `업로드 실패(HTTP 503) — 30초 후 재시도` 와 큐 잔량 유지 확인.
- **경보 생존** — 저장이 503 인 상태에서 SOS 샘플의 `recordAlert`·텔레그램이 나가는지(DB-POOL-02 회귀 방지).
- 복구 후 — 큐가 소진되고 **중복 행 0**(`worker_id`+`heart_rate_measured_at` 로 대조).
