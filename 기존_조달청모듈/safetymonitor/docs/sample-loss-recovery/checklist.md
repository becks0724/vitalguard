## A. POST 5xx 실기기 검증 — 유일하게 지금 할 수 있는 것

**성격이 바뀌었다.** 배포 전 관문이 아니라 **라이브 사후 확인**이다. `9464777` 은 실기기 확인 없이
라이브에 있고, *"폰이 503 을 받으면 큐를 유지하고 30초 뒤 재전송한다"* 를 **코드를 읽어서** 안다.

**DB 가 정상인 동안은 발동하지 않는다**(`persistFailed` 가 서지 않아 201 그대로). 위험은
**"다음 DB 장애 때 이 경로가 처음 라이브에서 돈다"** 하나다.

### 503 을 어떻게 받게 하나

**프로덕션에 `persistFailed` 강제 스위치를 넣지 않는다** — 장애를 흉내내려고 **장애를 만들 수 있는
코드를 라이브에 두는** 교환이다.

```
1. 로컬 dev 를 띄우되 DATABASE_URL 을 죽은 값으로 둔다
   → DB 연결 자체가 실패 = 진짜 persistFailed 경로(흉내가 아니다)
2. 폰의 업로드 대상만 로컬로 (PoCConfig.plist 의 DevBaseURLOverride)
3. 폰 로그 세 줄을 본다
     업로드 실패(HTTP 503) — 30초 후 재시도
     잔여 큐 N건            ← 줄지 않아야 한다(원본 유지)
     [UP] N건 업로드 성공    ← 대상을 프로덕션으로 되돌리면 소진
```

⚠ **`DATABASE_URL` 을 반드시 죽은 값으로.** 로컬 dev 는 `.env.local` 로 **프로덕션 DB 를 문다** —
그대로 두면 POST 가 `persistSample` 을 타고 **프로덕션에 실제로 쓴다**(L-04).

**성공 조건** = 503 구간 샘플이 복구 후 DB 에 들어온다 · **중복 행 0**
(`worker_id` + `heart_rate_measured_at` 대조).

## B. 08-18 시험 B — 기준선이 잡혔다

재서명 때 워치 진단 코드가 설치돼 **지금 상태가 대조군**이 됐다.
```
채널   sendMessage (54건 전부) · transferUserInfo 폴백 미발동
워치   전송34 · 도달 · 잔량4        ← 정상 범위
서버   201 연속 · 잔여 큐 0
```
**폰을 책상에 두고 워치만 20m·벽 너머로** 옮겼을 때 **`sendMessage` → `transferUserInfo` 로 바뀌고
워치 화면의 `잔량` 이 치솟는지**가 거리 가설의 직접 증거다.

## C. `ts` 정정 묶음 — 순서가 강제된다

```
08-18  시험 B                      ← 먼저
그 후   phone_received_at 컬럼      ← 선결
        ts 를 측정 시각으로
        (필요 시) 배치 트랜잭션
```

**시험 B 를 먼저 하는 이유** — `ts` 를 옮기면 `ts − heart_rate_measured_at` 이 항상 0 이 되어
**시험 B 의 판정 지표가 사라진다.** 대가 = `ts` 정정은 폰 변경이라 재설치가 필요한데 재서명에
얹지 못했으므로 다음 설치 기회를 기다려야 한다. 그래도 시험을 먼저 둔다.

## D. 관측 대기 — 조건이 와야 열린다 (L-60)

**배포 후 화면이 멀쩡한 것은 작동한다는 증거가 아니다.** 평상시엔 코드 경로를 타지 않는다.

| 항목 | 무엇이 있어야 관측되나 |
|---|---|
| GET 열화 · POST 5xx | **DB 가 실제로 끊겨야** 한다(A 로 선확인 가능) |
| 429 문구·`Retry-After` | **사용자가 10회를 소진**해야. per-IP 라 우리가 만들면 실사용을 막는다 |
| 스트레스 칩 3자리 | 지수가 100 에 도달해야 |
