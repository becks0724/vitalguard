## A. POST 5xx 검증 — ✅ 종결 (2026-08-15 · 서버측 + 폰측 실기기)

**성격이 바뀌었다.** 배포 전 관문이 아니라 **라이브 사후 확인**이다.
**DB 가 정상인 동안은 발동하지 않으므로**(`persistFailed` 가 서지 않아 201 그대로) 위험은
**"다음 DB 장애 때 이 경로가 처음 라이브에서 돈다"** 하나다.
프로덕션 로그 확인 = 배포(08-15 13:xx) 이후 `/api/app/vital` **5xx 0건**(대조군으로 같은 창의 201

### A-1. 서버측 — 실측 완료 (2026-08-15)

**프로덕션에 `persistFailed` 강제 스위치를 넣지 않았다** — 장애를 흉내내려고 **장애를 만들 수 있는
코드를 라이브에 두는** 교환이 된다. 대신 로컬 dev 의 `DATABASE_URL` 을 죽은 값
(`postgresql://…@127.0.0.1:1/…`)으로 둬 **진짜 실패 경로**를 탔다.

⚠ **선결 확인을 먼저 했다** — `.env.local` 이 프로덕션 DB 를 물고 있어, 죽은 값이 실제로 먹었는지
확인하기 전에는 POST 를 한 건도 보내지 않았다(L-04). `/api/health/db` 가 `ECONNREFUSED 127.0.0.1:1`
로 503 을 내는 것을 보고 착수. 셸 env 가 `.env.local` 을 이긴다는 것은 가정이 아니라 이 응답으로 확인.

| | 요청 | 결과 |
|---|---|---|
| ① | 단건 정상 샘플 | **503** |
| ② | 배치 3건 | **503** · `accepted 3` · `persistFailures 3` |
| ③ | SOS 동반 샘플 | **503** |
| ④ | 빈 샘플(실측 신호 0) | **202** `not_stored` |

| ⑥ | 미분류 source | **202** `not_stored` |
| ⑦ | 무토큰 | **401** |
| ⑧ | 토큰 사번 ≠ 본문 사번 | **403** |

**★ ④⑤⑥ 이 이 시험의 음성 대조다.** 같은 죽은 DB·같은 순간인데 503 이 아니라 202 가 나온다 —
"저장 대상이 아닌 것은 실패가 아니다"(가드 ④)가 **모의가 아니라 실제 실패 환경에서** 성립했다.
셋이 함께 503 이었다면 폰이 30초마다 영원히 재시도한다.

**★ 경보 경로 동시 확인(DB-POOL-02 계약).** 서버 로그에 `[store] DB persist failed:` **5건**과
`[store] 경보 기록 실패:` **1건**이 함께 남았다. 1건인 것이 정답이다 — ③의 SOS 만 경보 대상이고
나머지 4건은 정상 심박이라 `recordAlert` 자체를 안 부른다. **저장이 실패한 뒤에도 경보 경로가
실행됐다**는 직접 증거이고, 종전처럼 한 try 였다면 이 줄이 안 나온다.

### A-3. 남은 미확인 — 좁아졌다

정직하게 적으면 **위 사건은 `default`(503) 분기가 아니라 `401` 분기일 가능성이 높다**

## C. `ts` 정정 묶음 — 순서가 강제된다

```
08-18  시험 B                      ← 먼저
그 후   phone_received_at 컬럼      ← 선결
        ts 를 측정 시각으로
        (필요 시) 배치 트랜잭션
```

**시험 B 를 먼저 하는 이유** — `ts` 를 옮기면 `ts − heart_rate_measured_at` 이 항상 0 이 되어
**시험 B 의 판정 지표가 사라진다.** 대가 = `ts` 정정은 폰 변경이라 재설치가 필요한데,
**08-18 에 어차피 앱을 만지므로 그날 설치에 얹으면 추가 비용이 0 이다**
(오늘 재설치 3회의 실측 비용 = 매번 10~13건 유실).

**★★ 범위가 줄었다 — 실패 모드 하나가 반증됐다(2026-08-15 A-3).**
초판이 적은 *"재전송 → 새 `ts` → 중복"* 은 **폰 계층에서 성립하지 않는다.**
`ts` 는 `ingest()` 시점에 붙어 재전송해도 유지되므로(503 시험에서 **41회 재전송·중복 0** 실증)
`UNIQUE(worker_id, ts)` 가 오히려 방어로 작동한다.

```
남는 진짜 결함 = 한 배치 다건 → 같은 sentAt → ON CONFLICT 로 조용한 폐기   ← 이 한 방향뿐
사라진 우려   = 재전송 → 새 ts → 중복                                    ← 반증됨
```
따라서 **배치 트랜잭션(C-3)의 우선순위가 내려간다** — 트랜잭션은 부분 저장만 없애지
같은 `sentAt` 충돌은 못 없앤다. 고쳐야 할 곳은 `ingest()` 가 배치 전 항목에 **한 시각을
붙이는 것** 자체다.

설계 상세·선택지 비교 = [context-notes.md](context-notes.md).
