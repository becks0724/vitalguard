# OCR 각인 주소 — 결정과 근거

촬영 각인의 주소 줄이 세 축 모두 틀린 것을 고치는 트랙. 좌표는 처음부터 맞았다.

## 2026-08-28 · 진단 확정

사용자 제보는 "GPS 가 138m 틀리다" 였으나 **좌표는 맞았고 주소가 틀렸다.**

```
실제       전남광주 동구 금남로3가 1-10      (사용자 확인)
앱 각인    광주광역시    금남로3가 15-2      (2026-08-28 09:45 촬영분)
```

| 축 | 앱 표기 | 실제 | 원인 |
|---|---|---|---|
| 광역 | 광주광역시 | 전남광주(통합특별시) | 애플 지오코딩이 통합 전 옛 행정구역명을 낸다 |
| 자치구 | (없음) | 동구 | 코드가 `subAdministrativeArea` 를 안 읽는다 |
| 지번 | 15-2 | 1-10 | 애플이 다른 필지를 지목한다 |

세 축 중 **둘이 애플 데이터 문제**라 필드를 더해도 안 고쳐진다. 그래서 지오코더 교체로 간다.

### 좌표는 무죄임을 통제군으로 확인했다

같은 자리·같은 시각에 정확도 등급이 다른 두 경로를 재서 비교했다.

```
기본 카메라 (09:43)   35.15053 , 126.91630     최고 등급 · GNSS 우선
앱 OCR      (09:45)   35.150535, 126.916294    100m 등급
                      차이 0.8 m
```

★ **여기서 내 첫 가설이 반증됐다.** 나는 `desiredAccuracy = kCLLocationAccuracyHundredMeters`
때문에 GNSS 가 안 돌아 좌표가 틀렸다고 봤고, 근거로 "31분간 9건의 fix 가 6자리까지 동일"을 들었다.
값은 맞았지만 **해석이 틀렸다** — 등급이 다른 기본 카메라도 같은 답을 낸다. 반복되는 동일 좌표는
우리 설정 탓이 아니라 iOS 가 이 자리에서 안정된 측위 결과를 내주는 것이다.
`OneShotLocator` 등급 상향과 관련 가드 완화 제안은 **철회했다.**

⟹ 교훈. 정확도 등급을 의심할 때는 **등급이 다른 두 경로를 같은 자리에서 재는 것**이 유일한 판별법이다.
DB 안의 좌표 분포만으로는 "측위 수단"을 못 가린다.

## 결정 ① 지오코딩을 서버로 옮긴다 (사용자 결정 · ⓑ)

후보는 둘이었다.

- ⓐ 앱이 지오코딩 API 를 직접 호출 — 키가 앱 바이너리에 박힌다.
- ⓑ **앱이 관제웹에 좌표를 물어 주소를 받는다** ← 채택

근거. 키가 서버에만 남고, **지오코더를 갈아도 앱 재배포가 필요 없다.** 앱 JWT 로 서버를 부르는
경로가 이미 있어(`/api/app/vital`·`/api/app-media`) 라우트 하나면 된다.

⚠ 대가 = 각인 경로에 네트워크 왕복이 하나 붙는다. 실패해도 업로드는 계속돼야 한다
(현재도 주소는 실패해도 진행하는 구조다).

## 결정 ② 제공자는 NCP Maps Reverse Geocoding

병원 검색이 쓰는 NCP 자격증명(`NAVER_SEARCH_CLIENT_ID/SECRET`)을 그대로 찔러 봤다.

```
GET maps.apigw.ntruss.com/map-reversegeocode/v2/gc
 → 401 {"errorCode":"210","message":"Permission Denied",
        "details":"A subscription to the API is required."}
```

**키 인증은 통과했고 상품 구독만 없다.** 계정이 맞다는 뜻이라 새 자격증명 없이 콘솔에서
Maps 를 구독하면 된다. 카카오 로컬·행안부 도로명주소는 새 키·승인 절차가 필요해 뒤로 미뤘다.
ⓑ 구조라 나중에 갈아도 앱은 안 건드린다.

⚠ **구독 전에는 라우트가 `configured:false` 를 낸다.** `naver-local.ts` 가 이미 쓰는 관례를 따른다.

## 결정 ③ 실패하면 기기 추정으로 떨어지되 **밝힌다**

서버 주소를 못 받았을 때 셋 중 하나를 고른다.

1. 주소 줄을 비운다 — 실내·오프라인에서 정보가 통째로 사라진다.
2. 기존 CLGeocoder 값을 그냥 쓴다 — **틀린 주소가 맞는 것처럼 보인다.** 채택 불가.
3. CLGeocoder 값을 쓰되 `(기기 추정)` 을 붙인다 ← 채택

근거. 좌표 각인이 이미 같은 원칙을 쓴다 — 나쁜 값을 거르지 않고 `±00m`·`N분 전 좌표` 로
**밝힌다**(2026-08-22). 주소도 같은 자로 다룬다. 증빙에서 위험한 것은 부정확이 아니라
**부정확을 확정처럼 적는 것**이다.

## 남긴 것 · 안 한 것

- **이미 찍힌 사진의 주소는 안 고친다.** 사진에 구워진 글자는 못 고친다. 다만 DB
  `calendar_media.road_address` 는 좌표가 맞으므로 **재계산이 가능**하다. 별건으로 남긴다.
- `subAdministrativeArea` 만 더하는 부분 수리는 **하지 않는다.** 자치구는 살아나지만 광역명·지번은
  여전히 틀린 채라 틀린 주소가 더 그럴듯해지기만 한다.
- 실외 통제군 한 쌍은 **안 찍었다.** 실내에서 두 경로가 이미 일치해 등급 축이 닫혔기 때문이다.

## 병렬 세션 조율 (2026-08-28)

착수 시점에 옆 세션(`vitalguard-jodalcheong-50`)이 `vitalguard-dashboard` 배포를 잡고 있었고
실행은 사용자 명령 대기로 멈춰 있었다.

`scripts/deploy-dashboard.sh:115` 가 `git archive "$SHA:$SUBTREE"` 라 **이미지는 HEAD 커밋에
고정**된다. 그래서 미커밋 편집은 그쪽 이미지에 안 실린다 — 위험한 것은 편집이 아니라 **커밋**이다.
지금 커밋하면 나중에 스크립트가 읽는 HEAD 가 내 커밋이 되어 승인 범위가 조용히 커진다([[L-116]]).

⟹ **편집은 하되 그쪽 배포가 끝날 때까지 커밋하지 않는다.**
