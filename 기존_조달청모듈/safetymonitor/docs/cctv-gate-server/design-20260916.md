## 0. 한 줄 요약

젯슨 푸셔에 **이미 들어 있는 "서버로 JPEG 밀어 올리기" 기능**(`CCTV_BASE`)을 켜서 관제웹 서버로 보내고,
서버가 **DB 한 행에 최신 1장**을 저장·반환하면 — 가스포드와 같은 방향이 되어 Tailscale·duckdns·포트포워딩이
전부 필요 없어진다. 앱 코드 수정 0, 월 비용 ≈ $0.

## 1. 왜 지금 안 보이는가 (2026-09-16 실측)

| 사실 | 근거 |
|---|---|
| 앱은 티켓의 `gateApi` = `https://cctv-gate.example.invalid:8443` 에 **직접** 붙는다 | `cctv_screen.dart:136-165`, `cctv-ticket/route.ts:82` |
| 그 도메인이 **사설 IP `192.168.219.47`**(젯슨, MAC `44:49:c0:46:45:81`)을 가리킨다 | `dig` |
| 젯슨은 공유기 `80:ca:4b:28:76:5` 망 = Wi-Fi **AICAM_301B**(BSSID `…:28:76:06`) | 맥 유선 ARP · 태블릿 스캔 |
| 태블릿이 붙은 **AICAM_301A**(`…:64:d7:fa`)는 **별개 공유기** — 같은 `192.168.219.x` 여도 ping 불가 | 태블릿→`.47` ping 100% loss |
| 맥 유선(301B 망)에서는 게이트가 **401**(티켓 없음) = 젯슨 정상 | `curl -k https://….47:8443/cctv/stream3` |
| 외부 회선(태블릿 공인 `112.155.56.62`)에서 젯슨 공인 `112.155.56.10:8443` → **UNREACHABLE** = 포트포워딩 없음 | 태블릿 크롬 |
| 공인 IP 가 계획서 `125.244.144.225` → `112.155.56.10` 으로 바뀌었다(동적) | `api.ipify.org` |

→ CAM-03 이 죽은 게 아니라 **앱이 젯슨과 같은 망에 있어야만 닿는 구조**다. 밖에서 보려면 Tailscale 로 그 망에 들어가야 했다.

## 2. 지금 구조 — 젯슨에서 화면까지 9단계

**젯슨 안**
1. GoPro → 1080p 프레임
2. 푸셔 `gopro_ppe_edge.py` — 960×540 으로 줄여 3프레임당 1회 YOLO(안전모)+낙상 추론, 박스·한글 라벨을 그려
   **640×360 JPEG q72 ≈ 40KB** 를 메모리에 최신 1장으로 보관. `:8444` 로컬 HTTP(인증 없음)
3. 게이트 `cctv_gate.py` — `:8443` HTTPS(Tailscale cert 로 받은 Let's Encrypt). 푸셔 `127.0.0.1:8444` 를 **읽기만** 한다.
   젯슨에서 밖으로 열린 유일한 문

**태블릿 (갱신 간격마다 반복)**
4. 앱 → 서버 `POST /api/app/admin/cctv-ticket {cameraId}` (앱 JWT)
5. 서버 — 계정·현장 권한(`cctv_site_role`, owner 예외) 확인 → **Ed25519 서명 티켓**(`aud`=카메라·`scp=read`·`nbf/exp` 60초·`jti`) → `cctv_ticket_audit` 기록 → `{ticket, expiresAt, ttlSec, gateApi}`
6. 앱 → `GET {gateApi}/cctv/stream3` + `Authorization: Bearer <티켓>` — **젯슨으로 직접** ← ★ Tailscale 이 끼는 지점
7. 게이트 — kid→공개키 → 서명 → nbf/exp → 카메라·현장 일치 → `scp=read` → **jti 1회 소비** → 푸셔 `/stream` 을 MJPEG 로 릴레이
8. 앱 — MJPEG **첫 프레임 1장만** 읽고 연결 종료(`cctv_image_reader.dart`) → 디코드 → 화면
9. 3/5/10초 뒤 4 부터 다시 (jti 가 1회용이라 티켓도 새로)

**관제웹**은 5 까지 같고, 6 에서 `<img src>` 로 MJPEG 를 끊지 않고 계속 받는다. `gateApi` 는 빌드 때 박힌 `NEXT_PUBLIC_CAM03_GATE_API`.

서버가 하는 일은 **5번 티켓 발급뿐**. 영상 바이트는 젯슨 → 화면 직행이다.

## 3. 이 구조가 된 경위

| 시기 | 젯슨 | 서버 | 화면 | 비용 |
|---|---|---|---|---|
| **7월(발표)** | JPEG 를 `POST {CCTV_BASE}/cctv/ingest3` 로 push — `image/jpeg`, 인증 헤더 없음, `PUSH_FPS=10`, 워커 2 | `cctv-ai`(Cloud Run **4vCPU/4Gi · cpu-throttling false · maxScale 1**)가 **프로세스 메모리** `_ppe_live["frame"]` 에 보관. DB 코드 0줄. 서버 추론도 함 | `<img>` MJPEG | 켜면 인스턴스 24h 상주 |
| **9/9 결정 3** | `CCTV_BASE` 비움(로컬 전용·과금 0). 젯슨 자신이 게이트로 서빙 | 티켓만 | 젯슨에 직접 pull | 0 |
| **지금** | 위와 같음. 단 **포트포워딩 미개방·duckdns 사설 IP** 로 결정 3 이 미완 | | Tailscale 필요 | 0 |

**"POST → DB → GET" 은 한 번도 없었다.** 7월 push 의 목적지가 DB 가 아니라 Cloud Run 메모리였고, 그래서 인스턴스 1개 고정·4vCPU 상시가 필요했다 — 이것이 "저번 과대 비용"의 구조다.

### 왜 Tailscale 이었나
- **HTTPS 인증서 때문** — 아이폰 카메라 릴레이 페이지가 사파리 `getUserMedia` 를 쓰려면 보안 컨텍스트가 필요. 평문·자체서명은 사파리가 카메라를 안 준다. `tailscale cert` 로 Let's Encrypt 를 받았다 (`cctv-ai/README.md:338`)
- **운영자 SSH** — 계획서: "Tailscale 은 사용자가 젯슨을 제어할 때만 쓰는 운영자 전용 경로"
- 시청 경로로 쓰인 건 **부산물**. 현장 AP 가 클라이언트 격리라 Tailscale 도 P2P 가 아니라 DERP 중계로 돌아 느렸다 (`progress.md:552`)

### 9/9 결정 3 의 전제와 현재
- 결정: "Tailscale 을 쓰지 않는다 — 젯슨을 직접 이더넷(포트포워딩)으로 공개"
- 실측 완료: 공인 IP CGNAT 아님 · 상향 ≈300Mbps(시청자 50명분) · 위험 대책(UPnP/DMZ 끄기 · DHCP 예약 · DDNS) 정리
- **막힌 이유: AICAM_301B 공유기(학원 장비) 관리자 권한 없음** → 포트포워딩 불가 → 결정 3 실행 불가

## 4. 새 구조 — 가스포드 방식

```
지금    GoPro → 푸셔(추론·JPEG) → 게이트 :8443 ◀──── 앱이 들어와서 가져감      ← 사설 IP · Tailscale 필요
바꾸면  GoPro → 푸셔(추론·JPEG) ──POST(젯슨 토큰)──▶ 관제웹 서버 → DB 한 행 ◀── 앱이 서버에서 가져감(티켓)
```

| | 내용 |
|---|---|
| **바뀌는 것** | 2번 푸셔의 `CCTV_BASE` 를 켜서 목적지를 관제웹 서버로 · 서버에 받기/주기 라우트 · 프레임 테이블 |
| **안 바뀌는 것** | 1·2번(GoPro·추론·JPEG) · 5번 티켓 발급 · **앱 코드** |
| **없어지는 것** | 3번 게이트를 바깥에 열 이유 — Tailscale cert · duckdns · 포트포워딩 · `:8443` 노출. 젯슨은 아웃바운드 HTTPS 하나뿐 |

가스포드가 `POST → DB → 화면` 인 것과 같은 구조다. 젯슨→서버 방향 인증은 가스포드처럼 **젯슨 전용 업로드 토큰(env)**.

## 5. 상세 설계

### 5-1. 젯슨 (팀원 영역 · 변경 3줄)
```
Environment=CCTV_BASE=https://vitalguard-dashboard-7r2vb5q5qa-du.a.run.app/api/cctv-gate
Environment=PUSH_FPS=0.2          # 5초 1장 — /config?push_fps=0.2 로 재기동 없이도 조정 가능
Environment=CCTV_INGEST_TOKEN=…   # 서버와 공유하는 업로드 토큰
```
- `gopro_ppe_edge.py:626` `conn.request("POST", …, body=jpg, headers={"Content-Type": "image/jpeg"})` 에
  `"Authorization": f"Bearer {CCTV_INGEST_TOKEN}"` 한 줄 추가
- 기존 push 워커(`_push_worker`)·경로(`/cctv/ingest3`)·쿼리(`?drawn=1&persons=…`)는 그대로 쓴다
- 게이트 `:8443` 는 LAN 용으로 남기거나 끈다. **바깥에 열 필요가 없다**

### 5-2. 서버 (dashboard-web · astra 작업)

**라우트 ① 받기** — `POST /api/cctv-gate/cctv/ingest3?drawn=1&persons=…&violations=…&compliance=…`
- 인증: `Authorization: Bearer <CCTV_INGEST_TOKEN>` (env · 상수 시간 비교) → 아니면 401
- 본문: `image/jpeg`, 상한 256KB(40KB × 여유) → 초과 413
- 처리: `cctv_frame` UPSERT (`camera_id` PK) — jpg·captured_at·stats(쿼리 카운트 jsonb)
- 응답: `{ok:true}` 204 도 가능. **추론 없음·메모리 보관 없음** — 요청 처리 중만 CPU

**라우트 ② 주기** — `GET /api/cctv-gate/cctv/stream3`
- 인증: `Authorization: Bearer <티켓>` — **게이트 `_verify` 와 같은 규칙**: 서명(Ed25519 공개키 = `CCTV_TICKET_KEY` 개인키에서 유도) → `nbf/exp` → `aud`=카메라 → `scp=read` → **jti 1회 소비**
- jti 소비는 메모리가 아니라 **DB**(`cctv_ticket_jti(jti PK, exp)` INSERT — 충돌이면 401 "already used"). Cloud Run 은 인스턴스가 여럿이라 메모리로는 못 지킨다. 만료분은 주기 삭제
- 응답: `image/jpeg` 단발 + `X-Captured-At`. 앱 리더가 `contentType.primaryType == 'image'` 면 그대로 받는다(`cctv_image_reader.dart:40`) → **앱 수정 0**
- 프레임 나이가 `PPE_LIVE_TTL` 을 넘으면 503 `{"error":"stale"}` — 앱은 503 을 "현장 장비에 연결되지 않습니다" 로 표시한다(`cctv_screen.dart:354-374`)

**티켓 응답** — `cctv-ticket/route.ts:82` 의 `gateApi` 를 서버 자신 `https://…/api/cctv-gate` 로. env `CAM03_GATE_API` 값만 바꾸면 되므로 코드 변경 없음

**테이블** (`ensureSchema` 에 멱등 추가 — DDL 파일·직접 SQL 아님)
```sql
CREATE TABLE IF NOT EXISTS cctv_frame (
  camera_id   TEXT PRIMARY KEY REFERENCES cctv_camera(camera_id),
  jpg         BYTEA NOT NULL,
  captured_at TEXT  NOT NULL,          -- 기존 표들과 같이 text ISO
  stats       JSONB,
  updated_at  TEXT  NOT NULL DEFAULT (now_iso)
);
CREATE TABLE IF NOT EXISTS cctv_ticket_jti (
  jti TEXT PRIMARY KEY,
  exp BIGINT NOT NULL
);
```

**관제웹** — `CctvQuadView.tsx:195` 의 MJPEG `<img src>` 를 **5초 스냅샷 폴링**(fetch + Bearer 티켓 → blob → objectURL)으로. 444줄에 이미 같은 패턴(통계 fetch)이 있다. 장시간 연결을 없애야 요청 단위 과금이 유지된다

### 5-3. 앱
**변경 0.** `gateApi` 가 서버 주소로 오면 지금 코드가 `<gateApi>/cctv/stream3` 에 Bearer 티켓으로 붙고, `image/jpeg` 단발을 받는다.

## 7. 확인 필요 (설계 전 실측할 것)

1. **DB 한 행 5초 UPDATE 의 bloat** — 하루 17,280 dead tuple. autovacuum 기본값으로 따라오는지 실측. 안 되면 `UNLOGGED` 테이블 또는 `fillfactor` 조정
2. **jti 1회 소비를 DB 로** — 위 설계대로. 만료 jti 정리 주기(예: 티켓 라우트 호출 시 `DELETE … WHERE exp < now` 확률적)
3. **Cloud Run 콜드스타트** — dashboard 는 min 0. 젯슨이 5초마다 쏘면 사실상 warm 이지만 첫 요청 지연은 실측
4. **관제웹 MJPEG 제거** — `<img>` 스트림이 남아 있으면 요청 하나가 수십 분 열려 CPU 과금이 늘어난다. 폴링 전환은 필수
5. **푸셔 `PUSH_FPS=0.2` 동작** — `interval = PUSH_WORKERS(2) / 0.2 = 10초/워커`, 위상이 어긋나 합산 5초. 코드상 맞지만 실측
6. **업로드 본문 상한** — Cloud Run 요청 32MB 한도 안이라 문제 없음. 서버에서 256KB 로 자르는 건 방어용

## 9. 배터리 실측과의 관계

실측 목적은 "태블릿에 CCTV 를 둘지" 판단. 새 구조가 되면 태블릿이 어느 망에 있든 실측 가능하다.

USB 꽂은 채 CCTV 켜고 `dumpsys batterystats --reset`, USB 빼고 n 시간 뒤 다시 꽂아 `dumpsys batterystats` 로 읽는다.
