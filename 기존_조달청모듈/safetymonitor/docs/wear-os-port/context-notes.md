# 갤럭시워치 단독 수집기 — 결정과 근거

작업 중 내린 결정을 근거와 함께 쌓는다. 나중에 "왜 이렇게 했나" 를 다시 묻지 않기 위해서다.

## R-01 · SpO₂ "상시 불가" 는 과한 결론이었다 — 비교 기준이 틀렸다

08-24 1차 판단에서 *"SpO₂ 상시 불가 → 안드로이드 트랙 재고"* 까지 적었다. **철회한다.**

틀린 이유는 **iOS 쪽을 다시 안 잰 것**이다([[L-107]] ①). 현재 iOS 도 SpO₂ 를 상시로 재지 않는다.

```swift
// WatchStreamer.swift:735 — 앱은 측정을 시키지 않는다. 애플워치가 알아서 잰 것을 줍는다
query.updateHandler = { _, samples, _, newAnchor, _ in self?.ingestSpO2(...) }
```

`HKAnchoredObjectQuery` = **수동 구독**. 측정 시점·주기는 애플이 정하고 앱은 개입 못 한다.

| | iOS 현재 | 갤럭시워치8 |
|---|---|---|
| 측정을 누가 시키나 | 애플워치가 알아서 | **앱이 직접** (`SPO2_ON_DEMAND`) |
| 주기 | 애플 비공개 · 산발 | **앱이 정함** |

⟹ 이 항목은 **갤럭시워치가 우위**다. "연속 스트림이 없다" 와 "상시 값을 못 얻는다" 는 다른 말이다.

## R-02 · 판정 근거는 웹 문서가 아니라 AAR 바이트코드다

사용자가 로컬 SDK 2종을 제공해 `javap` 로 열거형을 직접 읽었다([[L-112]] ① — 채널을 코드로 확인).

```
SPO2              ← deprecated · on-demand
SPO2_ON_DEMAND    ← 현행 · "1 data point for each measurement"
```

**웹 요약만 봤으면 `SPO2` 라는 상수가 따로 있는 것을 근거로 "상시가 있다" 고 오독할 뻔했다.**
공식 API 레퍼런스가 둘 다 on-demand 라고 명시해 확정했다.

## R-03 · 이전 표를 뒤집은 발견 3건 — 워치8이 애플워치를 이긴다

AAR `ValueKey` 하위 클래스를 전수로 읽어 나왔다.

| 발견 | 근거 클래스 | 의미 |
|---|---|---|
| 주변 온도 | `SkinTemperatureSet` = `OBJECT_TEMPERATURE` + **`AMBIENT_TEMPERATURE`** | 스키마의 `skinTempC` **와** `ambientTempC` 를 둘 다 채운다. 애플은 주변온을 안 준다 ⟹ WBGT 환경축이 작업자별로 쪼개진다 |
| HRV 원본 | `HeartRateSet` = `HEART_RATE` + **`IBI_LIST`** + `IBI_STATUS_LIST` | IBI 가 상시로 온다 ⟹ SDNN 을 직접 계산. 애플의 산발 SDNN 보다 촘촘 |
| SpO₂ 원재료 | `PpgSet` = `PPG_GREEN`+`PPG_IR`+`PPG_RED` **25Hz 상시** | SpO₂ 는 red/IR 흡광비로 계산한다. 애플은 raw PPG 를 아예 안 준다 |

⟹ 1차 답변의 *"신호 3종 영구 결손"* 은 **호흡수·MET·일광시간** 셋으로 줄었고, 셋 다 가중치가 낮다.

## R-04 · `:wear` 를 Flutter 안드로이드 프로젝트 안에 둔다

워치가 **단독**이라 Flutter 앱에 기술적으로 의존하지 않는다. 그런데도 같은 Gradle 프로젝트에 둔다.

**이유 셋.**
1. **JWT 전달이 Data Layer 를 요구한다.** 워치 자판으로 로그인하는 건 현실성이 없어 폰에서
   1회 페어링해 넘겨야 하는데, Data Layer 는 **같은 패키지명·같은 서명**을 요구한다.
   팀원 앱 README 가 같은 제약을 적어 뒀다.
2. **툴체인이 이미 증명됐다.** 08-24 `flutter build apk --debug` 가 통과했다(에러 0 · APK 146MB).
   새 프로젝트를 파면 Gradle 9.1 / AGP 9.0.1 / JDK 25 조합을 다시 증명해야 한다.
3. 팀원 앱(`apps/VitAlGuard-Flutter-Android-App/android/wearos_companion`)이 같은 형태다 — 선례.

**부작용 하나.** 루트 `build.gradle.kts` 의 `subprojects { evaluationDependsOn(":app") }` 때문에
`:wear` 평가가 `:app`(Flutter) 평가를 먼저 부른다. 빌드는 되지만 `:wear` 단독 빌드에도
Flutter 플러그인 해석이 붙는다. 지금은 감수한다 — 분리는 되돌릴 수 있고, 서명 공유는 못 되돌린다.

## R-05 · 진단 UI 는 Compose 가 아니라 순정 View 로 쓴다

Wear Compose 를 붙이면 Kotlin 2.3.20 · AGP 9.0.1 과 Compose 컴파일러 버전을 맞춰야 하고,
그 실패는 **SDK 링크 성공 여부와 무관한 잡음**이다. 1단계 성공 기준은 "AAR 이 링크되고 빌드된다"
하나뿐이라 UI 는 최소로 간다. 팀원 wear 동반앱도 `LinearLayout`+`TextView` 다 — 선례.

**제품 UI 는 3단계에서 Compose 로 간다.** 지금 쓰는 것은 버리는 코드다.

## R-06 · `SDK_POLICY_ERROR` 가 파트너 승인 판별자다

`HealthTracker.TrackerError` 열거형에 둘뿐이다.

```
PERMISSION_ERROR    권한 미부여
SDK_POLICY_ERROR    ★ 패키지명·서명이 삼성에 등록 안 됨 = 파트너 미승인
```

삼성이 파트너 프로그램 **접수를 중단**한 상태라 승인은 못 받는다. 대신 **개발자 모드**
(설정 > 앱 > Health Sensor Service > 제목 10회 탭)로 미승인 상태에서도 완전히 동작한다.
공모전 시연·실증에는 문제가 없고 **상용 배포만** 막힌다.

⟹ 프로브가 이 오류를 **화면에 그대로 적게** 한다. 안 적으면 다음 사람이 "센서가 없다" 로 오독한다.

## R-07 · 권한은 Wear OS 6 에서 이름이 바뀐다 — 신·구 병기

갤럭시워치8 = Wear OS 6 = **Android 16 (API 36)**.

| targetSdk | 권한 |
|---|---|
| 33~35 | `BODY_SENSORS` + `BODY_SENSORS_BACKGROUND` |
| **36** | `android.permission.health.READ_HEART_RATE` + `READ_HEALTH_DATA_IN_BACKGROUND` |

구권한에 `maxSdkVersion="35"` 를 달고 신권한을 함께 선언한다(공식 권장 형태).

**⚠ 배포 시 반드시 걸리는 것.** 백그라운드 권한은 restricted 라 **런타임 팝업에 "항상 허용" 이 없다.**
사용자가 설정에 직접 들어가 켜야 한다. 안 켜면 앱이 백그라운드로 가는 순간 `onPermissionLost()`
가 뜨고 전경 권한까지 잃는다. 실측 ⑥ 이 이 단계 수를 세는 이유다 — 온보딩 문구를 그 수에 맞춘다.

## R-08 · 5초 배치를 그대로 옮기지 않는다 (2단계 결정 예고)

Wear OS 공식 전력 가이드가 *"비필수 네트워크 접근은 충전 중까지 미루라"* 고 명시한다.
LTE 상시 업로드는 정확히 그 반대다. 워치8 배터리는 325mAh(40mm)/425mAh(44mm) · AOD 30h 기준.

⟹ 배치 주기 후보 **30~60초**. 다만 **지금 정하지 않는다** — 실측 ⑤⑦⑧ 의 배터리 곡선을 보고
3단계에서 정한다. 근거 없이 숫자를 박으면 [[L-107]] 의 "전제 없는 착수" 가 된다.

## R-09 · flush 1회 = 병합 항목 1건 — 서버 UNIQUE(worker_id, ts) 가 설계를 정한다

iOS 는 배치에 심박 항목 여러 건을 담고 서버가 ts 충돌로 뒤 항목을 **조용히 버렸다**
(2026-08-14 가드 주석 — 그래서 실도착이 12행/분 = flush 주기와 일치했다). 워치 이식은
처음부터 **한 항목만** 만든다(`SampleBuilder`). 실질 도착률은 같고 유실이 설계가 된다.

같은 이유로 세 가지 규칙을 계약으로 굳혔다.
① 측정 시각은 ts(전송 시각)와 별개 키(`heartRateMeasuredAt`·`spo2MeasuredAt`) — 세 시각 구분.
② 측정된 것만 싣는다 — 0 채움·직전 값 복사 금지(구 앱 HRV 가짜 밀도 사고의 재발 방지).
   HRV 는 **창 주기(5분)당 1회만** — 매 flush 재계산 전송은 같은 사고의 재현이다.
③ 무동작 지속만은 단독 전송 허용 — 벗음/쓰러짐 판별이 정확히 그 구간에 필요하다(iOS 규칙).

부수 확정 — 로컬 실왕복에서 서버가 persist 실패를 **503 + accepted** 로 응답함을 확인.
큐를 지우면 안 되는 응답이다. 상태기계는 2xx 에서만 큐를 비운다(그 외 전부 30s/300s 재시도).

## R-10 · 실왕복은 DB 를 차단하고 한다 — L-04 의 이 트랙 적용형

`.env.local` 의 DATABASE_URL 은 프로덕션이다. 로컬 `next dev` 로 왕복하면 검증(Zod·JWT·
사번 결속)은 DB 앞단에서 끝나므로, DATABASE_URL 을 `127.0.0.1:1`(unroutable)로 덮어
**한 행도 쓰지 않고** 계약 통과만 실측한다. 판정 = `accepted` 건수(12/12). workerId 도
실제 사번이 아니라 `WEAR-LOCALTEST` 를 쓴다 — 만에 하나 DB 에 닿아도 실계정 오염이 없다.

## R-11 · 워치 무선 ADB 런북 — IPv6 전용 핫스팟의 4중 함정 (08-24 실전에서 전부 밟음)

공유기(무선 격리) → 폰 핫스팟 이동 후에도 3겹이 더 있었다. 다음에 그대로 재사용한다.

① **공유기 무선 격리** — 같은 SSID 인데 ARP `incomplete`. 공유기 우회 = 폰 핫스팟.
② **통신사 폰 핫스팟은 IPv6 전용(464XLAT)** — 클라이언트 IPv4 는 192.0.0.x/32 **더미**라
   기기 간 IPv4 유니캐스트가 원래 안 된다(페어링 화면의 192.0.0.4 는 미끼다). 판별 지문 =
   Mac ifconfig 에 `clat46` · 넷마스크 0xffffffff.
③ **경로** — `dns-sd -L`(SRV→호스트명) → `dns-sd -G v6`(AAAA) → **pair 는 글로벌 v6**
   `adb pair "[2001:...]:포트" 코드` → **connect 는 링크로컬+스코프** `adb connect
   "[fe80::...%en0]:포트"` (글로벌 connect 는 Network unreachable 로 실패했다).
④ **워치 Wi-Fi 절전이 유휴 TCP 를 수 초 만에 끊는다** — ping 은 9.5ms 인데 세션만 죽는 지문.
   해법 = 연결 직후 keep-alive 쉘(`shell "while true; do echo ka; sleep 1; done"` 백그라운드)로
   링크를 붙잡고 그 사이에 작업. 스트리밍 설치(abb_exec)는 이 링크에서 깨지므로
   **push + `pm install -r`** 로 우회한다(9.7MB 가 0.7초에 들어갔다 — 링크 자체는 빠르다).

기기 실측 = SM-L355N · Android 17 · API 37. 매니페스트의 SDK_INT>=36 분기·신권한 그대로 유효.

## R-12 · wake-up 센서는 배치로 온다 — 도착 시각을 측정 시각으로 쓰면 최대 3.7분이 어긋난다

08-24 실측 ⑤(12.2분)가 강제한 수정이다. 화면이 꺼지면 센서 허브가 표본을 FIFO 에 모았다가
CPU 가 깰 때 몰아서 준다. **유실은 0이었다** — 746건/732초 = 101.9%.

```
공백 219.4초 → 직후 2초 내 221건 도착   (5구간 모두 공백 초 ≈ 직후 건수)
분당 표본수 … 19:24=60 · 19:25~27=0 · 19:28=241 · 19:29=31
```

**판정 규칙 둘.**
① **"공백"을 유실로 읽지 않는다.** 배치인지 정지인지는 *공백 초 대 직후 도착 건수*가 가른다.
   같으면 배치(수집 계속), 직후에도 1Hz 면 진짜 정지다. 표본 수/경과 초로 수집률을 먼저 낸다.
② **측정 시각은 `event.timestamp`(부팅 후 나노초)를 벽시계로 환산해 쓴다.**
   `System.currentTimeMillis()` 를 쓰면 배치로 온 221건이 전부 같은 순간에 잰 값이 되어
   `heartRateMeasuredAt` 이 최대 3.7분 어긋난다. 서버가 ts(전송)·measured_at(측정)·
   received_at(도착) 셋을 나눠 두는 이유가 정확히 이것이다 — iOS 계약과 같은 자리.

⟹ `SensorTrackerSource.eventWallClockMs()` 신설 · 배치 구간 계약 시험(BatchDeliveryTest) 추가.
⚠ 이 배치 거동은 **배터리에 유리하다**(CPU 가 계속 깨지 않는다) — 없애려 하지 않는다.
   다만 flush 주기 설계(R-08)에서 "60초마다 올린다"가 실제로는 "몇 분에 한 번 몰아서"가 될 수
   있음을 전제해야 한다. 큐가 그 사이를 흡수하므로 유실은 없다.

## R-13 · 업로드를 메인 스레드에서 돌렸다 — 삼킨 예외가 원인을 3시간 숨겼다 (08-24 실기)

⑦ 본수집을 켰는데 관제웹에 한 건도 안 왔다. 로그에는 `업로드 대기 30s (auth=false) · 큐 1`
만 반복. 큐만 쌓이고 전송은 0이었다.

**원인 = `CollectorService` 의 tick 을 `Handler(Looper.getMainLooper())` 로 돌린 것.**
`HttpTransport.post()` 가 메인 스레드에서 소켓을 열자 Android 가 `NetworkOnMainThreadException`
을 던졌고, `runCatching{}.getOrDefault(-1)` 이 그것을 **네트워크 오류(-1)로 둔갑**시켜
상태기계가 "30초 뒤 재시도"로 읽었다. 영원히.

**재발방지 룰 셋.**
① **워치/폰의 네트워크 I/O 는 전용 워커 스레드에서만.** `HandlerThread("vg-collector")` 로
   교체했다. 센서 콜백은 메인에서 오므로 `CollectorEngine` 의 진입점을 `@Synchronized` 로 묶었다.
② **`runCatching`·`try/catch` 로 실패를 상수로 바꿀 때는 반드시 사유를 로그에 남긴다.**
   외부 리뷰가 INTERNET 누락 건에서 같은 구조를 지적했는데(그때는 SecurityException),
   **권한을 고쳐도 삼키는 구조가 남아 있어 다음 예외에서 똑같이 당했다.** 권한이 아니라
   **삼키는 코드가 결함**이었다. `onFailure { Log.w(...) }` + 비2xx 응답 본문 로깅을 추가했다.
③ **진단 순서** — 관제에 안 보이면 ⓐ 서비스 살아있나(`dumpsys activity services`)
   ⓑ source 화이트리스트 통과하나 ⓒ 권한 부여됐나(`dumpsys package … granted=true`)
   ⓓ 기기가 인터넷 되나(`ping`) ⓔ **그래도 모르면 삼킨 예외를 드러내는 빌드를 올린다.**
   이번엔 ⓐ~ⓓ 가 전부 정상이라 ⓔ 에서만 답이 나오는 상황이었다.

## R-14 · 관제 신선도 60초 = 워치 flush 60초 — 정상 수집이 "연결끊김"으로 보인다

`DemoDashboard.tsx:675` 의 `STALE_MS = 60_000` 과 `CollectorService.FLUSH_INTERVAL_MS` 가 같다.
게다가 [[R-12]] 의 센서 배치 전달이 겹치면 실제 도착 간격은 수 분까지 벌어진다.
iOS 는 5초 배치라 이 문제가 없었다 — **워치 단독 60초 설계가 만든 새 상황이다.**

⟹ **지금 숫자를 바꾸지 않는다.** 실측 ⑥(밤샘 배터리)과 ⑦(도착 간격 분포)이 나온 뒤
3단계에서 정한다. 후보 = ⓐ flush 를 30초로 ⓑ 관제 STALE_MS 를 단말별로 분기
ⓒ heartbeat 만 짧은 주기로 따로 보냄(iOS 하트비트와 같은 수법). 근거 없이 고르지 않는다.

## R-15 · Compose 전환 — R-05 의 보류 근거가 사라졌다 (08-25)

R-05 는 *"Compose 컴파일러 버전 맞춤 실패가 SDK 링크 검증과 무관한 잡음"* 이라 순정 View 를 썼다.
**그 전제가 두 가지로 무너졌다.**

① **Kotlin 2.0+ 부터 Compose 컴파일러는 Kotlin 과 같은 버전의 플러그인**이다
   (`org.jetbrains.kotlin.plugin.compose` version = Kotlin 2.3.20). 맞출 버전이 애초에 없다.
② **UI 반복이 실제 병목이 됐다.** 08-24 저녁 워치 무선 연결이 절전으로 계속 끊겨 화면 한 번
   확인에 10~15분이 들었다. 미리보기는 그 왕복을 0으로 만든다.

**구조 — 화면을 순수 함수로 짠다.** `ProbeScreen(state, actions)` 가 서비스·센서를 모르고
`ProbeUiState` 만 받는다. 그래서 `@Preview` 가 실기 없이 그대로 렌더한다.
미리보기 4종(대기 · 수집중 · **큐 적체** · 결과출력)을 두었다 — 상태마다 색과 줄바꿈이 달라
한 장으로는 못 본다. 큐 적체 미리보기는 08-25 서버 DB 장애 상황을 그대로 재현한 것이다.

**함정 둘.**
- `WearDevices`(LARGE_ROUND 등)는 `androidx.wear:wear-tooling-preview` 에 있고 **전이 의존으로는
  컴파일 경로에 안 들어온다.** 명시 선언해야 한다.
- `ComponentActivity` 는 `onRequestPermissionsResult` 를 그 시그니처로 안 받는다 —
  `registerForActivityResult(RequestMultiplePermissions())` 가 정석 경로다.

⚠ **APK 가 9.8MB → 27MB 로 커졌다**(Compose 런타임). 디버그 빌드 기준이고 R8 이 붙는 릴리스에서
다시 재는 것이 맞다. 워치 저장공간·설치 시간에 영향이 있으니 3단계에서 확인한다.

## R-16 · 제품 화면은 관제웹과 **같은 임계·같은 낱말**을 쓴다 (08-25)

작업자 화면이 "정상" 이라는데 관제는 "주의" 로 보이면 현장에서 신뢰가 무너진다. 그래서
`core/Severity.kt` 가 `packages/analyzers/src/thresholds.ts` · `dashboard-web/lib/severity.ts` 의
값을 그대로 갖는다 — 4단계(대기·정상·주의·위험)와 라벨까지 동일.

```
심박   danger ≥130 · ≤40   caution 110~129 · 41~50
SpO₂   danger <88          caution <92
심부온 danger ≥38.0        caution ≥37.5   (손목온 + 0.5 보정)
무동작 붕괴 후보 ≥90초
```

⚠ **손으로 옮긴 사본이다**([[L-106]] ①). 서버가 임계를 바꾸면 여기도 갈린다.
⟹ 3단계 F 에서 **두 파일의 숫자를 대조하는 가드**를 세운다. 지금은 시험(SeverityTest)이
경계마다 못을 박아 최소한 조용히 바뀌지는 않게 했다.

**화면 규칙 — iOS ContentView 에서 그대로 가져온 것 셋.**
① **0 건은 생략** — 측정 안 된 값은 줄 자체가 없다. 빈 자리를 0 으로 채우면 "측정했는데 0" 이 된다.
② **[시작]에 확인 없음, [중지]에만 확인** — 켜는 쪽 오탭은 손해가 없고, 끄는 쪽은 사람이
   알아챌 때까지 수집이 멎는다(iOS 08-20 무의도 정지 사고).
③ **값의 나이를 함께 적는다** — SpO₂ 는 기회 측정이라 "97%" 만으로는 언제 잰 값인지 모른다.

**워치8 우위를 화면에 반영한 것** — 주변 온도(`ambientTempC`)를 체온 줄에 얹었다.
애플워치에 없는 신호이고, WBGT 환경축을 작업자별로 쪼개는 재료다([[R-03]]).

**진단 화면은 숨긴다.** 실측 버튼 8개가 작업자 화면에 서면 안 된다 — 하단 "진단" 칩으로 들어간다.

## R-17 · Material 3 Expressive 원형 게이지 — 숫자 대신 "호가 어디까지 찼나" (08-25)

사용자가 Wear OS 6 워치페이스 이미지를 제시하며 그 언어로 가자고 했다. 채택한 이유는
미감이 아니라 **판정 속도**다.

> "SpO₂ 97%" 는 작업자에게 **숫자**다 — 97 이 안전한지 스스로 판단해야 한다.
> 호 게이지는 **판단을 대신한다** — 얼마나 찼는지·무슨 색인지가 곧 답이다.
> 장갑 낀 손으로 1초 보는 상황에서 이 차이가 크다.

**버블 3종 = SpO₂ · 심부체온 · 무동작** (사용자 결정). 기준 = **위험 판정에 직접 쓰이는 값**.
걸음·주변온은 뺐다 — 위험도와 직접 관련이 낮아 화면 자리를 차지할 값이 아니다.
(주변온은 여전히 수집·전송한다. 화면에 없을 뿐 WBGT 재료로 서버가 쓴다.)

**호의 범위를 명시적으로 준다** — `gaugeFraction(value, min, max)`.
```
SpO₂    85 ~ 100      (위험선 88 이 호의 20% 지점)
심부온  36.0 ~ 38.5   (위험선 38.0 이 80% 지점)
무동작  0 ~ 90초      (붕괴 후보선에서 호가 가득 찬다 — 차오르는 것이 곧 경고)
```
값이 없으면 **호도 비고 숫자는 `--`** — 0 으로 채우지 않는다(전 화면 공통 규칙).

**공식 가이드라인 위반 5건을 이 참에 고쳤다.**
① TimeText 추가(워치 표준 — 시계 보려고 앱을 나가지 않게)
② **절대 dp → 화면 비율**(`widthDp * 0.12f`) — 원형 가장자리 잘림 방지 공식 규칙
③ 225dp 브레이크포인트 분기(40mm/44mm)
④ 터치 타겟 — M3 `Button` 기본이 48dp 이상
⑤ `@Preview(fontScale = 1.24f)` 로 접근성 글꼴 확대 검증

**라이브러리 = M2.5 → M3 1.5.0.** `CircularProgressIndicator(startAngle/endAngle)` 가 M3 에만
있다. Chip → Button, ScalingLazyColumn → TransformingLazyColumn 으로 함께 옮겼다.

⚠ **APK 27MB → 44MB.** 디버그 기준이고 R8 전이다. 워치 저장공간에 영향이 있으니
릴리스 빌드에서 다시 재고, 넘치면 baseline profile·리소스 축소를 검토한다(3단계).

## R-18 · 화면이 "수집 중" 인데 값이 `--` 였다 — 표시 경로와 수집 경로가 갈라져 있었다 (08-25)

본수집을 켰는데 화면 심박이 `--` 로 남았다. 수집·업로드는 정상이었다(292건 전송 성공).

**원인** — 화면이 `HrForegroundService.lastBpm`(실측 ④ 진단용)만 읽고, 실제로 도는
`CollectorService` 는 안 봤다. 서비스가 둘인데 화면이 하나만 본 것이다.

**수리** — `CollectorEngine` 에 표시용 스냅숏(bpm·spo2·피부온·주변온·무동작·표본수)을 두고
`CollectorService.liveEngine` 으로 노출, 화면이 3초 폴링으로 **둘 중 실제로 도는 쪽**을 읽는다.

★ **표시 경로는 업로드 경로와 분리한다** — iOS `PhoneReceiver` 의 그 규칙 그대로다.
스냅숏에서 무엇을 하든 서버로 가는 값은 안 변한다. 반대로 화면이 얼어도 수집은 계속된다.

**재발방지 룰.** 서비스가 둘 이상이면 **화면이 무엇을 보는지 한 줄로 적는다.**
"수집 중" 이라는 상태 표시와 값의 출처가 다르면, 화면은 거짓말을 하면서도 초록불이다.

## R-19 · 베젤은 원형 워치에서 본문을 밀지 않는 유일한 공간이다 (08-25)

사용자가 갤럭시워치 워치페이스를 제시하며 *"애플워치와 다르게 원형 프레임"* 이라고 짚었다.
정확한 지적이다 — 사각 화면 사고로 짜면 원형에서 네 귀퉁이가 통째로 죽는다.

**채택 = 베젤 눈금(tick) 인디케이터.** 화면 전체에 `Canvas` 로 겹쳐 그리므로 본문 레이아웃을
한 픽셀도 밀지 않는다. 연속 호가 아니라 **눈금**인 이유는 개수가 곧 눈금이라 흘끗 봐도
"몇 칸 남았나" 가 읽히기 때문이다(참조 워치페이스도 같은 선택).

**무엇을 올리나 — 본문 버블과 겹치지 않는 값만.** 같은 값을 두 곳에 그리면 화면이 넓어
보일 뿐 정보량은 그대로다.
```
우상 -70°~-10°   심박이 안전대(40~130) 어디인가 — 본문은 숫자, 베젤은 위치
우하  20°~ 80°   배터리 (15% 이하 빨강 — 상태줄과 같은 경계)
좌하 100°~160°   전송 — 큐 0 이면 가득, 쌓일수록 줄고 주황으로 간다
좌상             비운다 — TimeText 가 12시에 앉아 눈금과 부딪힌다
```

**함정 둘.**
① 눈금을 화면 **가장자리에 붙이면 원형 마스크에 잘린다** — `inset = 0.93` 으로 안쪽에 그린다.
② 베젤이 가장자리를 쓰므로 **본문 여백을 늘려야 한다**(12% → 15.5%). 안 늘리면 숫자와
   눈금이 겹쳐 둘 다 안 읽힌다.

시험은 화면을 띄우지 않고 구성만 검사한다 — 구획이 서로 겹치지 않는지, 값이 없을 때
0 으로 그리지 않는지. **각도 겹침은 눈으로 못 잡는다**(포개져도 그려지기는 한다).

## R-20 · 시작 버튼을 없앤다 — 착용이 곧 시작이다 (08-25 사용자 결정)

**증상** — 화면에 시작 버튼이 안 보였다. **원인은 코드로 확정**: 스크롤 없는 `Column` 에
요소 7개(배지·주값·범위·차트·버블·상태·버튼)를 넣어 마지막 버튼이 화면 밖으로 밀렸다.

여백을 줄여 우겨넣는 대신 **버튼 자체를 없앴다.** 근거는 기기 실측이다 —
```
offbody_detect  Wakeup | type: android.sensor.low_latency_offbody_detect(34) | perm: n/a
```
★ **권한 불필요(perm: n/a) · wake-up** — 화면이 꺼져도 착용 변화가 온다.
그래서 "차면 시작, 벗으면 중지" 가 센서 하나로 성립한다.

**설계 셋.**
① **서비스는 벗어도 죽지 않는다** — 센서만 뗀다. 다시 차면 사람 개입 없이 재개된다.
   `stopSelf` 를 넣으면 재개 수단이 사라진다(시험이 이걸 막는다).
② **벗어도 큐를 지우지 않는다** — 미전송분은 다시 찼을 때 함께 올라간다.
③ **센서가 없는 기기면 항상 착용으로 본다** — 수집이 멎는 쪽보다 안전한 기본값.

⟹ iOS 의 [시작]/[중지] 오탭 사고([[R-16]] ②)가 **구조적으로 불가능**해진다.
   `watch-collect-control` 트랙이 워치 버튼을 없애 얻으려던 것과 같은 결론에 다른 길로 닿았다.

**진단 화면 진입** — 화면 아무 곳이나 **길게 누른다**. 작업자 화면에 진단 버튼을 두지 않는다.

## R-21 · 게이지 축은 임계가 아니라 **표시용**이다 — 둘을 섞으면 정상이 안 보인다

체온 게이지가 36.0~38.5 였다. 계산이 문제를 드러냈다 —
```
36.2℃ →  8%  (정상인데 거의 안 참)
39·40·41℃ → 전부 100%  (고열의 심각도가 뭉개짐)
```
축을 임상 저체온~고열(**35.0~40.0**)로 넓혔다. 정상 36.2=24% · 주의 37.5=50% ·
위험 38.0=60% · 40℃=100% — **위험선을 넘어도 남은 여유가 보인다.**

★ **축을 넓혀도 판정 임계는 안 움직인다**(37.5 주의 · 38.0 위험). 시험이 이 분리를 못 박는다.
같은 방식으로 SpO₂(85~100)·HRV(0~100ms)도 계산해 봤고 둘은 적절해 손대지 않았다.

## R-22 · 벗음 실측이 결함 3건을 드러냈다 — 중지는 "멈춤" 이 아니라 "비움" 이어야 한다

R-20 의 착용 자동수집을 실기로 시험하니 **감지는 정상**인데(`벗음 감지 — 수집 중지`)
화면이 거짓말을 하고 있었다.

```
벗은 뒤 로그: skin=37.30 core=37.80 still=9.5→24.5→39.6 collecting=true
```

**결함 셋, 전부 같은 뿌리** — `stop()` 이 센서만 떼고 상태를 안 비웠다.

| # | 증상 | 위험 |
|---|---|---|
| ① | 체온 37.8℃ 가 화면에 잔존 | 측정 끝난 값이 현재값으로 읽힌다(iOS `gateStaleVitals` 가 막는 그 사고) |
| ② | 무동작이 9.5→39.6 계속 증가 | **벗어둔 워치가 "쓰러져 있는 작업자" 로 보인다** — 가장 위험 |
| ③ | `collecting=true` 유지 | 관제·작업자 모두 수집 중으로 오독 |

**수리 셋.**
① `stop()` 이 표시용 스냅숏(bpm·spo2·피부온·주변온·HRV)을 **null 로 비운다.**
② `motionStopped` 게이트 — 벗으면 `stillSecNow()` 가 null 을 낸다(0 이 아니다).
③ `running`(서비스 생존)과 `collecting`(실제 수집)을 **분리**. 화면은 후자를 본다.

⚠ **큐와 IBI 창은 비우지 않는다** — 미전송분은 재착용 시 함께 올라가고, HRV 는 이어서 쌓인다.
시험이 이 경계를 못 박는다(`ibiWindow.clear` 가 stop 에 들어오면 빨간불).

**실측 확인** — 벗은 상태에서 `bpm=null spo2=null skin=null still=null collecting=false`.

⟹ 교훈 한 줄. **수집을 멈출 때 "센서를 떼는 것" 과 "값을 비우는 것" 은 다른 일이다.**
   전자만 하면 화면은 계속 옛 값을 현재값으로 말한다.

## R-23 · HRV 는 필터가 아니라 **표본 밀도**가 문제였다 — 문턱 30 으로 닫는다 (08-25 A안)

264ms → 필터 2단(연속성·심박정합) → 여전히 21.9~63.5ms 요동. **100초 실측이 원인을 확정했다.**

```
필터 통과:  입력68 → 상태59 → 범위59 → 심박9 → 연속7   (84% 폐기)
결과:      같은 사람 1분 안에 21.9 / 37.3 / 63.5ms
```

★ **필터는 정상 작동했다. 오염원은 센서다** — 손목 광학 센서가 움직일 때 박동을 자주 놓치고,
놓친 박동이 합쳐진 IBI 가 status=0(정상)으로 온다. 남는 유효 표본이 6~23개로 들쭉날쭉해
SDNN 이 안정될 수 없다. **임상 SDNN 은 연속 5분 기록을 전제**하는데 우리는 조각을 모으는 처지다.

⟹ **표시 문턱 `MIN_SAMPLES` 5 → 30.** 30 미만이면 `--`. 틀린 숫자보다 "못 쟀다" 가 낫다.
   정지 상태로 오래 착용하면 표본이 모여 값이 뜬다.

**시험 설계에서 배운 것** — 문턱을 올리자 기존 필터 시험 4건이 깨졌다. **표본 수를 늘려
우회하고 싶은 유혹**이 있었지만 그러면 "무엇을 거르는지" 가 시험에서 사라진다.
⟹ 필터 시험은 `continuous()`·`hrConsistent()` 를 **직접** 부르고, 문턱은 별도 시험이 맡는다.
   한 시험이 두 가지를 검증하면 하나가 바뀔 때 나머지가 인질이 된다.

⚠ **30 은 표시 문턱이지 임상 기준이 아니다.** 실사용에서 너무 자주 비면 낮춘다 —
   판정 근거는 "값이 뜨는 빈도" 이고, 사용자가 며칠 차 보고 정한다.

```
        (4분 벗어둠)
15:01  착용후 602초   피부온 38.24  주변 34.79   ← 재착용 10분 후
```

⟹ 삼성 온도 센서는 기기 표면 근처에 있어 **자체 발열을 피부온으로 읽는다.**

③ 온도 로그 밀도 완화 — 실험 때 필요했던 매 표본 로깅을 5개당 1개로.

ⓑ 착용 초기값 대비 상대 변화. **재측정 전에는 정하지 않는다**([[L-107]]).

## R-27 · 상세는 숫자가 아니라 **추이**를 보여준다 — 이력은 워치가 직접 든다 (08-25 사용자 지시)

**지시.** "스와이프하여 각 생체 데이터를 차트 및 시각적인 자료로 추이를 볼 수 있도록 —

R-26 에서 붙인 상세 4장은 **숫자 나열**이었다. 요약 화면이 이미 같은 숫자를 보여주므로
스와이프의 대가가 없었다. 상세의 존재 이유를 "지금 값" 이 아니라 **"어디서 와서 어디로
가는가"** 로 바꾼다.

**착수 전 실측 — 이력을 가진 지표가 하나뿐이었다.**
심박만 `timeline`(5분)이 있었고 SpO₂·피부온·주변온·스트레스는 **마지막 값만** 들고 있었다.
차트를 붙이기 전에 이력부터 만들어야 했다.

**① 이력은 워치 메모리에 둔다 — 서버 조회가 아니라.**
서버는 295,076건을 갖고 있지만 그걸 조회하면 LTE 왕복이 늘고 08-25 에 줄인 발열(R-25)이
되돌아온다. 워치 화면의 목적은 "지금 오르고 있나" 이지 하루치 회고가 아니다 —
회고는 관제웹이 한다. 앱 재시작 시 비워지는 것을 **의도된 성질**로 받아들인다.

**② 창은 지표의 수집 주기에 맞춘다.** 심박 15분 · SpO₂ 60분(5분 주기라 짧으면 점이 두어 개) ·
체온 30분(발열 판별에 필요) · 스트레스 30분.

**③ ⚠ 상한(240점)만 두면 창이 조용히 짧아진다.**
심박이 1초에 하나 들어오면 240점이 4분 만에 차고, "15분" 이라 적힌 차트가 실제로는
**최근 4분**만 보여준다. 들어오는 속도를 모르는 채로 창을 지키려면 간격을 코드가 강제해야
한다 — `minGapMs = windowMs / maxPoints`. 실기 케이던스를 재지 않고도 성립하는 성질이다.

**④ 솎을 때 평균을 내지 않는다 — 가장 튀는 값을 남긴다.**
평균은 임계를 넘긴 순간을 지운다. 안전 데이터에서 가장 하면 안 되는 일이다.
안정 심박 80 사이에 155 가 한 번 섞이면 그 점이 살아남아야 한다(시험으로 고정).
⚠ 이때 "튐" 의 기준은 **간격의 첫 값**이어야 한다. 대표값 자신을 기준으로 두면 비교가
자기 자신과의 거리(=0)가 되어 방금 살린 봉우리를 다음 평범한 표본이 곧바로 밀어낸다.

**⑤ 없는 데이터를 그리지 않는다.** 두 점 사이가 `maxGapMs` 보다 벌어지면 잇지 않는다.
SpO₂ 처럼 성긴 지표에서 선을 이으면 **측정하지 않은 구간을 측정한 것처럼** 보이게 만든다.
외톨이 점은 점으로 남긴다.

**⑥ 세로축은 표본에 맞춰 늘리되 임계선을 함께 담는다.** 근무 심박 90~100 을 40~130 고정축에

**⑦ 체온은 주변온을 같은 축에 겹친다 — 이것이 이 페이지의 존재 이유다.**
두 선이 **나란히** 오르면 기기 발열, 피부온만 오르면 진짜 체온이다(R-25 판별법).
축을 따로 주면 비교 자체가 성립하지 않는다. 작업자가 스스로 구별할 수 있게 한다.

**부수.** `HeartChart` 는 `TrendChart` 로 대체돼 호출부가 0이 되어 지웠다(내 변경이 만든 사체).

## R-28 · 워치는 단독이므로 서명을 폰과 맞출 이유가 없다 — 릴리스 변종을 세웠다 (08-26 사용자 결정)

**갤럭시는 워밍업이 애플워치의 2배 걸린다.** 심박 도착 간격 중앙값 **120.7초**(실측 · p75 129.4 ·

### 원인의 일부 확정 — `fs = 50.0` 하드코딩이 **창을 자른다**

이 워치의 IMU 지원 주기는 `119.99/n` 계열이라 **50Hz 가 없다**. 20,000µs 를 요청하면
**59.6Hz** 가 온다(실측 8회: 59.5~59.8, 표본기준=도착기준).

```kotlin
ImuWindowLogger: capacity = ((2.0 + 10.0 + 1.0) * fs).toInt()   // fs=50 → 650
```
59.6Hz 로 13초를 담으려면 **775표본**이 필요한데 버퍼는 **650**이다. 링버퍼가 넘쳐 앞부터 버린다.
```
설계  충격 전 2.0초 + 후 10.0초 = 12초
실제  충격 전 0.9초 + 후 10.0초 = 10.9초   ← 판정 로그의 samples=649 가 이 값이다
```
**충격 이전 구간이 절반 이하로 잘린다.** 게다가 `slice(…, 3.0)` 이 `Int(3.0 * FS)` = 150표본을
충격 중심으로 잡으려는데 앞이 모자라 **중심이 안 맞는다**. 주파수 피처도 `fs=50` 으로 계산돼
실제와 19% 어긋난다. `nonrecoveryProb` 만 실측 fs 를 넘긴다(`samples.size / spanSec`).

⚠ **자가검증은 이 축을 통과시킨다** — 정답지가 `fs=50.0` 고정 입력이라서다.
⟹ **자가검증 6/6 은 "탑재 성공" 을 말하지 "판정이 맞다" 를 말하지 않는다.**

① 호스트에서 ~50Hz 데시메이션(필터 없으면 에일리어싱) ② 모듈이 실측 fs 를 쓰도록

### 세 갈래

### ⚠ 착용 로그는 방향이 뒤집혀 있다 — 없는 것이 정상이다

`reviveHrIfStalled` 는 `if (!sensing) return` 으로 조기반환한다(`:311`). 그래서 셋째 갈래는
"벗고 있었나" 를 물어야 하는데, **`착용 감지` 로그를 찾는 방식은 틀린다.**

```
OffBodySource.kt:31   var worn: Boolean = true      기본값이 착용이다
              :55   if (nowWorn != worn) { … }     전이일 때만 로그·콜백
              :41   센서 없으면 경고 한 줄 찍고 return (worn=true 유지)
```

계속 차고 있으면 센서가 `1.0` 을 올려도 전이가 아니라 **로그가 한 줄도 안 남는다.**
`착용 감지` 가 없다고 "안 찼다" 로 읽으면 정확히 정상 착용 상태를 오판한다.
**양성 증거는 `벗음 감지` 쪽이다**(`:57` · 태그 `VgOffBody`).

| 서비스 시작 이후 `VgOffBody` | 뜻 |
|---|---|
| `벗음 감지 — 수집 중지` 가 있고 뒤에 `착용 감지` 가 없다 | `sensing=false` — 워치독이 조용한 것이 **정상**. 결함 아님 |
| `벗음 감지` 가 아예 없다 | `sensing=true` 였다 → 워치독이 떴어야 한다 → **제3갈래가 진짜다** |
| 시작 시 `착용 감지 센서 없음` 이 찍혀 있다 | `worn` 이 상수 true — 오판할 물건이 없다. 위 둘째 줄과 같게 읽는다 |

셋째 줄 덕분에 "`OffBodySource` 가 오판했을 가능성" 은 **시작 로그 한 줄로 먼저 배제된다.**

### ⚠ 시작 경계 — 표의 유일한 빈틈이고, 아직 안 쟀다

기본값이 착용이라 `CollectorService:206` 이 **낙관적으로 먼저 켠다.**

```
:205  offBody.start { wornNow -> if (wornNow) beginSensing() else endSensing() }
:206  if (offBody.worn) beginSensing()      // worn 기본값 true → 무조건 켠다
```

⟹ **벗은 채로 서비스가 시작되면** `sensing=true` 로 출발하고, 센서 이벤트가 와야 꺼진다.
그 이벤트가 안 오면 워치독이 계속 돌아 *재구독 로그는 있는데 심박은 없는* 상태가 되고,
이는 겉보기가 **ⓐ 와 똑같다**. 표 둘째 줄이 무너지는 유일한 경로다.

`-50` 이 보탠 근거 — `TYPE_LOW_LATENCY_OFFBODY_DETECT` 는 **on-change 센서**라
`registerListener` 직후 현재 값을 한 번 보고하므로, 벗은 채 시작해도 첫 이벤트가 `0.0` 으로
들어와 `nowWorn(false) != worn(true)` 가 성립하고 `벗음 감지` 가 뜬다 — 즉 경계가 닫힌다.

⚠ **이것은 Android 플랫폼 규약이고 이 기기에서 실측한 적이 없다.** 삼성 벤더 HAL 이 등록 직후
보고하는지는 기기마다 갈리는 부류다. **위 낙관적 기본값 때문에 이 성질이 장식이 아니라 하중을
받는다** — 실측 때 한 줄로 확인한다. **벗은 상태에서 서비스를 재시작해
`착용 감지 시작` 직후 1초 안에 `벗음 감지` 가 뜨는가.** 안 뜨면 표 둘째 줄은 못 쓰고,
`sensing` 을 로그로 직접 노출하는 수밖에 없다.

⚠⚠ **정정(08-28 · `-50` 지적).** 처음에 나는 *"`ts` 는 흩어져 있고 `received_at` 은 한 점이니

섀도**이고, 생체 행은 앞뒤 **2건뿐**이며 둘 다 **지연 1~3초로 즉시 적재**됐다. 두 모집단을 한

```

ts 15:21:00 → rx 15:21:01   지연 1초
ts 15:29:37 → rx 15:29:40   지연 3초
        ↑ 8.6분 사이에 만들어진 생체 행 0건 · 깨어난 뒤에도 **몰아치기 없이 1건**
```

**옳은 해석 — flush 만 멈춘 것이 아니라 `tick` 전체가 정지했다.** `engine.flush(now)` 도
`pipeline.flushOnce()` 도 같은 `tick` 안에 있고(`:275`·`:277`), `postDelayed`/`uptimeMillis` 는
절전에 함께 선다(`:248`). 섀도만 흩어진 `ts` 를 갖는 이유는 **IMU 스레드가 만들기 때문**이다.

★ **이 차이가 처방을 가른다.**

| | 뜻 | 복구 |
|---|---|---|
| flush 만 정지(내 오독) | 잰 것이 큐에 쌓였다 | 깨어나면 밀린 것이 다 온다 |
| **tick 전체 정지(사실)** | 그 8.6분은 **표본이 만들어지지 않았다** | **영영 없다 — 진짜 감시 공백** |

**증거 하나 더 — 깨어난 행의 심박은 새 값이다.**

15:21 의 낡은 값을 들고 온 것이 아니다. 즉 센서는 깨자마자 곧바로 값을 냈고, **재구독 없이
복구**됐다. 그리고 뒤이은 몰아치기가 **없다**(행 1건). ⟹ **그 8.6분은 지연이 아니라 소실이다.**

⚠ **안전 함의 — 3단계(실경보) 전에 반드시 푼다.** 낙상 판정은 IMU 스레드라 정지 중에도 돌지만

- 증상(사용자) — 손목 움직임에 따라 앱 화면이 돌았다. 실측 = 기기 자동회전 켜짐(`accelerometer_rotation=1`) + `MainActivity` 에 방향 미지정 → 센서 추종. 착용 중 `mRotation=ROTATION_180`(뒤집힘).
- 처방 = `android:screenOrientation="nosensor"`.
  ⚠ **`portrait` 가 아니다.** portrait 는 회전 0 으로 못박아 반대 손목·다른 버튼 방향 사용자의 **기기 기본 방향까지 뒤집는다.** nosensor 는 기본 방향을 그대로 쓰고 센서만 무시한다.
- ⚠ **초록불을 믿지 않고 눈으로 확인했다** — 매니페스트(`screenOrientation=5`)·dumpsys(`SCREEN_ORIENTATION_NOSENSOR` · 출처 MainActivity)가 다 초록이어도 이 디스플레이는 `mIgnoreOrientationRequest=true` 라 **시스템이 앱 요청을 무시할 여지**가 있었다([[L-118]] 계열: 초록불이 답한 질문 ≠ 묻고 싶던 질문). 사용자 실기 확인으로 **09-01 수리 확정**.
- 폴백(쓰지 않음) = 기기 자동회전 끄기(`settings put system accelerometer_rotation 0`). 앱 밖으로 새고 초기화하면 사라져 차선이다.

## 09-01 · 위치 — 위성을 되살린다(GPS 주력 + 네트워크 폴백)
- **발단** — 배터리 해부에서 나온 역설. `gnss 0.00269 mAh · 누적 가동 198ms / 8시간 26분` — **위성이 사실상 한 번도 안 돌았다.** 위치는 전부 네트워크 측위였다.
- **원인은 환경이 아니라 코드였다.** `LocationManager.requestLocationUpdates(provider, 60_000, 0f, this)` — 구형 호출에는 **정확도 요구 인자가 없다.** 요구가 없으니 시스템이 제일 싼 것(기지국·wifi)만 내준다. 08-26 에 `GPS_PROVIDER` → `FUSED` 로 옮긴 것이 실내 fix 0건을 고쳤지만, 그 대가로 **위성이 영영 안 켜졌다.**
- **피해 실측(24시간).**
  ```
  장우진  표본 946 → 좌표 244(26%) → 오차 50m 이하 78  =  8.2%
  김태곤  표본 473 → 좌표  85(18%) → 오차 50m 이하 44  =  9.3%
  평균 오차 82.6m · 최대 400m
  ```
  구획 이탈 판정은 `fixUsableForJudgment`(>50m 버림)를 통과한 것만 쓰므로 **위치가 전체 표본의 8~9%로만 돌고 있었다.**
- **처방** — 위성과 폴백을 **둘 다** 구독하고, `pickFix` 가 **신선한 것 중 가장 정확한 것**을 고른다.
  ★ "위성이면 무조건 우선" 이 아니다 — 하늘이 가리면 위성도 수백 m 로 튄다. 정확도로 고르면 실외에서는 자연히 위성이 이기고(±5~15m ↔ ±80~400m) 실내에서는 폴백이 이긴다. **의도한 우선순위가 규칙 하나에서 나온다.**
  ⚠ `Location.accuracy` 는 값이 없으면 **0** 을 낸다 — 그대로 비교하면 **품질 미상이 항상 이긴다.** 0 이하는 최후순위로 밀되 단독 후보면 쓴다.
- **배터리 — 깨우기 횟수는 안 늘어난다.** 위성 연속 가동은 이 기기 전력 모델로 ~49 mAh/h(총 소모 51 과 맞먹는다)지만, 위치를 찾으려는 깨우기(8시간 433회)는 **이미 내고 있던 비용**이고 위성은 그 깨어 있는 시간 안에서 fix 를 뜬다. 실측 증가분은 fix 소요 시간이 정한다(핫스타트 5초/60초면 +4 mAh/h·수명 9.3→8.6h, 실내 실패로 20초까지 끌면 +16·7.1h).
- **가드 교체** — 종전 `assertFalse(src.contains("requestLocationUpdates(LocationManager.GPS_PROVIDER"))` 는 "위성 단독으로 되돌아가지 마라" 의 **대리 지표**였다. 위성을 되살리는 지금 그 문구는 불변식을 못 지킨다(리터럴이 없어도 폴백을 잃을 수 있다). 진짜 불변식 둘(`subscribe(fallback)` 생존 · 위성 구독 존재)을 직접 단언하도록 바꿨다.
- **남은 것** — ⓐ 실기 설치·실외 위성 fix 확인(설치 시도 3회 모두 충전 거치 중 전송 끊김) ⓑ 실내에서 위성이 **실패하며 켜져 있는 시간**의 비용 실측 → 필요하면 "이동 중·실외에서만" 게이트 추가 ⓒ 판정 게이트(서버)와의 영향 조율.

### 09-01 · 위성 상시 구독의 대가 — 단발 요청 + 백오프로 전환
- **실측이 전제를 깼다.** "60초 주기로 요청하면 OS 가 듀티 사이클을 돈다" 는 틀렸다. 구독이 걸려 있으면 **GNSS 가 계속 켜져 있다.**
  ```
  실내(fix 0건)   GNSS 가동 9분26초 / 배터리 10분57초 = 86%
  소모율          51 → 87.8 mAh/h   (adb 없는 깨끗한 창 17:00~17:46)
  수명            9.3 → 5.4시간
  정확도          82.6m → 13.4m · 판정 가능 32% → 100%   ← 얻은 것
  ```
  정확도는 확실히 얻었지만 이 비용으로는 현장에 못 쓴다.
- ⚠ **측정 도구를 잘못 읽은 것도 기록해 둔다.** `dumpsys location` 의 `total/active/foreground duration` 은 **GNSS 하드웨어 가동 시간이 아니라 요청이 등록돼 있던 시간**이다. 20초 사이에 25초가 늘어난 걸 보고 알았다. **하드웨어 가동은 `dumpsys batterystats` 의 `gnss:` 줄로만 잰다.**
- **전환** — 폴백은 상시 구독 그대로, 위성은 tick(120초)마다 `getCurrentLocation` **단발**. 한 번 재고 플랫폼이 GNSS 를 끈다.
- **코드로 확인한 것(추론 금지 · 사용자 지시).**
  | 전제 | 확인 방법 | 결과 |
  |---|---|---|
  | `getCurrentLocation` 이 minSdk 에서 되나 | `platforms/android-37.0/data/api-versions.xml` | 4인자형 **since=30** · minSdk 30 → 안전 (LocationRequest 오버로드는 31이라 회피) |
  | 걸음을 이동 신호로 쓸 수 있나 | `ActivitySource.kt:74` 주석 + 실기 로그 | **못 쓴다** — "이 워치는 구간형 걸음을 안 보냈다", 로그도 `걸음0건=0` |
  | 대체 이동 신호 | `MotionTracker.variabilityMg()` + DB `motion_var_mg` | 실내 착석·손동작 **1~78mg** · 실외 보행 **166~212mg** → 문턱 **100mg** |
  | tick 주기·스레드 | `CollectorService.FLUSH_INTERVAL_MS` | 120초 · 콜백은 수집 `handler` |
- **게이트** — 실패 1회는 다음 tick 에 바로 재시도(잠깐 처마 밑일 수 있다) · 2회 5분 · 3회 10분 · 4회 이상 15분 상한. **움직임(≥100mg)이 감지되면 백오프 즉시 해제** — 실내→실외 전이가 곧 그 순간이다.
- ⚠ **구현 중 스스로 만든 버그 하나.** `stop()` 에서 `handler.removeCallbacksAndMessages(null)` 로 타임아웃을 걷었는데, **그 handler 는 CollectorService 와 공유**라 tick 알람 콜백까지 지운다. 내가 건 Runnable 참조만 회수하도록 고치고 가드 테스트를 넣었다.
- ⚠ **가드가 너무 넓으면 자기 문서에 걸린다.** `removeCallbacksAndMessages` 낱말로 단언했더니 KDoc 설명 문장이 걸렸다(`uncommented` 는 `//` 만 걷는다). `handler.removeCallbacksAndMessages` 호출 형태로 좁혔다.
- **남은 것** — 실기 설치·실내/실외 소모 재측정(워치9이 핫스팟 밖이라 미완). 목표는 실내 87.8 → 55 mAh/h 안팎.
