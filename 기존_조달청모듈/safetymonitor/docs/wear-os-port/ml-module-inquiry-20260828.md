## ① 카운트다운 결말이 서버에서 **전량 무음 유실**된다 — 조치 요청 (한 줄)

### 실측

갤럭시 `danger` **64건 전부**가 결말 없이 남아 있다(`fall_prompt_outcome IS NULL`).
같은 기간 애플은 50건 중 40건이 결말을 남겼다 — `auto_escalated` 33 · `moved_cancelled` 4 · `dismissed` 3.

### 원인 (코드로 확정 · 추정 아님)

세 지점이 맞물린다.

1. **모듈** — `FallShadowReporter.outcome()` 이 만드는 결말 항목의 키는 다섯이다.
   `ts` · `fallCandidateId` · `fallUpdatePhase` · `fallPromptOutcome` · `fallPromptResponseSec`.
2. **서버** — `apps/dashboard-web/app/api/app/vital/store.ts` 의 `hasMonitorableSignal()` 관문(:234)이
   `fallUpdatePhase === "prompt_result"` 분기(:253)보다 **먼저** 있다. 그 관문이 인정하는 16개 필드
   (`heartRate`·`spo2`·…·`fallCandidate === true`) 중 결말 항목에 해당하는 것이 **하나도 없다**.
   ⟹ `addSample` 이 `{sample: null}` 로 조기 반환 → `updateFallCandidateState()` 가 **아예 안 불린다**.
   응답은 그대로 **201** 이고 `dropped` 카운터만 오르며 **경고 로그도 안 남는다** → 워치는 성공으로 알고 큐에서 지운다.
3. **애플은 왜 되나** — 폰 중계(`ios/Runner/VitalPipeline.swift:224-227`)가 `fcid` 가 있으면
   **`fallCandidate = true` 를 함께 붙인다.** 그 한 줄이 결말 항목을 관문에 통과시키고 있다.
   워치 Swift(`WatchStreamer.reportFallOutcome`)도 결말을 단독 항목으로 보내지만 중계가 표식을 채워준다.
   **Wear 는 중계가 없는 단독 업로드라 그 한 줄이 비어 있다.**

### 모듈 로직 자체는 정상이다 (기기 없이 확인)

`FallCountdownOutcomeTest`(JVM 단위시험 · 신규)로 `FallShadowReporter` 를 실기와 같은 59.6Hz 로 구동했다.

- 무반응 30초 → `auto_escalated` 항목 1건 방출 **✅**
- 지속 움직임 5초 → `moved_cancelled` 항목 1건 방출 **✅**  (2/2 통과)

즉 카운트다운·결말 생성은 정상이고, **잃는 자리는 전송 뒤 서버 관문**이다.

### 요청

`FallShadowReporter.outcome()` 의 항목에 **애플 중계와 같은 한 줄**을 넣어 주십시오.

```kotlin
item["fallCandidate"] = true   // 서버 hasMonitorableSignal 관문 통과용 — iOS VitalPipeline:226 과 동일
```

행이 새로 생기지는 않는다(서버가 `prompt_result` 를 UPDATE 로 처리하고 조기 반환한다). 표식만 통과시키면 된다.

> **대안** 서버 관문을 `prompt_result` 분기 **뒤로** 옮기는 방법도 있다. 그쪽이 구조적으로는 더 옳지만
> 프로덕션 배포가 걸리고, 애플이 이미 ①의 모양으로 돌고 있어 **모듈 한 줄이면 두 플랫폼이 같은 모양이 된다.**
> 판단은 ML 담당께 맡긴다. 서버 수정을 택하시면 그쪽은 우리가 처리한다.

## ② 갤럭시 센서가 **50Hz 를 못 준다** — 창이 잘리고 슬라이스가 어긋난다 — 조치 요청

### 실측

- 요청 `SENSOR_DELAY` = 20,000µs(50Hz) · **실측 59.5 ~ 59.7Hz** (3,000표본 기준 · 최대공백 41~106ms)
- 원인은 하드웨어 양자화다. SM-L355N IMU(lsm6dsv)는 **119.99/n Hz 만** 낸다 → 50Hz 요청이 59.995Hz 로 올림된다.
- 애플 대조군은 `effective_hz` **49.92 ~ 50.17** · `samples` 599~602 — 규약 그대로다.

### 결과 (모듈 상수로부터의 산술)

```
링버퍼 용량 = (preSec + postSec + 1.0) × fs = (2 + 10 + 1) × 50 = 650 표본
13초에 실제 필요 = 13 × 59.6                              = 775 표본   ← 125 부족
방출 시점 보유   = 650 표본 = 10.91초
⟹ 실제 창 = [충격 −0.91s, 충격 +10s] = 649 표본   (규약 = 전 2s + 후 10s)
⟹ impactIndex = 649 − 10×59.6 = 53                (규약 = 100)
```

DB 실측이 이 산술과 정확히 맞는다 — **136건 중 131건이 `samples=649` · `effective_hz=54.08`**
(나머지 5건은 절전 스로틀 구간의 150·168·335·467·512).

그래서 세 곳이 어긋난다.

| 슬라이스 | 규약 | 갤럭시 실제 |
|---|---|---|
| `work_veto` 3s | 충격 중심 ±1.5s (150표본 = 3.00초) | **[0, 150) = 충격 −0.89s ~ +1.63s** — 길이 2.52초, **중심이 아니다** |
| `impact` ±1s | 충격 중심 ±1.0s (100표본 = 2.00초) | [3, 103) = 충격 ±0.84s — 중심은 맞고 **길이가 1.68초** |
| `recovery` fs | 실효 표본율 | `samples/spanSec = 649/12 = 54.08` 을 넘긴다 — **실제 59.6 보다 10% 낮다** |

`work_veto` 의 비중심 잘림은 `_slice` 의 `maxOf(0, …)` 클램프에서 나온다(`center − n/2 = 53 − 75 = −22`).
학습 때는 `impactIndex = 100` 이라 클램프가 안 걸렸다.

### 통합 쪽에서 먼저 할 수 있는 것 (모듈 무수정)

`ImuWindowLogger` 의 `fs` 는 **생성자 인자**다. 통합 코드가 `ImuWindowLogger(fs = 60.0)` 으로 만들면

```
용량 = 13 × 60 = 780 ≥ 775   → 12초 창이 안 잘린다 (715표본)
impactIndex = 2 × 59.6 = 119 → work_veto·impact 슬라이스가 다시 중심에 온다
effective_hz = 715/12 = 59.6 → recovery 가 받는 fs 가 맞아진다
```

**남는 것은 슬라이스 길이 두 개뿐이다**(2.52초·1.68초). 그건 `FallMLPipeline.FS = 50.0` 상수와
`slice()` 가 표본수로 자르는 구조에서 나오므로 **모듈 쪽 판단이 필요하다.**

### 요청

1. `ImuWindowLogger(fs = 60.0)` 로 바꿔도 되는지 확인 부탁드린다(통합 쪽 1줄, 우리가 적용).
2. `slice()` 가 `sec × FS` **표본수 고정**인 것이 학습과 일치하는 계약인지, 아니면 **실효 fs 기준 초 단위**로
   잘라야 하는지 알려주십시오. 전자면 지금이 정답이고 ①만 고치면 된다.

## ④ 추론이 실패하면 안전 기본값이 **뒤집힌다** — 잠재 결함(현재 미발현)

`FallMLPipeline.prob()` 의 `catch (_: Exception) { 0.0 }` 은 recovery 경로에서
**추론 실패 → p = 0.0 → 0.35 미만 → `no_danger`** 가 된다. 주석이 선언한 의도(*"애매하면 위험"*)와 정반대다.
`assess()` 는 모델 **부재**만 `?: 1.0` 로 위험측 처리하고, **추론 예외**는 이 경로로 샌다.

- 애플 Swift 원본도 같은 성질이라 **포팅 결함이 아니다.**
- 우리는 모듈을 안 고치는 대신 **호스트에 지문 관측만** 달았다
  (`warnIfInferenceLooksDead` — `p_nonrecovery == 0.0` 이면 경고 로그, **판정은 그대로 둔다**).
- **실측 269건 중 `p_nonrecovery == 0.0` 은 양 플랫폼 모두 0건** — 아직 한 번도 안 났다.

발현 전에 방향만 정해 주시면 좋겠다. 위험측(`1.0`)으로 바꿀지, 판정을 내지 않고 건너뛸지.
