## ① 카운트다운 결말 전량 무음 유실 — **v6.1.2 에서 해결됨** (근거 기록)

갤럭시 `danger` **64건 전부**가 결말 없이 남아 있었다(`fall_prompt_outcome IS NULL`).
같은 기간 애플은 50건 중 40건이 결말을 남겼다 — `auto_escalated` 33 · `moved_cancelled` 4 · `dismissed` 3.

원인은 세 지점이 맞물린 것이었다.

1. **모듈** — `FallShadowReporter.outcome()` 의 항목 키가 다섯뿐(`ts`·`fallCandidateId`·`fallUpdatePhase`·`fallPromptOutcome`·`fallPromptResponseSec`).
2. **서버** — `hasMonitorableSignal()` 관문(`store.ts:234`)이 `prompt_result` 분기(`:253`)보다 **먼저** 있고,
   관문이 인정하는 16개 필드 중 결말 항목에 해당하는 것이 하나도 없다 → `{sample: null}` 조기 반환 →
   `updateFallCandidateState()` 가 아예 안 불린다. 응답은 **201**, `dropped` 카운터만 오르고 **로그도 안 남는다**.
3. **애플은 왜 됐나** — 폰 중계(`ios/Runner/VitalPipeline.swift:224-227`)가 `fcid` 가 있으면 `fallCandidate=true` 를 붙인다.

**모듈 로직 자체는 정상이었다.** `FallCountdownOutcomeTest`(JVM 단위시험 · 신규)로 `FallShadowReporter` 를
실기와 같은 59.6Hz 로 구동하니 무반응 30초 → `auto_escalated`, 지속 움직임 5초 → `moved_cancelled` 가
각각 1건씩 나온다(2/2). 잃는 자리는 **전송 뒤 서버 관문**이었다.

⟹ v6.1.2 의 `item["fallCandidate"] = true` 가 정확히 이 자리를 막는다. 확인 지표는 §⑦.

## ② 갤럭시 센서가 50Hz 를 못 준다 — **v6.1.3 에서 해결됨** (근거 기록 + 수치 정정 1건)

- 요청 `SENSOR_DELAY` = 20,000µs(50Hz) · **실측 59.5 ~ 59.7Hz** (센서 콜백 3,000표본 기준 · 최대공백 41~106ms)
- 원인은 하드웨어 양자화다. SM-L355N IMU(lsm6dsv)는 **119.99/n Hz 만** 낸다 → 50Hz 요청이 59.995Hz 로 올림된다.

### ⚠ 수치 정정 — 실제 입력은 ~54Hz 가 아니라 **59.6Hz** 였다

v6.1.3 커밋 메시지는 입력을 *"DB 실측 실효 52~54"* · slice 를 *"~2.8초"* 로 적었다.
**`effective_hz` 자체가 왜곡된 값이라 그렇다** — `samples/spanSec` 인데 분자(창)가 이미 잘려 있었다.

```
링버퍼 용량 = (preSec + postSec + 1.0) × fs = (2 + 10 + 1) × 50 = 650 표본
13초에 실제 필요 = 13 × 59.6                              = 775 표본   ← 125 부족
방출 시점 보유   = 650 표본 = 10.91초
⟹ 실제 창 = [충격 −0.91s, 충격 +10s] = 649 표본   (규약 = 전 2s + 후 10s)
⟹ impactIndex = 649 − 10×59.6 = 53                (규약 = 100)
⟹ trace 의 effective_hz = 649/12 = 54.08          ← 센서율이 아니라 "잘린 창의 밀도"
```

DB 실측이 이 산술과 정확히 맞는다 — **136건 중 131건이 `samples=649` · `effective_hz=54.08`**
(나머지 5건은 절전 스로틀 구간의 150·168·335·467·512).

따라서 실제 왜곡은 세 겹이었다.

| 슬라이스 | 규약 | v6.1.1 실제 |
|---|---|---|
| `work_veto` 3s | 충격 중심 ±1.5s (150표본 = 3.00초) | **[0, 150) = 충격 −0.89s ~ +1.63s** — 길이 **2.52초**, **중심이 아니다** |
| `impact` ±1s | 충격 중심 ±1.0s (100표본 = 2.00초) | [3, 103) = 충격 ±0.84s — 중심은 맞고 길이 **1.68초** |
| `recovery` fs | 실효 표본율 | `649/12 = 54.08` 을 넘김 — 실제 59.6 보다 **10% 낮다** |

`work_veto` 의 비중심 잘림은 `_slice` 의 `maxOf(0, …)` 클램프에서 나왔다(`center − n/2 = 53 − 75 = −22`).
학습 때는 `impactIndex = 100` 이라 클램프가 안 걸렸다. **커밋 메시지의 "2.8초"는 2.52초가 맞다.**

### v6.1.3 이 이것까지 함께 닫는다

`ImuResampler` 는 타임스탬프 기반 20ms 격자 보간이라 **입력 실제 주파수를 몰라도 된다** — 정정 수치가 수정을 바꾸지 않는다.
그리고 리샘플 뒤 로거가 받는 것이 정확히 50Hz 이므로 **용량 650 = 13초 ≥ 12초** 가 되어
**창 잘림·`impactIndex`·`recovery` fs 세 개가 한꺼번에 해소된다.** 우리가 검토했던 `ImuWindowLogger(fs=60.0)`
우회는 필요 없어졌다(그쪽은 슬라이스 길이를 못 고쳤다).

## ④ 추론이 실패하면 안전 기본값이 뒤집힌다 · **방향 결정 요청** (현재 미발현)

`FallMLPipeline.prob()` 의 `catch (_: Exception) { 0.0 }` 은 recovery 경로에서
**추론 실패 → p = 0.0 → 0.35 미만 → `no_danger`** 가 된다. 주석이 선언한 의도(*"애매하면 위험"*)와 정반대다.
`assess()` 는 모델 **부재**만 `?: 1.0` 로 위험측 처리하고, **추론 예외**는 이 경로로 샌다.

- 애플 Swift 원본도 같은 성질이라 **포팅 결함이 아니다.**
- 모듈을 안 고치는 대신 **호스트에 지문 관측만** 달았다(`warnIfInferenceLooksDead` — `p_nonrecovery == 0.0` 이면 경고 로그, **판정은 그대로**).
- 실측 269건 중 `p_nonrecovery == 0.0` 은 양 플랫폼 모두 **0건** — 아직 한 번도 안 났다.

위험측(`1.0`)으로 바꿀지, 판정을 내지 않고 건너뛸지만 정해 주시면 된다.
