# 계정 찾기(ID/PW) — 결정과 근거 (2026-08-15 착수)

발단 = 사용자 지적. **"관제웹 로그인 화면에 가장 기본적인 ID/PW찾기 기능이 없음."**
확인 결과 사실이다. 그리고 "그냥 만들면 안 되는" 이유가 둘 있었다.

## 1. 착수 전 전수 확인

### C-1. 기능 부재는 사실 — 관리자에게도 되돌릴 길이 없다

- `/api/admin/*` 라우트 21개 중 찾기·재설정 계열 **0건**.
- [LoginScreen.tsx](../../apps/dashboard-web/app/components/LoginScreen.tsx) 의 `mode` 는 `login | signup | gcomplete` 셋뿐.
- owner 의 사용자 관리 액션은 `approve|reject|delete|grant_admin|revoke_admin|set_profile` **6종**
  ([users/route.ts](../../apps/dashboard-web/app/api/admin/users/route.ts)) — 비밀번호를 되돌리는 액션이 없다.
- 즉 비밀번호를 잊으면 **계정을 지우고 다시 가입하는 것 말고 방법이 없었다**(그마저 owner 재승인 필요).

### C-2. ★ 이메일 발송은 지금 배달되지 않는다 — 같은 벽에 두 번째로 부딪힌다

라이브(`vitalguard-dashboard-00275-bvr`) env 실측.

- `RESEND_API_KEY` = Secret Manager 연결됨 ✅
- **`EMAIL_FROM` = 미설정** ❌ → [lib/email.ts](../../apps/dashboard-web/lib/email.ts) 가
  `onboarding@resend.dev` 로 폴백. 이 주소는 **Resend 계정 본인 메일로만** 발송된다.

이건 새 사실이 아니다. **2026-06-29 에 회원가입 이메일 인증을 걷어내고 승인제로 바꾼 이유가 정확히 이것**이다
(`a9ce0de` · [claude-md-archive-20260723.md](../claude-md-archive-20260723.md) 참조). 재설정 메일을 붙였다면
같은 벽에 두 번째로 부딪혔을 것이고, 이번엔 증상이 더 나쁘다 — 가입은 "승인 대기"라도 뜨지만
재설정은 **"신청했는데 아무 일도 안 일어남"** 이 된다.

해소 조건 = 도메인 확보 → Resend 도메인 인증 → `EMAIL_FROM` 갱신(`services update`, **재빌드 불필요**).
사용자 확인 = **도메인 없음**(2026-08-15). → 이메일 경로는 이번 범위에서 배제한다.

### C-3. ★ 기존 인증코드 저장소는 재사용 불가 — 다중 인스턴스에서 갈린다

[lib/email-verify.ts](../../apps/dashboard-web/lib/email-verify.ts) 는 코드를 `globalThis` Map 에 담는다.
라이브는 `maxScale=4 / minScale=1` 이라 **A 인스턴스가 발급한 코드를 B 인스턴스가 모른다.**
지금은 그 경로를 아무도 쓰지 않아(가입 인증 제거됨) 드러나지 않을 뿐, 살아 있는 지뢰다.

→ 재설정 상태는 **반드시 DB** 에 둔다. 이번 구현은 이 모듈을 건드리지도, 재사용하지도 않는다.

(같은 함정의 선례 = `maxScale>1` 에서 in-memory 별칭 캐시가 인스턴스별로 갈려 작업자 병합이
들쭉날쭉했던 2026-06-29 건. 그때 얻은 규칙 = **일관성이 필요한 상태는 메모리가 아니라 DB**.)

## 2. 방식 결정 — 관리자 승인 (사용자 선택 2026-08-15)

제시한 3안과 판정.

| 안 | 내용 | 판정 |
|---|---|---|
| **(A) 관리자 승인** | 신청 → owner 가 임시 비번 발급 → 전화·문자로 전달 | **채택** |
| (B) 이메일 재설정 링크 | 표준. 1회용 토큰 링크 | **보류** — C-2 로 배달 불가(도메인 없음) |
| (C) 본인정보 즉시 재설정 | 이름+생년월일+연락처+이메일 일치 시 즉시 변경 | **기각** — 그 4개는 명함·가입서류로 새어나가는 값이라 계정 탈취 경로가 된다 |

**(A)를 고른 근거는 도메인 부재만이 아니다.** 이 시스템은 이미 승인제다(가입 신청 → owner 승인).
재설정을 같은 길로 태우면 owner 가 이미 보고 있는 화면 하나만 늘어난다. 새 채널·새 습관이 생기지 않는다.

## 3. 설계 요점

### D-1. 아이디 찾기는 관리자를 거치지 않는다

이름 + 이메일 일치 → 마스킹 ID 표시. 외부 의존 0, 대기 0. 재설정과 달리 **즉시 답이 나온다.**

- **마스킹하는 이유** — 이름·이메일은 명함에 있는 값이다. 전체 노출이면 그 둘만으로 남의 계정 ID 를 캐낼 수 있다.
  본인은 앞뒤 글자만 봐도 "아 그거였지"가 되므로 실용성은 거의 잃지 않는다.
- **가입일을 함께 보여준다** — 같은 이름·이메일로 계정이 여럿일 때(회사 이관 등) 구분 단서가 된다.
- `email` 컬럼에 UNIQUE 제약이 없어 **복수 행이 정상**이다. 전부 반환한다.

### D-2. 임시 비밀번호는 DB에 평문으로 남기지 않는다

승인 시 12자 임시 비번을 생성해 **해시만** `users.password_hash` 에 쓰고,
평문은 승인 API **응답에서 1회만** 돌려준다. 새로고침하면 다시 볼 수 없다(UI에 명시).

- 혼동 문자(`0 O 1 l I`)를 뺀다 — 전화로 불러주는 값이라 오해가 곧 재문의다.
- 생성값은 `checkPassword` 정책(8~19자)을 통과해야 한다. 통과 못 하는 값을 발급하면
  사용자가 "내 정보"에서 바꾸려 할 때가 아니라 **로그인 직후**에 막힌다.

### D-3. ★ 방치 방어는 "강제 변경 화면"이 아니라 만료다

`users.temp_password_expires_at` 컬럼 하나. 24시간이 지나면 **로그인 자체가 거부**된다.

강제 변경 화면을 만들지 않은 이유.

- 클라이언트 게이트는 우회된다(토큰을 손에 쥔 뒤 화면만 건너뛰면 그만).
- 서버에서 진짜 강제하려면 세션 JWT 클레임을 늘리고 **모든 보호 라우트**가 그것을 보게 해야 한다.
  "찾기 기능 추가"에 붙일 변경이 아니다.
- 만료는 코드 한 줄로 실효가 있다. 임시 비번의 위험은 "오래 살아 있는 것"이지 "화면을 건너뛰는 것"이 아니다.

비번을 실제로 바꾸면 만료를 해제한다 — `updateUserProfile` 이 `password_hash` 를 쓸 때 같이 NULL 로 만든다.
**한 곳에서 처리**해야 경로가 늘어도(관리자 대행 변경 등) 빠뜨리지 않는다.

### D-4. 신청 실패를 숨기지 않는다

계정 열거를 막으려고 "접수되었습니다"로 통일하는 관행이 있지만, 여기선 쓰지 않는다.
승인제라 **실제로 접수 안 된 사용자가 무한정 기다리게** 되기 때문이다. 불일치는 불일치라고 답한다.

열거 위험은 다른 것으로 낮춘다 — **ID·이름·이메일 3개를 모두** 맞춰야 하고(찾기는 이름+이메일 2개),
IP 당 토큰버킷을 건다. 3개를 다 아는 상대에게 "그 계정이 있다"는 사실은 이미 새 정보가 아니다.

### D-5. 중복 신청은 부분 유니크 인덱스로 막는다

`CREATE UNIQUE INDEX ... ON password_reset_request(user_id) WHERE status = 'pending'`
→ 한 계정당 미처리 요청은 하나. 이력은 남으므로 처리 후 재신청은 가능하다.
애플리케이션 레벨 검사만 두면 동시 요청 2건이 통과한다(다중 인스턴스라 더 그렇다).

### D-6. 별도 컴포넌트로 분리한다

`LoginScreen.tsx` 는 이미 1,398줄이다. 찾기 화면 2개를 그 안에 넣으면 읽을 수 없게 된다.
`AccountRecovery.tsx` 로 분리하고 자체 다국어 문자열을 갖게 해서 `LoginScreen` 의 `Strings` 타입을 안 건드린다.

## 4. 하지 않은 것

- **텔레그램 알림(owner 에게 요청 도착 통지)** — 봇은 이미 라이브지만 요청 범위 밖이라 넣지 않았다.
  사용자 관리 모달이 60초 폴링을 하므로 화면을 열어두면 보인다. 필요하면 다음 단계로.
- **이메일 재설정 링크** — 도메인 확보 시 재검토. 그때는 이번에 만든 `password_reset_request` 테이블을
  그대로 쓰고 승인 주체만 사람 → 토큰으로 바꾸면 된다(스키마 재설계 불필요하게 설계해 두었다).
- **비밀번호 변경 강제 화면** — D-3 참조.
