# 실시간 레이더 영상 — 가독성 개선 후보 조사 (2026-08-01)

관제 탭 `실시간 레이더` 의 강수 영상이 읽기 어렵다는 지적에서 출발. **조사만 했고 코드는 바꾸지 않았다.**
현재 구현 = `app/components/RadarRealtime.tsx` + `app/api/radar/route.ts`(RainViewer 프록시).

## 현재 구성

| 요소 | 값 |
|---|---|
| 베이스맵 | CARTO `a.basemaps.cartocdn.com/{dark_all\|light_all}` |
| 레이더 | RainViewer `{host}{path}/256/{z}/{x}/{y}/**7**/**1_1**.png` |
| 줌 | 인라인 6 · 확대 팝업 7 |
| 갱신 | `/api/radar` 2분 캐시 · 프레임 700ms 애니메이션 |

## ★★ 핵심 발견 — 색상 지정이 실제로는 무시된다

URL 의 `7`(color=Rainbow)과 `1_1` 의 `snow=1` 이 **서버에서 무시**된다. 같은 프레임·같은 타일로
파라미터만 바꿔 받아 md5 를 비교해 확인했다.

| 파라미터 | 현재 | 실측 |
|---|---|---|
| `color` 0~8 | 7 | ❌ **9개 전부 동일 md5** (`3136198b…`) · 줌·smooth 조건 바꿔도 동일 |
| `snow` | 1 | ❌ `1_1` 과 `1_0` 동일 md5 (`f7f23d87…`) |
| `smooth` | 1 | ✅ 작동 — `1_1` 9,867b vs `0_0` 7,000b |
| `size` | 256 | ✅ 작동 — 512 는 다른 이미지(24,465b) |

→ **"색상 스킴을 바꿔 가독성을 높인다"는 가장 흔한 처방이 이 API 에서는 통하지 않는다.**
무료 티어가 색상을 고정하는 것으로 보인다. 코드의 `/7/` 은 아무 효과가 없다.

⚠️ 조사 함정 — 처음엔 한국 영역(z6 54/25) 타일로 비교하려 했는데 **9개가 전부 1,516b 로 같았다.**
색상 무시가 아니라 **폭염 중이라 강수가 없어 빈 타일**이었던 것이다. 파일 크기로 강수 유무를
먼저 훑어(빈 타일 = 1,516b) 강수가 있는 z4/13/6(한국·일본, 9,867b)을 찾은 뒤에야 비교가 성립했다.
**빈 데이터로 비교하면 "차이 없음"이 나오는데 그건 결론이 아니라 측정 실패다.**

## 실물에서 본 문제

타일을 직접 열어보니 약한 강수가 **흩뿌려진 점으로 파편화**돼 있다. 색상표 문제라기보다
**전지구 합성 자료의 해상도 한계**에 가깝다 → 색을 바꿀 수 있었더라도 크게 나아지지 않았을 것이다.

## 후보

### A. 기상청 레이더영상 — 최선, **활용신청 필요**

```
apis.data.go.kr/1360000/RadarImgInfoService/getCmpImg   → 현재 HTTP 403 Forbidden
```

**우리가 이미 쓰는 `1360000`(기상청) 계정의 서비스**다. 새 키 발급 없이 **활용신청만** 하면 된다.
403 = 오퍼레이션은 존재하고 미승인 — 태풍정보 서비스와 같은 패턴(`typhoon.ts` 주석 참조).
다른 이름(`getRdrImg`·`getSrdImg`·`getRadarImg`)은 404 로 존재하지 않는다.

- **HSR · CAPPI · PPI0 · CMAX**, **500m 해상도 · 5분 간격**
- 가독성 관점에서 **HSR 유력** — 지형에코·차폐·비강수 에코가 제거된 자료라 파편 노이즈가 준다
- ⚠️ **응답이 타일이 아니라 완성 PNG 일 가능성** — 그러면 현재의 슬리피맵 오버레이 구조가 아니라
  이미지 표시 방식으로 바뀐다. 승인 후 실물을 보고 판단해야 한다.

### B. RainViewer 유지 + 즉시 가능한 개선

색상은 못 바꾸지만 **해상도는 바꿀 수 있다.**

- **256 → 512px 타일** — 같은 영역에 픽셀 2배. 실물 확인 시 강수 패턴이 확실히 선명
- 줌 상향(인라인 z6 → z7)
- `/7/`·`_1` 이 무의미하다는 주석 추가(다음 사람이 색상 조정을 시도하다 시간을 버리지 않게)

### C. 다른 소스

OpenWeatherMap 강수 타일(무료 티어·색상 제한) · Windy(유료).
**국내 현장 관제**라는 목적에서 A 보다 나을 이유가 없어 우선순위 낮음.

### 왜 줌 값을 바꾸는 것만으로는 안 되는가

기존 레이더는 **한국 bbox 를 % 로 채우는 고정 그리드**였다(`tilesForBBox`). 여기서 줌만 올리면
**같은 영역을 더 많은 타일로 그릴 뿐** — 선명해지지만 확대되지 않는다(z6→z7 이면 타일 4배, 화면은 그대로).
진짜 확대는 **표시 범위가 좁아지는 것**이므로 태풍과 같은 `center + zoom` 슬리피맵이 필요하다.

```
인라인(캐러셀·사이드 패널)  기존 고정 그리드 유지 — 클릭이 '팝업 열기'라 드래그와 충돌한다(태풍도 같은 구조)
확대 팝업                   슬리피맵으로 교체 — 휠 줌(커서 기준) · 드래그 팬 · ＋ － ↺ · 줌 뱃지
```

### 좌표 변환을 공유 모듈로 분리

`app/lib/slippy-tiles.ts` 신설(웹 메르카토르 ↔ 픽셀 · `kmToPx`). 태풍이 갖고 있던 로컬 정의를 옮겼다 —
**두 지도가 같은 타일 좌표계를 쓰게 되므로 한쪽만 바뀌면 서로 다른 위치를 가리킨다.**
줌 범위·팬 한계는 지도마다 다르므로 공유하지 않는다(태풍 z2~11 / 레이더 **z4~10**).

## 2026-08-12 — 레이더가 이틀간 502 였다 (NAT 도입 부수 회귀 · 해소)

가독성 이야기가 아니라 **아예 안 뜬 사고**의 기록이다. 이 문서 위쪽의 "로컬 dev 에서는 레이더가 아예 안 뜬다(코드 문제 아님)" 와 **증상은 닮았지만 원인이 다르다** — 그때는 이 맥에서 나가는 TCP 가 막힌 것이었고, 이번엔 **프로덕션이** 못 나갔다.

**증상.** 관제 화면 `실시간 레이더` 가 `레이더 — 프레임 없음`. `/api/radar` 가 502(`fetch failed`)를 내는데 **실패까지 0.26~0.5초로 빠르다** — 라우트의 6초 `AbortSignal.timeout` 에 한참 못 미치므로 타임아웃이 아니다. 8-10 오후부터 200/502 가 섞이다 8-12 아침 6/6 전부 502.

**원인.** Node `fetch`(undici)의 Happy Eyeballs 는 **주소 하나당 250ms 안에 TCP 연결이 끝나지 않으면 그 시도를 버린다**(`autoSelectFamilyAttemptTimeout`). **8-10 Cloud NAT 도입**(고정 아웃바운드 IP · 교훈 L-49·L-50)으로 경로가 길어지며 RainViewer(독일 Hetzner)까지 connect 가 **253~266ms** 가 됐고, 매번 완료 **6~16ms 전에** 잘렸다. 다음 후보인 IPv6(`2a01:4f8:…`)는 IPv4 전용 VPC 라 경로가 없어 즉시 실패한다. RainViewer 쪽 문제도, 코드 문제도 아니다.

**★ curl 로 재면 정상으로 보인다.** VPC 프로브 VM 에서 **NAT IP 로 `curl` 이 A레코드 3개 전부 200**(`157.90.66.200`·`157.90.67.199`·`176.9.90.248`)이었다. 같은 VM 에서 `node:22-alpine` 으로 재현해야 드러난다 — `fetch` 5/5 ETIMEDOUT @254~255ms. **도구를 잘못 고르면 "네트워크는 정상"으로 결론난다.** connect 10회 실측 `0.2536~0.2663s`.

**조치.** `instrumentation.ts` 기동 훅에서 `setDefaultAutoSelectFamilyAttemptTimeout(3000)` 전역 1회(커밋 `3a1931a` · 리비전 `00247-8p4`). 가드 = `lib/2026-08-12-connect-attempt-timeout.guard.test.ts`.

**⚠ 로컬에서 재현되지 않는다.** 기본값이 런타임마다 달라 프로덕션 `node:22` 는 250ms, 로컬 `node:26` 은 이미 500ms 다. 이 문서 위쪽 "로컬에서 안 뜸" 항목과 헷갈리지 말 것 — **이번 건은 로컬이 오히려 멀쩡한 쪽**이다.

**레이더에 국한된 이야기가 아니다.** 같은 경계에 **open-meteo 가 237~246ms** 로 붙어 있다(지금은 위 전역 설정이 덮는다). 이그레스 경로(VPC·NAT·프록시·리전)를 바꾸는 변경을 할 때는 외부 의존 호스트마다 `curl -4 -o /dev/null -w '%{time_connect}\n' https://<host>/` 를 10회 재서 250ms 대비 여유를 기록한다. 2026-08-12 기준 = JMA 24ms · 기상청 42ms(안전) / open-meteo 237~246ms(경계) / RainViewer 253~266ms(당시 고장).

**타일은 무죄다.** 이 패널에서 **프레임 목록만 서버가 가져오고 타일은 브라우저가 직접 받는다**. 그래서 서버 이그레스가 죽어도 타일 요청은 멀쩡하고, 화면만 보면 정상으로 오판한다(8-10 배포 기록이 실제로 그렇게 적혔다). 판정은 `/api/radar` 응답의 `ok`·`frames` 길이로 한다.
