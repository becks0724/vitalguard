## 진단 기법 (재사용 가치 있음)

**T-1. 세 시각을 분리해서 본다.** `heart_rate_measured_at`(워치 측정) · `ts`(폰 수신 = 서버 계약상 전송 시각) · `received_at`(서버 insert). 이 셋이 다 남아 있어서 "어느 구간이 밀렸는지"가 산술로 갈렸다. `ts` 하나만 봤다면 전 구간이 "유실"로 보인다.

**T-2. id 시퀀스 델타로 "서버 무음 폐기"와 "미도달"을 가른다.** Postgres 는 `ON CONFLICT DO NOTHING` 으로 버려진 INSERT 도 시퀀스를 소비한다. 수신 공백 앞뒤 행의 `id` 차이가 **정확히 1** → 그 구간에 서버는 아무것도 받지 않았다(무음 폐기 아님). 반대로 6시간 전체로 보면 **id 소비 4,710 vs 행 4,611 = 99 차이**라 다른 자리에서 무음 폐기가 일어나고 있음이 같은 방법으로 드러났다.

**용어 정확성.** "폰 경유를 없앤다"는 **폰 앱과 WCSession 큐**를 없앤다는 뜻이다. 네트워크는 여전히 BT 로 연결된 폰의 인터넷을 프록시로 쓴다 → **LTE 워치가 아니어도 된다.**

**만들 것 넷.**
1. **워치 업로더**(신규 ~200줄) — `VitalPipeline.swift` 가 하는 일(디스크 영속 큐·상한·30초 백오프·401/403 시 5분 대기·배치 500건 상한)을 워치로 이식. 상시 워크아웃 세션이 살아 있어 백그라운드 요청이 나간다.

3. **★ ts 계약 결정** — 아래.
4. **폰 경로 정리** — 컷오버 스위치 후 폰 vital 파이프라인 제거. 폰엔 로그인·화면만 남는다.

**서버·DB·관제웹 무변경.** `/api/app/vital` 은 Bearer JWT + 본문 workerId 일치만 요구하므로 워치는 또 하나의 클라이언트가 된다. 스키마 `ts` 에 신선도 제약이 없어(`z.string().datetime()`) 밀린 큐를 나중에 올려도 받는다.

- **(나) ts = 전송 시각 유지.** 계약 불변·실질 오차 5초 이내. 다만 네트워크 끊김 후 밀린 큐에서 같은 문제가 재발한다.
- 권고 = **(가)**.

**대가와 위험.** ① **배터리가 최대 쟁점**(현행 실측 6.46%/h — 5초 HTTPS 는 WC 배달보다 무겁다. 완화 = 배치 주기 15~30초·커넥션 재사용. 실측 없이 결정 금지) ② 워치 코드 복잡도·디버깅 난이도 ③ 컷오버 중복 ④ **현장 NAT 레이트리밋**(IP당 120회/분 = 워치 10대면 한도. 지금도 같은 속도라 신규 위험은 아니나 다인 현장 확장 전 필수) ⑤ 워치 앱 사망 시 폰 큐라는 얇은 안전망 소멸.

## 2026-08-14 — 08-18 시험용 진단 코드 (준비 완료 · **미설치**)

**D-5. 왜 워치 화면인가.** 시험 B 는 "폰을 두고 워치만 들고 멀어진다" 라서 그 순간 볼 수 있는 화면이 손목뿐이다. 같은 정보가 폰 로그(`PhoneReceiver.swift:41`)에 이미 있지만 읽으려면 `log collect`(root)를 거쳐야 하고 그건 시험이 끝난 뒤의 일이다.

**D-6. `잔량`이 결정적 지표다.** `WCSession.outstandingUserInfoTransfers.count` = 아직 폰에 도달하지 않은 큐. **멀어지면 늘고 돌아오면 0 으로 떨어진다.** 이게 실시간으로 보이면 "전달이 밀린다"가 추론이 아니라 관측이 된다. 도달 여부(`isReachable`)는 시험의 독립 변인 자체라 함께 띄운다.

**D-7. 채널을 서버로 보내지 않는다.** 스키마·폰·서버·DB 4계층 계약 변경인데, **얻는 것이 작다** — 큐 경유 여부는 이미 `ts − heart_rate_measured_at` 지연으로 드러난다(즉시 2~5초 vs 큐 수십~수백 초). 남는 모호함은 5초 안팎의 경계 사례뿐이고, 그건 워치 화면이 답한다. 시험 직전 재서명에 큰 계약 변경을 얹지 않는 것이 안전하기도 하다.

**D-8. 줄을 늘리지 않는다.** 워치 화면은 이미 7요소로 꽉 차 있어 한 줄을 더하면 시작/중지 버튼이 밀린다. 기존 `전송 N회` 자리를 확장했다 — 정상일 때 `전송405 도달`(짧음), 이상일 때만 `전송405 단절 큐25 잔량12`(길어짐). 0 생략은 이산 측정 줄과 같은 규칙이고, `즉시`는 `전송 − 큐`라 적지 않는다. 잔량이 0 보다 크면 주황색으로 바뀌어 손목에서 한눈에 들어온다.

**D-9. 곁다리 수정 1건 — 계기 자신의 오계수.** `flush()` 의 즉시 채널 실패 경로가 `noteSent()` 를 **두 번** 부르고 있었다(동기 1회 + errorHandler 1회). 그래서 **실패한 flush 만 전송 2회로** 세어졌다. 채널 계수를 이 자리에 넣는 김에 분리했다(`noteSent(queued:)` / `noteFallback()`). 진단 계기가 스스로 틀린 수를 보이면 안 된다.

**검증.** `swiftc -typecheck -target arm64_32-apple-watchos10.0` 통과 · `xcodebuild -scheme VitalWatch -destination 'generic/platform=watchOS'` **BUILD SUCCEEDED**. **기기 설치는 하지 않았다** — 지금 설치하면 `HKWorkoutSession` 이 끊겨 오늘 돌고 있는 수집이 멈춘다. 설치 시점은 **08-17 재서명**이다.

**08-18 판독법.** 시험 B 중 워치를 보고 ⓐ `단절`로 바뀌는 지점(몇 걸음·어느 벽) ⓑ `잔량`이 쌓이는 속도 ⓒ 복귀 후 잔량이 0 으로 떨어지는 시각을 기록한다. DB 쪽 지연 급증과 시각이 맞으면 거리 가설 확정이다.

## 9. ts 계약 정정 — 설계 (결정 2026-08-15 · 착수 08-18 이후)

사용자 결정 = **(가) 측정 시각**. 근거와 설계를 남긴다.

### E-1. 왜 바꾸는가 — 실패 모드가 둘이고 방향이 반대다

`sentAt` 은 `VitalPipeline.swift:117` 에서 **`ingest()` 1회당 한 번** 찍히고 `:136` 이 배치 전 항목에 같은
값을 붙인다. 여기서 두 결함이 동시에 나온다.

| | 언제 | 결과 | 발견 |
|---|---|---|---|
| **충돌** | 워치가 밀렸다 한 배치에 여러 건 | 같은 ts → `ON CONFLICT (worker_id, ts)` 가 조용히 버림 | 08-14 (2.4%) |
| **미충돌** | 재전송 때 ts 새로 찍힘 | 다른 ts → `ON CONFLICT` 가 못 잡음 → 중복 | 옆 세션(sample-loss-recovery 3절) |

**둘 다 "ts = 전송 시각"이 원인이고 측정 시각으로 옮기면 동시에 사라진다.**
08-15 재측정 = 최근 6시간 119분에서 기대 1,428건 중 **27건 부족(1.9%)** — 지금도 계속 새고 있다.

**C-3(배치 트랜잭션)만으로는 부족하다.** 그건 재전송 중복만 막는다. 같은 배치 안의 ts 충돌은
트랜잭션과 무관하게 남는다.

### E-2. ★ 부작용 — 이 트랙을 가능하게 한 지표가 사라진다

지금 전달 지연은 `ts − heart_rate_measured_at` 으로 잰다. ts 가 측정 시각이 되면 **이 값이 항상 0** 이라
워치→폰 지연을 DB 에서 못 잰다. 08-14·08-15 진단이 전부 이 지표 위에 있었다.

→ **폰 수신 시각을 받을 컬럼을 먼저 만든다**(예 `phone_received_at`). 세 시각(측정·폰 수신·서버 도착)을
셋 다 남긴다 — L-64 가 정확히 이 상황을 위해 쓴 교훈이고, 이번엔 내가 그걸 어길 뻔했다.

### E-3. 키 구조는 바꾸지 않는다

C-1 처럼 UNIQUE 컬럼을 `heart_rate_measured_at` 으로 갈아끼우면 인덱스 재생성 + 기존 행 충돌 처리가
붙는다. **`UNIQUE(worker_id, ts)` 를 그대로 두고 폰이 ts 에 넣는 값만 바꾼다** — 서버·스키마·인덱스 무변경.

측정 시각이 없는 샘플은 전송 시각으로 폴백한다. (08-15 실측 = 최근 6시간 1,402건 중 측정 시각 없는 행
**0건** 이라 지금은 사각이 비어 있지만, 미래에 생길 수 있어 폴백을 명시한다.)

### E-4. 착수 순서 — 시험이 먼저다

```
08-17  재서명 + 워치 진단 코드 설치      ← 파이프라인 무변경
08-18  시험 B (거리 가설 확정)            ← 변인 하나만
그 후   E-2 컬럼 → ts 정정 → A안 + C-3
```

**ts 를 먼저 바꾸면 시험 B 의 판정 지표가 사라진다**(E-2). 그리고 거리 가설이 확정돼야 A-1~A-4 중
무엇을 만들지 정해진다.

⚠ **설치 창 유의** — ts 정정은 폰 변경이라 재설치가 필요하다. 08-17 재서명에 얹지 않으면 다음 설치
기회까지 기다려야 한다. 그 대가를 알고도 시험을 먼저 두는 선택이다.

### E-5. 전환 경계

기존 행은 전송 시각 ts 를 갖고 있어, 전환 직후 같은 측정이 옛 ts·새 ts 두 행으로 남을 수 있다.
전환 시각을 기록하고 그 경계에서만 중복을 허용한다(전수 마이그레이션은 하지 않는다 — 과거 행의
전송 시각을 측정 시각으로 되돌릴 방법이 없다).
