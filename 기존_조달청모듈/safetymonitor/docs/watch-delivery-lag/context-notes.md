## 진단 기법 (재사용 가치 있음)

**T-1. 세 시각을 분리해서 본다.** `heart_rate_measured_at`(워치 측정) · `ts`(폰 수신 = 서버 계약상 전송 시각) · `received_at`(서버 insert). 이 셋이 다 남아 있어서 "어느 구간이 밀렸는지"가 산술로 갈렸다. `ts` 하나만 봤다면 전 구간이 "유실"로 보인다.

**T-2. id 시퀀스 델타로 "서버 무음 폐기"와 "미도달"을 가른다.** Postgres 는 `ON CONFLICT DO NOTHING` 으로 버려진 INSERT 도 시퀀스를 소비한다. 수신 공백 앞뒤 행의 `id` 차이가 **정확히 1** → 그 구간에 서버는 아무것도 받지 않았다(무음 폐기 아님). 반대로 6시간 전체로 보면 **id 소비 4,710 vs 행 4,611 = 99 차이**라 다른 자리에서 무음 폐기가 일어나고 있음이 같은 방법으로 드러났다.

## 부수 발견 — 무음 유실 약 2.4%

버스트 때 여러 payload 가 **같은 밀리초에 ingest** 되면 `VitalPipeline.swift:117` 이 찍는 `ts`(수신 시각)가 충돌하고, `db.ts:912` 의 `ON CONFLICT (worker_id, ts) DO NOTHING` 이 조용히 버린다. 실측 = 6시간 결손 **약 103건(2.4%)**, 버스트 60건 중 **31쌍이 5ms 이내 간격**. 08-14 오전에 잡은 배치 ts 중복 유실([[CLAUDE.md Status 08-14 (3)]])의 **잔여 형태**다.

16:25:34 | 12건/분 | 최대지연 5.1초   ← 잠금 시작 부근

**잠금 내내 12건/분 유지·최대 지연 5.1초·버스트 없음.** 폰의 잠금·백그라운드 여부는 정체를 만들지 않는다.

**가설 정정.** `transferUserInfo` 가 본질적으로 느린 것이 아니다. 폰이 잠겨 있어도 워치와 붙어 있으면 5초 안에 배달된다. 지연은 **전달 링크가 끊겼을 때** 큐가 쌓이는 것이다.

**미해결 관찰.** 잠금과 함께 지연이 2초대→5초대로 한 단계 오른 뒤 **복귀 후에도 안 내려왔다**. 채널이 `sendMessage`→`transferUserInfo` 로 바뀐 흔적일 수 있으나 단정 근거는 없다(3초 차이는 관제에 무해).

**다음 가설 = 거리(BT 링크 단절).** 정체 시간대(11·12·15시)와 정상 시간대(09·10·14시)의 대비, 특히 12시대 최악(332건)과 13:32~13:44 최장 공백은 **폰을 두고 이동하는 패턴**과 겹친다. 5분치가 1초에 쏟아지는 모양도 재연결 순간의 큐 방출과 같다.

## A-3 설계 요점 (착수 전 정리 · 미착수)

**용어 정확성.** "폰 경유를 없앤다"는 **폰 앱과 WCSession 큐**를 없앤다는 뜻이다. 네트워크는 여전히 BT 로 연결된 폰의 인터넷을 프록시로 쓴다 → **LTE 워치가 아니어도 된다.**

**만들 것 넷.**
1. **워치 업로더**(신규 ~200줄) — `VitalPipeline.swift` 가 하는 일(디스크 영속 큐·상한·30초 백오프·401/403 시 5분 대기·배치 500건 상한)을 워치로 이식. 상시 워크아웃 세션이 살아 있어 백그라운드 요청이 나간다.
2. **토큰 전달** — JWT 는 현재 **폰 Keychain 전용**(`VitalBridge.swift:25-35`). 로그인 직후 폰이 워치로 1회 전달 → 워치 Keychain 저장. 토큰 수명은 **30일**(`app-jwt.ts` LEGACY_TTL — 이 앱은 15분 access 경로를 안 쓴다)이라 갱신 로직 대신 만료 시 재로그인 안내면 된다. ⚠ `updateApplicationContext` 는 디스크 평문 영속이라 쓰지 않는다([[watch-jwt-appcontext-risk]]).
3. **★ ts 계약 결정** — 아래.
4. **폰 경로 정리** — 컷오버 스위치 후 폰 vital 파이프라인 제거. 폰엔 로그인·화면만 남는다.

**서버·DB·관제웹 무변경.** `/api/app/vital` 은 Bearer JWT + 본문 workerId 일치만 요구하므로 워치는 또 하나의 클라이언트가 된다. 스키마 `ts` 에 신선도 제약이 없어(`z.string().datetime()`) 밀린 큐를 나중에 올려도 받는다.

**ts 계약 — 미결정(사용자 판단 대기).**
- **(가) ts = 측정 시각.** 타임라인 왜곡 소멸 + `UNIQUE(worker_id, ts)` 가 **자연 멱등키**가 되어 재시도 중복과 무음 유실 2.4%가 구조적으로 사라진다. 대가 = **컷오버 시점에 계약 경계**가 생긴다(과거 행 소급 변경은 하지 않는 것이 레포 선례). 사고 조사 뷰가 그 경계를 알아야 한다.
- **(나) ts = 전송 시각 유지.** 계약 불변·실질 오차 5초 이내. 다만 네트워크 끊김 후 밀린 큐에서 같은 문제가 재발한다.
- 권고 = **(가)**.

**대가와 위험.** ① **배터리가 최대 쟁점**(현행 실측 6.46%/h — 5초 HTTPS 는 WC 배달보다 무겁다. 완화 = 배치 주기 15~30초·커넥션 재사용. 실측 없이 결정 금지) ② 워치 코드 복잡도·디버깅 난이도 ③ 컷오버 중복 ④ **현장 NAT 레이트리밋**(IP당 120회/분 = 워치 10대면 한도. 지금도 같은 속도라 신규 위험은 아니나 다인 현장 확장 전 필수) ⑤ 워치 앱 사망 시 폰 큐라는 얇은 안전망 소멸.

**성공 기준.** ① 1시간 실착용 `ts − measured_at` 60초 초과 **0건** ② 측정 기준 12건/분 유지 + id 소비 = 행 수(무음 유실 0) ③ 배터리 **6.5%/h 이하** ④ 폰 앱 강제종료 상태에서 수집 지속 ⑤ 기내모드 5분 후 밀린 큐 중복 없이 전량 도착.

## Xcode Debug 전수조사 — 검토 후 기각

사용자 제안. **연결은 유용하나 Debug 실행은 역효과**로 판단했다.
1. **관측이 현상을 지운다** — 디버거가 붙은 앱은 iOS 가 suspend 하지 않아 `isReachable=true` 가 유지되고 폴백 경로 자체가 안 생긴다.
2. **운용 조건이 되돌아간다** — 08-14 에 확보한 Release 설치(Xcode 없이 생존)가 풀린다. 특히 **워치 앱 재설치는 `HKWorkoutSession` 을 끊고 자동 복구 경로가 없어** 사람이 워치에서 "시작"을 눌러야 한다([[watch-counterpart-not-installed]]).
3. **얻을 게 거의 없다** — 미관측 고리는 "그 순간 채널이 무엇이었나" 하나뿐이고, 그건 이미 `PhoneReceiver.swift:41` 이 배치마다 로그로 남긴다.

**대안 = 로그 회수.** 이 맥은 `log stream --device-name` 이 제거됐고 `log collect` 는 root 를 요구하므로 사용자가 직접 실행한다(우리 로그는 전부 `log.notice` 라 디스크 영속됨).
