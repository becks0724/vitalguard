## 1. 왜 하는가 — 목적은 지연이 아니다

푸시로 바꿔도 화면은 빨라지지 않는다. 워치가 120초마다 배치로 올리고
(`CollectorService.kt:704` `FLUSH_INTERVAL_MS = 120_000`), 관제도 그것을 알고 갤럭시만
`STALE_MS_WEAROS = 150_000` 으로 신선도 기준을 따로 둔다(`lib/vital-age.ts:71`).
122초 사슬에서 마지막 2초를 없애는 일이다.

그래서 목적은 **부하 감소**와 **서버발 이벤트의 즉시 반영** 둘로 한정한다.

## 3. 범위

**한다** — 관제 대시보드 생체·경보 갱신 경로 하나.
**안 한다** — WebSocket(양방향 필요 기능 없음), 워치 업로드 주기 변경(발열·배터리 트랙),
캘린더·사진·날씨 등 60초 폴링(빈도가 낮아 이득 없음), 앱(`/api/app/*`) 경로.

## 4. 설계 결정 4개

### D1. 스트림은 데이터를 싣지 않는다 — "바뀌었다"만 보낸다
이벤트 payload = `{type, ts}` 정도. 화면은 그 신호를 받으면 **기존 `/api/monitor/vital` 을 1회 호출**한다.

이유. 지금 폴 요청은 `Authorization: Bearer <세션토큰>` 을 실어 보내고, 서버가 그 토큰으로
GPS·보호자 같은 PII 노출 여부를 가른다(`DemoDashboard.tsx:5619`). 스트림이 데이터를 직접 실으면
그 redaction 규칙을 두 곳에서 유지해야 한다. 신호만 보내면 규칙은 한 곳에 남는다.

### D2. `EventSource` 를 쓰지 않고 `fetch` + `ReadableStream` 으로 읽는다
`EventSource` 는 헤더를 실을 수 없어 Bearer 토큰을 못 보낸다. 토큰을 쿼리스트링에 넣는 방식은
로그·리퍼러에 토큰이 남아 채택하지 않는다. `fetch` 는 헤더를 실을 수 있고, SSE 프레이밍 파싱은
30줄 남짓이다. 자동 재연결은 직접 쓴다(지수 백오프 + 지터).

### D3. 팬아웃은 1단계에서 인프로세스 버스 + `maxScale=1`
수집 POST 와 화면 스트림이 다른 인스턴스에 붙으면 신호가 못 간다. 현재 `maxScale=4`.
1단계는 `maxScale=1` 로 묶고 모듈 싱글턴 이벤트 버스를 쓴다(새 인프라 0).
동시성은 `containerConcurrency=80` 이라 관리자 수십 명까지 여유가 있다.
2단계(필요해지면) = Postgres `LISTEN/NOTIFY` — 이미 `pg` 풀과 VPC 가 있어 장비 추가가 없다.

### D4. 폴링은 지우지 않는다 — 스트림이 죽으면 되살아나는 폴백으로 남긴다
플래그 `MONITOR_STREAM_ENABLED` 기본 off. 스트림 연결 실패·중단 시 즉시 2초 폴링 복귀.
"켜면 가벼워지고, 꺼도 지금과 같다"가 이 작업의 안전선이다.

## 6. 스트림 응답 규약

```
Content-Type: text/event-stream
Cache-Control: no-cache, no-transform
Connection: keep-alive
```
- 25초마다 `: ping` 주석 프레임 — 중간 프록시 유휴 차단 방지.
- Cloud Run `timeoutSeconds=300` 이라 5분마다 정상 종료된다. 재연결은 클라 몫(정상 동작으로 취급).
- 동시 스트림 상한을 둔다(초과 시 503 + 폴링 유지). 열린 스트림이 동시성 슬롯을 먹기 때문이다.

## 7. 롤아웃과 되돌리기

1. 플래그 off 로 배포 → 기존 동작 그대로인지 확인(G3).
2. `maxScale=1` 로 조정 → 트래픽 정상 확인.
3. 플래그 on → G1·G2 측정.
4. 되돌리기 = 플래그 off. Cloud Run env 변경은 새 리비전 배포가 필요하므로,
   즉시성이 필요하면 이전 리비전으로 트래픽 100% 되돌린다.

## 8. 리스크

| 리스크 | 완화 |
|---|---|
| `maxScale=1` 로 낮추면 인스턴스 1대 장애가 전체 정지 | 트래픽이 작고 `minScale=1` 로 이미 상시 1대. 2단계에서 LISTEN/NOTIFY 로 4대 복귀 |
| 열린 스트림이 동시성 슬롯 점유 | 동시 스트림 상한 + 초과 시 폴링 폴백 |
| 배포 때 전 연결 동시 끊김 → 재연결 폭주 | 지수 백오프 + 지터 |
| 상시 연결로 인스턴스가 idle 로 못 내려가 과금 성격 변화 | 1주 관측 후 판단. 요청 수는 줄고 활성 시간은 늘어난다 |
| 프록시·프레임워크 버퍼링으로 프레임이 안 나감 | `no-transform` + 하트비트 + 배포 후 실측 1회 |

## 9. 보류 사유 — 과금 실측 (2026-09-08)

계획의 1순위 근거는 "요청 1,800회/시간 → 60회로 줄여 부하·요금을 낮춘다" 였다. 실측 결과 성립하지 않는다.

| 측정 | 값 | 의미 |
|---|---|---|
| 5분 구간 288개 중 활성 인스턴스가 있던 구간 | 288개 (100%) | 이미 쉬는 시간이 없다 |
| 평균 활성 인스턴스 | 1.08대 | 스트림을 열어도 새로 청구될 시간이 없다 |
| 하루 과금 인스턴스시간 | 48시간 | 라이브 1대 + `verify` 태그 리비전 1대 |

Cloud Run 은 요청 수가 아니라 인스턴스가 켜져 있던 시간으로 과금한다. GasPod 5초·워치 2분·대시보드 2초·
CCTV 폴러 1.5초가 겹쳐 인스턴스가 상시 활성이라, 요청을 줄여도 요금은 그대로다.

부수 소득 — 하루 48시간의 절반은 트래픽 0% 인 `verify` 태그 리비전(07-31 생성, `minScale=1`)이 먹고 있었다.
같은 날 태그를 제거했다. 이쪽이 SSE 로 아낄 수 있었던 것보다 크다.

## 10. 함께 드러난 것 — CCTV 낙상 경로 사망 (별건, 보류)

`cctv-fall-poller` 가 `cctv-ai/cctv/stats2` 를 1.5초마다 부르는데 **2026-09-07 14:44 KST 이후 전부 403** 이다.
cctv-ai 는 `ingress=internal` + 인증 필요인데 폴러가 토큰 없이 부른다. 게다가 CAM-02 는 엣지 푸시가 0건이라
403 이 풀려도 `"source":"synthetic"` 합성값이 돌아온다. 따라서 G2(낙상 지연 단축)는 지금 측정 자체가 불가능하다.
복구 순서 = 권한 → 실피드 → 그다음 주기 조정. 이 건도 사용자 지시로 보류.
