# SSE 전환 컨텍스트 노트

## 2026-09-08 · 착수 전 조사

### 확인한 사실
- 관제웹 전체에 WebSocket·SSE 코드 0건 (`git grep "new WebSocket|EventSource\(|text/event-stream"` → 무출력).
- 화면 갱신은 폴링. 생체 2초(`DemoDashboard.tsx:5639`), 위치 15초, 경보 배지·캘린더 60초.
- Cloud Run 실측 설정 — `timeoutSeconds=300` · `containerConcurrency=80` · `minScale=1` · `maxScale=4` · VPC 전 트래픽 egress.
- 워치 업로드는 120초 배치(`FLUSH_INTERVAL_MS`), 근거 주석에 "10분 착용에 피부온 +2.3℃ · 배터리 15%".
- 관제는 그 간극을 알고 `STALE_MS_DEFAULT=60초` vs `STALE_MS_WEAROS=150초` 로 갈라 둠.

### 결정과 근거
- **지연 개선을 목적으로 삼지 않는다.** 122초 사슬의 2초를 없애는 일이라 체감이 없다.
  목적은 부하 감소(G1)와 서버발 이벤트 즉시 반영(G2)으로 한정.
- **payload 는 신호만.** 폴 경로가 Bearer 토큰으로 PII redaction 을 가르고 있어
  (`DemoDashboard.tsx:5619`), 데이터를 스트림에 실으면 규칙이 두 곳으로 갈라진다.
- **`EventSource` 를 버리고 `fetch` 스트림으로 읽는다.** `EventSource` 는 헤더를 못 실어
  Bearer 를 보낼 수 없다. 토큰을 쿼리스트링에 싣는 대안은 로그 잔존 때문에 기각.
- **1단계는 인프로세스 버스 + `maxScale=1`.** 새 인프라 0. 4대를 유지해야 할 때만
  Postgres `LISTEN/NOTIFY` 로 승격(장비 추가 없음).
- **폴링을 지우지 않는다.** 플래그 off 가 곧 완전한 되돌리기가 되도록.

### 기각한 대안
| 대안 | 기각 이유 |
|---|---|
| WebSocket | App Router 가 업그레이드를 못 받아 커스텀 서버·Dockerfile 변경 필요. 지금 양방향이 필요한 기능 없음 |
| 쿠키 인증 + `EventSource` | 세션 토큰이 localStorage 기반이라 쿠키 도입 = 새 인증 표면(CSRF) 추가 |
| 처음부터 `LISTEN/NOTIFY` | 요청 밖에서 도는 리스너라 CPU 상시 할당이 필요해져 비용이 먼저 오른다. 1대로 충분한지 먼저 본다 |
| 폴링 주기 단축(2초 → 0.5초) | 데이터는 120초마다 오는데 요청만 4배가 된다 |

### 열린 질문
- `maxScale=1` 로 낮추는 것을 사용자가 승인하는가. 승인 못 하면 1단계를 건너뛰고
  `LISTEN/NOTIFY` 부터 해야 하며 비용·작업량이 함께 오른다.
- 탭 숨김 시 스트림을 끊을 것인가. 기존 60초 폴러는 탭 숨김에 폴링을 멈춘다(DB 부하 배려).
- 상시 연결이 Cloud Run 과금에 실제로 얼마를 더하는가 — 1주 관측 후 판단.

## 2026-09-08 · 보류 결정

### 과금 구조를 잘못 알고 있었다
"요청이 줄면 요금이 준다" 가 전제였는데, Cloud Run 은 **인스턴스가 켜져 있던 시간**으로 과금한다.
실측하니 최근 24시간 5분 구간 288개 전부에서 활성 인스턴스가 있었다(평균 1.08대). 쉬는 시간이 없으니
스트림을 열어도 추가로 청구될 시간이 없고, 반대로 요청을 줄여도 아낄 시간이 없다.

교훈 — 최적화 전에 **과금 단위**를 먼저 확인한다. 여기서는 요청 수가 아니라 인스턴스시간이었다.

### 조사 중 나온 별건 두 가지
1. `verify` 태그가 붙은 07-31 리비전이 트래픽 0% 로 39일간 인스턴스 1대를 24시간 물고 있었다 → 같은 날 제거.
   하루 과금 인스턴스시간 48 → 24 예상(09-09 확인).
2. CCTV 낙상 경로가 09-07 14:44 KST 이후 403 으로 죽어 있다. 폴러는 1.5초마다 계속 두드리는 중이고
   cctv-ai 컨테이너는 24시간 과금 0초(403 은 프론트엔드에서 잘림). CAM-02 엣지 푸시도 0건이라 합성값이다.
   → 사용자 지시로 조치 보류.

### 남은 판단
- SSE 는 재개 조건 3개 중 하나가 충족될 때 다시 꺼낸다.
- 그때도 이 문서의 설계 결정 4개(신호만 전송 / `fetch` 스트림 / 인스턴스별 장부 감시 / 폴링 폴백)는 그대로 유효하다.
  단 팬아웃 방식은 `maxScale=1` 대신 **인스턴스별 1초 장부 감시**로 바꾸기로 정리됐다(사용자 논의 09-08).
