# DB 용량 — 실측과 선택지 (2026-08-15 착수)

발단 = 08-15 DB 장애(3시간 50분)의 원인이 **캠퍼스 서버 용량**이었고, 우리 몫이 1,252MB 로
집계됐다. "보존 정책을 넣자"로 가기 전에 **그 1,252MB 가 무엇인지** 먼저 쟀다.

**결론 먼저 — 대부분이 데이터가 아니다. 행을 하나도 안 지우고 ~730MB 를 회수할 수 있다.**

---

## 1. 실측 (읽기 전용 조회 · L-04 무위반)

```
vital_samples   총 1,252 MB  =  본체 888 MB  +  인덱스 364 MB
행수            363,495       (2026-06-24 ~ 08-15 · 수집 42일)
행 평균 크기     418~432 B     (월별 균일 — 6월 418 · 7월 426 · 8월 432)
                              그중 raw_json 213~238 B (약 55%)
```

**논리 데이터는 363,495 × 425 B ≈ 147 MB 인데 본체가 888 MB 다.**

### ★ 페이지 단위 실측이 결정적이다

평균값 비교는 추정이라 페이지로 확인했다.
```
relpages       113,719 페이지 × 8 KB = 888 MB
실제 밀도       364,059 ÷ 113,719 = 페이지당 3.2 행
정상 밀도       8,160 B ÷ (736 + 28) B = 페이지당 약 10.7 행
                                        → 3.3 배 헐겁다
```
재적재하면 `364,059 ÷ 10.7 ≈ 34,000` 페이지 = **약 266 MB**.
**본체에서만 ~620 MB 회수**, 인덱스(314 MB)도 함께 줄어든다.

> **⚠ 초판 수치 정정(같은 날 · ② 실행 후).** 처음에 행 폭을 425 B·정상 밀도 18 행·회수
> ~730 MB 로 적었는데 **측정 방법이 틀렸다.** `pg_column_size(t.*)` 는 **메모리상 합성 행**의
> 크기라 저장 폭과 다르다. `ANALYZE` 가 돌아 정확해진 `pg_stats` 로 재니
> **`sum(avg_width) = 736 B`(50개 컬럼)** 이다. 헐거운 정도는 5.6 배가 아니라 **3.3 배**이고
> 회수 가능량은 ~620 MB 다. **결론(대부분이 데이터가 아니다)은 유지되지만 수치는 이쪽이 맞다.**
> 교훈 = 저장 폭은 `pg_stats.avg_width` 로 재고, 그러려면 `ANALYZE` 가 선행돼야 한다.

### ⚠ 종전 판정 "dead tuple 0 이라 VACUUM 문제 아님" 은 근거가 없었다

`pg_stat_user_tables` 실측 = `n_live_tup 4,438`(실제 363,495) · `n_dead_tup 0` ·
`last_vacuum`/`last_autovacuum`/`vacuum_count` **전부 null·0**.
**통계가 초기화된 상태다**(08-15 02:51 DB 재기동으로 추정 — 그 뒤 쌓인 양과 맞는다).
초기화된 통계에서 `n_dead_tup 0` 은 **"죽은 행이 없다"가 아니라 "센 적이 없다"** 이다.
숫자가 0 이라고 정보가 있는 것이 아니다.

### 원인 — ② 실행이 가설 하나를 죽이고 다른 하나를 세웠다

**기각된 가설 = "죽은 튜플이 쌓였다".** ② 직후 `n_dead_tup` 이 **2,775 건**(364,059 중 **0.76%**)
이다. 약 1.2 MB 어치라 620 MB 를 설명하지 못한다. **`ON CONFLICT` 충돌 누적설은 무너졌다.**

**남은 유력 가설 = FSM(Free Space Map)이 없어서 빈 자리를 재사용하지 못했다.**
FSM 은 `VACUUM` 이 만들고 갱신한다. 그런데 이 테이블은 **vacuum 이력이 없었다**
(`vacuum_count 0` · `last_vacuum` null — 통계 초기화 영향을 감안해도 정황은 같다).
FSM 이 없으면 삽입은 **빈 자리를 못 찾고 파일 끝에 새 페이지를 붙인다.** 그래서
"죽은 행은 거의 없는데 페이지는 헐거운" 지금 상태가 만들어진다.

**★ 이 가설은 지금 검증 가능하다.** ② 가 FSM 을 만들었으므로, 이후 삽입이 빈 자리를 채우면
**파일이 안 자란다.** ② 직전까지는 12건/분에 약 5페이지/분씩 늘고 있었다(일 60 MB).
→ 아래 "④ 증가 정지 관측" 항목.

⚠ 정확히 가르려면 여전히 `pgstattuple` 이 필요하다(미설치 · 확장은 `plpgsql` 하나뿐).
지금 가진 것은 **페이지 밀도와 죽은 튜플 수라는 두 하드 지표**이고, 인과는 관측으로 확인한다.

### ⚠ 부수 발견 — 이 서버는 `/dev/shm` 이 작다

첫 시도 `VACUUM (ANALYZE) vital_samples` 가 실패했다.
```
ERROR: could not resize shared memory segment "/PostgreSQL.780999120"
       to 67144960 bytes: No space left on device
```
**데이터 디스크가 아니라 공유 메모리다**(컨테이너 기본 `/dev/shm` 64 MB). PG14 의
**병렬 인덱스 vacuum** 이 DSM 을 잡으려다 막힌 것이다. `PARALLEL 0` 으로 우회했다.
- 앞으로 이 서버에서 수동 `VACUUM`·`VACUUM FULL` 은 **`PARALLEL 0` 을 붙인다.**
- autovacuum 은 병렬 인덱스 vacuum 을 쓰지 않으므로 이 제약과 무관하다.
- 같은 제약이 병렬 질의(`max_parallel_workers_per_gather`)에도 걸릴 수 있다 — 미확인.

## 2. 별건 — 중복 인덱스는 확정이다

```
uq_vs_worker_ts   141 MB  UNIQUE btree (worker_id, ts)   scan 4,516
idx_vs_worker_ts   49 MB         btree (worker_id, ts)   scan 1     ← 완전 중복
```
**컬럼 조합·순서가 동일**하다. UNIQUE 인덱스가 같은 질의를 전부 처리하므로 비-UNIQUE 쪽은
구조적으로 쓸모가 없다. `DROP INDEX idx_vs_worker_ts` = **49 MB 즉시 회수 · 위험 0**.

⚠ scan 횟수는 통계 초기화 이후 값이라 그것만으로 판단하지 않았다 — **정의가 동일하다는 것이
근거**다(scan 이 많았어도 UNIQUE 쪽으로 갈 수 있다).

다른 인덱스는 전부 다른 조합이라 중복이 아니다(`vital_samples_pkey`·`idx_vs_ts`·
`idx_vs_data_origin_ts`·`idx_vs_ts_id`).

## 3. 선택지 — 순서가 중요하다

**보존 정책은 마지막이다.** 데이터를 지우는 것은 되돌릴 수 없고, 지금 용량의 대부분은
데이터가 아니다.

| | 조치 | 회수 | 위험·비용 | 결정 필요 |
|---|---|---|---|---|
| **①** | `DROP INDEX idx_vs_worker_ts` | **49 MB** | 없음(완전 중복) | 승인만 |
| **②** | `VACUUM (ANALYZE) vital_samples` | 0 MB(OS 반환 없음) | 낮음·온라인 | 승인만 |
| **③** | `VACUUM FULL vital_samples` | **~730 MB + 인덱스분** | ⚠ ACCESS EXCLUSIVE 락 · 작업 중 **수집 전면 중단** · 일시적으로 **2배 공간 필요** | 창 잡기 |
| **④** | 보존 정책(오래된 행 삭제) | 기간에 비례 | **되돌릴 수 없다** · `incidents` 구간 3년 보존 룰 선적용 필수 | 정책 결정 |

**②를 ③보다 먼저 두는 이유** — `VACUUM` 은 공간을 OS 에 돌려주지 않지만 **재사용 가능하게
표시**한다. 그러면 이후 삽입이 새 페이지를 안 만들고 빈 자리를 채워 **증가가 멎는다**.
락도 거의 없다. ③ 없이 ②만으로도 "일 60MB 증가"가 상당 기간 사실상 0 이 될 수 있다.

**③의 진짜 제약은 공간이다.** `VACUUM FULL` 은 새 사본을 만든 뒤 옛것을 지우므로 **작업 중
피크가 현재의 약 2배**다. 용량이 모자라서 터진 서버에서 그 피크를 감당할 수 있는지 확인이
선행돼야 한다(학원 관리 서버 · 30GB 확보 후라 여유는 있어 보이나 우리가 측정할 수 없다).
⚠ **작업 중 수집이 끊긴다** — 폰 큐가 5,000건(≈6.9시간) 버티므로 그 안에 끝나야 유실 0 이다.
