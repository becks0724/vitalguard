## 1. 왜 지금 드러났나 — 오늘 정직해진 표시가 응급을 감췄다

이 문제는 **어제까지 존재하지 않았다.** 워치가 마지막 심박을 영원히 복사해 보내고 있었기 때문에
(08-14 실측 **12시간 34분·8,531건 전부 102bpm**) 화면에는 늘 값이 있었다. "심박 없음" 이라는
상태 자체가 없었다.

`541bfa9`(하트비트 30초 유효기간)로 **복사를 끊자 처음으로 "심박 없음" 이 나타났고**,
그 상태의 의미가 하나가 아니라는 것이 드러났다.

```
08-14  값이 늘 있다        → 미착용도 "정상 90bpm" 으로 보였다        (거짓 안심)
08-15  값이 비게 됐다      → 미착용도 심정지도 "대기" 로 보인다        (응급 은폐)
```

**전자를 고친 것이 후자를 만들었다.** 고친 것이 잘못이 아니라, 정직해지고 나니 다음 결함이
보인 것이다 — 관제 화면이 **최우선 응급을 가장 낮은 등급으로 세고 있다.**

## 3. ★ 판별에 필요한 신호 — `motionStillSec` 하나가 핵심이다

| 상황 | 심박 | 움직임 | 낙상 |
|---|---|---|---|
| 벗어서 책상·사물함 | 없음 | **없음**(정지 지속이 길게 쌓임) | 없음 |
| 벗어서 들고 이동 | 없음 | 있음 | 없음 |
| **심정지·의식소실** | **없음** | **없음** | **있을 수 있음** |
| 정상 착용·휴식 | 있음 | 미세하게 있음 | 없음 |

⚠ **"벗어서 책상" 과 "심정지" 는 신호가 같다**(심박 없음 + 정지). 움직임만으로는 못 가른다.
가르려면 **착용 여부**를 알아야 하는데 watchOS 는 상시 워크아웃 중 손목 감지를 우회하므로
직접 알 방법이 없다(2026-08-15 실증 — 벗어도 센서가 켜져 있고, 몸에 닿으면 값이 나온다).

**현실적인 조합** — 확정이 아니라 후보다.
```
심박 없음 + 정지 지속 짧음(움직임 있음)        →  미착용 (누가 들고 다닌다)
심박 없음 + 정지 지속 김 + 낙상 감지 있음      →  ★ 응급 의심 (최우선)
심박 없음 + 정지 지속 김 + 낙상 없음           →  판별 불가 → 확인 요청(호출·SOS 유도)
```

## 4. ★ 설계 원칙 — 오탐과 미탐의 대가가 비대칭이다

```
오탐  응급이 아닌데 응급으로  →  관제자가 헛걸음. 반복되면 경보 피로
미탐  응급인데 대기로        →  사람이 죽는다
```
**이 트랙에서는 오탐 쪽으로 기운다.** 이 레포의 다른 판정(온열 ②·PSI·WBGT)이 전부
"판정 미주입 · 확실할 때만" 이었던 것과 **방향이 반대**다. 그 원칙들은 *"근거 없는 값을
판정에 올리지 않는다"* 였고, 여기는 *"판별 불가를 안전으로 세지 않는다"* 다.

### ★ 재검토 결론 (2026-08-16 · 문헌 조치 E) — 원칙을 **경로별로 쪼갠다**

문헌(Nature 2025 loss-of-pulse)의 특이도 목표는 **99.99%**(오경보 21.67년당 1회)다.
위 원칙을 그대로 두면 *"오탐 쪽으로 기운다"* 가 **곧 기능 폐기**라는 반박이 성립한다.

**둘 다 옳고, 충돌은 경로를 안 나눈 데서 온다.** 그 논문이 재는 것은 **자동 응급 호출**이다 —
오탐 하나가 구급차를 부르므로 99.99% 가 필요하다. **우리가 하려는 것은 화면 표시**다.

```
표시 경로   "판별 불가 · 확인 요청"  →  오탐 비용 = 관제자가 한 번 본다
            ⟹ 민감도 우선. 원칙 유지.  판별 불가를 대기로 접지 않는다
알림 경로   텔레그램 · 자동 격상      →  오탐 비용 = 경보 피로 → 그날로 꺼진다
            ⟹ 특이도 우선. 문헌 기준 적용.  확실할 때만
```

⟹ **원칙 개정** — *"판별 불가를 안전으로 세지 않는다"* 는 **표시에만** 적용한다.
알림은 이 레포의 다른 판정과 같은 선(확실할 때만)에 둔다. 이 문서 §5 의 "알림 정책" 항목은
이제 *"쏠 것인가"* 가 아니라 *"어떤 조건이 99.99% 를 만족하는가"* 를 묻는다.

⚠ **착용 감지가 없는 한 그 조건을 만들 수 없다.** 논문도 on-wrist 확인이 된 경우에만
분류를 낸다. 우리는 상시 워크아웃이 손목 감지를 우회한다(실증 완료).
**⟹ 알림 경로는 당분간 열지 않는다.** 표시부터 만든다.

⚠ 그래서 **"판별 불가" 를 조용히 대기로 접으면 안 된다.** 화면에 판별 불가로 드러내고
관제자가 확인하게 한다(연락·호출). 오늘 고친 "미수신을 정상으로 세던" 결함과 같은 계열이다.

## 4-2. ★★ 2026-08-18 실측 — 이 트랙의 전제 둘이 바뀌었다

착수 전에 "얼마나 자주 뜨는가"(§5 오탐률)를 먼저 쟀는데, 그 과정에서 **설계 전제 자체가 두 군데
틀렸다는 것**이 나왔다. 표시를 설계하기 전에 이것부터 고정한다.

### ✅ 전제 ① 정정 — "둘 다 대기로 센다"는 이미 해소됐다

이 문서 §2 는 `overallStatus(null…) → idle → 대기` 를 근거로 **응급이 최저 등급으로 세어진다**고
적었다. **2026-08-15 `13ebe51`(신선도 심박 기준 전환)로 이미 고쳐졌다.** 현재 코드 실측.
```
DemoDashboard.tsx:4957   const stale = isStale(sample, now)
             :4955 주석   "연결끊김은 생체 상태보다 우선 — stale 이면 주의로 강등하고 이상으로 집계"
worker-signal.ts          "{이름} 연결끊김 — 즉시 연락·현장 확인"
```
⟹ **지금은 대기가 아니라 "이상"이고 신호등도 주의로 오른다.** 이 트랙이 발견한 결함의
**절반은 다른 트랙이 이미 닫았다.** 남은 것은 *"연결끊김 안에서 미착용과 응급을 가른다"* 뿐이다.

### ⚠⚠ 전제 ② 붕괴 — §3 판별표는 **데이터상 성립하지 않는다**

§3 은 이 조합을 전제한다.
```
심박 없음 + 정지 지속 짧음  →  미착용
심박 없음 + 정지 지속 김    →  응급 의심 / 판별 불가
```
**그런데 심박이 없을 때는 정지 지속도 함께 없다.** 행 자체가 안 오기 때문이다.

실측(08-16 이후 · 신규 앱 · `EMP-6861`).
```
전체 9,955행 중 심박 NULL = 40행(0.40%)      ← "심박만 없는 행" 은 사실상 없다

긴 공백 동안 도착한 행(ts 기준)
  08-17 18:03→21:31 (208분)   2건
  08-17 14:10→17:03 (174분)   2건
  08-16 13:05→14:14 ( 69분)   2건
```
**세 시간 넘게 끊긴 구간에 도착이 2건**이다(경계 부근). 즉 **벗으면 전송이 통째로 멎는다** —
상시 워크아웃이 활동에너지를 계속 산출하므로 행이 이어질 것이라 기대했는데 그렇지 않다.

⚠ **[2026-08-18 정정 — §4-3]** 아래 두 문단의 *"벗으면 전송이 통째로 멎는다"* 는 **틀렸다.**
실기기 시험에서 벗어도 12행/분이 그대로 왔다. 긴 공백의 원인은 벗음이 아니라 **수집 정지**다.
다만 **판별 축이 없다는 결론 자체는 유지**된다 — 이유가 바뀌었을 뿐이고, §4-3 이 더 나쁜 사실을 더한다.

⟹ **미착용과 심정지가 "신호가 없다" 는 점에서 완전히 같다.** 문서가 *"착용 감지가 없다"* 고
적은 것보다 한 단계 더 나쁘다 — **무동작 신호조차 없어 가를 축이 하나도 없다.**
`motionStillSec` 은 착용 중일 때만 오므로 이 판별에는 쓸 수 없다(온열 활동 축에는 여전히 유효).

### 오탐률 실측 (§5 항목 — 완료)

```
날짜    60초 초과   5분 초과   30분 초과   공백 총분
08-16       8          6          3        1,322
08-17       5          5          3        1,011
08-18       4          1          0           15
```
**하루 4~8회** 연결끊김이 뜬다(워커 1명 기준). 큰 것들(208·174·69분)은 명백히 벗어둔 구간이다.
⟹ 워커 10명이면 하루 40~80회다. **표시는 이 빈도를 견뎌야 하고, 알림은 이 빈도로는 못 쏜다**
(§4 의 경로 분리 결론이 실측으로 뒷받침됐다).

### ⟹ 그래서 남은 미결은 하나로 좁혀진다 — **워치 생존 신호**

가르려면 "심박이 없다" 와 "워치가 없다" 를 분리해야 하고, 그러려면 **심박과 독립인 생존 신호**가
주기적으로 와야 한다.
```
생존 신호 O + 심박 X   →  워치는 켜져 있는데 심박이 안 잡힘   ← 착용 이상·응급 후보
생존 신호 X            →  워치 꺼짐·절전·거리 이탈            ← 시스템 문제(전달 트랙)
```
⚠ **2026-08-15 에 끊은 "하트비트" 와 다른 것이다.** 그때 끊은 것은 **심박 값 복사**(12시간 34분
8,531건 전부 102bpm)였고, 여기서 필요한 것은 **값이 없는 생존 표식**이다. 혼동하면 그 사고가
재발한다 — 값을 실어 보내면 안 된다.

⚠ 선결 = **배터리 영향**(현행 6.46%/h)과 **벗었을 때도 전송이 유지되는가**. 후자가 관문이다 —

## 4-3. ★★★ 2026-08-18 실기기 시험 — §4-2 의 내 결론이 틀렸다

§4-2 에서 *"벗으면 전송이 통째로 멎는다"* 고 적고 커밋했다. **실기기 시험이 반증했다.**

### 시험 — 워치만 벗어 폰 옆에 5분 (거리 변인 통제)

**상시 `HKWorkoutSession` 이 광학센서를 켜 둔 채 손목 감지를 우회한다**(08-15 70분 실측의 재현).

## 4-4. 수집 정지의 지문 — 세션이 갑자기 죽고, 재개는 사람이 눌러야 한다 (2026-08-18)

배터리 없이도 어디까지 좁혀지는지 봤다. 긴 공백 3건의 **양 끝**을 읽으니 지문이 일치한다.

### 끝나는 쪽 — 세 건 모두 "세션이 새로 시작됐다"

```

```
첫 행이 **측정 시각도 심박도 없이 정지값만** 실려 있다 = `flush` 가 심박 이벤트 없이 처음 돈 배치다.
정지값도 **작은 값에서 시작**한다(`stop()` 이 `lastMovementAt = nil` 로 기준점을 버리므로).
⟹ 전달이 재개된 것이 아니라 **세션이 새로 켜진 것**이다. 그리고 **재개는 수동**이다
(`ContentView.swift:50-52` 의 [시작] 버튼뿐 — 자동 복구 경로가 없다는 기록된 사실 그대로).

### 시작하는 쪽 — 열화 없이 갑자기

**복사행 0건 · 고유심박 4~7** = 끊기기 직전까지 **실측이 정상으로 오고 있었다.**
센서가 먼저 멎고 하트비트로 버티다 끊긴 것이 **아니다**(그랬다면 복사행이 쌓였을 것이다).
마지막 5행도 12건/분·지연 0.1~3.4초로 정상이다가 뚝 끊긴다.

⟹ **센서가 아니라 프로세스가 통째로 죽었다.** 08-17 두 건은 끊기는 순간 정지값이 0.5~0.8초로
**움직이는 중**이었다(08-16 건만 41.9초 = 앉아 있음).

### ⟹ 남은 후보는 둘로 좁혀졌다

**둘을 가르는 것이 `battery_pct` 다** — 재개 시점 레벨이 낮거나 상승 중이면 ②, 충분하면 ①.
그래서 이 트랙에서 배터리 전송이 "있으면 좋은 것" 이 아니라 **다음 한 걸음 그 자체**다.

⚠ **①이면 이 시스템의 결함이 더 크다.** 워치 앱이 죽으면 **아무도 모르는 채 수집이 멎고**
사람이 손으로 다시 켤 때까지 돌아오지 않는다 — 08-17 에 그 상태가 **하루 6.4시간**(208+174분)
이었다. 관제 화면은 그동안 연결끊김을 띄우지만 **왜인지도, 스스로 복구되지 않는다는 것도**
말하지 않는다.

      **사람이 손으로 켤 때까지 영영 안 돌아온다**(자동 복구 경로 0 · 재개는 [시작] 버튼뿐).
      08-17 에 그 상태가 **하루 6.4시간**이었다. 관제는 연결끊김을 띄우지만 **스스로 복구되지
      않는다는 사실을 말하지 않는다** — 관리자가 "곧 돌아오겠지" 로 읽으면 그날은 그대로 끝난다.
      조치 후보 = ⓐ 워치 앱 재기동 시 자동 세션 재개 ⓑ 관제 문구에 "수동 재개 필요" 명시
      ⓒ 일정 시간 이상 정지 시 알림. **선행 조건이던 원인 규명은 완료됐다(§4-5 · ①)** —
      ⓐ 가 무의미해지는 경우(②)는 반증됐다. ⚠ 다만 ⓐ 단독으로는 부족하다 — watchOS 는 죽은
      앱을 스스로 켜지 않아 **사람이 앱을 열어야** 발동한다. ⓑ·ⓒ 는 대체가 아니라 보완이다.
      ⚠ ⓑ 는 **"수동 재개 필요" 라고 단정할 수 없다** — 같은 연결끊김이 거리 이탈(자동 복구됨 ·
      시험 B 확증)일 수도 있고, 그 순간에는 둘을 가릴 데이터가 없다. 문구는 사용자 결정 사항

## 6. 하지 않기로 한 것

- **심박 없음만으로 응급 판정** — 미착용이 압도적으로 흔하다. 그대로 쏘면 첫날 경보 피로로
  꺼진다(2026-07-30 CCTV "미수신 → 준수율 100%" 를 회색+안내로 고친 선례의 반대 실수).
- **손목 감지 API 로 해결** — watchOS 가 상시 워크아웃 중에는 주지 않는다. 실증 완료.
