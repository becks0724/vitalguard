# 관제웹 안정화 — 계획

**목표.** 관제웹(dashboard-web)의 구동을 시뮬레이션으로 정밀 분석해 안정성 문제를
전수 파악하고, 심각도·우선순위를 매긴 리스트를 낸다. **이 트랙은 분석까지다 — 수리는
리스트를 보고 사용자가 고른 뒤 별도 트랙.**

## 방법 — 세 겹

1. **정적 전수조사** — 클라이언트 타이머(폴링) 전수 + 각 폴이 부르는 API + 그 API 의
   요청당 DB/외부 왕복 수. "매분 같은 초 버스트"(D-3 실측)를 만드는 구조를 수치화한다.
2. **정상 구동 시뮬레이션** — 로컬 dev + 헤드리스 브라우저 로그인 후 수 분 관찰.
   요청 케이던스·같은 초 정렬·콘솔 오류·응답 실패·메모리 추세.
3. **장애 주입 시뮬레이션** — `DATABASE_URL` 을 죽은 주소로 바꾼 dev 를 따로 띄워
   DB 전면 장애 때 화면이 어떻게 무너지는지 관찰(08-15 07:39 실제 장애 전례).
   ⚠ 프로덕션은 건드리지 않는다. 재시도 폭주·무한 스피너·거짓 정상 표시를 본다.

## 판정 원칙 (이 레포 교훈 그대로)

- 찾은 것만 적는다 · 0 옆에는 같은 자의 통제군 (L-88·L-98③)
- 도구가 무엇을 재는지 한 문장으로 쓰고 나서 이름을 붙인다 (L-98①)
- 코드에서 세운 인과는 관측으로 확인 전에 결론으로 적지 않는다 (L-85)
- 심각도는 "깨지면 보이는 모습"(seams.md 형식)과 함께 적는다 — 재현 경로 없는 심각도는 추측이다
