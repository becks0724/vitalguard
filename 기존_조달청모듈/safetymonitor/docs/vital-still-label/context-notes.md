## 발단

OCR 각인 트랙의 화면 실측 중 애플워치(EMP-6861)를 **11분간 벗어 두었는데** 관제 화면이 내내
`수신 중 · 89bpm` 이었다. 갤럭시는 같은 순간 하드웨어 착용 센서로 수집을 끊어 `대기` 였다.
두 기기가 비대칭이고, 애플 쪽은 사람이 자리를 비워도 화면이 그것을 모른다.

## ★ 절반은 08-15~20 에 이미 밝혀져 있었다 — 오늘 그것을 모르고 다시 쟀다

착수 전에 `grep` 했으면 안 했을 실측이 셋이다. 오늘 아침 OCR 트랙에서 *"외부 서비스를
붙이기 전에 그 일을 이미 하는 코드가 있나 grep 한다"* 를 교훈으로 적어 놓고 같은 날 되풀이했다.
그래서 **여기 적는다** — 다음 사람이 이 질문을 받으면 아래 표부터 본다.

| 오늘 잰 것 | 선행 기록 | 일치 |

| 벗어도 심박이 계속 온다 (11분 · 92.9 vs 착용 91.5) | 08-13 70분 · 08-18 5.5분 (108.4 vs 108.1) | 3번째 재현 |

스파이크 하나에 지배된다. 재서명 창 목록에 올리지 않는다(사용자 3번 결정의 후반부 · 근거 보고 후).

## 오늘 새로 잰 것 (선행 기록에 없던 것)

### ① 착용 + 의도적 정지 — `still` 은 착용 중에도 멈추지 않고 오른다

```
17:02:21  착용 직후   still 0.6
17:03:26              still 62.5   mv 3
          120초 통과  still 122.5  mv 4     ← 착용 중
          정지 종료   still 137.5  → 움직임 → 0.4 · 심박 96→106
```
사람은 원하는 만큼 가만히 있을 수 있다. **어떤 문턱도 착용 중 정지에서 발화한다.**
그래서 이 값으로 "벗음" 을 말하면 거짓이고, "N분째 움직임 없음" 을 말하면 참이다.

### ② 7일 꼬리 — 관제자가 하루에 몇 번 보게 되나 (근무시간 07~19 KST)

```
날짜   행수   ≥300s  ≥600s
08-22  6346    17      3
08-23  4064     3      3
08-24  7208    25     23      ← 장시간 정지가 많은 날 (벗어 둔 날로 추정 · 라벨 없음)
08-27  5488     2      0
08-28  5943     3      1
전체 7일(야간 포함)  ≥120s 110회 · ≥300s 56회 · ≥600s 35회
```
표시 전용 라벨이라 이 정도는 부담이 아니다 — 라벨이 말하는 것이 사실(정지 시간)이므로
"오탐" 이 없다. 오탐이 성립하는 것은 *벗음·응급을 단정할 때* 뿐이다.

### ③ 조건 기록 — 손목 감지 **켜짐**(사용자 확인)

애플이 벗김을 알고 잠금까지 걸면서도 워크아웃 심박은 계속 낸다는 뜻이다. 선행 기록은
"우회한다" 고만 적었고 설정값은 없었다. 앞으로 이 실험을 재현할 때 이 조건을 맞춘다.

### ④ 배치 뭉개짐 속에서도 `still` 은 정확했다

워치→폰 링크가 2.5분 끊겼다 붙으면서 30행이 같은 `ts`(17:02:16)로 왔다 — `watch-delivery-lag`
9절이 08-15 에 적은 실패 모드 그대로(`ts = sentAt` · 측정 시각 이전은 아직 미적용).
그 30행 안에서 `still` 은 511.5 → 636.5 로 5초씩 정확히 올랐다. **워치 자체 카운터라 도착
시각에 안 흔들린다.** 행 `ts` 로 재는 신선도와 달리 이 축은 전달 지연의 영향을 받지 않는다.

### ⑤ 단서 하나 — 움직인 직후 심박이 96→106

착용 중 정지를 끝내고 움직이자 수 초 안에 심박이 10 뛰었다. 벗어 둔 워치를 손댄 16:43 에는
87→89 였다. **산 사람의 심박은 동작에 반응한다.** 다만 벗어 둔 워치는 움직임 자체가 없어 이
반응을 볼 기회가 없다 — 판별기가 아니라 관측 1건이다. 기록만 한다.

## 결정 — **질문을 바꾼다**

관제자가 알아야 하는 것은 "워치가 벗겨졌나" 가 아니라 **"이 사람을 확인하러 가야 하나"** 다.

```
5분 넘게 0.03g 도 안 움직였다
  의식을 잃었거나     → 확인하러 간다
  워치를 벗어 뒀거나  → 확인하러 간다     (조치가 같다)
```
**두 경우의 조치가 같으면 둘을 못 가르는 것은 결함이 아니다.** 결함은 그 구간에 `수신 중` 이
떠서 아무도 안 가는 것이고, 그것은 **`무동작` + 경과** 라는 정직한 라벨로 고쳐진다.
선행 트랙 §3 의 후보 조합은 *심박 없음* 을 전제했는데, 같은 트랙의 08-18 결과 ②가 *심박은
착용의 증거가 아니다* 를 확정했으므로 **심박이 있어도** 정지를 드러내야 한다. 그 빈틈이 오늘 화면이다.

### 규칙

| | |
|---|---|
| 조건 | `!stale` ∧ `tone === "normal"` ∧ `motionStillSec ≥ 300` |
| 표시 | 상태 칸 `무동작` + 아래 줄에 경과(`N분`) — `연결끊김` 칸과 같은 모양 |
| 톤 | **`normal` 그대로.** 신호등 색·집계·게이트·경보 어디에도 안 닿는다 |
| 우선순위 | `stale` > `낙상/SOS/위험/주의` > **`무동작`** > `수신 중` |

- **300초.** 착용 의도적 정지 137초의 2배 이상 · 08-18 착용 정지 82초보다 훨씬 위 ·
  `absence-check` 10분보다 아래. 상수 하나라 바꾸는 비용이 0 이다.
  ⚠ 문헌(Choi 2011)의 90분과 자릿수가 다르지만 목적이 다르다 — 그쪽은 *역학 집계에서 비착용
  구간을 잘라내는* 것이고 이쪽은 *실시간으로 사람을 보러 갈지* 다. 선행 트랙 §4 가 표시 경로는
  민감도 우선이라고 정해 뒀다.
- **`주의`·`위험` 은 덮지 않는다.** 그 라벨이 더 많은 정보를 담는다. 무동작은 `수신 중`(=아는 게
  없다) 자리만 대신한다.
- **`stale` 이면 안 뜬다.** 끊긴 행의 `still` 은 그 시각의 값이라 지금을 말하지 않는다.

### 받아들인 위험 — `still` 이 store 에서 sticky 다

`store.ts` 병합이 `{...older, ...newer}` 라 워치가 `still` 을 안 실은 표본(오늘 8%)에서는 직전 값이
남는다. 워치는 창을 못 채웠을 때만 nil 을 보내므로(세션 시작 첫 1분) 실제 지연은 표본 몇 개다.
길게 굳는 경우는 워치가 모션 콜백을 통째로 잃는 때뿐인데, 그러면 `still` 이 안 오는 게 아니라
**오르지 않고 굳는다** — 300초 아래서 굳으면 라벨이 안 뜨고(안전측), 위에서 굳으면 라벨이 남는다.
후자는 `stale` 이 함께 오므로 곧 가려진다. 비-sticky 로 바꾸면 8% 표본마다 라벨이 깜빡인다 —
더 나쁘다. 그대로 둔다.

### 하지 않는 것

- **판정·경보 변경.** 선행 트랙 §4 — 알림 경로는 특이도 99.99% 가 필요하고 착용 감지 없이는
  못 만든다. 이 트랙은 표시만이다.
- **`무동작` 을 `벗음` 이나 `응급` 으로 적기.** 둘 다 모른다. 아는 것만 적는다(08-20 `수신 중` 과 같은 자).
- **`mv` 사용.** 위 철회 참조.
- **`motionStillSec` 값에 `now - ts` 를 더하기.** sticky 와 겹치면 이중 계산이고, `!stale` 조건이
  그 차이를 60초 안으로 묶는다. 워치 값을 그대로 보인다.
- **갤럭시 대칭화.** 갤럭시는 벗으면 수집을 끊어 `대기/연결끊김` 이 된다 — 이미 정직하다.

## 08-28 저녁 추가 검토 — 충전 감지 · 전송 주기 (사용자 요청 · 00335 배포 직후)

질문 둘. ① 충전 중이면 벗은 것이다 — 인지할 수 있나. ② 벗으면 전송 주기가 길어지나 — 길어지면 미착용 의심으로 쓸 수 있나.

### ① 충전 = 벗음. 신호는 있다. 그런데 그 구간은 화면이 이미 `연결끊김` 으로 보여 준다
- 워치 코드는 `batteryLevel` 만 읽어 `bat` 로 싣는다(`WatchStreamer.swift:416-417,530`).
  `WKInterfaceDevice.batteryState`(`.charging`/`.full`)는 **안 읽는다** — 한 줄이고 권한 없음.
  갤럭시는 `BatteryManager` 로 같은 값이 나오고, 하드웨어 off-body 가 이미 있어 벗음 자체가 잡힌다.
- 서버만으로도 간다 — `battery_pct` 가 연속 표본에서 **오르면** 충전이다(5% 단위 · +5 까지 3~5분).
- ★ 실측은 "충전 중엔 표본이 거의 안 온다" 다.
  ```
  오늘 19:20~20:20  배터리 15 → 95 · 그 창의 표본 0~2건 · 20:20 에 836건이 한꺼번에(ts 뭉개짐 · still 3580s)
  7일               배터리 상승 시간대 5개(08-25) · 표본 4~37건/시간(정상 720) · 심박 0~26건
  ```
  ⟹ 충전 구간은 화면에서 이미 `연결끊김`(stale) 이다. `수신 중` 으로 잘못 뜨는 창이 **아니다**.
- 남는 가치는 **사후 설명** — 끊김이 끝난 뒤 배터리가 크게 올라 있으면 "충전이었다" 를 붙일 수 있다
  (`연결끊김 58분 · 충전`). 서버 라벨이라 앱 무변경. 실시간 판정 가치는 낮다.
- 결정 = `chg`(batteryState) 는 재서명 창(09-01~03)에 **양쪽 워치 동시 추가**(지시 ③). 비용이 한 줄이고,
  정확한 값이 있으면 사후 설명이 추정(배터리 상승)에서 사실로 바뀐다. 단독 트랙으로는 열지 않는다.

### ② 전송 주기는 벗어도 안 변한다 — 기각
- flush 타이머는 5.0s 고정(`WatchStreamer.swift:477`), 착용과 무관. 심박은 30초 이내 신선한 값이 있을 때만
  싣는다(`:495`) — 상시 워크아웃 아래서는 벗어도 그 값이 계속 온다(08-13·08-18·08-28).
- 오늘 실측(5분 버킷 · 표본 간 간격).
  ```
  착용 16:20~16:35   p50 5.0s · max 5.1s
  벗음 16:40~16:50   p50 5.0s · max 5.1s   ← 1초도 안 늘었다
  이후 16:50~17:50   p50 0.0s · max 90~410s — 벗은 창과 착용·이동 창(17:35 · still 2s)에 똑같이
  ```
  간격이 흐트러지는 것은 착용이 아니라 **전달**(폰 링크 · `ts=sentAt` 뭉개짐 · watch-delivery-lag §9)이다.
- ⟹ "주기가 길어지면 미착용 의심" 은 판별력 0 이고, 폰이 멀어진 것을 벗음으로 오판한다.

### 남는 것
- 벗음을 실시간으로 가르는 축은 여전히 없다(심박 · `mv` · 주기 전부 기각). 화면은 `무동작` 으로
  "가서 보라" 만 말한다 — 이 트랙의 결론이고 오늘 저녁 검토로도 안 바뀌었다.
