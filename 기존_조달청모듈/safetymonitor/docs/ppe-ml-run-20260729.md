**⚠️ 단 5차의 존재 이유인 "E63 밖에서 head 검출 > 0" 은 아직 측정하지 못했다 —

## 2. 함정 ① — 부분 라벨이 평가를 오염시킨다

E63 은 `head`·`helmet` 만, HHW 는 `head`·`helmet` 만 라벨링돼 있다.
val 1,906장의 대부분이 이 둘이라, **사람을 정확히 검출해도 정답이 없어 오탐으로 계산**된다.

```
전체 val        person P 0.493   ← "person 이 무너졌다"고 오판했다
sh17+css 만     person P 0.891   ← 1차 0.821 보다 오히려 좋다
```

`safety_vest` `shoes` `foot` `gloves` 도 같은 이유로 눌린다.

**대응** — v4 노트북에 `fair_eval` 신설. 클래스마다 **그 클래스를 라벨링한 출처의 이미지에서만**
평가한다.

```
person, safety_vest         ← sh17 + css
head, helmet                ← css + hhw + e63
foot, shoes, hands, gloves  ← sh17
```

## 3. 함정 ② — 데이터셋마다 head/helmet 박스의 의미가 다르다

같은 모델인데 평가 대상에 따라 helmet 이 4배 차이 났다.

```
전체 val (1,906장)   helmet P 0.813  mAP50 0.854
sh17+css (408장)     helmet P 0.219  mAP50 0.177
```

라벨 겹침을 직접 세어 확인했다(IoU > 0.3 기준).

| 출처 | 공존 이미지 | helmet 중 head 와 겹침 |
|---|---|---|
| sh17 | 71 | **78.2%** |
| css | 119 | 0.0% |
| hhw | 151 | 0.7% |
| e63 | 0 | — (공존 자체가 없음) |

| 출처 | `head` | `helmet` |
|---|---|---|
| E63 · CSS · HHW | 안전모 **미착용** 머리 | 안전모 **착용** 머리 (배타적) |
| **SH17** | **머리 (착용 여부 무관)** | **안전모 물체 자체** |

SH17만 같은 머리에 둘을 동시에 붙이고 박스 정의도 다르다. IoU 가 안 맞아 서로를
오탐/미탐으로 만든다.

**★ 1차 실패(교차 홀드아웃 head P 0.181)의 진짜 원인이 개수 불균형이 아니라 이것일 수 있다.**
1차는 SH17 비중 0.5였으므로 모델이 "안전모를 써도 head" 라고 배웠을 여지가 크다.

**대응** — 4차에서 SH17 의 `head`·`helmet` 매핑을 제거하고
`person`·`foot`·`shoes`·`hands`·`gloves`·`safety_vest` 만 쓴다.

## 4. 함정 ③ — 홀드아웃을 학습에 넣어 채점 불능이 됐다

1차 홀드아웃이던 HHW 를 3차에서 학습에 편입했다(균형 교정 목적). CSS 도 학습에 있다.

E63 로 대체하려 했으나 **43개 시퀀스 전부가 학습에 노출**돼 불가능했다.

```
E63 시퀀스 43개 · 시퀀스당 프레임 중앙값 567 (최대 5,280)
프레임 단위로 20% 무작위 추출 → 통째로 빠진 시퀀스 0개
```

567장짜리 시퀀스가 통째로 빠질 확률은 사실상 0이다.

Roboflow 후보 3종도 전부 부적합했다.

| 후보 | 문제 |
|---|---|
| `safety-helmet-and-reflection-vest` | `head` 클래스 없음 |
| `helmet-detection-v3` | 클래스 목록이 CSS 와 동일 — 재업로드 |
| `safety-helmet-wearing-dataset` | Roboflow API 오류 |

누수를 인정한 상한선 평가는 `head P 0.919 · helmet P 0.955` 로 나왔으나, 같은 시퀀스의
옆 프레임이라 **반증에 실패했을 뿐 판정 근거는 되지 못한다.**

**대응** — 4차부터 학습 **전에** 시퀀스를 통째로 떼어 홀드아웃으로 예약한다.
`link_yolo(exclude_seqs=...)` + 학습셋과 교집합 0 을 `assert` 로 강제.

```
시퀀스 43개 중 12개 예약 → 2,166장 (head 1,566 · helmet 600)
```

**프레임 단위 무작위 분할은 영상 데이터에서 홀드아웃을 만들지 못한다.**

## 6. 4차 설계

```python
SH17_MAP = {'person', 'safety_vest', 'foot', 'shoes', 'hands', 'gloves'}   # head·helmet 제거
SH17_FRACTION = 0.5    # 0.3 → foot 499 로는 학습 불가였다 (831 로 증가)
CSS_FRACTION  = 1.0
HHW_FRACTION  = 0.15   # 0.5 → helmet 편중 + person 라벨 없어 평가 오염
E63_FRACTION  = 0.4    # 0.2 → 배포 도메인 · 라벨 배타적
EPOCHS        = 30     # 20 에서 손실이 끝까지 하락 중이었다
E63_HOLDOUT_SEQ_RATIO = 0.30   # ★ 시퀀스 12개 예약
```

```

학습      약 17,200장
★ helmet : head = 1 : 0.69
A100 30에포크 약 1.8시간 / T4 약 10.3시간
```

## 7. 관제웹 CCTV 라이브 투입 — 우리 모델이 처음 실전에

학습과 별개로, **아이폰 카메라 → 관제웹 CAM-03** 을 우리 학습 모델로 돌렸다.
"현행 `vyra_ppe.pt` 를 교체할 수 있는가" 가 이 트랙의 목표이므로, 라이브에 태우는 것이
shadow 비교의 실질적 시작이다.

```
iPhone(사파리·Tailscale)
  │ https://yahboom-1.<tailnet>.ts.net:8443/   ← 젯슨이 캡처 페이지를 직접 서빙
  ▼
Jetson  yolo26 TensorRT 14.7ms · 박스·한글 라벨 · 고정 cadence push
  │ POST /cctv/ingest3?drawn=1   (display-only)
  ▼
Cloud Run  추론 0  →  관제웹 CAM-03
```

관제웹 헤더가 `CAM-03 Live (Jetson TensorRT) PPE (yolo26)` 로 바뀌었고,
사람 2명·안전모 미착용 2건을 정확히 판정했다.
**같은 장면에서 Hexmon 은 person 을 0명으로 잡았다** — 3차 person P 0.891 과 일치한다.

Cloud Run 이 추론을 하지 않으므로 서버 CPU 부하가 0 이고, 과거 429 의 원인이던
"단일 인스턴스 서버 추론 1개 제한"에서 벗어나 카메라를 늘릴 여지가 생겼다.

### 관문 — `getUserMedia` 는 보안 컨텍스트를 요구한다

브라우저 카메라는 HTTPS 에서만 열린다. `sudo tailscale cert <name>.ts.net` 으로
**유효한 Let's Encrypt 인증서**를 받아 젯슨이 직접 HTTPS 로 서빙해 해결했다.
Cloud Run 페이지에서 젯슨으로 POST 하는 방식은 mixed content 로 막힌다.

### 끊김 수정 — 왕복 직렬화 (3.2 → 4.89 fps)

캡처 페이지가 한 번에 한 장만 보내는데 왕복(실측 평균 264ms·최대 420ms)이
`setInterval` 주기 200ms 를 넘으면 다음 tick 이 버려졌다.
① 파이프라이닝(3장 동시) ② 즉시 응답 ③ 디코드 스레드풀 로 해소.

### ★ 전송 천장 = 약 4.8 fps · iOS Safari 타이머 스로틀

| 설정 | 결과 |
|---|---|
| 640×360 · Q0.5 · 목표 5 | 4.80 fps |
| 640×360 · Q0.5 · 목표 8 · 슬롯 4 | 4.80 fps |
| 480×270 · Q0.4 · 목표 8 | 4.75~5.20 fps |

해상도 44% 감소·목표 상향·슬롯 증설 어느 것도 효과가 없었다.
네트워크·인코딩·젯슨이 전부 배제되고 남는 것은 **Safari 의 타이머 스로틀(≈208ms)** 이다.
5fps 초과는 **WebCodecs** 또는 **RTMP 송출앱**으로 방식을 바꿔야 하며, WebSocket 은 효과가 없다.
PPE 판정에 필요한 갱신율은 초당 3~5회라 현재로도 목적에는 충분하다.

소스 = [cctv-ai/edge/phone_ppe_relay.py](../cctv-ai/edge/phone_ppe_relay.py) ·
절차·한계 상세 = [cctv-ai/README.md](../cctv-ai/README.md)

## 9. 4차 판정 (2026-07-30) — ★ 게이트 통과 · 그리고 도메인 한계

4차 학습이 30에포크 완주했고(A100 재개 후 8.7분/에포크), 예약해 둔 홀드아웃으로 판정했다.

### 예약 홀드아웃 — 학습 미노출 시퀀스 12개 · 2,166장

```
head    P 0.800 · R 0.893 · mAP50 0.906 · mAP50-95 0.654
helmet  P 0.946 · R 0.433 · mAP50 0.555 · mAP50-95 0.365
all     P 0.873 · R 0.663 · mAP50 0.731
```

**1차 교차 홀드아웃 `head P 0.181` → 4차 `0.800`** — precision 4.4배 · recall 3.4배.
`SH17 의 head·helmet 라벨 의미 충돌 제거`가 정답이었음이 확인됐다.

### 2층 게이트 — 통과

```
conf   P      R      F1     TP    FP  FN
0.10  0.999  0.941  0.969  1473   1   93   ← 통과
0.15  0.999  0.928  0.963  1454   1  112   ← 통과 (권장 운영값)
0.20  0.999  0.917  0.956  1436   1  130   ← 통과
0.35  1.000  0.870  0.931  1363   0  203
```

요구 `recall ≥ 0.90 @ precision ≥ 0.85` 를 세 임계에서 만족했다.
**음성 600장에서 오탐 1건.** 관제 알림의 최대 위험 요인이 사실상 없다.

### 원인 — 클래스마다 학습 도메인이 갈려 있다

| 클래스 | 학습 출처 | 그 출처의 장면 |

### 함의 셋

1. **게이트 통과는 E63 도메인 안에서만 유효하다.** 예약 홀드아웃이 E63 이라 결함이 가려져 있었다.
2. **`judge_ppe`(person↔helmet 포함관계)는 E63 현장에서 못 쓴다** — person 이 0이므로.
   `bare_head_eval`(이미지 단위)로 잰 게이트는 유효하나 **개인별 판정은 불가능**하다.
3. **현행 Hexmon 이 이 점에서 강하다** — 사무실 근거리에서도 미착용을 정확히 잡았다.
   교체 판정에서 불리한 요소이므로 정직하게 기록한다.

### ★ 5차 해법 — SH17 을 통째로 뺀 것이 과했다

SH17 의 `head` 는 helmet 과 78.2% 겹쳐 충돌을 일으켰다. 그런데
**겹치지 않는 head 만 골라내면 그것이 곧 "안전모 안 쓴 머리"** 이고 우리 정의와 일치한다.

```
SH17 head 중  helmet 과 IoU > 0.3 겹침 → 버린다 / 겹치지 않음 → 채택 (약 20% 잔존)
```

**라벨 충돌은 피하면서 도메인 다양성만 가져온다.** 4차 부작용을 정확히 되돌리는 방법이다.

```python
SH17_HEAD_FILTER   = True      # ★ helmet 과 겹치지 않는 head 만
SH17_HEAD_IOU      = 0.3       #    겹침 판정 임계
E63_PERSON_PSEUDO  = True      # ★ E63·HHW 에 person 자동 라벨(COCO 사전학습)
PSEUDO_CONF        = 0.5       #    자동 라벨 신뢰도 하한
HHW_FRACTION       = 0.45      # helmet recall 복원
SCALE              = 0.8       # 스케일 내성 보강 (설계 밴드 0.7~0.9 의 중간값)
EPOCHS             = 30 · E63_HOLDOUT_SEQ_RATIO = 0.30   # 유지
```

### ★★ 교훈 — 홀드아웃 도메인이 결함을 가린다

**예약 홀드아웃만으로는 이 문제를 절대 볼 수 없었다.** 홀드아웃이 학습과 같은 도메인이면
"학습 안 된 도메인에서 통째로 실패하는" 결함이 측정되지 않는다.

측정 문제가 아니라 실제다. recall 은 유지(0.841 → 0.844)하고 precision 만 떨어졌으니
**person 을 더 남발한다**. 자동 라벨의 대가다 — `conf 0.5` 자동 박스가 사람 라벨보다
느슨하거나, 검출 실패한 15%(1,715장)가 배경으로 학습돼 혼선을 준 것이다.

`judge_ppe`(person↔helmet 포함관계)에서 person 남발은 유령 작업자를 만들어 준수율을
왜곡한다. **완화책** = 운영에서 person 만 conf 를 따로 높게 잡는다(R 여유 있음).

### ★★★ 함정 — ultralytics `res.path` 가 평가를 조용히 무효화했다

**오늘 가장 값비싼 교훈이다.** 같은 원인으로 세 번 막혔다.

```
ultralytics 8.4.112 · 리스트 소스
  입력      /content/ppe3/images/val/css_-1079-_png_jpg.rf.1909….jpg
  res.path  image0.jpg        ← 입력 경로가 아니라 순번 이름
```

4차의 8.4.x 는 입력 경로를 보존했다. **버전이 올라가며 거동이 바뀌었고, 그 결과
4차에서 정상 동작한 코드가 아무 오류 없이 잘못된 답을 냈다.**

| 증상 | 실제 원인 |
|---|---|
| `person 자동 라벨 0개` (11,589장) | `lb = res.path.stem + '.txt'` → `image0.txt` 없음 → 전부 skip |
| 진단 프로브도 0 | `tgt[:6]` 이 같은 시퀀스 연속 프레임 6장 — 대표성 0 |
| `미착용자 있는 장면 0장` (val 2,652장) | 정답 라벨 전부 미인식 → GT 전부 False → P·R 전부 0 |

**세 번째가 가장 위험했다.** `bare_head_eval` 은 7·8·9장이 공유하므로 그대로 돌렸으면
**5차의 판정 게이트를 "미달" 로 오판**했다. 표가 정상적으로 출력되기 때문에 눈으로는 안 걸린다.

**대응(노트북에 반영)**
- 외부 라이브러리가 돌려주는 식별자에 의존하지 않는다 → **입력 리스트와 `zip` 으로 1:1 대응**
- `stream=True` 제거(배치 추론엔 이득 없음)
- **`assert sum(gt) > 0`** — 정답이 0건이면 멈춘다. 조용히 0을 내놓아선 안 된다
- `assert added > 0` — 자동 라벨이 0개면 멈춘다
