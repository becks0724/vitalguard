# 긴급재난문자 연동 — 컨텍스트 노트

> 결정과 근거를 쌓는 문서. 작업 목록은 [checklist.md](checklist.md).
> 시작 2026-07-30. 근거 데이터 = `행정안전부_긴급재난문자` 샘플 CSV 100건(2023-09-16 ~ 09-19).

---

## D-01 · 데이터 출처 — data.go.kr 이 아니라 safetydata.go.kr 이다

공공데이터포털 `행정안전부_긴급재난문자`(15134001)는 **LINK형 API** 라 실제 호출은
재난안전데이터공유플랫폼 `safetydata.go.kr` (dataSn=228)으로 넘어간다.
구 `재난문자방송 발령현황` · `(지역별)` API 는 신규 접근이 막혔고 종료 예정이다.

**근거.** 포털 상세 페이지가 safetydata 로 리다이렉트하고, 대체 안내가 명시돼 있다.
**함의.** 인증키·호출 URL·트래픽 정책이 기존 `apis.data.go.kr` 계열(KMA·KOSHA)과 **다르다.**
`kma.ts` 의 호출 코드를 복사하면 안 되고 어댑터를 따로 쓴다.

---

## D-02 · 샘플 CSV 를 골든 픽스처로 쓴다

인증키·명세서가 없어도 **파싱·정규화·지역매칭·알림포맷은 CSV 100건만으로 전부 개발·테스트한다.**
실 API 는 마지막에 "HTTP 응답 → 동일한 레코드 배열" 어댑터 한 겹만 붙인다.

**근거.** 이 순서를 뒤집으면 키 발급이 전체 일정을 막는다. 그리고 실 API 는 재난이 없는 날엔
관심 유형 응답이 0건이라 **정상 동작을 확인할 시험지가 없다.** 고정 픽스처가 유일한 회귀 방어선이다.

**픽스처에 반드시 남길 케이스**(전부 샘플에 실재).

| 케이스 | 실제 값 | 검증 대상 |
|---|---|---|
| 괄호 안 콤마 | `임진강 수계지역(경기도 연천군,파주시)  ,경기도 임진강 ` | 지역 분리가 안 깨지는가 |
| 다지역 나열 | 고양시 3개 구 (총 16건) | 콤마 분리 + 개별 매칭 |
| 동 단위 | `서울특별시 강남구 역삼동` | 시·도까지만 좁혀 매칭되는가 |
| `~ 전체` | `경상남도 전체` | 시·도 전역 매칭 |
| 긴급재난 1건 | 경기 안산 단원구 · 호우 | severity=danger 승격 |
| 실종자 31건 | `[서울경찰청] … 찾습니다` | **전량 차단** |

## D-03 · 수신 대상 = 재난재해만. 화이트리스트 방식

**받는다.** 호우 · 산사태 · 폭염 · 강풍 · 대설 · 지진 · 태풍 · 산불 (+ 확장 여지)
**안 받는다.** 실종자 찾기 · 교통통제 · 그 밖의 생활정보

**근거 세 가지.**

1. `DST_SE_NM` 은 코드값이 아니라 **한글 자유 문자열**이다. 발령 기관이 새 값을 쓰면 우리가 모르는 값이 들어온다.
2. 샘플의 `기타` 31건은 전부 **실종자 찾기**였다. 즉 이 필드만으로는 성격을 판별 못 한다.
3. 샘플은 **나흘치**다. 폭염·강풍·대설·지진·태풍·산불은 한 건도 등장하지 않는다.
   **샘플로 값 목록을 확정하면 안 된다.**

**그래서 블랙리스트(기타 제외)가 아니라 화이트리스트다.** 블랙리스트는 유형이 늘 때마다 구멍이 생긴다.
다만 **모르는 값은 버리되 로그를 남긴다** — 운영하며 목록을 사람이 채운다.

## D-04 · 위치 = 작업자 GPS 평균 → 시·도. **새로 만들 것이 0이다**

사용자 요구("작업자 gps 평균 값 기반, 범위는 시·도")를 만족하는 자산이 이미 전부 있다.

| 필요한 것 | 기존 자산 | 위치 |
|---|---|---|
| 작업자 GPS 평균 | `fieldCoords` useMemo | `app/components/DemoDashboard.tsx:4137` |
| 평균값 서버 캐시 | `site_coord_daily` · `captureSiteCoordDaily()` | `lib/db.ts:2194` |
| 무인 경로용 좌표 조회 | `getLatestSiteCoord()` (폴백 `getLatestWeatherDaily()`) | `lib/db.ts:2156` |
| 좌표 → 시·도 | `latLonToSido()` | `app/lib/kma-regions.ts:30` |
| 인근 시·도(반경 120km) | `nearbySidos()` · `NEAR_SIDO_KM` | `app/lib/kma-regions.ts:46` |
| 괄호 보존 지역 분리 | `splitRegions()` | `app/lib/kma-regions.ts:73` |
| 지역 ↔ 시·도 매칭 | `regionMatchesSido()` | `app/lib/kma-regions.ts:100` |

`fieldCoords` 는 이미 **한국 범위 게이트**(위 32.5~39.5 / 경 123.5~132.5)로 시뮬레이터 기본값·좌표 swap 오염을 막고,
**소수 3자리(≈110m) 양자화**로 GPS 지터에 의한 재호출을 억제한다. 그대로 쓴다.

`splitRegions()` 는 기상특보의 `경기도(안산, 시흥)` 때문에 만든 함수인데,
재난문자의 `임진강 수계지역(경기도 연천군,파주시)` 가 **정확히 같은 문제**다. 재사용이 우연이 아니다.

**결론.** 신규 라우트는 `/api/kma-warning` 과 똑같이 `lat`/`lon` 쿼리만 받으면 되고,
크론 경로는 `/api/cron/env-check` 가 이미 좌표를 조회해 자체 호출하므로 **한 줄 추가**로 끝난다.

## D-05 · 매칭 범위를 시·도로 고정하는 이유

시·군·구나 동 단위로 좁히지 않는다.

1. **평균 좌표는 특정 지점이 아니다.** 여러 작업자의 중점이라 시·군·구 경계를 쉽게 넘나든다.
2. **110m 양자화**가 걸려 있어 기초단체 경계 부근에서 판정이 흔들린다.
3. **재난은 광역으로 번진다.** 옆 동에 산사태 주의보가 떴는데 우리 동이 아니라고 거르면 그게 오히려 사고다.
4. 샘플의 수신지역 단위가 시·도 전체 / 시·군·구 / 동 / 하천 수계로 **뒤섞여 있어** 기초단체 정규화 자체가 불안정하다.

⚠️ **알려진 한계.** 작업자가 여러 현장에 흩어져 있으면 평균 좌표는 아무도 없는 중간 지점을 가리킨다.
경기·충남처럼 넓은 시·도에서는 시·도 판정까지 틀어질 수 있다. 지금은 단일 현장 전제라 수용하되,
멀티 현장 단계에서 **현장별 좌표**로 바꿔야 한다. (`fieldCoords` 의 날씨·특보도 같은 전제를 이미 깔고 있다.)

**인근 시·도는 "참고"로만 표시한다.** 알림은 쏘지 않고 화면에만 남긴다. 기상특보가 `nearbySidos` 로
인근 특보를 보여주는 것과 같은 맥락이다 — 옆 시·도 상황은 판단 재료지 경보는 아니다.

## D-06 · CRT_DT 는 반드시 KST 를 명시해 파싱한다

형식이 `2023/09/19 12:22:17` 이다. ISO 가 아니라 **슬래시 형식**이라
`new Date("2023/09/19 12:22:17")` 은 **실행 환경의 로컬 시각**으로 해석된다.
Cloud Run 컨테이너는 **UTC** 이므로 그대로 넣으면 **9시간이 밀린다.**

신선도 게이트가 이 값 위에 서 있으므로, 9시간 오차는 곧 "모든 문자가 만료" 또는 "만료가 안 됨"이 된다.
**명시적으로 `+09:00` 을 붙여 파싱한다.** 로컬 개발(맥=KST)에서는 증상이 안 보이고 배포 후에만 터지는 계열이다.

## D-07 · 신선도 게이트가 곧 "해제" 역할을 한다 — ★ 이걸 빠뜨리면 알림이 딱 한 번만 간다

**함정.** `notifyEnvAlerts()` 는 `itemKey` 단위로 이전 severity 를 DB 에 저장하고
`shouldSendEnv(prev, next)` = **악화 전이일 때만** 발송한다 (`lib/env-alert-notify.ts`).
`prev=caution, next=caution` 이면 발송하지 않는다.

기상특보는 해제되면 목록에서 빠져 자연히 normal 로 돌아간다.
그런데 **재난문자에는 해제 문자가 없다.** 발령만 있고 끝이다.

→ 관심 유형이 한 번 `caution` 이 되면 **영원히 caution 에 머물러 두 번 다시 알림이 안 간다.**

**해법.** 폴링 때마다 **화이트리스트 전 유형**을 `notifyEnvAlerts()` 에 넘긴다.
신선한 문자가 있는 유형은 실제 severity, 없는 유형은 **`normal`** 로.
그러면 신선도 만료가 곧 해제가 되어 다음 발령 때 정상적으로 다시 발송된다.

```
매 폴링:
  호우   ← 30분 전 문자 있음  → caution   (전이하면 발송)
  산사태 ← 신선한 문자 없음    → normal    (해제 = 다음 발령 대비)
  폭염   ← 없음               → normal
  …화이트리스트 전 유형을 매번 넘긴다
```

## D-08 · 중복 제거는 SN 집합. 연속성을 가정하지 않는다

폴링이라 같은 문자를 계속 다시 받는다. 키는 `SN`(일련번호)이다.

⚠️ **SN 은 연속하지 않는다.** 샘플은 100건인데 번호 폭이 205151~205376 = **226** 이다.
이 CSV 가 전체가 아닌 추출본이기 때문인데, 실 API 도 그럴 수 있다고 봐야 한다.

→ `lastSN + 1` 같은 **증분 커서 방식 금지.**
→ **최근 N건을 받아 SN 집합으로 걸러낸다.** 집합은 신선도 윈도우와 같은 기간만 유지해 무한 증가를 막는다.

부수 관찰. `REG_YMD`·`MDFCN_YMD` 는 샘플 100건 전부 `CRT_DT` 날짜와 같고 수정 이력 0건이다.
**정정 발령은 당장 다루지 않는다.** 다만 나흘치라 단정 못 하므로 `MDFCN_YMD ≠ REG_YMD` 면 로그를 남긴다.

## D-09 · 알림 itemKey 는 유형 단위. SN 이면 안 된다

```
itemKey  = "disaster:호우"                    ← 유형 단위
severity = 긴급재난 → danger / 안전안내 → caution
detail   = 발령시각 · 지역 · 본문 90자
```

**근거.** `itemKey = disaster:${SN}` 으로 두면 ① `env_alert_state` 행이 문자 개수만큼 **무한 증가**하고
② 매 키가 "이전 없음 → 발송"이라 **전이 판정이 무의미**해져 억제 장치가 통째로 무력화된다.
호우 문자 10건이 쏟아지면 10번 발송된다.

유형 단위면 "정상→주의" 1회, 나중에 긴급재난이 뜨면 "주의→위험" 1회로 끝난다.
기존 날씨·기상특보 알림과 동작이 일관된다.

**severity 매핑 근거.** 샘플 100건 중 `긴급재난` 은 1건뿐이고
(`[기상청] 20:33 단원구 대부동 인근 시간당 50mm 이상 강한 비`) 나머지 99건이 `안전안내` 다.
즉 `긴급재난` = 실제 위험 임박 신호라 `danger` 가 맞다.

**본문 90자.** 샘플 전건이 55~90자(평균 82)로 CBS 상한 안에 있다. 자를 필요가 사실상 없다.

## D-10 · 개인정보를 설계로 회피한다

'기타' 31건에는 **실명·나이·키·몸무게·인상착의**가 그대로 들어 있다.

```
[서울경찰청] 노원구에서 실종된 김현주씨(여,41세)를 찾습니다 -160cm,68kg,꽃무늬티,회색칠부바지,검정슬리퍼
```

**화이트리스트를 통과한 것만 저장한다.** 그러면 이 데이터는 애초에 우리 DB 에 들어오지 않는다.
"일단 전건 적재하고 나중에 거른다"를 피할 이유가 하나 더 있는 셈이다.

## D-11 · 인증 — 조회는 공개, 알림 발사는 세션·크론키

`/api/kma-warning` 의 감사 지적(BE-AUTHZ-02)을 그대로 답습한다.
무인증 GET 으로 외부인이 텔레그램을 임의 발사시킬 수 있었던 사고가 이미 한 번 있었다.

```
조회 GET            → 공개
텔레그램 발사 조건  → verifyBasicAuth(로그인 세션) || cronAuth(x-cron-key)
목업 데이터         → 절대 발사 안 함 (source === "live" 일 때만)
```

## D-12 · 폴링 주기 — ✅ 실측 정정 (2026-07-31)

**초안이 틀렸다.** 타 인터페이스(DSSP-IF-00195) 사례의 **일일 100건**을 가정해 15분을 역산했는데,
실제 발급 내역에는 **일일호출량 1000건**으로 나온다("일일호출량이 0이면 최대 호출량(1000건)입니다").

```
예산 1000회/일
  15분(96회)   =  9.6%   ← 초안. 지나치게 보수적
  ★ 5분(288회) = 28.8%   ← 채택. 재난 긴급성에 맞고 여유 3.5배
    2분(720회)  = 72.0%   ← 재배포·수동 테스트 여유가 사라져 위험
```

**캐시 TTL 도 15분 → 5분.** 이 값이 곧 호출 예산이다(기상특보는 10분).

⚠️ **로컬 개발도 같은 예산을 쓴다.** 키가 하나라 `.env.local` 로 돌리는 테스트 호출이
프로덕션 몫을 깎는다. 개발 중에는 목업 폴백(키 미설정)을 기본으로 두고 실 호출은 필요할 때만.

## D-16 · ⚠️ 인증키 만료 2027-07-31 — 조용히 목업으로 떨어진다

발급 내역의 **만료일자 = 2027-07-31**(발급 1년). 갱신하지 않으면 그날부터 인증이 실패한다.

**왜 위험한가.** 우리 설계는 `kma.ts` 정책을 따라 **키가 없거나 실패하면 목업 폴백**이다.
만료돼도 화면은 200 으로 잘 뜨고 카드도 나온다 — **내용만 가짜**가 된다.
관제 화면에서 "재난 없음"으로 보이는데 실제로는 조회가 죽어 있는 상태가 최악이다.

**대응 두 가지.**
1. **캘린더에 2027-07 갱신 일정 등록**(사람 쪽 방어).
2. **프로덕션에서 `source: "mock"` 이면 경고 로그**(Phase C 항목). 키가 설정돼 있는데도
   목업으로 떨어졌다면 그건 폴백이 아니라 장애다 — 둘을 구분해 로그해야 한다.

**함께 확인된 것.** 유저아이피 `*.*.*.*`(전체 허용)로 정상 등록됐다(D-13 대로).
수집방법 = 시스템연계 · 정보제공기관 = 행정안전부.

## D-13 · 활용신청의 "아이피" 항목 = `*.*.*.*` (전체 허용)

신청서의 필수 입력란이고 예시가 `개인 IP 121.xxx.xxx.xxx` / `대역 121.xxx.*.*` / `전체 `*.*.*.*`` 로 제시된다.

**이 칸의 목적.** 발급된 인증키를 **여기 적은 IP 에서 호출할 때만** 받아준다.
키가 유출돼도 남의 IP 에서는 못 쓰게 하는 화이트리스트다. 즉 **키 + IP 이중 자물쇠**다.

**왜 우리는 IP 를 못 적나.** 호출자가 **Cloud Run** 이다.
Cloud Run 의 아웃바운드 IP 는 기본적으로 Google 공용 풀에서 **동적으로 배정**된다 —
인스턴스가 새로 뜰 때마다, 리비전이 바뀔 때마다 달라진다.
오늘 확인한 IP 를 적으면 **내일 403 이 난다.**

**실측(2026-07-30).**

```
gcloud run services list → vitalguard-dashboard, cctv-ai 둘 다 VPC 커넥터 없음
gcloud compute addresses list → Compute Engine API 자체가 비활성 (PERMISSION_DENIED)
```

= 이 프로젝트에는 **고정 아웃바운드 IP 가 존재하지 않고, 만들 준비도 안 돼 있다.**

**고정 IP 를 원한다면 필요한 것.** Compute Engine API 활성화 → VPC 네트워크 →
**Cloud NAT + 예약 고정 IP** → Cloud Run `--vpc-egress=all-traffic`.
⚠️ **Cloud NAT 게이트웨이는 상시 과금**이라 이 API 하나 때문에 세울 이유가 없다. 보류한다.

**전체 허용의 대가와 상쇄책.** IP 자물쇠를 포기하므로 **인증키가 유일한 방어선**이 된다. 그래서

- 키는 **Secret Manager** 에만 둔다(`.env` 커밋 금지)
- 호출은 **서버 라우트에서만** — 클라이언트 번들에 절대 넣지 않는다
- 이 조건은 D-11(조회 공개·발사는 세션/크론키)과 이미 일치한다

참고. 개발 중 로컬 맥에서 호출하더라도 **ISP 가 주는 IP 는 수시로 바뀐다.**
사무실 고정회선이 있어도 대역 허용(`121.xxx.*.*`) 정도가 한계다.
어차피 Cloud Run 이 최종 호출자라 전체 허용이 유일한 실용 답이다.

## D-14 · ★★ 발견 — `latLonToSido` 가 도(道) 현장을 인접 광역시로 오판한다 (정확도 50%)

Phase B 구현 중 실측으로 드러났다. **D-04 에서 "새로 만들 것 0" 이라 적은 전제가 부분적으로 깨진다.**

**원인.** `latLonToSido()` 는 **17개 시·도 중심점 최근접(유클리드)** 이다.
광역시는 면적이 작아 중심점이 시가지에 있고, 도(道)는 넓어 중심점이 멀다.
그래서 **광역시에 인접한 도 지역이 전부 광역시로 빨려 들어간다.**

**실측(주요 시·군 34곳 · 2026-07-30).**

```
오판 17/34 = 정확도 50%

경기 안산 → 인천      경기 고양 → 서울      경기 수원 → 서울
경기 성남 → 서울      경기 김포 → 인천      경기 파주 → 서울

경남 창원 → 부산      경남 김해 → 부산      경남 양산 → 부산
경북 포항 → 울산      경북 구미 → 대구      경북 경산 → 대구
```

**영향 범위는 좁다.** `latLonToSido`·`nearbySidos` 사용처는 `app/lib/kma.ts` **한 곳**뿐이고
기존 `kma-regions.test.ts` 는 광주 시청 좌표(광역시 본체)만 검증한다 = **개선해도 깨질 기존 테스트가 없다.**

### ✅ 해소 (2026-07-30) — A안(시·도 대표점 다중 시드) 채택

`kma-regions.ts` 의 `latLonToSido` 를 **시·도당 대표점 여러 개 중 최근접**으로 교체했다.

덤으로 기상특보도 함께 정확해졌다 — 안산 현장이 인천 특보를 보던 것이 경기 특보로 고쳐졌다.

## D-15 · ⚠️ 미결 — '기타' 안에 진짜 재난 대피 안내가 섞여 있다

D-03 에서 "'기타' 31건은 전부 실종자 찾기"라고 적었는데 **정확하지 않았다.** 실측 결과다.

```
'기타' 31건
  ├ 27건  실종자 찾기      ← 개인정보, 차단이 맞다
  ├  2건  사천시 싱크홀 도로 통제(중복 발송)
  └  2건  ★ 하천 수위 대피 안내 ← 명백한 재난인데 함께 버려진다
        [한국수자원공사] 주암댐 수문방류로 하류 수위 상승 … 안전한 곳으로 대피
        [경기도청] 임진강 수위 1m 이상 상승 중 … 즉시 대피하시기 바랍니다
```

**현재 동작.** 화이트리스트가 유형만 보므로 이 2건도 버린다. 사용자 지시("기타는 받지 않는다")대로다.

**재승격이 가능한가 — 실측으로 확인한 분리 조건 두 가지.**

| 기준 | 실측 |
|---|---|
| 발신기관 | 실종자 27건 = **전부 경찰청**. 경찰청 발신 27건 = **전부 실종자**. 완전한 1:1 |
| 본문 키워드 | 실종자 문자에 "대피" **0건**. `'기타' + '대피'` = 정확히 위 2건 |

두 기준 모두 샘플에서는 **개인정보 유출 0** 으로 하천 대피만 건져낸다.
다만 나흘치 표본이라 일반화 보장은 없고, 키워드 규칙은 문구가 바뀌면 샌다.

### ✅ 결정 (2026-07-30) — ②안 재승격 채택

화이트리스트를 통과하지 못한 문자라도 **두 조건을 모두** 만족하면 되살린다.

```
① 발신기관이 경찰청이 아님   senderOrg(message) 가 "경찰청" 미포함
② 본문에 대피 키워드          EVACUATION_KEYWORDS = ["대피"]
→ type 을 PROMOTED_TYPE("대피안내") 로 치환해 통과
```

**설계 판단 네 가지.**

1. **키워드는 "대피" 하나로 시작한다.** 샘플에서 이 하나가 대상 2건을 정확히 잡는다.
   "방류"·"수위" 를 더해도 추가로 잡히는 게 없고 오탐 여지만 는다. 못 잡으면 기존처럼
   버려질 뿐이라 **실패 방향이 안전**하다 — 넓히는 건 실제 누락 사례를 본 뒤에.
2. **기관 표기가 없으면(`null`) 되살리지 않는다.** 판정 근거가 없을 때는 버리는 쪽이 안전하다.
3. **`type` 을 `"대피안내"` 로 치환한다.** 알림 `itemKey` 가 유형 단위라(D-09) 그대로 두면
   `disaster:기타` 라는 의미 불명 키가 생긴다. Phase D 에서 알림 대상 유형 목록에
   **`PROMOTED_TYPE` 도 반드시 포함**해야 한다(D-07 의 해제 로직이 이 유형에도 필요).
4. **"찾습니다" 차단 조건은 코드에 넣지 않았다.** 경찰청 조건과 중복이라 샘플에서 무효과다.
   대신 **테스트 불변식**으로 박았다 — 통과분에 "찾습니다" 0건 · 경찰청 발신 0건.
   재승격 조건을 나중에 손대도 이 불변식이 먼저 깨진다.

**결과.** 통과분 65 → **67건**(호우 61 + 산사태 4 + 대피안내 2). 차단 35 → 33건.
개인정보 유출 0 유지.

⚠️ **한계.** 표본이 나흘치다. 경찰청이 아닌 기관(지자체 등)이 실종자 안내를 보내는 경우가
실제로 있는데, 그런 문자에 "대피"가 함께 들어가면 샌다. 불변식 테스트는 픽스처에 대해서만
성립하므로, **실 API 연동 후 재승격분을 한 번 눈으로 확인**할 것(Phase C 항목).

## D-17 · ✅ Phase 0 완료 — 실 API 호출로 명세 전부 확정 (2026-07-31)

키를 `.env.local` 에 넣고 직접 호출해 확인했다. **추정이 아니라 실측이다.**

**엔드포인트·파라미터** — 포털이 발급 내역에 준 URL 이 그대로 답이었다.

```
https://www.safetydata.go.kr/V2/api/DSSP-IF-00247
  ?serviceKey=<키>        ← 대문자 K 맞음. 키 16자·특수문자 없음(URL 인코딩 불필요)
  &returnType=json
  &pageNo=1&numOfRows=1000
  &crtDt=YYYYMMDD         ← ★ 날짜 필터
```

**응답 구조** — `body` 가 최상위다(`response.body.items` 아님).

```json
{ "header": {"resultMsg":"NORMAL SERVICE","resultCode":"00","errorMsg":null},
  "numOfRows": 3, "pageNo": 1, "totalCount": 57119, "body": [ … ] }
```

**필드명은 CSV 와 동일**(MSG_CN·RCPTN_RGN_NM·CRT_DT·REG_YMD·EMRG_STEP_NM·SN·DST_SE_NM·MDFCN_YMD).

**⚠️ 단 `SN` 만 number 다.** CSV 는 문자열, JSON 은 숫자. `String(r.SN).trim()` 으로 고쳤고
회귀 테스트를 박았다. **골든 픽스처가 CSV 출신이라 원리적으로 못 잡는 결함**이었다 —
픽스처는 형식(format)을 고정할 뿐 형(type)을 고정하지 못한다.

### ★ `crtDt` 가 페이징·정렬 문제를 통째로 없앤다

```
필터 없음        totalCount 57,119   (2023-09 ~ 현재)
crtDt=20260731   totalCount     16   ← 하루치만
```

**⚠️ 정렬을 절대 신뢰하면 안 된다.** 하루치 응답의 시각 순서가 뒤죽박죽이다
(08:21 → 09:07 → … → 09:54 → 09:27 → 09:55 → … → 06:46 → 08:30). SN 순도 시간순도 아니고,
`numOfRows` 만 바꿨을 때 다른 구간이 나온 관측도 있었다.

→ **`crtDt` 로 하루치 전건을 `numOfRows=1000` 으로 받고 우리가 정렬·필터한다.**
페이징도 정렬도 신경 쓸 필요가 없어진다. D-08 의 "증분 커서 금지"가 그대로 유효하다.

**호출 예산 재계산** — 폴링당 **1회**면 된다.

```
5분 주기 = 288회/일 (예산 1000 의 28.8%)
+ KST 00:00~03:00 에만 전날 crtDt 도 조회(신선도 3시간 윈도우가 자정을 걸침) = +36회
합계 약 324회/일 (32%)
```

**지역 필터도 있다** — `rgnNm=경기` 로 16 → 2건. 다만 **쓰지 않는다.**
우리는 시·도 매칭을 자체 수행하고(D-05), 아래 표기 변화 때문에 서버측 문자열 필터에
의존하는 게 더 위험하다. (`rcptnRgnNm` 은 안 먹고 `rgnNm` 만 먹는다.)

### ⚠️ 실데이터에서 새 행정구역 표기 발견 — `전남광주통합특별시`

오늘 발령 중 `전남광주통합특별시 영암군`·`전남광주통합특별시 곡성군` 이 있다.
샘플 CSV(2023년)에는 없던 표기다.

우리 매칭은 **부분 문자열 포함**이라 `"전남광주통합특별시".includes("광주")` 와
`.includes("전남")` 이 **둘 다 true** → 광주 현장·전남 현장 모두 `site` 로 잡힌다.
통합된 단일 광역단체라면 옳은 동작이지만, `SIDO` 테이블은 아직 광주·전남을 별개로 둔다.
**누락은 없고 과다 매칭 가능성만 있다.** 실제 통합 범위를 확인하고 필요하면 SIDO 를 정리한다.

### 실데이터 end-to-end 검증 (2026-07-31 오전)

오늘 발령 17건을 Phase A~B 파이프라인에 그대로 통과시켰다.

```
① normalize     17건 파싱 · invalid 0 · 최신 발령이 현재와 2분 차(KST 파싱 정확)
② filterWatched 17 → 15건(폭염) · 차단 ["기타"] 2건 · 개인정보 통과 0건
③ isFresh(3h)   15 → 15건
④ matchSite     김포(경기) site 2 · 당진(충남) site 4 · 포항(경북) site 3 · 서울 site 0/nearby 7
```

**화이트리스트에 `폭염` 을 넣어둔 것이 실전에서 바로 유효했다**(오늘 15/17 이 폭염).
서울 현장이 `site` 0 인 것도 정상 — 오늘 서울 발령이 없고 인근 7건만 참고로 잡힌다.

## D-18 · ★ CSV 픽스처가 못 잡는 결함이 두 번 더 나왔다 — 전부 "형식이 아니라 형·표현"

Phase C 에서 실 API 를 붙이자 골든 픽스처가 원리적으로 잡을 수 없는 결함이 **연달아 두 건** 나왔다.

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | `(r.SN ?? "").trim is not a function` | CSV=string / **API=number** | `String(r.SN).trim()` |
| 2 | 폴링마다 **"정정 발령 40건"**(오늘 전건) | CSV=`"2023-09-19"` / API=`"2026/07/31 08:22:17.000000000"` 이고 **MDFCN 이 REG 보다 항상 10분쯤 뒤**(내부 처리 시각) | 필드명(YMD)대로 **날짜 부분만** 비교 |

**교훈.** 골든 픽스처는 **형식(어떤 값이 오는가)** 을 고정할 뿐 **형(type)과 표현(representation)** 을 고정하지 못한다.
CSV 는 모든 값이 문자열이고 날짜가 이미 잘려 있어서, JSON 의 number 와 나노초 타임스탬프를 예고할 방법이 없었다.

→ **어댑터를 붙이는 단계에서 실 응답 한 건을 반드시 눈으로 훑는다.** 두 결함 모두
"돌려보니 터졌다/로그가 이상하다"로 발견됐지 코드 리뷰로는 안 보였다.

②는 특히 조용한 종류였다 — 예외가 안 나고 로그만 40줄씩 쌓인다. 진짜 정정 발령이 왔을 때
그 신호가 노이즈에 묻혀 무의미해졌을 것이다.

## D-19 · Phase C 설계 결정 — 목업·빈 결과·로그

**① 빈 body 를 목업으로 떨어뜨리지 않는다.** `resultCode "00"` + `body: []` 는
**"그날 재난문자가 없었다"는 정상 상태**다. 이걸 목업 폴백으로 처리하면 **재난이 없는 날
관제 화면에 가짜 경보가 뜬다.** `kma.ts` 가 실제로 겪은 사고(무특보 날 MOCK_WARNINGS 점등,
`resultCode === "03"` 분기가 그 흉터)라 같은 함정을 처음부터 피했다.

목업은 **키 미설정 · 호출 실패** 두 경우에만 나온다.

**② 목업은 전국 발령 2건.** 안전안내(호우) + 긴급재난(호우)로 caution·danger 양쪽 경로를
Phase D 에서 볼 수 있게 했다. 발령 시각은 호출 시점 기준으로 생성해 신선도 게이트를 통과한다.
수신지역은 17개 시·도 `~ 전체` 라 **어느 현장 좌표로 개발하든 보인다.**
⚠️ 화면에 가짜 재난이 뜨므로 호출부는 `source` 를 표시해야 하고, 알림은 `live` 에서만 발사한다(D-11).

**③ 로그는 `warn`/`error` 만.** 레포 ESLint 가 `console.info` 를 막는다(`no-console`).
그리고 **상시 차단 유형(`기타`·`교통통제`)은 로그에서 뺐다** — 매일 오는 값이라
폴링마다 같은 줄이 찍히면 정작 처음 보는 유형이 묻힌다.

**④ 캐시 키에 조회 날짜를 넣는다.** `queryDates()` 결과를 그대로 키로 쓰므로
자정을 넘어가면(오늘 → 어제,오늘) 키가 바뀌어 낡은 결과가 안 나온다.

## D-20 · ✅ 해소 (2026-08-01) — 시·도 매칭이 하위 시·군·구까지 읽었다 + 통합시 분리

### ① `경기도 광주시` 가 광주 현장에 잡혔다 — 형식 전제가 어긋남

| 기상특보 t6 | `경기도(광주, 하남)` | `경기도` | ✗ |

기상특보는 하위를 **괄호로 감싸서** head 매칭이 통했는데, 재난문자는 시·도와 시·군·구를
**공백으로 이은 한 토큰**이다. head 전체를 부분 문자열 검사하면 하위 지명이 시·도로 읽힌다.

(`임진강 수계지역(경기도 연천군,파주시)` 는 그대로 매칭 — 회귀 테스트 유지).

### ② 광주가 "안 잡히는" 게 아니라 전남에 파묻혔다 — D-17 의 과다 매칭 확정

광주 관할 발령은 `전남광주통합특별시 광산구` 로 온다. 매칭 자체는 됐다. 문제는 통합으로
**광주와 전남이 시·도 문자열을 공유**한다는 것이다. `"광주"` 가 전남 22개 시·군을 전부 끌고 온다.

```
수정 전  광주 현장 site 50건 = 광주 관할 1(광산구) + 전남 시·군 47 + 경기도 광주시 2
         전남 목포 site 44건 ← 광주 현장과 사실상 같은 목록(두 현장이 구별되지 않는다)
수정 후  광주 현장 site  1건 = 광산구         (나머지 전남분은 nearby 26 → 69)
         전남 목포 site 43건 = 광산구만 빠짐
         경기 현장  site 42건 (변화 없음 · 경기도 광주시 포함)
```

**알림도 site 기준**이라 목포·여수(100km+) 폭염이 광주 현장 텔레그램으로 나가고 있었다.

**결정(사용자)** — 두 번째 토큰(시·군·구)으로 가른다. 광주 5개 구(동구·서구·남구·북구·광산구)와
`광주…` 로 시작하는 표기는 광주, 그 밖은 전남. **하위가 없으면(전역 발령) 양쪽 다** 자기 발령으로
본다 — 한쪽만 주면 나머지 현장이 재난을 통째로 놓친다. 거리 기준(반경 N km)은 전국 시·군 좌표
테이블이 필요해 보류했다.

⚠️ 광주 5개 구 목록은 **`전남광주통합특별시` 토큰 안에서만** 판정에 쓴다. `동구`·`서구` 는
다른 광역시에도 있어서 전역으로 풀면 곧바로 오탐이 된다.

### ③ 부수 발견 — `crtDt` 는 그 날짜 "이후"를 준다

`crtDt=20260731` 응답 337건 중 **121건이 08-01 발령분**이었다. D-17 의 "하루치" 전제와 다르다.

## D-21 · ★ 긴급재난 문자의 67%가 유형 화이트리스트에서 버려지고 있었다 (2026-08-03)

사용자 질문("실제 긴급재난문자가 있으면 관제웹이 표시")을 확인하다 발견했다.
실 API 표본 4400건(`crtDt=20260701`·`20260715` 각 3페이지) 중 `EMRG_STEP_NM='긴급재난'` 58건의 유형 분포.

```
수집  산사태 9 · 호우 7 · 화재 2 · 산불 1                     = 19건 (33%)
버려짐 (DST_SE_NM 비어있음) 29 · 홍수 6 · 환경오염사고 4        = 39건 (67%)
```

**`DST_SE_NM` 이 비어서 오는 문자 29건은 전부 기상청 극한호우다.**

```
00:41 나주시 금천면 인근 50mm/h 이상 강한 비로 침수 등 우려(국민행동요령: cbs062.kma.go.kr)
  수신지역 = 전남광주통합특별시 남구 구소동   ← 광주 관할, 2026-07-19 00:42
```

표본 29건 중 광주 관할이 1건 있었으므로 실제로 놓친 발령이다.

**결정** — 단계가 `긴급재난` 이면 유형으로 거르지 않는다. 지자체·기상청이 최고 위급으로 보낸 것이라
화이트리스트로 판단할 대상이 아니고, 긴급재난은 전체의 1.3%(58/4400)뿐이라 노이즈 위험도 없다.

하나로 묶는다 — `ALERT_TYPES` 는 해제 역할 때문에 고정 목록이어야 해서 유형을 동적으로 늘릴 수 없다(D-07).

⚠️ `안전안내` 단계의 목록 밖 유형은 그대로 버린다. 위급도 판단 없이 전부 받으면 단수·정전·교통사고까지

## D-23 · `numOfRows` 는 서버가 1000 으로 캡한다 — totalCount 로 잘림을 탐지한다 (2026-08-03)

D-20 ③(`crtDt` 는 그 날짜 "이후"를 준다)의 후속. 누적으로 오다 보니 상한을 넘으면 조용히 잘린다.

```
crtDt=20260715  numOfRows=1000 → totalCount 3491 · 받은 1000   ★잘림
                numOfRows=10000 → totalCount 3491 · 받은 1000   응답 numOfRows 도 1000 (요청 무시)
```

**응답 최상위에 `totalCount` 가 온다**(`{header, numOfRows, pageNo, totalCount, body}`).
그리고 **페이징은 완전하다** — 3491건을 1000×4페이지로 받으면 고유 SN 3491, 누락·중복 0(500×7도 동일).
D-17 의 "페이징에 기댈 수 없다"는 **정렬**에 관한 서술이고, 전건 수집의 완전성과는 다른 문제였다.

**결정** — `totalCount > 받은 건수` 면 다음 페이지를 이어받는다. 페이지 상한 `MAX_PAGES=3`.
평소 하루 발령이 200~270건이라 이 루프는 한 번도 돌지 않는다(호출 예산 변화 없음 — D-17 의 32% 유지).
상한을 넘으면 경고 로그를 남긴다. 실측 재현 —

```
crtDt=20260803 → 호출 1회 · 189/189   전건 수집
crtDt=20260731 → 호출 1회 · 925/925   전건 수집
crtDt=20260715 → 호출 3회 · 3000/3492 ★경고(상한 도달)
```

⚠️ `numOfRows=100` 같은 소단위 페이징에서는 한 페이지가 통째로 비어 오는 현상을 한 번 관측했다
(10p×100 = 824건 / 실제 924건). 1000·500 단위에서는 재현되지 않았다. 소단위 페이징을 쓰지 않는다.

```
실측 08-01~08-04 · 광주 현장 · 표본 918건
  site 13건 · nearby 183건
  nearby 내역   폭염/안전안내 177 · 화재/안전안내 4 · 산불/안전안내 1 · 강풍/안전안내 1
```

**결정(사용자)** — 인근은 ① `긴급재난` 단계이거나 ② 번질 수 있는 유형(`호우·태풍·산사태·산불`)일 때만
알림. 폭염·대설 같은 광역 기상은 인근에서 나도 현장 대응이 달라지지 않으므로 화면 참고에 그대로 둔다.
화면 표시는 현행 유지(칩 + "N건 참고") — 인근을 본문 목록에 넣으면 하루 50건이 현장 발령을 묻는다.

```
새 규칙 적용 결과   인근 183건 → 알림 승격 1건(0.5%)
  08-01 13:38 산불 · 전북 김제시 만경읍 "갈대밭 화재 발생. 불길이 번지고 있으니 출입 금지"
    → caution · detail "13:38 발령 · 인근 전북특별자치도 김제시 만경읍"
```

⚠️ **인근이 대표(lead)가 되면 `detail` 에 `인근` 을 반드시 붙인다.** 안 붙이면 관제자가 현장 발령으로
읽는다. 대표 선정은 긴급재난 우선(위급도) → 현장 우선(관련도) → 최신 순.

⚠️ 테스트에서 `detail` 전체를 `/인근/` 으로 검사하면 안 된다 — 재난문자 **본문**에도
"…대부동 인근에 시간당 50mm" 처럼 이 단어가 들어간다. 지역 줄(첫 줄)만 본다.

`buildAlertItems(site, nowMs, nearby = [])` — 세 번째 인자에 기본값을 둬서 기존 호출부·테스트가
그대로 동작한다(회귀 테스트로 고정).

## D-25 · ★ 문구 판정이 배포 당일 뚫렸다 — 소방청이 캠페인 문구를 바꿨다 (2026-08-04)

D-22 는 소방청 정기 캠페인을 **본문 문구 `화재위험경보`** 로 식별했다. 그 근거는 실측이었다
(08-01~08-03 캠페인 전건이 이 문구를 포함, 사고 문자 오검출 0건). **그런데 배포 당일 밤에 바뀌었다.**

```
~08-03 13:50   "화재위험경보 ‘경계’ 발령 전기화재예방 알림 ▲실외기 주변 가연물…"
```

배포는 08-03 15:05, 문구 변경은 같은 날 19:30. **판정이 4시간 반 만에 무력화됐고**
08-03 19:30·08-04 13:52 두 건이 캠페인인 채로 알림에 올랐다. 08-04 14:00 `disaster:화재`

**교훈 — 남이 쓰는 문장은 계약이 아니다.** 실측으로 확인해도 상대가 언제든 바꾼다.
발신 주체·구조(범위·단계)처럼 **그쪽이 바꿀 이유가 없는 것**으로 판정해야 한다.

**새 판정** — 발신기관 + 발령 범위. 실측 25건(08-01~08-04)에서 완전히 갈린다.

```
캠페인 7건  전부 [소방청] + 수신지역 2개 이상이 모두 시·도 전역(하위 시·군·구 없음)
사고  18건  전부 지자체 발신([군산시]·[서구]·[전주시]…) + 1~3개 지역, 대개 하위 포함

전수 검증   캠페인 정확히 제외 7 · 놓침 0 · 사고를 잘못 제외 0
```

⚠️ `senderOrg()` 는 쓸 수 없다 — 그 함수는 **맨 앞** 대괄호를 보는데 캠페인은 `[소방청]` 이 **끝**에 있다.
⚠️ 단계도 함께 본다 — 소방청이 긴급재난으로 보낸 진짜 위급 문자까지 막으면 안 된다.

## D-26 · ★ 외부 API 가 과거 데이터를 주자 관제 화면이 5분간 "재난문자 없음" 으로 굳었다 (2026-08-04)

사용자 제보("다시 재난문자가 없는 상태"). 서버는 정상인데 화면만 0건이었다.

**추적** — Cloud Run 접근 로그의 **응답 크기**가 결정적이었다.

```
정상 7812B (site 1 · nearby 18)  vs  이상 755B (site 0 · nearby 0)
755B 응답 5건이 06:07:50 ~ 06:11:19(UTC)에 몰려 있다 = 정확히 5분 = 서버 캐시 TTL
```

같은 시각 서버 로그의 '처음 보는 유형' 목록이 평소와 달랐다.

```
평소       ["풍랑","교통사고","통신"]
06:07:50   ["한파","정전","수도","붕괴","홍수","전염병","환경오염사고","교통사고"]
06:13:38   ["풍랑","교통사고","통신"]   ← 정상 복귀
```

**8월인데 한파·전염병**이다. 정상 조회를 대조하면 오늘(20260804) 206건은 전부 08-04 발령이고
그 유형들이 없다 → 그 순간 외부 API 가 **`crtDt` 를 무시하고 과거 데이터만 1000건 반환**했다.

**연쇄** — 오늘 발령이 하나도 없음 → 신선도 게이트(3시간)에서 전멸 → `msgs` 0건 →
**그 0건이 캐시(TTL 5분)** → 그동안 모든 조회가 "재난문자 없음" → 관제 화면이 굳었다.

**수정** — 조회한 날짜의 발령이 응답에 하나도 없으면 이상으로 보고 **캐시하지 않는다.**
직전 캐시가 있으면 그 값을 유지해 화면이 굳지 않게 하고, `console.error` 로 남긴다.
⚠️ `raws` 가 0건인 것은 이상이 아니다 — 그날 재난이 없으면 빈 배열이 정상이다(D-19).
둘을 구분하지 않으면 재난 없는 날에 매번 실 API 를 다시 부르게 되어 호출 예산이 깨진다.

**교훈** — 외부 데이터는 "실패"만 오는 게 아니라 **성공한 척하며 엉뚱한 내용**이 온다.
`resultCode 00` · HTTP 200 이어도 내용이 요청과 맞는지 봐야 한다. 그리고 그런 응답을
**캐시하면 사고가 캐시 TTL 만큼 늘어난다**.

### 부수 기록 — 오진 2건

1. "GPS 좌표가 흔들려 재조회 폭주" 로 진단했으나 **틀렸다.** 로그의 요청 URL 을 보면 24회
   전부 동일 좌표(`35.12,126.869`)였다. 좌표 반올림 수정은 근거가 없어 되돌렸다.
   → **추측으로 코드를 고치기 전에 로그에서 실제 파라미터를 확인할 것.**
2. 1초 간격 8회 요청은 결함이 아니라 **사용자가 새로고침 버튼을 누른 흔적**이다
   (패널 헤더의 `reloadKey` 가 즉시 재조회를 트리거한다). 빈도만 보고 결함으로 단정하지 말 것.

## D-27 · 알림 발사 로그 추가 — 오알림을 17시간 뒤에 발견한 근본 원인 (2026-08-04)

D-25 의 오알림을 **다른 작업의 라이브 검증 중 우연히** 발견했다. 발송 경로에 관측이 없었기 때문이다.

```
notifyEnvAlerts  → sendTelegramMessage 를 쏘고 끝. 성공·실패·내용 어느 것도 안 남긴다.
env_alert_state  → severity 만 저장. "무엇을 왜 보냈는지" 가 없다.
sendTelegramMessage → 반환 타입이 void. 실패도 미배선도 호출부가 구별할 수 없다.
```

**수정** — `sendTelegramMessage` 가 `"sent" | "skipped" | "failed"` 를 반환하고,
`notifyEnvAlerts` 가 발사 건마다 한 줄 남긴다.

```
[env-alert] disaster:호우 none→danger · 호우 외 2건 · 14:42 발령 · 경기도 안산시 단원구 · 발송됨
[env-alert] 상태 저장 실패 — disaster:폭염 알림 건너뜀. <error>
```

설계 판단 두 가지.
- **전이가 없어 안 보낸 건은 남기지 않는다** — 유형 11종 × 5분 폴링이라 로그가 도배되고,
  정작 발사된 줄이 묻힌다. 남길 가치가 있는 것은 "실제로 나간 것"과 "나갔어야 하는데 못 나간 것"이다.
- **`detail` 은 첫 줄(시각·지역)만** — 본문 전문에는 개인정보가 섞일 수 있다(D-10).
  화이트리스트가 실종자 문자를 막지만 로그는 방어선을 하나 더 둔다.

⚠️ 이 로그가 있었다면 D-25 를 17시간이 아니라 첫 발사(08-03 19:30) 때 알 수 있었다.
판정 로직은 언제든 틀릴 수 있다 — **틀렸다는 것을 알 수 있는 장치**가 판정 자체만큼 중요하다.

## D-28 · 경찰 표기 문자는 단계·유형 불문 제외 — 개인정보가 긴급재난 경로로 샐 수 있었다 (2026-08-04)

사용자 지시("경찰청 관련 긴급재난문자는 제외 처리"). 확인해 보니 **실제 구멍이 있었다.**

D-15 는 실종자 안내를 '기타' 유형 + `senderOrg` 의 경찰청 체크로 막았다. 그런데 **D-21 이후
긴급재난 단계는 유형 불문 채택**한다. 경찰이 긴급재난으로 실종자 문자를 보내면 실명·나이·키·
체격·인상착의가 그대로 텔레그램으로 나간다.

**게다가 지금까지 막힌 이유가 경찰청 판정 때문이 아니었다.**

```
"함양군에서 실종된 김○○씨(남, 59년생)를 찾습니다. 특징:키 170cm, 65kg … -함양경찰서- [함양군]"
  맨 앞 대괄호 없음 → senderOrg() = null → 경찰청 체크에 도달조차 안 함
  발신 표기는 [함양군](지자체) · 경찰은 본문 중간에 -함양경찰서-
```

즉 **유형이 '기타'라서 우연히 막히고 있었다.** 유형이 바뀌거나 단계가 긴급재난이면 뚫린다.

**수정** — `isPoliceNotice(msg)` 를 `filterWatched` 의 **맨 앞**에 둔다(긴급재난 분기보다 앞).
본문 전체에서 `경찰청`·`경찰서` 를 본다 — `senderOrg` 로는 위 형태를 못 잡기 때문이다.
`경찰` 단독은 쓰지 않는다("경찰과 협력하여" 같은 정상 문구에 걸린다).

**실측** — 표본에서 경찰 표기 문자는 **전부 `기타/안전안내`(실종자 안내)이고 관심 유형에는 0건**이다.
가드 적용 전후 수집량이 동일(4137건 = 4137건)해 정상 재난 문자를 막지 않는다.

⚠️ 골든 픽스처 `ALL[0]` 이 실종자 문자(`[경기남부경찰청] …김학균씨…`)라 기존 테스트 하나가 깨졌다.
그 테스트가 보려던 것은 '모르는 유형' 처리이므로 본문만 경찰 표기 없는 것으로 바꿨다 —
**가드가 의도대로 작동한 증거**이지 회귀가 아니다.

⚠️ 경찰이 보낸 **진짜 재난 문자**도 함께 막힌다. 같은 재난은 지자체·기상청도 발령하므로 감수한다 —
개인정보 유출 쪽이 훨씬 비싼 실수다(D-10).

## D-29 · 화면을 3일 누적으로 — 신선도(알림)와 표시 윈도우를 분리했다 (2026-08-04)

사용자 요청 — "일회성으로 보여주는 것만이 아닌 3일 누적 기준". 종전에는 3시간이 지나면
목록에서 사라져 "무슨 일이 있었는지" 를 되짚을 수 없었다.

**핵심 = 두 윈도우를 분리한다.** `FRESH_WINDOW_MS`(3시간)는 **알림 해제를 겸하므로**(D-07)
절대 늘릴 수 없다 — 늘리면 3일 전 발령으로 알림이 계속 울린다. 그래서 표시 전용
`HISTORY_WINDOW_MS`(3일)를 따로 뒀다.

```
site      3일 누적 · 항목마다 fresh 플래그      ← 넓힌 것은 이것 하나뿐
severity  신선분 기준(변경 없음)  — 3일 전 위험을 지금 danger 로 칠하면 오해를 부른다
summary   신선분 기준(변경 없음)  — 상단 한 줄은 "지금" 을 말해야 한다
칩(신호등) 신선분 기준(변경 없음)  — 지난 지역이 색점으로 남으면 현재 상태를 잘못 읽는다
nearby    신선분 기준(변경 없음)  — 3일이면 고유 지역 38곳이라 칩이 폭증한다(실측)
알림       신선분 기준(변경 없음)
```

**호출은 늘지 않았다.** `crtDt` 가 그 날짜 "이후" 누적을 주므로(D-20 ③) **3일 전 하루만 조회**하면
3일치가 전부 온다. `queryDates` 가 항상 1건을 반환하도록 바뀌어, 종전에 자정 인근만 2건이던 것이
사라져 오히려 줄었다(D-17 예산 32% → 29%).

```
실측 2026-08-04 — crtDt=3일 전 totalCount 734건(1000 상한 이내, 1페이지)
dev 검증 — site 11건(신선 1 · 지난 10) · nearby 15건 · 응답 10.2KB
```

⚠️ **이상 감지 가드의 비교 기준을 함께 고쳤다.** 종전에는 "조회일 **당일** 발령이 응답에 있는가"로
봤는데, 이제 `dates` 가 3일 전 하루라 **그날 발령이 0건인 날에 정상 응답을 이상으로 오판**한다.
"조회 시작일 **이후**" 로 바꿨다(`crtDtYmd(r.CRT_DT) >= from`).

⚠️ 화면에서 지난 발령은 `opacity-60` + `오늘/어제/N일 전` 배지로 구분한다. 날짜 계산은
**KST 달력 날짜 기준**이다(경과 시간이 아니라) — 23:50 발령을 00:10 에 보면 "어제" 가 맞다.

## D-30 · `홍수`·`환경오염사고` 채택 — 대피 지시가 담긴 문자가 버려지고 있었다 (2026-08-04)

사용자 결정. D-21 이후 **긴급재난 단계는 이미 유형 불문** 받고 있었으므로, 이번에 새로 늘어나는
것은 **안전안내 단계**뿐이다. 그런데 그 안전안내가 대부분이었다.


## D-31 · ★ 3일 누적 배포가 목업 가짜 재난을 띄웠다 — 타임아웃과 폴백 정책 (2026-08-04)

D-29(3일 누적) 배포 직후 라이브 검증에서 응답이 **670B · `호우 danger`** 로 나왔다. 목업이다.

```
[disaster-msg] 실 API 실패 — 목업 폴백. The operation was aborted due to timeout
→ 화면에 "[기상청] (목업) 시간당 50mm 이상 강한 비로 침수 우려" 가 긴급재난으로 표시됐다
```

**원인 = 조회량 증가.** 3일 누적으로 crtDt 를 3일 전으로 옮기자 응답이 200건대 → **990건대**가 됐고
`AbortSignal.timeout(8000)` 을 넘겼다. 로컬에서 같은 요청은 **219ms** 인데 Cloud Run 은 8초 초과 —
아웃바운드 경로 차이다(D-13 의 고정 IP 미확보와 같은 자리).

**조치 두 가지.**

1. **타임아웃 8s → 25s.** 크론은 `attemptDeadline 180s`, 브라우저는 5분 캐시라 부담이 없다.
2. **실패 시 목업보다 직전 캐시를 우선한다.** 목업은 호우 긴급재난을 담고 있어 관제 화면에
   **가짜 경보**를 띄운다. 낡은 진짜 데이터가 그럴듯한 가짜보다 낫고, 신선도 게이트가 오래된 건
   어차피 걸러낸다. 목업은 **캐시조차 없는 첫 조회 실패** 때만 남긴다(D-11 의 데모 연속성 취지 유지).

**교훈 — 조회 범위를 넓히면 시간 예산도 함께 넓혀야 한다.** D-29 에서 호출 "횟수" 가 늘지 않는 것만
확인하고 **한 번의 응답이 5배로 커진다**는 점을 놓쳤다. dev 에서는 로컬 네트워크라 드러나지 않았고,
**라이브 검증에서만 잡혔다**.

⚠️ 목업 폴백은 남아 있다(캐시 없는 첫 실패). 관제에서 가짜 경보가 맞는지는 별도 판단이 필요하다 —
"화면이 비는 것"과 "가짜 재난" 중 무엇이 나은지는 운영 정책이다.

## D-32 · 목업 폴백 제거 — 가짜 재난 대신 "연결 끊김" (2026-08-04)

D-31 에서 실 API 실패 시 직전 캐시를 우선하게 했지만, **캐시조차 없으면 여전히 목업**이었다.
사용자 결정으로 그 경로도 없앤다.

**근거** — 목업은 호우 긴급재난을 담고 있어 관제 화면에 **실제 재난과 구분되지 않는 가짜 경보**가
뜬다(실사고 2026-08-04 08:11). D-11 의 "데모 무중단" 취지는 시연용이었는데, 지금은 프로덕션
관제다. **모르는 상태를 아는 것이 가짜를 믿는 것보다 낫다.**

```
실 API 실패 → 직전 캐시 있으면 그것(source: live)
           → 캐시 없으면 throw → 라우트가 503 → 카드가 "연결 끊김" 표시
```

화면 분기는 이미 있었다 — `DisasterMsgCard` 는 `!r.ok` 를 catch 해 `failed=true` 로 두고
"연결 끊김" 을 그린다. 즉 **API 가 정직하게 실패를 알리기만 하면 됐다.**

⚠️ **키 미설정(로컬 개발)의 목업은 그대로 둔다.** 그건 실패가 아니라 의도된 데모 모드이고,
`source: "mock"` 배지로 화면에 명시된다(D-11).

⚠️ 이 변경으로 "재난문자 없음"(정상)과 "조회 실패"(장애)가 화면에서 갈린다. 종전에는 장애가
가짜 재난으로 보였으니 오히려 더 위험했다 — false-OK 가 아니라 **false-ALARM** 이었다.

## D-33 · 미결 4건 처리 — 인근 홍수·발사 로그 고정·배포 트래픽 판정·'기타' 판단 (2026-08-04)

### ① 인근 알림에 `홍수` 추가 (채택)

`SPREADING_TYPES` = 호우·태풍·산사태·산불 **+ 홍수**. **하천은 하류로 번진다** — 인근 시·도
상류의 홍수주의보·댐 방류가 현장 하천 수위로 이어진다. 실측 문구가 그대로 근거다.

```
"무한천 예산군(예산대교) 홍수주의보 발령… 하천변 이용을 자제" [금강홍수통제소]
```

### ② 발사 로그 형식을 순수 함수로 고정 (D-27 후속)

`formatEnvAlertLog(item, prev, result)` 로 분리했다. **실제 발사는 전이가 있어야 일어나
라이브에서 확인하기 어렵다** — 형식만이라도 테스트로 못 박아 조용히 바뀌지 않게 한다.
회귀 3건 추가(전이·현재값·지역·결과 / 본문 전문 미포함 / 실패·미배선 구분).

### ③ 배포 스크립트 트래픽 판정 — **오탐이 아니었다**(2026-08-05 정정)

`status.traffic[0]` 을 그대로 읽던 것은 실제 결함이 맞다. **태그가 붙은 옛 리비전**(`tag=verify`)이
배열에 함께 들어가고 순서가 보장되지 않아 **엉뚱한 리비전명**이 찍혔다(태그 항목은 `percent` 가 비어 있다).

```
옛  traffic[0].revisionName = 00223-vot · percent = ''      ← 태그 항목
새  traffic.filter("revisionName:$REV").extract(percent)        ✅ 대상 리비전만 본다
```

⚠️ **그런데 필터를 넣고도 "0%" 경고가 계속 떴고, 나는 그것을 오탐으로 보고 세 번 더 고쳤다. 세 번 다 틀렸다.**

```
1차  status.traffic[0] 이 태그(verify) 항목을 읽음        → revisionName 필터        ✅ 진짜 결함
2차  "0%" → deploy 직후 status 가 아직 0 이라 판단        → 5초×6회 재시도          ❌ 오진
3차  30초로 부족 → 라우팅 전파가 60초 이상이라 판단       → spec 으로 판정           ❌ 오진
4차  배포 후 spec 을 직접 조회 → **트래픽이 핀 고정돼 있다**                          ★ 진짜 원인
```

**진짜 원인 = 이 서비스는 트래픽이 리비전 이름으로 고정(pinned)돼 있다.**

```json
spec.traffic:
 [ { "percent": 100, "revisionName": "vitalguard-dashboard-00232-rql" },
   { "revisionName": "…-00223-vot", "tag": "verify" } ]
★ latestRevision: true 가 없다
```

`latestRevision` 이 없으므로 `gcloud run deploy` 는 **새 리비전을 만들 뿐 라우팅을 옮기지 않는다.**
판정이 읽은 0% 는 실제 상태였고, 뒤따르는 `update-traffic` 보정은 **매 배포에 실제로 필요한 절차**였다.
지금까지 사고가 없었던 것은 보정이 매번 성공했기 때문이지 경고가 무해해서가 아니다.
같은 뿌리로 **시크릿 회전도 리비전을 갈아야만 반영된다**(L-41 — 콘솔에서 새 버전을 배포해도 트래픽이 안 넘어간다).

**조치(사용자 결정) = 현 구조 유지 + 문구 정정.** `--to-latest` 로 되돌리면 배포 즉시 트래픽이
넘어가 **문제 있는 리비전이 나가도 중간에 멈출 여지가 없어진다**. 지금은 보정 단계가 확인 지점 역할을 한다.
경고(`⚠`)를 정상 절차 안내로 바꿨다. 판정식(`spec.traffic` + `revisionName` 필터)은 그대로 둔다 —
`spec` 은 의도된 라우팅이라 보정 전후를 즉시 반영하고, `status` 는 보정 뒤 전파에 60초 넘게 걸린다.

💡 **교훈 — 반복되는 경고를 오탐으로 단정하지 말 것.** 세 번 다 "판정식이 틀렸다"고 가정하고
판정식만 고쳤다. **경고가 가리키는 대상(트래픽 구성)을 직접 조회한 것은 네 번째였고, 그때 30초 만에 원인이 나왔다.**
같은 증상이 반복되면 판정 코드가 아니라 **판정 대상의 실제 상태**를 먼저 본다.

### ④ `기타` 유형 채택 — **하지 않는다**(실측 근거)

표본 3434건 중 '기타' 368건. 경찰 가드(D-28)가 7건을 막고 **361건이 남는다.**

```
남는 것의 내용   물놀이 32 · 물놀이 안전사고 16 · 수상안전 14 · 쿠팡물류센터 화재 13 ·
                수상안전 10 · 물놀이 7 · 6 · 6 · 5 · 5 …  → 대부분 물놀이·수상안전 캠페인
⚠️ 가드를 통과하는 실종 관련 4건 — "수난사고 실종자 수색 중… 물품·흔적 발견 시 119·112 신고"
   (실명·인상착의는 없지만 관제와 무관하고, 개인정보 차단선을 얇게 만든다)
```

```
지역 매칭   ✅ 통과  '전남광주통합특별시' 전역 발령 → 광주 현장 site
3일 표시창  ✅ 통과
신선도 3h   ✅ 통과(발송 당시 기준)
유형 필터   ❌ 탈락  DST_SE_NM='기타' — WATCHED_TYPES 에 없다
재승격      ❌ 실패  ⓐ senderOrg 가 null ⓑ 본문에 '대피' 없음
```

게다가 `KNOWN_IGNORED_TYPES` 에 '기타' 가 있어 **로그조차 남지 않는다.** 완전 무음 탈락이라
D-33 에서 판단을 내린 뒤로 아무도 이 문자가 사라지는 것을 보지 못했다.

### ② ★ 진짜 결함 — `senderOrg()` 가 발신기관을 거의 못 읽고 있었다

조건을 정하려고 한 달치(07-16~08-15 · **5,281건**)를 받아 재보니, 물놀이보다 큰 것이 나왔다.

```
senderOrg() 가 null 을 돌려준 문자   5,279 / 5,281건 (99.96%)
그 결과 D-15 '대피' 재승격 실적       한 달간 0건
```

원인은 단순하다. 재난문자는 발신기관을 **문장 끝**에 붙이는데(`…대피 바람.[연천군]`)
`senderOrg` 는 `message.startsWith("[")` 로 **맨 앞만** 봤다. D-15 가 참고한 샘플(2023년 CSV)에
앞에 붙는 형태가 섞여 있어 그때는 동작했고, 실 API 로 넘어오면서 조용히 죽었다.

**되살아난 것 15건이 전부 진짜 대피 지시다** — 그중에는 현장 직결 문자가 있다.

```
"17시 50분 진보면 천둥·번개 예상. 낙뢰 위험이 있으니 옥외 작업자 및 야외 활동객은
 즉시 안전한 실내로 대피하시고…"                                    ← 옥외 작업자 지목
"임진강 수위 지속 상승 중. 하천변의 행락객·낚시객·야영객·어민… 대피"   (4건)
"군남댐 방류량 2배 증가 예정으로 계곡, 하천, 급경사지, 농수로 등 위험지역에서 대피 바람.[연천군]"
```

⚠️ **방어선이 2겹에서 1겹으로 줄었다.** 실종자 문자("…-함양경찰서- [함양군]")도 이제
`senderOrg` 가 '함양군' 을 뽑으므로 `isEvacuationNotice` 의 경찰청 조건으로는 못 막는다.
**`filterWatched` 선두의 `isPoliceNotice`(D-28)가 유일한 방어선이다** — 테스트에 못 박았고,
재승격 키워드를 섞은 실종자 문자 3형태가 전부 차단되는지 직접 검증한다.

### ③ 수상안전 재승격 — D-33 이 남긴 경로를 따랐다

D-33 ④ 는 '기타' 전체 채택을 기각하면서 *"필요해지면 D-15 처럼 **조건부 재승격**으로 좁혀
다시 검토할 것"* 을 남겼다. 그 경로다. 유형 전체(한 달 557건)가 아니라 키워드로 좁힌다.

```
키워드 후보              통과      광주 site   ⚠ 실종·수색 문구
물놀이                   296건                 0건
물놀이+수상안전          324건     21건        0건        ← 채택(하루 0.68건)
+계곡·하천               389건                 2건        ← 기각
+연안·갯벌               327건                 0건        ← 미채택(효과 3건)
```

`계곡`·`하천` 을 넣으면 **"수난사고 실종자 수색 중… 흔적 발견 시 신고"** 가 딸려온다 —
D-33 이 지목한 그 4건이다. 실명·인상착의는 없지만 관제와 무관하고 개인정보 차단선을 얇게 만든다.
**두 키워드로 좁히면 실종·수색 문구가 0건**이라 여기서 끊었다.

### ④ 표시는 하되 알리지 않는다 — 두 지점

승격만 하고 끝내면 **매일 텔레그램이 울리고 신호등이 매일 주의로 앉는다.** 실측이 근거다.

```
같은 문자의 한 달 반복 횟수   행정안전부 19회(매일 13:30) · 울산 23회(매일 10:00) · 김천 19회
```

```
알림   ALERT_TYPES 에 WATER_SAFETY_TYPE 을 넣지 않는다
       → 소방청 캠페인(D-25)은 유형이 화이트리스트(화재)라 판정 함수가 필요했지만,
         이쪽은 승격 유형이라 **목록에 안 넣는 것**으로 끝난다. 화면은 지역·기간으로 고르므로 영향 없다
신호등  severity 계산에서만 제외(disaster-msg-api.ts) — 목록·요약에는 남는다
       → 물놀이 안전수칙으로 관제 색이 매일 바뀌면 정작 위험한 발령의 색 변화가 값을 잃는다
```

⚠️ 둘 다 **빠뜨린 것이 아니라 뺀 것**이라 주석과 가드 테스트로 못 박았다. 다음 사람이
"수상안전이 ALERT_TYPES 에 없네" 하고 채워 넣으면 그날부터 매일 알림이 나간다.

### ⑥ 부수 관측 — 외부 API 간헐 이상 응답 2형태 (미조치)

조사 중 같은 요청(`crtDt=20260812` · `numOfRows=1000` · `pageNo=1`)에 다른 응답이 왔다.

```
정상    217건(08-12~08-15)          — 반복 6회 전부 정상
이상 ⓐ  2023년 과거분 1000건        — D-26 가드가 잡는다(캐시 갱신 건너뜀)
이상 ⓑ  87건만 + totalCount 217     — 08-14·08-15 만 오고 2페이지부터 0건
```

**ⓑ 는 기존 가드를 통과한다** — 조회 시작일 이후 발령이 섞여 있기 때문이다. `fetchDay` 가
`전건 미수집 87/217` 경고는 남기지만 화면은 부족한 데이터로 그려지고 5분간 캐시된다.
간헐이라 재현 빈도부터 봐야 하고, 이번 변경 범위 밖이라 **미조치**로 둔다(후순위에 등록).
