# 긴급재난문자 연동 — 컨텍스트 노트

> 결정과 근거를 쌓는 문서. 작업 목록은 [checklist.md](checklist.md).
> 시작 2026-07-30. 근거 데이터 = `행정안전부_긴급재난문자` 샘플 CSV 100건(2023-09-16 ~ 09-19).

---

## D-01 · 데이터 출처 — data.go.kr 이 아니라 safetydata.go.kr 이다

공공데이터포털 `행정안전부_긴급재난문자`(15134001)는 **LINK형 API** 라 실제 호출은
재난안전데이터공유플랫폼 `safetydata.go.kr` (dataSn=228)으로 넘어간다.
구 `재난문자방송 발령현황` · `(지역별)` API 는 신규 접근이 막혔고 종료 예정이다.

**근거.** 포털 상세 페이지가 safetydata 로 리다이렉트하고, 대체 안내가 명시돼 있다.
**함의.** 인증키·호출 URL·트래픽 정책이 기존 `apis.data.go.kr` 계열(KMA·KOSHA)과 **다르다.**
`kma.ts` 의 호출 코드를 복사하면 안 되고 어댑터를 따로 쓴다.

---

## D-02 · 샘플 CSV 를 골든 픽스처로 쓴다

인증키·명세서가 없어도 **파싱·정규화·지역매칭·알림포맷은 CSV 100건만으로 전부 개발·테스트한다.**
실 API 는 마지막에 "HTTP 응답 → 동일한 레코드 배열" 어댑터 한 겹만 붙인다.

**근거.** 이 순서를 뒤집으면 키 발급이 전체 일정을 막는다. 그리고 실 API 는 재난이 없는 날엔
관심 유형 응답이 0건이라 **정상 동작을 확인할 시험지가 없다.** 고정 픽스처가 유일한 회귀 방어선이다.

**픽스처에 반드시 남길 케이스**(전부 샘플에 실재).

| 케이스 | 실제 값 | 검증 대상 |
|---|---|---|
| 괄호 안 콤마 | `임진강 수계지역(경기도 연천군,파주시)  ,경기도 임진강 ` | 지역 분리가 안 깨지는가 |
| 다지역 나열 | 고양시 3개 구 (총 16건) | 콤마 분리 + 개별 매칭 |
| 동 단위 | `서울특별시 강남구 역삼동` | 시·도까지만 좁혀 매칭되는가 |
| `~ 전체` | `경상남도 전체` | 시·도 전역 매칭 |
| 긴급재난 1건 | 경기 안산 단원구 · 호우 | severity=danger 승격 |
| 실종자 31건 | `[서울경찰청] … 찾습니다` | **전량 차단** |

## D-03 · 수신 대상 = 재난재해만. 화이트리스트 방식

**받는다.** 호우 · 산사태 · 폭염 · 강풍 · 대설 · 지진 · 태풍 · 산불 (+ 확장 여지)
**안 받는다.** 실종자 찾기 · 교통통제 · 그 밖의 생활정보

**근거 세 가지.**

1. `DST_SE_NM` 은 코드값이 아니라 **한글 자유 문자열**이다. 발령 기관이 새 값을 쓰면 우리가 모르는 값이 들어온다.
2. 샘플의 `기타` 31건은 전부 **실종자 찾기**였다. 즉 이 필드만으로는 성격을 판별 못 한다.
3. 샘플은 **나흘치**다. 폭염·강풍·대설·지진·태풍·산불은 한 건도 등장하지 않는다.
   **샘플로 값 목록을 확정하면 안 된다.**

**그래서 블랙리스트(기타 제외)가 아니라 화이트리스트다.** 블랙리스트는 유형이 늘 때마다 구멍이 생긴다.
다만 **모르는 값은 버리되 로그를 남긴다** — 운영하며 목록을 사람이 채운다.

## D-04 · 위치 = 작업자 GPS 평균 → 시·도. **새로 만들 것이 0이다**

사용자 요구("작업자 gps 평균 값 기반, 범위는 시·도")를 만족하는 자산이 이미 전부 있다.

| 필요한 것 | 기존 자산 | 위치 |
|---|---|---|
| 작업자 GPS 평균 | `fieldCoords` useMemo | `app/components/DemoDashboard.tsx:4137` |
| 평균값 서버 캐시 | `site_coord_daily` · `captureSiteCoordDaily()` | `lib/db.ts:2194` |
| 무인 경로용 좌표 조회 | `getLatestSiteCoord()` (폴백 `getLatestWeatherDaily()`) | `lib/db.ts:2156` |
| 좌표 → 시·도 | `latLonToSido()` | `app/lib/kma-regions.ts:30` |
| 인근 시·도(반경 120km) | `nearbySidos()` · `NEAR_SIDO_KM` | `app/lib/kma-regions.ts:46` |
| 괄호 보존 지역 분리 | `splitRegions()` | `app/lib/kma-regions.ts:73` |
| 지역 ↔ 시·도 매칭 | `regionMatchesSido()` | `app/lib/kma-regions.ts:100` |

`fieldCoords` 는 이미 **한국 범위 게이트**(위 32.5~39.5 / 경 123.5~132.5)로 시뮬레이터 기본값·좌표 swap 오염을 막고,
**소수 3자리(≈110m) 양자화**로 GPS 지터에 의한 재호출을 억제한다. 그대로 쓴다.

`splitRegions()` 는 기상특보의 `경기도(안산, 시흥)` 때문에 만든 함수인데,
재난문자의 `임진강 수계지역(경기도 연천군,파주시)` 가 **정확히 같은 문제**다. 재사용이 우연이 아니다.

**결론.** 신규 라우트는 `/api/kma-warning` 과 똑같이 `lat`/`lon` 쿼리만 받으면 되고,
크론 경로는 `/api/cron/env-check` 가 이미 좌표를 조회해 자체 호출하므로 **한 줄 추가**로 끝난다.

## D-05 · 매칭 범위를 시·도로 고정하는 이유

시·군·구나 동 단위로 좁히지 않는다.

1. **평균 좌표는 특정 지점이 아니다.** 여러 작업자의 중점이라 시·군·구 경계를 쉽게 넘나든다.
2. **110m 양자화**가 걸려 있어 기초단체 경계 부근에서 판정이 흔들린다.
3. **재난은 광역으로 번진다.** 옆 동에 산사태 주의보가 떴는데 우리 동이 아니라고 거르면 그게 오히려 사고다.
4. 샘플의 수신지역 단위가 시·도 전체 / 시·군·구 / 동 / 하천 수계로 **뒤섞여 있어** 기초단체 정규화 자체가 불안정하다.

⚠️ **알려진 한계.** 작업자가 여러 현장에 흩어져 있으면 평균 좌표는 아무도 없는 중간 지점을 가리킨다.
경기·충남처럼 넓은 시·도에서는 시·도 판정까지 틀어질 수 있다. 지금은 단일 현장 전제라 수용하되,
멀티 현장 단계에서 **현장별 좌표**로 바꿔야 한다. (`fieldCoords` 의 날씨·특보도 같은 전제를 이미 깔고 있다.)

**인근 시·도는 "참고"로만 표시한다.** 알림은 쏘지 않고 화면에만 남긴다. 기상특보가 `nearbySidos` 로
인근 특보를 보여주는 것과 같은 맥락이다 — 옆 시·도 상황은 판단 재료지 경보는 아니다.

## D-06 · CRT_DT 는 반드시 KST 를 명시해 파싱한다

형식이 `2023/09/19 12:22:17` 이다. ISO 가 아니라 **슬래시 형식**이라
`new Date("2023/09/19 12:22:17")` 은 **실행 환경의 로컬 시각**으로 해석된다.
Cloud Run 컨테이너는 **UTC** 이므로 그대로 넣으면 **9시간이 밀린다.**

신선도 게이트가 이 값 위에 서 있으므로, 9시간 오차는 곧 "모든 문자가 만료" 또는 "만료가 안 됨"이 된다.
**명시적으로 `+09:00` 을 붙여 파싱한다.** 로컬 개발(맥=KST)에서는 증상이 안 보이고 배포 후에만 터지는 계열이다.

## D-07 · 신선도 게이트가 곧 "해제" 역할을 한다 — ★ 이걸 빠뜨리면 알림이 딱 한 번만 간다

**함정.** `notifyEnvAlerts()` 는 `itemKey` 단위로 이전 severity 를 DB 에 저장하고
`shouldSendEnv(prev, next)` = **악화 전이일 때만** 발송한다 (`lib/env-alert-notify.ts`).
`prev=caution, next=caution` 이면 발송하지 않는다.

기상특보는 해제되면 목록에서 빠져 자연히 normal 로 돌아간다.
그런데 **재난문자에는 해제 문자가 없다.** 발령만 있고 끝이다.

→ 관심 유형이 한 번 `caution` 이 되면 **영원히 caution 에 머물러 두 번 다시 알림이 안 간다.**

**해법.** 폴링 때마다 **화이트리스트 전 유형**을 `notifyEnvAlerts()` 에 넘긴다.
신선한 문자가 있는 유형은 실제 severity, 없는 유형은 **`normal`** 로.
그러면 신선도 만료가 곧 해제가 되어 다음 발령 때 정상적으로 다시 발송된다.

```
매 폴링:
  호우   ← 30분 전 문자 있음  → caution   (전이하면 발송)
  산사태 ← 신선한 문자 없음    → normal    (해제 = 다음 발령 대비)
  폭염   ← 없음               → normal
  …화이트리스트 전 유형을 매번 넘긴다
```

## D-08 · 중복 제거는 SN 집합. 연속성을 가정하지 않는다

폴링이라 같은 문자를 계속 다시 받는다. 키는 `SN`(일련번호)이다.

⚠️ **SN 은 연속하지 않는다.** 샘플은 100건인데 번호 폭이 205151~205376 = **226** 이다.
이 CSV 가 전체가 아닌 추출본이기 때문인데, 실 API 도 그럴 수 있다고 봐야 한다.

→ `lastSN + 1` 같은 **증분 커서 방식 금지.**
→ **최근 N건을 받아 SN 집합으로 걸러낸다.** 집합은 신선도 윈도우와 같은 기간만 유지해 무한 증가를 막는다.

부수 관찰. `REG_YMD`·`MDFCN_YMD` 는 샘플 100건 전부 `CRT_DT` 날짜와 같고 수정 이력 0건이다.
**정정 발령은 당장 다루지 않는다.** 다만 나흘치라 단정 못 하므로 `MDFCN_YMD ≠ REG_YMD` 면 로그를 남긴다.

## D-09 · 알림 itemKey 는 유형 단위. SN 이면 안 된다

```
itemKey  = "disaster:호우"                    ← 유형 단위
severity = 긴급재난 → danger / 안전안내 → caution
detail   = 발령시각 · 지역 · 본문 90자
```

**근거.** `itemKey = disaster:${SN}` 으로 두면 ① `env_alert_state` 행이 문자 개수만큼 **무한 증가**하고
② 매 키가 "이전 없음 → 발송"이라 **전이 판정이 무의미**해져 억제 장치가 통째로 무력화된다.
호우 문자 10건이 쏟아지면 10번 발송된다.

유형 단위면 "정상→주의" 1회, 나중에 긴급재난이 뜨면 "주의→위험" 1회로 끝난다.
기존 날씨·기상특보 알림과 동작이 일관된다.

**severity 매핑 근거.** 샘플 100건 중 `긴급재난` 은 1건뿐이고
(`[기상청] 20:33 단원구 대부동 인근 시간당 50mm 이상 강한 비`) 나머지 99건이 `안전안내` 다.
즉 `긴급재난` = 실제 위험 임박 신호라 `danger` 가 맞다.

**본문 90자.** 샘플 전건이 55~90자(평균 82)로 CBS 상한 안에 있다. 자를 필요가 사실상 없다.

## D-10 · 개인정보를 설계로 회피한다

'기타' 31건에는 **실명·나이·키·몸무게·인상착의**가 그대로 들어 있다.

```
[서울경찰청] 노원구에서 실종된 김현주씨(여,41세)를 찾습니다 -160cm,68kg,꽃무늬티,회색칠부바지,검정슬리퍼
```

**화이트리스트를 통과한 것만 저장한다.** 그러면 이 데이터는 애초에 우리 DB 에 들어오지 않는다.
"일단 전건 적재하고 나중에 거른다"를 피할 이유가 하나 더 있는 셈이다.

## D-11 · 인증 — 조회는 공개, 알림 발사는 세션·크론키

`/api/kma-warning` 의 감사 지적(BE-AUTHZ-02)을 그대로 답습한다.
무인증 GET 으로 외부인이 텔레그램을 임의 발사시킬 수 있었던 사고가 이미 한 번 있었다.

```
조회 GET            → 공개
텔레그램 발사 조건  → verifyBasicAuth(로그인 세션) || cronAuth(x-cron-key)
목업 데이터         → 절대 발사 안 함 (source === "live" 일 때만)
```

## D-12 · 폴링 주기 — ✅ 실측 정정 (2026-07-31)

**초안이 틀렸다.** 타 인터페이스(DSSP-IF-00195) 사례의 **일일 100건**을 가정해 15분을 역산했는데,
실제 발급 내역에는 **일일호출량 1000건**으로 나온다("일일호출량이 0이면 최대 호출량(1000건)입니다").

```
예산 1000회/일
  15분(96회)   =  9.6%   ← 초안. 지나치게 보수적
  ★ 5분(288회) = 28.8%   ← 채택. 재난 긴급성에 맞고 여유 3.5배
    2분(720회)  = 72.0%   ← 재배포·수동 테스트 여유가 사라져 위험
```

**캐시 TTL 도 15분 → 5분.** 이 값이 곧 호출 예산이다(기상특보는 10분).

⚠️ **로컬 개발도 같은 예산을 쓴다.** 키가 하나라 `.env.local` 로 돌리는 테스트 호출이
프로덕션 몫을 깎는다. 개발 중에는 목업 폴백(키 미설정)을 기본으로 두고 실 호출은 필요할 때만.

## D-16 · ⚠️ 인증키 만료 2027-07-31 — 조용히 목업으로 떨어진다

발급 내역의 **만료일자 = 2027-07-31**(발급 1년). 갱신하지 않으면 그날부터 인증이 실패한다.

**왜 위험한가.** 우리 설계는 `kma.ts` 정책을 따라 **키가 없거나 실패하면 목업 폴백**이다.
만료돼도 화면은 200 으로 잘 뜨고 카드도 나온다 — **내용만 가짜**가 된다.
관제 화면에서 "재난 없음"으로 보이는데 실제로는 조회가 죽어 있는 상태가 최악이다.

**대응 두 가지.**
1. **캘린더에 2027-07 갱신 일정 등록**(사람 쪽 방어).
2. **프로덕션에서 `source: "mock"` 이면 경고 로그**(Phase C 항목). 키가 설정돼 있는데도
   목업으로 떨어졌다면 그건 폴백이 아니라 장애다 — 둘을 구분해 로그해야 한다.

**함께 확인된 것.** 유저아이피 `*.*.*.*`(전체 허용)로 정상 등록됐다(D-13 대로).
수집방법 = 시스템연계 · 정보제공기관 = 행정안전부.

## D-13 · 활용신청의 "아이피" 항목 = `*.*.*.*` (전체 허용)

신청서의 필수 입력란이고 예시가 `개인 IP 121.xxx.xxx.xxx` / `대역 121.xxx.*.*` / `전체 `*.*.*.*`` 로 제시된다.

**이 칸의 목적.** 발급된 인증키를 **여기 적은 IP 에서 호출할 때만** 받아준다.
키가 유출돼도 남의 IP 에서는 못 쓰게 하는 화이트리스트다. 즉 **키 + IP 이중 자물쇠**다.

**왜 우리는 IP 를 못 적나.** 호출자가 **Cloud Run** 이다.
Cloud Run 의 아웃바운드 IP 는 기본적으로 Google 공용 풀에서 **동적으로 배정**된다 —
인스턴스가 새로 뜰 때마다, 리비전이 바뀔 때마다 달라진다.
오늘 확인한 IP 를 적으면 **내일 403 이 난다.**

**실측(2026-07-30).**

```
gcloud run services list → vitalguard-dashboard, cctv-ai 둘 다 VPC 커넥터 없음
gcloud compute addresses list → Compute Engine API 자체가 비활성 (PERMISSION_DENIED)
```

= 이 프로젝트에는 **고정 아웃바운드 IP 가 존재하지 않고, 만들 준비도 안 돼 있다.**

**고정 IP 를 원한다면 필요한 것.** Compute Engine API 활성화 → VPC 네트워크 →
**Cloud NAT + 예약 고정 IP** → Cloud Run `--vpc-egress=all-traffic`.
⚠️ **Cloud NAT 게이트웨이는 상시 과금**이라 이 API 하나 때문에 세울 이유가 없다. 보류한다.

**전체 허용의 대가와 상쇄책.** IP 자물쇠를 포기하므로 **인증키가 유일한 방어선**이 된다. 그래서

- 키는 **Secret Manager** 에만 둔다(`.env` 커밋 금지)
- 호출은 **서버 라우트에서만** — 클라이언트 번들에 절대 넣지 않는다
- 이 조건은 D-11(조회 공개·발사는 세션/크론키)과 이미 일치한다

참고. 개발 중 로컬 맥에서 호출하더라도 **ISP 가 주는 IP 는 수시로 바뀐다.**
사무실 고정회선이 있어도 대역 허용(`121.xxx.*.*`) 정도가 한계다.
어차피 Cloud Run 이 최종 호출자라 전체 허용이 유일한 실용 답이다.

## D-14 · ★★ 발견 — `latLonToSido` 가 도(道) 현장을 인접 광역시로 오판한다 (정확도 50%)

Phase B 구현 중 실측으로 드러났다. **D-04 에서 "새로 만들 것 0" 이라 적은 전제가 부분적으로 깨진다.**

**원인.** `latLonToSido()` 는 **17개 시·도 중심점 최근접(유클리드)** 이다.
광역시는 면적이 작아 중심점이 시가지에 있고, 도(道)는 넓어 중심점이 멀다.
그래서 **광역시에 인접한 도 지역이 전부 광역시로 빨려 들어간다.**

**실측(주요 시·군 34곳 · 2026-07-30).**

```
오판 17/34 = 정확도 50%

경기 안산 → 인천      경기 고양 → 서울      경기 수원 → 서울
경기 성남 → 서울      경기 김포 → 인천      경기 파주 → 서울
경기 평택 → 충북      경기 남양주 → 서울    ← 경기도 표본 8곳 전부 오판
경남 창원 → 부산      경남 김해 → 부산      경남 양산 → 부산
경북 포항 → 울산      경북 구미 → 대구      경북 경산 → 대구
충남 천안 → 세종      전남 순천 → 광주      전남 나주 → 광주

정상 = 광역시 본체(서울·부산·대구·인천·광주·대전·울산·세종·제주) + 광역시에서 먼 도 지역(전주·청주·춘천·강릉·목포·아산 등)
```

**재난문자에서의 실제 피해.** 샘플의 유일한 긴급재난(`경기도 안산시 단원구 풍도동` · 호우)을

**왜 지금까지 안 드러났나.** 기상특보는 `localizeRegions()` 로 현장+인근을 **함께 표시**해서
오판이 "인근에 섞여 보임"으로 완충됐다. 재난문자는 `site` 가 곧 발송 조건이라 **바로 미발송**이 된다.

**영향 범위는 좁다.** `latLonToSido`·`nearbySidos` 사용처는 `app/lib/kma.ts` **한 곳**뿐이고
기존 `kma-regions.test.ts` 는 광주 시청 좌표(광역시 본체)만 검증한다 = **개선해도 깨질 기존 테스트가 없다.**

### ✅ 해소 (2026-07-30) — A안(시·도 대표점 다중 시드) 채택

`kma-regions.ts` 의 `latLonToSido` 를 **시·도당 대표점 여러 개 중 최근접**으로 교체했다.

**채점 = 홀드아웃.** 시드에 넣은 도시로 재면 자기충족이라 판정력이 0 이다.

**남은 3건은 전부 경계 인접**이고 최근접 방식의 원리적 한계다. 시드를 더 넣어도 다른 경계에서

덤으로 기상특보도 함께 정확해졌다 — 안산 현장이 인천 특보를 보던 것이 경기 특보로 고쳐졌다.

**회귀 고정.** 안산·고양·창원·구미·순천·천안 6곳 + 홀드아웃 정확도 ≥85% 게이트를 테스트로 박았다.

## D-15 · ⚠️ 미결 — '기타' 안에 진짜 재난 대피 안내가 섞여 있다

D-03 에서 "'기타' 31건은 전부 실종자 찾기"라고 적었는데 **정확하지 않았다.** 실측 결과다.

```
'기타' 31건
  ├ 27건  실종자 찾기      ← 개인정보, 차단이 맞다
  ├  2건  사천시 싱크홀 도로 통제(중복 발송)
  └  2건  ★ 하천 수위 대피 안내 ← 명백한 재난인데 함께 버려진다
        [한국수자원공사] 주암댐 수문방류로 하류 수위 상승 … 안전한 곳으로 대피
        [경기도청] 임진강 수위 1m 이상 상승 중 … 즉시 대피하시기 바랍니다
```

**현재 동작.** 화이트리스트가 유형만 보므로 이 2건도 버린다. 사용자 지시("기타는 받지 않는다")대로다.

**재승격이 가능한가 — 실측으로 확인한 분리 조건 두 가지.**

| 기준 | 실측 |
|---|---|
| 발신기관 | 실종자 27건 = **전부 경찰청**. 경찰청 발신 27건 = **전부 실종자**. 완전한 1:1 |
| 본문 키워드 | 실종자 문자에 "대피" **0건**. `'기타' + '대피'` = 정확히 위 2건 |

두 기준 모두 샘플에서는 **개인정보 유출 0** 으로 하천 대피만 건져낸다.
다만 나흘치 표본이라 일반화 보장은 없고, 키워드 규칙은 문구가 바뀌면 샌다.

### ✅ 결정 (2026-07-30) — ②안 재승격 채택

화이트리스트를 통과하지 못한 문자라도 **두 조건을 모두** 만족하면 되살린다.

```
① 발신기관이 경찰청이 아님   senderOrg(message) 가 "경찰청" 미포함
② 본문에 대피 키워드          EVACUATION_KEYWORDS = ["대피"]
→ type 을 PROMOTED_TYPE("대피안내") 로 치환해 통과
```

**설계 판단 네 가지.**

1. **키워드는 "대피" 하나로 시작한다.** 샘플에서 이 하나가 대상 2건을 정확히 잡는다.
   "방류"·"수위" 를 더해도 추가로 잡히는 게 없고 오탐 여지만 는다. 못 잡으면 기존처럼
   버려질 뿐이라 **실패 방향이 안전**하다 — 넓히는 건 실제 누락 사례를 본 뒤에.
2. **기관 표기가 없으면(`null`) 되살리지 않는다.** 판정 근거가 없을 때는 버리는 쪽이 안전하다.
3. **`type` 을 `"대피안내"` 로 치환한다.** 알림 `itemKey` 가 유형 단위라(D-09) 그대로 두면
   `disaster:기타` 라는 의미 불명 키가 생긴다. Phase D 에서 알림 대상 유형 목록에
   **`PROMOTED_TYPE` 도 반드시 포함**해야 한다(D-07 의 해제 로직이 이 유형에도 필요).
4. **"찾습니다" 차단 조건은 코드에 넣지 않았다.** 경찰청 조건과 중복이라 샘플에서 무효과다.
   대신 **테스트 불변식**으로 박았다 — 통과분에 "찾습니다" 0건 · 경찰청 발신 0건.
   재승격 조건을 나중에 손대도 이 불변식이 먼저 깨진다.

**결과.** 통과분 65 → **67건**(호우 61 + 산사태 4 + 대피안내 2). 차단 35 → 33건.
개인정보 유출 0 유지.

⚠️ **한계.** 표본이 나흘치다. 경찰청이 아닌 기관(지자체 등)이 실종자 안내를 보내는 경우가
실제로 있는데, 그런 문자에 "대피"가 함께 들어가면 샌다. 불변식 테스트는 픽스처에 대해서만
성립하므로, **실 API 연동 후 재승격분을 한 번 눈으로 확인**할 것(Phase C 항목).

## D-17 · ✅ Phase 0 완료 — 실 API 호출로 명세 전부 확정 (2026-07-31)

키를 `.env.local` 에 넣고 직접 호출해 확인했다. **추정이 아니라 실측이다.**

**엔드포인트·파라미터** — 포털이 발급 내역에 준 URL 이 그대로 답이었다.

```
https://www.safetydata.go.kr/V2/api/DSSP-IF-00247
  ?serviceKey=<키>        ← 대문자 K 맞음. 키 16자·특수문자 없음(URL 인코딩 불필요)
  &returnType=json
  &pageNo=1&numOfRows=1000
  &crtDt=YYYYMMDD         ← ★ 날짜 필터
```

**응답 구조** — `body` 가 최상위다(`response.body.items` 아님).

```json
{ "header": {"resultMsg":"NORMAL SERVICE","resultCode":"00","errorMsg":null},
  "numOfRows": 3, "pageNo": 1, "totalCount": 57119, "body": [ … ] }
```

**필드명은 CSV 와 동일**(MSG_CN·RCPTN_RGN_NM·CRT_DT·REG_YMD·EMRG_STEP_NM·SN·DST_SE_NM·MDFCN_YMD).

**⚠️ 단 `SN` 만 number 다.** CSV 는 문자열, JSON 은 숫자. `String(r.SN).trim()` 으로 고쳤고
회귀 테스트를 박았다. **골든 픽스처가 CSV 출신이라 원리적으로 못 잡는 결함**이었다 —
픽스처는 형식(format)을 고정할 뿐 형(type)을 고정하지 못한다.

### ★ `crtDt` 가 페이징·정렬 문제를 통째로 없앤다

```
필터 없음        totalCount 57,119   (2023-09 ~ 현재)
crtDt=20260731   totalCount     16   ← 하루치만
```

**⚠️ 정렬을 절대 신뢰하면 안 된다.** 하루치 응답의 시각 순서가 뒤죽박죽이다
(08:21 → 09:07 → … → 09:54 → 09:27 → 09:55 → … → 06:46 → 08:30). SN 순도 시간순도 아니고,
`numOfRows` 만 바꿨을 때 다른 구간이 나온 관측도 있었다.

→ **`crtDt` 로 하루치 전건을 `numOfRows=1000` 으로 받고 우리가 정렬·필터한다.**
페이징도 정렬도 신경 쓸 필요가 없어진다. D-08 의 "증분 커서 금지"가 그대로 유효하다.

**호출 예산 재계산** — 폴링당 **1회**면 된다.

```
5분 주기 = 288회/일 (예산 1000 의 28.8%)
+ KST 00:00~03:00 에만 전날 crtDt 도 조회(신선도 3시간 윈도우가 자정을 걸침) = +36회
합계 약 324회/일 (32%)
```

**지역 필터도 있다** — `rgnNm=경기` 로 16 → 2건. 다만 **쓰지 않는다.**
우리는 시·도 매칭을 자체 수행하고(D-05), 아래 표기 변화 때문에 서버측 문자열 필터에
의존하는 게 더 위험하다. (`rcptnRgnNm` 은 안 먹고 `rgnNm` 만 먹는다.)

### ⚠️ 실데이터에서 새 행정구역 표기 발견 — `전남광주통합특별시`

오늘 발령 중 `전남광주통합특별시 영암군`·`전남광주통합특별시 곡성군` 이 있다.
샘플 CSV(2023년)에는 없던 표기다.

우리 매칭은 **부분 문자열 포함**이라 `"전남광주통합특별시".includes("광주")` 와
`.includes("전남")` 이 **둘 다 true** → 광주 현장·전남 현장 모두 `site` 로 잡힌다.
통합된 단일 광역단체라면 옳은 동작이지만, `SIDO` 테이블은 아직 광주·전남을 별개로 둔다.
**누락은 없고 과다 매칭 가능성만 있다.** 실제 통합 범위를 확인하고 필요하면 SIDO 를 정리한다.

### 실데이터 end-to-end 검증 (2026-07-31 오전)

오늘 발령 17건을 Phase A~B 파이프라인에 그대로 통과시켰다.

```
① normalize     17건 파싱 · invalid 0 · 최신 발령이 현재와 2분 차(KST 파싱 정확)
② filterWatched 17 → 15건(폭염) · 차단 ["기타"] 2건 · 개인정보 통과 0건
③ isFresh(3h)   15 → 15건
④ matchSite     김포(경기) site 2 · 당진(충남) site 4 · 포항(경북) site 3 · 서울 site 0/nearby 7
```

**화이트리스트에 `폭염` 을 넣어둔 것이 실전에서 바로 유효했다**(오늘 15/17 이 폭염).
서울 현장이 `site` 0 인 것도 정상 — 오늘 서울 발령이 없고 인근 7건만 참고로 잡힌다.

## D-18 · ★ CSV 픽스처가 못 잡는 결함이 두 번 더 나왔다 — 전부 "형식이 아니라 형·표현"

Phase C 에서 실 API 를 붙이자 골든 픽스처가 원리적으로 잡을 수 없는 결함이 **연달아 두 건** 나왔다.

| # | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | `(r.SN ?? "").trim is not a function` | CSV=string / **API=number** | `String(r.SN).trim()` |
| 2 | 폴링마다 **"정정 발령 40건"**(오늘 전건) | CSV=`"2023-09-19"` / API=`"2026/07/31 08:22:17.000000000"` 이고 **MDFCN 이 REG 보다 항상 10분쯤 뒤**(내부 처리 시각) | 필드명(YMD)대로 **날짜 부분만** 비교 |

**교훈.** 골든 픽스처는 **형식(어떤 값이 오는가)** 을 고정할 뿐 **형(type)과 표현(representation)** 을 고정하지 못한다.
CSV 는 모든 값이 문자열이고 날짜가 이미 잘려 있어서, JSON 의 number 와 나노초 타임스탬프를 예고할 방법이 없었다.

→ **어댑터를 붙이는 단계에서 실 응답 한 건을 반드시 눈으로 훑는다.** 두 결함 모두
"돌려보니 터졌다/로그가 이상하다"로 발견됐지 코드 리뷰로는 안 보였다.

②는 특히 조용한 종류였다 — 예외가 안 나고 로그만 40줄씩 쌓인다. 진짜 정정 발령이 왔을 때
그 신호가 노이즈에 묻혀 무의미해졌을 것이다.

## D-19 · Phase C 설계 결정 — 목업·빈 결과·로그

**① 빈 body 를 목업으로 떨어뜨리지 않는다.** `resultCode "00"` + `body: []` 는
**"그날 재난문자가 없었다"는 정상 상태**다. 이걸 목업 폴백으로 처리하면 **재난이 없는 날
관제 화면에 가짜 경보가 뜬다.** `kma.ts` 가 실제로 겪은 사고(무특보 날 MOCK_WARNINGS 점등,
`resultCode === "03"` 분기가 그 흉터)라 같은 함정을 처음부터 피했다.

목업은 **키 미설정 · 호출 실패** 두 경우에만 나온다.

**② 목업은 전국 발령 2건.** 안전안내(호우) + 긴급재난(호우)로 caution·danger 양쪽 경로를
Phase D 에서 볼 수 있게 했다. 발령 시각은 호출 시점 기준으로 생성해 신선도 게이트를 통과한다.
수신지역은 17개 시·도 `~ 전체` 라 **어느 현장 좌표로 개발하든 보인다.**
⚠️ 화면에 가짜 재난이 뜨므로 호출부는 `source` 를 표시해야 하고, 알림은 `live` 에서만 발사한다(D-11).

**③ 로그는 `warn`/`error` 만.** 레포 ESLint 가 `console.info` 를 막는다(`no-console`).
그리고 **상시 차단 유형(`기타`·`교통통제`)은 로그에서 뺐다** — 매일 오는 값이라
폴링마다 같은 줄이 찍히면 정작 처음 보는 유형이 묻힌다.

**④ 캐시 키에 조회 날짜를 넣는다.** `queryDates()` 결과를 그대로 키로 쓰므로
자정을 넘어가면(오늘 → 어제,오늘) 키가 바뀌어 낡은 결과가 안 나온다.
