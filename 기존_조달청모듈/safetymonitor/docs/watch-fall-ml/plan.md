# 애플워치 낙상 ML 3종 모듈 주입 — 계획

**착수 2026-08-27** · 대상 = `apps/vitalguard_app/ios/VitalWatch`(오늘 재서명·설치한 라이브 워치 앱).

## 무엇을 왜

작업자가 쓰러진 뒤 스스로 신고하지 못하는 구간을 워치가 대신 잡는다. 판정은 **온디바이스**다 —
서버 왕복이 없어야 통신이 끊긴 현장에서도 동작하고, 원시 IMU 를 서버로 보내지 않아도 된다.

모듈은 **완제품으로 받는다**(ML 담당 김태곤 제작 · v6.1.0). 우리 몫은 **호스트 배선**이고
모듈 내부는 수정하지 않는다 — 그것이 모듈이 폴더 교체만으로 업데이트되는 경계다.

## 원본 — 레포 사본을 쓰지 않는다

```
사용본  ~/Documents/조달청-공모전 관련자료/ML 3종 모듈.ios.android   (v6.1.0)
금지    레포 `ML 3종 모듈/`(v6.0.0) · `apps/VitAlGuard-iOS-WatchOS-App/`(구 워치앱 통합본)
```
사용자 지시(08-27). 무결성 = MANIFEST 30/30 OK·실패 0 로 수령 검수 통과.
⚠ **애플워치 면만 보면 v6.1.0 과 v6.0.0 은 `FallMLModule.version` 문자열 한 줄 차이**이고
모델 3종은 바이트 동일하다. 그래도 지시대로 제시본을 쓴다 — 판별은 로그의 `module_version` 으로 한다.

## 판정 구조 (모듈이 정한 것 · 우리가 안 바꾼다)

```
12초 윈도(충격 전2s + 후10s, 게이트 1.5G) → FallMLModule.assess()
  ① work_veto  p≥0.675 → 기각        (작업동작 · precision 0.97)
  ② recovery   비회복 p≥0.35 → danger → CountdownGuard 30초
                                          ├ 버튼 취소
                                          ├ 지속움직임 5초 자동취소
                                          └ 무반응 → 확정
  ③ impact     증거 첨부 전용 — 거부권 없음(fail-open · v5 사태의 교훈)
```

## ★ 이 트랙의 진짜 일 — 모듈이 아니라 호스트다

통합가이드는 "30분 · 콜백 4조각"이라 적혀 있지만 그것은 **호스트에 고속 IMU 스트림이 이미 있을 때**다.
모듈은 구 워치앱(`FallDetector.swift`, 전용 `OperationQueue` 고속 스트림)을 전제로 만들어졌고,
**라이브 `VitalWatch` 에는 그 스트림이 없다.**

| | 모듈 요구 | 현재 VitalWatch |
|---|---|---|
| 표본율 | `fs = 50.0` | `deviceMotionUpdateInterval = 1.0` → **1Hz** |
| 12초 윈도 | 600샘플 | 12샘플 |
| 큐 | 전용 직렬 | `.main` |

⚠ **부족하면 조용히 죽는다.** `IMUWindowLogger.emit()` 이 `win.count >= Int(fs)`(50) 미만을 버리므로
`onWindow` 가 **영영 안 불린다** — 크래시도 에러도 없이 ML 이 없는 것처럼 동작한다.
그래서 P5 자가검증을 통과 의례로 둔다(탑재됐다는 착각을 막는 유일한 장치).

## 단계 — 각 단계는 검증으로 닫는다

| 단계 | 하는 일 | 성공 기준(검증 방법) |
|---|---|---|
| **P0** | 계획·체크리스트·컨텍스트 노트 | 이 문서 3종 |
| **P1** | 파일 탑재(Sources 6 + Models 3 + 정답지) · 타깃 등록 | 무서명 빌드 통과 + `.mlmodelc` 3종 생성 실측 |
| **P2** | 50Hz IMU 스트림 신설 · 무동작 경로 보존 | 실효 Hz 로그 ≥45 · `motionStillSec`·`motionVariabilityMg` 종전과 같은 의미 |
| **P3** | 배선 4조각(logger·ml·guard) | `onWindow` 실호출 로그 · `Verdict.trace` 출력 |

| **P5** | 실기기 자가검증 | `MLSelfCheck.run()` **6/6 ✅** |
| **P6** | 배터리 실측 | 1시간 관찰 — 현행 6.46%/h 대비 증가분 |
| **P7** | 서버 보고(별건) | 아래 "미해결" |

## 미해결 — 착수 전에 알고 있어야 할 것

- **서버 어휘 불일치.** 스키마에 낙상 필드는 있으나 `fallDecision` 이 `fall`·`rejected_no_corroboration`·
  `rejected_timeout` 이고 모듈은 `veto_work`·`danger` 로 판정한다. `Verdict.trace`(module_version·확률
  3종·실효Hz·피크G)를 담을 자리도 없다. **P6 까지는 온디바이스+로그로만 닫고 서버는 별건으로 연다.**
- **배터리.** 현행 6.46%/h · 8시간 시프트 여유가 크지 않다. 모듈이 말하는 2.8%/h 는 워크아웃·5초 업로드·
  GPS 가 **없는** 미니앱 조건이라 **더하면 안 된다.** P6 실측 전에는 상시 활성 여부를 결정하지 않는다.
- **recovery 모델 표본.** 1인 21윈도(정확도 86%·위험미탐 1/11)로 주판정을 맡는다. 증량은 ML 담당 몫이고
  우리는 임계·로직을 건드리지 않는다.
- **IMU_ML_Test 계보.** `FallMLPipeline.swift` 머리가 그 미니앱을 출처로 적는데 워치에 설치된 동명 앱의
  번들 ID 가 `com.yangjeehoo.*` 다. 모듈 본문에 해당 문자열은 **0건**이고 저자·이력은 김태곤으로 일관한다.
  사용자가 제시본 사용을 확정했으므로 진행하되, **레포의 구 워치앱 트리에서는 아무것도 가져오지 않는다.**

- impact 확률로 알림을 **억제**하는 로직 추가 (fail-open 위반 = v5 사태의 원인)
