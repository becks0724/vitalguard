사용자가 "오늘 서명한 앱"으로 지정했다. 오늘 09:10 재서명·설치한 그 타깃이고

### 발견 1 — ★ 진짜 블로커는 표본율이다 (이 트랙의 핵심)
모듈은 `fs = 50.0` 을 전제하는데 라이브 워치앱은 `deviceMotionUpdateInterval = 1.0`,
즉 **1Hz** 다. 12초 윈도가 600샘플이어야 하는데 12샘플이 된다.

**부족하면 조용히 죽는다** — `IMUWindowLogger.emit()` 이
`guard win.count >= Int(fs) else { return }` 로 50샘플 미만을 버려서 `onWindow` 가
**영영 안 불린다.** 크래시도 없고 에러 로그도 없다. 오늘 오전 프로파일에서 워치가
빠졌는데 만료일 검증은 통과하던 것과 **같은 형태**다([[L-117]]) — 초록불이 답한 질문이
우리가 묻고 싶던 질문이 아닌 경우. 그래서 `MLSelfCheck` 6/6 을 통과 의례로 못 박는다.

왜 이런 전제가 생겼나 = 모듈은 구 워치앱의 `FallDetector.swift`(전용 `OperationQueue`,
`deviceMotionUpdateInterval = 1/sampleHz`)를 호스트로 쓰고 만들어졌다. 통합가이드의
"콜백에 2줄만"은 그 스트림이 이미 있다는 전제였고, 우리 앱에는 없다.

### 발견 2 — 50Hz 로 올리면 기존 지표가 조용히 뜻이 바뀐다
`motionMagWindow` 의 창 크기가 `motionWindowSize = 60` 이다. 1Hz 에서 60개 = **60초**인데
50Hz 로 올리면 같은 60개가 **1.2초**가 된다. `motionVariabilityMg` 는 계속 값을 내므로
아무도 안 알아챈다.

→ **무동작·변동폭 경로는 1Hz 로 다운샘플해 적재한다.** ML 은 원시 50Hz 를 받고,
기존 지표는 종전 의미를 유지한다. 두 소비자가 한 스트림을 나눠 쓰는 형태다.

`motionUpdates`(콜백 횟수) 로그 문구도 50배 부푼다 — 문구를 손보거나 다운샘플 후 카운트한다.

### 발견 3 — 서버는 아직 이 판정을 받을 그릇이 없다
스키마에 낙상 필드는 있다(`fallDetected`·`fallCandidate`·`fallDecision`·`fallPromptOutcome` 등).
그런데 **어휘가 다르다** — 서버는 `fall`·`rejected_no_corroboration`·`rejected_timeout` 이고
모듈은 `veto_work`·`danger` 로 판정한다. `Verdict.trace`(module_version·확률 3종·샘플수·
실효Hz·피크G·판정시각)를 담을 자리는 아예 없다.

trace 가 없으면 **어떤 판정도 사후 재현이 불가능하다** — 모듈이 v5 사태 재발 방지 장치로
못 박은 계약이다. 그래서 서버 확장을 P7 별건으로 연다. **그 전까지 `onConfirm` 은 로그만
남기고 서버로 보내는 척하지 않는다.**

### 유보 — 배터리 상시 활성 여부는 실측 전에 정하지 않는다
현행 6.46%/h(2026-08-13 재현 확인). 모듈이 말하는 2.8%/h 는 워크아웃·5초 업로드·GPS 가
**없는** 미니앱 조건이라 두 수치를 더하는 것은 틀렸다. P6 에서 1시간 재고 결정한다.
8%/h 를 넘으면 수집 모드 게이트·표본율 하향·배칭을 검토한다.
지금 게이트를 미리 만들지 않는 이유 = 필요한지 모르는 기능이다(투기적 유연성 금지).

### ★ 자가검증 6/6 은 "판정이 맞다" 를 말하지 않는다 — `fs` 축이 통과된다 (08-27 · 옆 세션 19 발견)

`FallMLPipeline.probs()` 는 `slice(…, sec: 3.0)` 을 `Int(3.0 * FallMLPipeline.fs)` = **150표본 고정**으로
자르고, 잘린 창의 특징추출도 기본값 `fs: 50.0` 을 쓴다. 실측 fs 를 넘기는 것은 `nonrecoveryProb` 뿐이다.

**실효 표본율이 50 이 아니면 두 가지가 조용히 어긋난다** — ⓐ 3초라고 믿은 창이 실제로는 다른 길이
ⓑ 주파수 영역 피처가 비율만큼 이동. 갤럭시 실측이 **59.6Hz**(센서 최소지연 8334µs 라 지원 주기가
`119.99/n` 계열이고 50 이 그 안에 없다)라 그쪽은 150표본 = **2.52초**가 된다(−16%).

⚠ **자가검증은 이 축을 못 본다** — 정답지가 `fs=50.0` 고정 입력이라 실측 표본율이 개입할 자리가 없다.
그래서 6/6 은 **"탑재가 온전하다"(모델 로드·특징추출 수치 일치)** 를 보장하지 **"현장 판정이 맞다" 를
보장하지 않는다.** 실기 스트림에서만 드러난다.

**애플은 아직 미측정.** 다만 구조는 유리하다 — iOS `deviceMotionUpdateInterval` 은 임의 값을 받아
안드로이드처럼 양자화되지 않으므로 요청한 `1/50` 이 그대로 나올 개연성이 높다. **재기 전엔 모른다.**
측정 경로 = 세션 종료 로그의 `실효 N.NHz`, 또는 `trace.effective_hz`(**서버 배포 후에만** — 라이브
스키마가 `fallTrace` 를 몰라 스트립한다).

임의로 안 고친다 — `slice` 를 실측 fs 로 바꾸면 모델이 본 적 없는 창 길이가 되어 확률이 조용히
달라진다. **ML 담당 질문 목록**에 올린다(옆 세션 19 도 갤럭시 쪽에서 같은 판단).
