# 태풍 구역·반경 하이브리드 판정 — 결정과 근거

2026-08-01 착수. 기상청 3구역(감시·경계·비상)과 기존 강풍/폭풍반경 판정을 합성해
태풍 진로 추적 민감성을 높인다. 대상 = `app/lib/typhoon-gate.ts` · `app/components/TyphoonTrack.tsx`.

---

## T-01 · 두 기준은 축이 다르다 — 대체가 아니라 합성

| | 기상청 3구역 | 기존 반경 판정 |
|---|---|---|
| 기준점 | 태풍 중심의 **절대 위경도** | **현장 GPS** 기준 상대 거리 |
| 결정하는 것 | 기상청 예보 강화·비상근무 단계 | 이 현장의 작업중지 여부 |
| 태풍 크기 | 반영 없음(고정 경계선) | `typ15`·`typ25` 그대로 |
| 법령 연결 | 없음 | 산안규칙 제143조 순간풍속 15/25m/s |

**어느 한쪽이 우월하지 않다.** 구역은 "얼마나 가까이 왔나"를 태풍 크기와 무관하게 알려주고,
반경은 "우리 현장이 위험한가"를 알려준다. 소형 태풍이 비상구역에 있어도 현장은 안전할 수 있고,
초대형 태풍은 경계구역에 있어도 강풍역이 이미 국토에 닿는다. → **worst-of 합성**.

## T-02 · 6단계 체계 (사용자 결정)

```
none  <  watch  <  alert  <  emergency  <  approach  <  gale  <  storm
  0       1        2          3             4           5       6
```

- `watch`·`alert`·`emergency` = 구역 축(태풍 중심 위치)
- `approach`·`gale`·`storm` = 반경 축(현장 영향권)
- 최종 `zone` = 두 축의 **등급 최고값**

5단계안(감시+경계 통합)도 제시했으나 사용자가 6단계를 선택했다. 기상청 운영 단계와 1:1 대응하고
현장에서 "지금 어느 단계인지"를 공식 용어로 말할 수 있다는 이점이 크다고 판단.

## T-03 · 구역 경계 — 중첩 포함 구조로 구현

이미지(기상청 방재기상운영규정 요약)의 정의를 그대로 따른다.

- 비상구역 — 북위 **28°** 북쪽 AND 동경 **132°** 서쪽
- 경계구역 — 북위 **25°** 북쪽 AND 동경 **135°** 서쪽
- 감시구역 — 북위 25° 남쪽, 동경 135° 동쪽의 북서태평양

**⚠️ 원문 그대로 배타 조건으로 구현하면 사각지대가 생긴다.** 예를 들어 북위 20°·동경 130°
(필리핀 동쪽)는 감시(25°N 남쪽 ✓, 135°E 동쪽 ✗)에도 경계(25°N 북쪽 ✗)에도 걸리지 않는다.
이미지의 감시구역 서술은 "경계구역에 들어오기 전 단계"를 풀어 쓴 것으로 읽는 것이 자연스럽다.

→ **판정을 비상 → 경계 → 나머지 전부 감시 순서의 중첩 구조로 구현한다.**
`getTyphoonInfo` 는 북서태평양 태풍만 반환하므로 "발효 중인 태풍 = 최소 감시구역"이 성립한다.

**결과 — `태풍 추적 중지` 화면이 사실상 사라진다.** 발효 태풍이 하나라도 있으면 항상 `watch`
이상이라 `zone === "none"` 에 도달하지 않는다. 이는 "민감성 최대"의 직접적 귀결이며 의도된 것이다.
`TrackingStopped` 컴포넌트는 방어용으로 남긴다(진로 데이터 결손 등).

## T-04 · ★★ 예보 스캔 순서를 바꾸지 않으면 선행 경보가 죽는다

기존 `computeGate` 는 **`zone === "none"` 일 때만** 예보점을 스캔했다(`typhoon-gate.ts:99`).
하이브리드 후에는 발효 태풍이 항상 `watch` 이상이므로 **이 조건이 영원히 거짓**이 되어
예보 선행 경보 기능이 통째로 죽는다. 기능이 사라져도 타입 오류도 테스트 실패도 나지 않는다
(기존 테스트는 현재 위치가 `none` 인 케이스만 검증하는데 그 케이스 자체가 없어진다).

→ **예보 스캔을 조건 없이 항상 실행**하고, 현재 시점 등급과 예보 최고 등급을 마지막에 합성한다.

```
curZone = worst(현재 반경 판정, 현재 구역 판정)
fcZone  = max over 예보점 { worst(예보점 반경 판정, 예보점 구역 판정) }
zone    = worst(curZone, fcZone)
forecast = rank(fcZone) > rank(curZone)
```

**이번 작업에서 가장 조용히 망가질 뻔한 지점이다.** 회귀 테스트를 반드시 남긴다
(현재가 `emergency` 인데 예보가 `approach` 면 선행 점등되는지).

## T-05 · 예보점도 반경 판정 전 단계까지 본다

기존 예보 스캔은 `rad15` 만 보고 적중하면 무조건 `approach` 였다. 이제 예보점에서도
`rad25`(폭풍반경)를 봐서 `gale`·`storm` 까지 판정한다 — 앞선 분석의 갭 ⓸ 해소.

**단, 등급이 올라가도 지시 문구는 예보용으로 분리한다.** 5일 뒤 폭풍역 직격 예보로
"전면 작업중지·대피"를 지금 띄우면 오작동이다. `ZONE_ADVISORY`(실측) 와
`ZONE_FORECAST_ADVISORY`(예보) 를 별도 테이블로 두고 `forecast` 플래그로 고른다.

예보점 `rad15` 가 **명시 `"0"`**(강풍역 소멸 예보)이면 반경 판정은 기존 정책대로 건너뛴다.
구역 판정은 위경도만 보므로 그대로 산출된다 — 우회가 아니라 별개 축이다(강풍역이 소멸해도
태풍 중심이 비상구역에 있으면 감시 대상인 것이 맞다).

## T-06 · 리드타임은 클라이언트 시계를 쓰지 않는다

`leadHours` = `track[히트 예보점].tm − track[currentIndex].tm`. **둘 다 통보문 안의 KST
문자열**이라 브라우저 시계와 무관하다.

`Date.now()` 로 계산하면 07-31 에 겪은 사고가 재발한다 — 팀 PC 시계가 1분 빨라
서버 기준 신선한 값이 전부 `수신 지연` 으로 표시됐던 건(하네스 교훈 대상). 태풍은 예보 시각이
데이터 안에 들어 있으므로 **외부 시계를 끌어들일 이유가 아예 없다.**

`tm` 파싱은 `typhoon-parse.ts` 의 `tmFcToMs` 와 형식이 같지만 그 파일은 `typhoon-gate.ts` 를
import 하는 방향이라 역참조하면 순환이 된다. → `typhoon-gate.ts` 에 `tmToMs` 를 두고
`typhoon-parse.ts` 는 건드리지 않는다(외과적 수정 · 12줄 중복은 감수).

## T-07 · 색은 5종, 단계는 6종

`emergency` 와 `approach` 는 같은 amber 를 공유한다. 색 어휘를 절약하려는 것이 아니라
**두 단계에서 현장이 할 행동이 같기 때문이다**(자재 결박·타워크레인 하강 = 사전 대비).
등급·라벨·문구는 분리되어 있으므로 정보 손실은 없다.

```
watch     zinc    감시구역 — 배너 없음(패널 텍스트만)
alert     sky     경계구역 — 정보 배너
emergency amber   비상구역 — 대비 배너
approach  amber   영향권 접근
gale      orange  강풍역 진입 (15m/s)
storm     red     폭풍역 진입 (25m/s)
```

`watch` 에 배너를 띄우지 않는 이유 = 태풍 시즌에 상시 점등되어 배너가 벽지가 된다.
감시 단계는 패널 안 텍스트로 충분하다.

## T-09 · ★★ 하이브리드가 지도 프레이밍의 잠재 결함을 드러냈다

적용 후 사용자가 **"육안으로 확인 안 됨"** — 지도가 검은 사각형에 빨간 점 하나였다.

원인은 두 겹이다.

**ⓐ 진로점 1개 → bbox 가 점 → 최대 줌.** `fit()` 이 bbox 를 담는 최대 줌을 찾는데 스팬이 0 이면
`z11` 이 즉시 통과한다. 그 줌의 태평양 원양은 특징 없는 바다라 **타일은 정상 로드되는데(실측 4/4)
화면에는 아무 정보가 없다.** 타일 실패로 오진하기 쉬워 `naturalWidth` 로 먼저 갈랐다.

**ⓑ 담을 줌이 없으면 조용히 `MIN_Z` 를 썼다.** 원래 코드는 루프가 끝까지 실패해도 초기값
`zoom = MIN_Z` 를 그대로 반환한다. 그래서 **bbox 가 화면을 넘겨도 지도는 멀쩡히 그려지고
마커만 캔버스 밖으로 나갔다**(실측 현장 `cx=-24`, 태풍 `cx=155` / 캔버스 131px — 둘 다 밖).
`frameOf()` 가 **실패하면 `null` 을 돌려주도록** 바꾸고 폴백을 명시했다.

**이 결함은 이전에는 관측 불가능했다** — 원거리 태풍이면 `zone === "none"` 이라 지도 자체가
안 떴기 때문이다(추적 중지 패널). 하이브리드가 지도를 띄우면서 비로소 드러났다.
**기능을 확장하면 그 기능이 처음 도달하는 코드 경로가 함께 열린다.**

처방 — ① 진로 + **현장 좌표**를 함께 bbox 에 넣는다(거리 맥락이 눈에 보인다) ② 최소 스팬 4°
③ `MIN_Z` 3 → 2(131px 캔버스에 31.5° 를 담으려면 z3 으론 부족) ④ 현장 마커 + 「현장」 라벨.

## T-10 · ★ 배너 한 줄이 지도를 0 으로 만든다

예보 문구를 넣자 진로 5점 시나리오에서 **지도가 통째로 사라졌다**(`svg` 없음). 배너는 `shrink-0`,
지도는 `flex-1 min-h-0` 이라 **배너가 커진 만큼 지도가 0 까지 눌린다.** 판정·문구는 전부 정확한데
지도만 없어서 텍스트 검증만 했다면 통과했을 상태였다.

세 가지로 고쳤다.
- `ZONE_FORECAST_ADVISORY` 에서 등급명 반복 제거 — 제목이 이미 `강풍역 진입 예보` 라고 말하는데
  본문이 또 `강풍역 예보 ·` 로 시작하고 있었다.
- **태풍명을 배너에서 뺐다**(헤더에 이미 있다). 쌍태풍일 때만 원인 귀속을 위해 유지.
- 지도에 `min-h-[88px]` 하한 — 지도 없는 '태풍 진로'는 무의미하므로, 극단적으로 긴 배너에서는
  패널이 조금 늘어나는 쪽을 택했다. ⚠️ 이 경우 `min-h-[277px]` 기준 좌우 하단선 정렬이 어긋날 수 있다.

**교훈 — 텍스트가 맞다고 화면이 맞은 게 아니다.** 앞선 6단계 검증은 배너 문구만 읽어 전부 통과로
봤는데, 같은 화면에서 지도는 사라져 있었다. 레이아웃을 공유하는 형제 요소의 크기까지 재야 한다.

## T-11 · 검증 도구 함정(이 샌드박스)

- `page.addInitScript` 는 실패한다(`__transport_receive ... expected object, got undefined`).
- **탭·캐러셀 전환은 언마운트가 아니다**(CSS 숨김) — 전환만으로는 재fetch 가 일어나지 않는다.
  응답 교체 검증은 **리로드 직후 `window.fetch` 를 감싸는** 방식이어야 한다.
- `SquareFit` 은 ResizeObserver 로 크기를 잡으므로 **정착 전에 재면 `size.w === 0` 이라
  지도 `svg` 자체가 없다**(L-28 재확인). 클릭 후 충분히 대기하고 측정한다.
- `page.screenshot({path})` 는 절대경로를 거부한다 → 상대명으로 저장되고
  `~/.dev-browser/tmp/` 에 떨어진다.

## T-12 · ★★ getTyphoonInfo 의 예보점 — 실측과 그 한계

사용자가 "기상청 예상 경로를 오버랩할 수 있나" 물어 원본 응답을 전수 확인했다.

**지금 발효 중인 돌핀(괌 동북동 2,020km)에는 예보점이 없다.** 최근 2일 통보문 10건이
전부 **1건당 1행**이고 `typTm` 은 늘 `tmFc` 보다 1시간 이른 관측 시각이다. 전체 필드에도
예보 항목이 없다(`typ15ed/er`·`typ25ed/er` 는 강풍·폭풍반경의 **비대칭 방향/반경**,
`typLoc` 은 "괌 동북동쪽 약 2020 km 부근 해상" 같은 설명문).

**⚠️ 그렇다고 "예보를 절대 안 준다"고 단정하면 안 된다.** 레포 픽스처
(`typhoon-parse.test.ts`)에 **한 통보문이 관측 + 예보 2행을 갖는 바비 사례**가 실사례 축약으로
남아 있다. 과거 구간 조회는 API 가 응답하지 않아(`totalCount` 없음) 검증하지 못했다.
**근접 태풍에는 예보점이 올 여지가 있다** — 원거리 구간 표본 하나로 일반화한 것이 내 성급한 결론이었다.

→ 그래서 진로를 **관측 궤적 + (오면) 예보 구간**을 함께 담는 구조로 만들었다.
예보점이 오는 날 코드 변경 없이 미래 구간이 점선으로 그려진다.

**예상 경로 이미지는 있다** — 응답 `img` 가 기상청 공식 진로도(700×550 PNG, HTTP 200)로
5일 예상경로·70% 확률반경·시점별 강도를 전부 담고 있다. 다만 **위성 지도 위 오버레이는
부적합**하다: ⓐ 이미지에 자체 지도가 그려져 있어 지도가 이중이 된다 ⓑ 지리 범위(bbox)가
비공개이고 진로를 담느라 태풍마다 달라질 수 있어 눈대중 정렬은 위치를 왜곡한다
(작업중지 판단 화면에서 감수할 수 없는 오차) ⓒ `http` 라 mixed content 프록시가 필요하다.
**사용자 결정 — 예상경로 이미지는 넣지 않고 관측 궤적만.**

## T-13 · 궤적 구성 규칙 — 낡은 예보를 섞으면 안 된다

기존 구현은 **최신 통보문 행만** 진로로 썼다(그래서 track 이 늘 1점이었고 지도에 점 하나만 찍혔다).
2일치 통보문 10건을 이미 받아놓고 9건을 버리고 있었다 — 추가 호출 없이 궤적을 만들 재료가 있었다.

바꾼 규칙:
- **관측점**(`typTm ≤ tmFc`) — 모든 통보문에서 모은다 → 지나온 경로
- **예보점**(`typTm > tmFc`) — **최신 통보문 것만** 채택. 옛 통보문의 예보는 이미 갱신된 낡은
  예측이라 버린다. 섞으면 **실제로 지나가지 않은 위치가 궤적에 낀다.**
- 같은 `typTm` 이 겹치면(옛 예보 vs 새 관측) **관측 우선**, 동급이면 최신 통보문
- `pickCurrentIndex` 는 최근접 → **`tmFc` 이하의 마지막 지점**으로. 예보점이 `tmFc` 에 더
  가까울 수 있는데 현재 위치는 어디까지나 관측이어야 한다.

화면에서는 **지나온 경로 = 실선, 예보 진로 = 점선**으로 나눈다. 같은 선으로 그리면
'앞으로 갈 길'로 오독되는데, 지나온 곳과 예측은 신뢰도가 다르다.

## T-14 · ★★★ 예보 API 를 찾았다 — `getTyphoonFcst`

T-12 에서 "예보 좌표는 안 온다"고 했던 것이 **틀렸다.** 같은 서비스에 오퍼레이션이 하나 더 있었다.

**찾은 경로** — data.go.kr 문서에 *"태풍정보조회 · 태풍정보목록조회 · **태풍예상정보조회**"* 세 기능이
적혀 있는데 상세 명세는 `getTyphoonInfo` 하나만 있었다. 오퍼레이션 이름을 탐색해 두 개를 더 찾았다
(404 = 없음 / `code=11` = 있는데 파라미터 부족 으로 갈린다).

| 오퍼레이션 | 필수 파라미터 | 내용 |
|---|---|---|
| `getTyphoonInfo` | `fromTmFc`+`toTmFc` | 통보문(관측점 1건당 1행) |
| `getTyphoonInfoList` | `tmFc` | 통보문 목록(`announceSeq`·`title`) |
| **`getTyphoonFcst`** | **`tmFc`+`typSeq` 둘 다** | **5일 예보점 + 확률반경** |

⚠️ `getTyphoonFcst` 는 **둘 중 하나만 주면 `APPLICATION_ERROR`(code=01)** 다. 파라미터 조합이
맞아야 열린다 — 하나씩 시도했으면 "없는 API" 로 오판했을 것이다.

**응답 필드** — `tm`(예보 유효시각)·`lat`·`lon`·`ps`·`ws`·`rad15`·`rad25`·`dir`·`sp`·`fcLocKo`
그리고 **`radPr` = 70% 확률반경(km)**. 통보문과 **필드명이 다르다**(`typLat`→`lat`, `typTm`→`tm`)
→ 별도 파서 `parseForecastItems` 가 필요하다.

**실측(제13호 돌핀 · 08-01 10:00 발표)** — 예보점 7개(+12h ~ +120h),
`radPr` 40 → 80 → 110 → 130 → 190 → 290 → **440km** 로 시간에 비례해 커진다.

**이로써 T-12 의 처방이 전부 불필요해졌다** — 지속성 외삽도, 불확실성 마진 추정도 필요 없다.
기상청 공식 예보와 공식 확률반경이 그대로 온다. 자체 예측 모델을 만들지 않기로 한 판단이 옳았다.

## T-15 · 확률반경은 더하는 값이지 바꾸는 값이 아니다

`radPr` 을 `rad15` 자리에 넣으면 판정 근거가 통째로 바뀐다 — **강풍반경은 15m/s 가 닿는 범위이고
확률반경은 중심이 있을 수 있는 범위**다. 서로 다른 물리량이다.

올바른 사용 = **가산**. 중심이 확률반경 안 어디든 있을 수 있으므로 최악의 경우 그만큼 현장에
더 가깝다 → `거리 ≤ (강풍반경 + 확률반경)` 로 보수적으로 본다.

```
gale15 > 0 ? gale15 + prKm : 0     // 반경이 0(미제공·소멸 예보)인 축에는 더하지 않는다
storm25 > 0 ? storm25 + prKm : 0   // 더하면 없던 영향권이 생긴다
```

## T-16 · 캐시 키 회전 — track shape 이 바뀌면 필수

예보점을 붙인 뒤에도 화면이 그대로였다. `active-v2` 캐시(30분)에 관측점만 든 배열이 남아 있어서다.
`active-v3` 으로 올려 해소(v2 회전과 같은 이유). **배포 시에도 같은 일이 난다** — 새 코드가 떠도
구 캐시가 30분간 서빙되므로, track 구조를 바꿀 때는 키 회전을 함께 커밋한다.

## T-08 · 손대지 않은 것

- **현재 위치 `rad15="0"` 폴백 불일치** — 예보점은 명시 `"0"` 을 존중해 미점등하는데 현재 위치는
  값 없음과 구분하지 않아 500km 폴백 `approach` 가 켜진다(`typhoon-gate.ts:90-95`).
  안전측 오류이고 이번 요청 범위 밖이라 그대로 둔다. 구역 판정이 들어오면서 이 폴백의 역할이
  상당 부분 대체되므로(비상구역 700~900km) 후속으로 정리 여지가 있다.
- **태풍특보 연동** — `kma.ts:59` 의 `parseT6` 가 이미 `태풍경보`·`태풍주의보` 를 파싱하고 있어
  공식 특보와 자체 판정을 대조할 수 있다. 별도 작업으로 미룬다.
- **구역의 서쪽·남쪽 한계 없음** — 중국 내륙 깊숙이 들어간 태풍도 위경도만으로는 `emergency` 가
  된다. 이미지에 해당 경계가 없어 정의를 그대로 구현했다. 화면에 거리를 항상 병기하므로
  오독 위험은 낮지만 한계로 기록한다.
