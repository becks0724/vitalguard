## 왜 협업하는가 — 컴퓨팅 단위 풀링

A100 30에포크가 약 **4.8시간**이고 A100 은 T4 의 약 6배를 소모한다.
한 계정의 컴퓨팅 단위가 중간에 떨어지면 학습이 끊긴다.
체크포인트가 **공유 Drive** 에 쌓이므로 다른 계정이 이어받으면 처음부터 다시 하지 않는다.

**그래서 협업은 "동시 병렬"이 아니라 "교대(릴레이)"다.**

```
A 계정이 돌린다 → 단위 소진 / 세션 끊김 → B 계정이 RESUME=True 로 이어받는다
```

## ⛔ 가장 먼저 알아야 할 것 — 동시 실행 금지

학습 셀은 `project=` 를 공유 Drive(`vitalguard-ppe/runs/`)로 쓰고 `exist_ok=True` 다.
두 계정이 같은 `RUN_NAME` 을 **동시에** 돌리면 `last.pt`·`best.pt`·`results.csv` 를
서로 덮어쓴다. **오류가 나지 않는다** — 몇 시간 뒤에 조용히 망가진 것을 발견한다.

노트북에 **잠금 셀**을 넣어 두었다(학습 셀 바로 앞). `RUNNER` 에 각자 이름을 적으면
상대 세션이 살아있는지 `last.pt` 갱신 시각으로 판정해 막는다.

```
직전 실행자 teammate (...) · last.pt 갱신 5분 전
⛔ teammate 의 세션이 살아있다(마지막 갱신 5분 전 · 기준 30분).
```

이 메시지가 나오면 **거기서 멈추고 상대에게 확인한다.** 우회하지 말 것.

> 잠금은 `last.pt` 갱신을 심장박동으로 쓴다. 에포크가 약 9.5분이므로 30분 정지면
> 세션이 죽은 것으로 본다. 첫 에포크가 끝나기 전(약 10분)에는 잠금 파일 시각으로 판정한다.

## 실행 — 처음 돌리는 사람

설정 셀에서 두 값만 확인하고 **맨 위부터 순서대로** 실행한다.

```python
RESUME = False        # 처음이므로 False
RUNNER = '<본인 이름>'
```

### 반드시 눈으로 확인할 4곳

**① 설정 셀**

```
GPU  : NVIDIA A100-SXM4-40GB · CPU 12코어 → batch 64 · workers 8
E63  : .../e63_yolo.tar → 2.06 GB
```

`batch 16 · workers 2` = T4 다(정상, 5~6배 느림). `⚠️ 없음` = 3번(바로가기) 미완.

**② 리매핑 직후 — `★ SH17 필터` 줄이 있어야 한다**

```
   ★ SH17 필터 — 안전모 쓴 머리 제외 N · helmet 박스 제외 M
시퀀스 43개 중 12개를 홀드아웃으로 예약
★ helmet : head = 1 : 0.5~0.7
```

`★ SH17 필터` 줄이 **없으면 5차의 절반이 동작하지 않은 것**이다(`SH17_HEAD_FILTER` 확인).
제외 건수가 0 이면 매핑이 빠진 것이니 멈춘다.

**③ 자동 라벨 셀 — `person` 총량이 늘어야 한다**

```
person 자동 라벨 대상 N장 (train 분할·person 라벨 없는 것만 · conf 0.5)
★ person 라벨 M개 추가 · 이미지 K장
=== 5차 최종 클래스별 인스턴스 (train+val · 자동 라벨 포함) ===
```

`대상 0장` 이면 `e63_*`·`hhw_*` 가 train 분할에 없다는 뜻이니 ② 출력을 다시 본다.
이 셀이 3~6분 걸린다(A100).

**④ 홀드아웃 누수 검사**

```
홀드아웃 시퀀스 12개 → 2,166장 (학습 미노출)
  누수 검사: 통과 (학습셋과 교집합 0)
```

`assert` 로 강제하므로 실패하면 자동으로 멈춘다.

그 다음 **잠금 셀 → 학습 셀**. 화면의 ETA 는 무시하고 **완료된 에포크 실측**으로만 판단한다.

## 인수인계 — 끊겼을 때 이어받는 사람

세션이 끊기거나 컴퓨팅 단위가 떨어지면 **상대에게 알린 뒤** 이어받는다.

```python
RESUME = True         # ★ 이것만 바꾼다
RUNNER = '<본인 이름>'
```

**다른 값은 절대 건드리지 말 것.** 특히 `SH17_FRACTION`·`HHW_FRACTION`·`SCALE`·`EPOCHS`·
`E63_HOLDOUT_SEQ_RATIO` 를 바꾸면 학습 데이터가 달라져 이어받기가 무의미해진다.

실행 순서는 **설치 → 설정 → 데이터 → 리매핑 → 자동 라벨 → 홀드아웃 → 잠금 → 학습**.
데이터 재구축이 필요한 이유는 `/content` 가 세션마다 비워지기 때문이다.
해시가 결정적이므로 **같은 12개 시퀀스·같은 분할이 재현된다** — 그래서 이어받기가 성립한다.

### 잠금 셀 출력별 대응

| 출력 | 뜻 | 할 것 |
|---|---|---|
| `잠금 기록 → 본인` 만 | 잠금 없음 | 진행 |
| `<상대> 세션은 멈춰 있다 → 이어받는다` | 안전하게 이어받는 중 | 진행 |
| `⛔ <상대> 의 세션이 살아있다` | 상대가 지금 돌리는 중 | **멈추고 확인** |
| `⚠️ last.pt 가 있는데 RESUME=False` | 0에포크부터 덮어쓴다 | `RESUME=True` 로 바꾸고 다시 |
| `⚠️ RESUME=True 인데 last.pt 가 없다` | 이어받을 것이 없다 | 첫 실행이면 `False` |

## 학습 후 — 판정 (원 계정에서 몰아서)

노트북 뒷부분을 순서대로 돌린다.

```
공정 평가(fair_eval)      helmet R ≥ 0.70 이 5차의 존재 이유 (4차 0.433)
예약 홀드아웃             head P ≥ 0.70 유지 (4차 0.800 에서 회귀하면 실패)
미착용 알림 임계 스윕      R ≥ 0.90 @ P ≥ 0.85 유지 (4차 0.941 / 0.999)
기준선 비교(9절)          현행 vyra_ppe.pt 와 같은 홀드아웃·같은 잣대
내보내기(10절)            Drive weights/ 로 복사 + 젯슨 변환 명령 출력
```

### ⚠️ 홀드아웃 통과만으로 5차 성공이 아니다

**5차의 목적은 도메인 얽힘 해소이고, 그것은 홀드아웃으로 측정되지 않는다.**
예약 홀드아웃도 E63 도메인이라 4차의 결함을 가렸던 구조가 그대로다.

```
★ E63 밖에서 head 검출 > 0 건   ← GoPro·사진 30장·폰 라이브로만 측정된다
```

이 항목은 학습이 끝난 뒤 **젯슨에 엔진을 올려 GoPro 로 재시험**해야 확인된다.
홀드아웃 수치가 4차보다 좋아도 이게 0 이면 5차는 목적을 달성하지 못한 것이다.
