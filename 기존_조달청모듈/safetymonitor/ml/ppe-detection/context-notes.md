작업 중 내린 결정과 근거를 계속 덧붙인다. 코드만 보면 알 수 없는 "왜"를 남기는 것이 목적이다.

## 2026-07-26 — 트랙 개시

### 목표

상용화 전 성능 테스트. 현재 라이브(CAM-03)에서 돌고 있는 Hexmon `vyra_ppe.pt`(YOLOv8m 14클래스)를
**yolo26m 자체 학습 모델로 교체할 수 있는가**를 숫자로 판정한다.

### 결정 1 — 기준선은 공개 데이터셋 논문값이 아니라 현행 모델

`cctv-ai/main.py` 의 CAM-03 이 이미 PPE 추론을 서버에서 돌리고 있다. 따라서 "얼마나 좋은가"가 아니라
**"현행보다 나은가"** 가 판정 기준이다. 같은 홀드아웃 셋에 두 모델을 태워 비교한다.

### 결정 2 — 클래스 설계는 부위+장비 8클래스, 미착용은 코드로 판정

```
0 person  1 head  2 helmet  3 safety_vest  4 foot  5 shoes  6 hands  7 gloves
```

현행 Hexmon 모델처럼 `NO-Hardhat` 을 별도 클래스로 두지 않는다.

**왜** — "미착용"은 시각적 객체가 아니라 부정(negation)이라 각도·가림에 따라 `Hardhat` ↔ `NO-Hardhat` 을
오가며 깜빡인다. `head`(맨머리)와 `helmet`(안전모)을 각각 탐지하고 person 박스와의 포함관계로 착용을
판정하면, 임계값을 코드에서 조정할 수 있어 현장 튜닝이 가능하다.

부수 효과로 CSS 데이터셋의 `NO-Hardhat` 라벨을 `head` 로 흡수할 수 있어 데이터가 낭비되지 않는다.

### 결정 3 — SH17 은 이 단계 한정, 상용 빌드 반입 금지

SH17(CC BY-NC-SA 4.0)은 비상업 라이선스다. 성능 상한 측정과 안전화(`shoes`) 데이터 확보를 위해
이 단계에서는 쓰되, **가중치 파일명에 `-nc` 접미사를 강제**해 상용 파이프라인으로 흘러가지 않게 한다.
상용화 시에는 CSS(CC BY 4.0) + AI Hub + 자체 수집으로 **데이터만 교체해 재학습**한다.
그래서 학습 스크립트는 데이터셋 조합을 플래그로 켜고 끌 수 있게 만들었다(`USE_SH17`).

### 결정 4 — 안전화는 이 단계에서 "탐지 가능성 확인"까지만

SH17 의 `Shoes` 는 신발 일반이라 안전화/운동화를 구분하지 않는다. 따라서 "안전화 착용 여부" 판정은
공개 데이터만으로 불가능하다. 이번 단계 목표는 **원거리 CCTV 화각에서 발·신발이 애초에 잡히는지**를
확인해, 국내 데이터 재라벨링 투자 가치를 판단하는 것이다.

### 결정 5 — 학습은 코랩, TensorRT 변환은 젯슨

코랩은 x86 + 데이터센터 GPU라 여기서 만든 `.engine` 은 Jetson 에서 못 쓴다(아키텍처·TensorRT 버전 종속).
코랩 산출물은 `.pt` 까지이고, 엔진 변환은 타깃 젯슨에서 한다. INT8 캘리브레이션도 마찬가지다.

### 결정 6 — 노트북은 자기완결형(self-contained)

리매핑 로직을 별도 `.py` 로 빼지 않고 노트북 셀에 둔다. 레포가 private 이라 코랩에서 raw 로 못 받아오고,
파일 업로드를 요구하면 세션마다 마찰이 생긴다. 단일 소스는 노트북이다.

### 미해결 — 실 현장 홀드아웃 영상

공개 데이터셋 val 성적만으로는 "이벤트 단위 오탐률" 을 만들 수 없다. 현장 영상 확보 전까지
3층 지표 중 3층(시간당 오탐 건수)은 측정 불가다. `cctv-ai/samples/cam03.mp4`(유튜브 건설현장 30초)가
임시 대용이 될 수 있으나 정답 라벨이 없어 정성 확인용이다.

## 2026-07-28 — 1차 학습 완주 결과 (yolo26s · 640 · 25ep)

### 실행 조건

코랩 T4 Pro · `yolo26s.pt` · `imgsz 640` · `batch 16` · `epochs 25` · **12.345시간**
학습 데이터 12,591장(SH17 9,933 + CSS 2,658) → train 11,521 / val 970

960 → 640 으로 낮추고 batch 를 -1(AutoBatch) → 16 으로 고정한 것이 결정적이었다.
960 + AutoBatch 는 에포크당 31분이라 60에포크 완주가 불가능했다(77시간 추정).

### 결과

| 클래스 | val 인스턴스 | Recall | mAP50 | mAP50-95 |
|---|---|---|---|---|
| all | 5,733 | 0.651 | 0.676 | 0.447 |
| person | 1,662 | 0.867 | 0.901 | 0.712 |
| head | 1,282 | 0.874 | 0.903 | 0.680 |
| hands | 1,559 | 0.791 | 0.844 | 0.572 |
| shoes | 505 | 0.612 | 0.667 | 0.382 |
| helmet | **169** | 0.628 | 0.590 | 0.358 |

| foot | 105 | 0.371 | 0.407 | 0.213 |

### 판정

**① 가장 중요한 지표는 통과** — `head` recall 0.874. 안전모 미착용(맨머리)을 87% 잡는다.
안전 관점에서 가장 비싼 실패를 막고 있다.

**② 안전조끼는 실사용 전 보정 필수** — `safety_vest` recall 0.567. 위반 판정이
`조끼 미검출 = 위반` 이라 **조끼 착용자의 43%가 위반으로 오탐**된다.

**③ 안전모는 구조적으로 안전** — `judge_ppe()` 가 위반을 `맨머리 AND 헬멧 없음` 으로
정의해서, 헬멧을 놓쳐도 맨머리가 안 잡히면 위반으로 세지 않는다.
미착용을 별도 클래스로 두지 않은 설계(2026-07-26 결정 2)가 여기서 효과를 봤다.

**④ 안전화 — 이번 단계 목표 달성** — `shoes` 0.612 / `foot` 0.371.
640 해상도 원거리에서도 신발이 61% 잡힌다 → 국내 재라벨링 투자 가치 있음.

### ★ 한계 — helmet·vest 수치는 신뢰구간이 넓다

학습에는 helmet 4,478 · vest 3,788 인스턴스를 썼는데 **val 에는 169 / 90 밖에 안 들어갔다.**
분할 편향이다. 90개로 낸 recall 은 통계적으로 불안정하다.

→ **교차 데이터셋 홀드아웃(Hard Hat Workers, helmet 19,747개 = val 의 117배)이
helmet 성능의 진짜 측정치**가 된다. 이 트랙에서 홀드아웃을 넣어둔 가치가 여기서 나온다.

## 2026-07-28 — 교차 데이터셋 홀드아웃 결과 (★ 결론이 바뀜)

홀드아웃 = Hard Hat Workers v13 (Roboflow Universe, `joseph-nelson/hard-hat-workers`).

### 함정 두 개를 먼저 걷어냈다

**① v14 는 클래스가 병합돼 있다** — 내보내기 클래스가 `['head']` 하나뿐.
인스턴스 26,424 = 원본 helmet 19,747 + head 6,677 과 정확히 일치해서 확인됨.
안전모 쓴 머리도 `head` 로 라벨돼 있어, 우리 모델이 `helmet` 으로 맞혀도 전부 오답 처리된다.
→ 이 버전으로 낸 "62.4% 하락"은 허상. **버전별 클래스 확인이 필수.**

**② v13 은 증강본이다** — 원본 7,035장 → 16,866장(2.4배). 회전·cutout·흑백이 걸려 있고
사무실 실내 장면까지 섞여 있다. 증강본을 홀드아웃으로 쓰면 부당하게 어렵다.
→ Roboflow 는 `train` 만 증강하므로 **`valid`/`test` 원본만(2,119장) 사용**해야 공정하다.

증강 포함 → 제외로 바꾸자 head 83.7%→70.4%, helmet 35.7%→19.3% 로 개선됐다.

### 공정 조건 결과 (2,119장 · helmet 5,828 / head 2,065)

| class | R_인도메인 | R_교차 | 하락률 | P_교차 | mAP50_교차 |
|---|---|---|---|---|---|
| helmet | 0.633 | 0.511 | **19.3%** | 0.524 | 0.383 |
| head | 0.874 | 0.259 | **70.4%** | **0.181** | 0.130 |

### 진단 — head 오탐의 원인이 특정됨

핵심 지표는 recall 이 아니라 **head precision 0.181**(예측한 head 의 82%가 오답)이다.
홀드아웃은 helmet 이 74%인 데이터인데 여기서 head 오탐이 쏟아진다는 것은 하나를 뜻한다.

> **모델이 안전모 쓴 머리를 `head`(맨머리)로 예측하고 있다.**

helmet recall 이 0.511 이라 못 잡은 자리를 head 로 채운다. 학습 데이터가
`head 14,413 : helmet 4,478 = 3.2 : 1` 로 맨머리에 치우친 결과다(2026-07-27 지적한 출처 편중).

### ★ 2026-07-28 오전 판단 정정

앞서 "안전모는 구조적으로 안전 — 헬멧을 놓쳐도 맨머리가 안 잡히면 위반으로 안 센다"고
기록했으나 **틀렸다.** 모델이 헬멧 쓴 사람에게 적극적으로 `head` 를 예측하므로
`judge_ppe()` 의 `맨머리 AND 헬멧없음` 두 조건이 동시에 성립한다.

**실사용 시 안전모 착용 작업자가 미착용 위반으로 오탐된다.**
안전조끼 recall 0.567 과 합쳐 **현 상태로는 관제 투입 불가.**

### 해결 방향 — 홀드아웃으로 쓴 데이터가 곧 해답

Hard Hat Workers 원본에는 helmet 이 19,744개 있다. 학습에 편입하면 불균형이 뒤집힌다.

```
현재     helmet  4,478 : head 14,413 = 1 : 3.2
편입 후  helmet 24,222 : head 21,090 = 1 : 0.87
```

단 편입하면 홀드아웃 자격을 잃으므로 **홀드아웃은 CHV 또는 SHWD 로 교체**해야 한다.

### 다음

1. Hard Hat Workers 편입 재학습(2차)
2. 홀드아웃 교체(CHV / SHWD)
3. 내일 사진 촬영 — 안전모 착용 비중 상향(근거 확정됨)
4. AI Hub 국내 데이터 신청
5. 현행 `vyra_ppe.pt` 도 같은 홀드아웃에 태워 비교

### 교훈

- **공개 홀드아웃은 "버전 클래스 구성"과 "증강 여부"를 먼저 확인해야 한다.**
  둘 다 확인 없이 쓰면 결론이 정반대로 나온다(62.4% 허상 → 70.4% → helmet 은 19.3%).
- 인도메인 val 만 봤다면 head recall 0.874 로 "충분하다"고 판단하고 배포했을 것이다.
  현장 영상 부재를 메우려 넣은 교차 홀드아웃이 정확히 제 역할을 했다.

## 2026-07-28 — 2차 학습 설계

### 문제

교차 홀드아웃에서 head precision 0.181. 모델이 안전모 쓴 머리를 `head` 로 예측한다.
학습 데이터 `head : helmet = 3.2 : 1` 편중이 원인.

### 결정 1 — Hard Hat Workers 를 학습에 편입

홀드아웃으로 쓰다가 문제를 찾아낸 데이터가 곧 해답이다. helmet 19,744개가 있다.

```
1차   helmet  4,478 : head 14,413 = 1 : 3.2
2차   helmet ~23,700 : head ~15,100 = 1 : 0.64
```

편입하면 홀드아웃 자격을 잃으므로 **제3 데이터셋으로 교체**해야 한다.

### 결정 2 — SH17 서브샘플 (기본 0.5)

SH17 은 helmet 이 927개뿐이라 helmet 보강에 기여가 없는데 학습 시간만 늘린다.
절반으로 줄여도 `shoes`·`gloves`·`foot` 은 2,000개 이상 남는다.
학습 시간 조절 레버로도 쓴다(1.0 → 15.7h / 0.5 → 12h / 0.3 → 10.4h).

### 결정 3 — Roboflow 증강 사본 제거

`<원본>_jpg.rf.<해시>` 패턴으로 묶어 원본 1장만 학습에 넣는다.
Ultralytics 가 자체 증강을 하므로 이중 증강을 피한다.
HHW v13 은 16,866장 중 약 9,800장이 증강본이다.

### 결정 4 — 홀드아웃은 2단 확인 구조

후보를 다운로드해 **클래스 구성·증강 여부를 먼저 출력**하고, 확인 후 평가한다.
1차에서 병합본(v14)과 증강본(v13)에 연달아 데인 것을 절차로 막는다.

**클래스 이름이 같아도 뜻이 다를 수 있다** — SHWD 계열의 `person` 은 "사람 전체"가 아니라
"헬멧 안 쓴 머리"인 경우가 있다. 매핑 확정 전에 프로젝트 설명을 확인할 것.

### 결정 5 — 에포크 20 (1차는 25)

데이터가 늘어 에포크당 학습량이 1.28배다. `2차 20 에포크 ≈ 1차 25.6 에포크`(총 step 기준)
이므로 20 이면 충분하다.

  (SH17 공식 클래스 순서 · Kaggle 신규 토큰 인증 · 패키지 자동설치 가드 · 결정적 분할)

### 조사 결과 — 3개 데이터셋 검토

163 은 샘플 830장을 전수 분석해 부적합을 확인했다. **라벨을 까보기 전에는 쓸모를 알 수 없다** —

### 채택 — E63 안전장비 (dataSetSn=71771 / DATA3)

```
안전모 착용머리   → helmet   train 15,698 · val 1,943
```

`safety_vest` `shoes` `foot` `gloves` 도 같은 이유로 눌린다.
**출처가 섞인 데이터셋에서 클래스별 지표를 볼 때는 그 클래스를 라벨링한 출처만 남겨야 한다.**

### ⚠️ 함정 ② — 데이터셋마다 head/helmet 박스의 의미가 다르다

같은 모델인데 평가 대상에 따라 helmet 이 4배 차이 났다(전체 val P 0.813 → sh17+css P 0.219).

|---|---|---|
| E63 · HHW · CSS | 안전모 **미착용** 머리 | 안전모 **착용** 머리 (배타적) |

### ⚠️ getUserMedia 는 보안 컨텍스트를 요구한다 — 이게 최대 관문이었다

브라우저 카메라는 HTTPS 에서만 열린다. 평문 HTTP·자체서명으로는 사파리가 카메라를 안 준다.
`sudo tailscale cert <name>.ts.net` 으로 **유효한 Let's Encrypt 인증서**를 받아 젯슨이 직접
HTTPS 로 서빙해 해결했다. 발급 직후 root 소유라 `chown jetson:jetson` 이 필요하다(Flask 가 못 읽는다).

Cloud Run 페이지에서 젯슨으로 POST 하는 방식은 **mixed content 차단**으로 불가능하다.
→ 캡처 페이지를 젯슨이 서빙해 same-origin 으로 만드는 것이 정답이었다.

### ⚠️ 전송 천장 = 약 4.8 fps · 원인은 iOS Safari 타이머 스로틀

| 설정 | 결과 |
|---|---|
| 640×360 · Q0.5 · 목표 5 | 4.80 fps |
| 640×360 · Q0.5 · 목표 8 · 슬롯 4 | 4.80 fps |
| 480×270 · Q0.4 · 목표 8 | 4.75~5.20 fps |

**해상도를 44% 줄여도, 목표·슬롯을 올려도 오르지 않았다.** 네트워크(슬롯 증설 무효)·
JPEG 인코딩(해상도 감소 무효)·젯슨(추론 14.7ms·CPU 6%)이 전부 배제되고
남는 것은 **iOS Safari 의 `setInterval` 스로틀(≈208ms)** 이다. 페이지 JS 로는 우회할 수 없다.

5fps 초과는 방식을 바꿔야 한다 — **WebCodecs `VideoEncoder`**(Safari 17+·H.264 하드웨어) 또는
**RTMP 송출앱 + 젯슨 `mediamtx`**(개발 0·30fps). **WebSocket 은 효과가 없다**(전송이 병목이 아님).
PPE 착용 판정에 필요한 갱신율은 초당 3~5회라 현재로도 목적에는 충분하다.

### 그 전에 고친 것 — Cloud Run 직결 경로의 끊김

원인은 **왕복 직렬화**였다. 캡처 페이지가 한 번에 한 장만 보내는데 왕복(실측 평균 264ms·
최대 420ms)이 `setInterval` 주기 200ms 를 넘으면 다음 tick 이 통째로 버려졌다(실측 3.2fps).

- ① 파이프라이닝(최대 3장 동시 + 5초 abort) ② ingest3 즉시 응답 ③ 디코드 스레드풀
- → **3.2 → 4.89 fps**. 파이프라이닝이 주효과였다(네트워크 변동을 겹쳐서 감춤).
- 파이프라이닝은 프레임이 겹쳐 도착하므로 `draw_ts` 로 늦게 끝난 옛 프레임을 폐기해야 한다.

### 라벨이 헤더에 가리던 문제

박스를 먼저 그리고 헤더를 나중에 그려 상단 박스의 라벨이 먹혔다.
**헤더 → 박스 → 라벨 순으로 바꾸고**, 라벨이 헤더에 닿으면 박스 안쪽에 붙이도록 했다.

## 2026-07-30 (오후) — ★★ 진짜 원인은 스케일이 아니라 도메인 얽힘이었다

오전에 "근거리 미검출 = 스케일 한계"로 진단했다. **그 진단은 불완전했다.**
GoPro 를 CCTV 처럼 높이 거치해 학습 스케일(0.037~0.10)을 맞췄는데도 `head` 가 0건이었다.

### GoPro 파이프라인은 성공했다

```
GoPro HERO9 (USB-net UDP 8554) → 젯슨 yolo26 v4 TensorRT → /cctv/ingest3?drawn=1 → CAM-03
스트림 30.1 fps · 추론 14.8ms · 재연결 0회 · 13,038프레임 / 4,275회 추론
```

아이폰의 두 병목(**iOS Safari 타이머 스로틀 4.8fps · 근거리 화각**)이 둘 다 사라졌다.
유선이라 6배 빠르고, 높이 거치로 CCTV 부감 화각이 재현됐다. `edge/gopro_ppe_edge.py`.

### ★ 결정적 A/B — 같은 모델, 두 장면, 결과가 완벽히 반대

```
E63 학습 도메인(전기설비 공사현장) 실이미지 3장
  head 1 · helmet 0 · person 0     ← 머리는 잡고 사람은 0
  head 1 · person 0                   (크기 0.049~0.073)
  head 1 · person 0

GoPro 사무실 화면
  head 0 · helmet 0 · person 6~7   ← 사람만 잡고 머리는 0
```

**크기는 둘 다 학습 범위(0.033~0.086) 안이었다.** `conf` 를 0.15 → 0.05 → **0.01**(사실상 무제한)
까지 내려도 `head` 는 0건이고 `person 19 · hands 31 · shoes 17` 만 나왔다. 임계 문제가 아니다.

### 원인 — 클래스마다 학습 도메인이 갈려 있다

| 클래스 | 학습 출처 | 그 출처의 장면 |
|---|---|---|
| `person` | SH17 + CSS | 일반 인물 사진 · 건설현장 |
| `head` `helmet` | **E63(주력)** + HHW + CSS | 전기설비 공사현장 CCTV |
| `hands` `shoes` `foot` `gloves` | SH17 | 일반 인물 사진 |

**E63 에는 `person` 라벨이 아예 없다.** 그래서 모델은 "E63 처럼 보이는 장면"에서 person 을 찾지 않는다.
반대로 `head` 는 E63 에서만 배웠으니 "사무실처럼 보이는 장면"에서 찾지 않는다.

신경망은 물체만 배우지 않고 **주변 맥락까지 함께** 배운다.
`배전반·작업복·현장 조명 + 둥근 실루엣 → head` / `모니터·형광등 + 사람 형태 → person`.
**클래스가 장면 유형에 묶여버린 것**이다(domain–class entanglement).

### 함의 셋

1. **게이트 통과는 E63 도메인 안에서만 유효하다.** 예약 홀드아웃이 E63 이라 이 결함이 가려져 있었다.
   같은 업종·카메라 계열이면 잘 되고, 다른 업종 현장은 검증되지 않았다.
2. **`judge_ppe`(person↔helmet 포함관계)는 E63 현장에서 못 쓴다** — person 이 0이므로.
   다행히 `bare_head_eval` 은 이미지 단위(head 유무)라 게이트는 통과했다.
   하지만 **"3번 작업자가 미착용" 같은 개인별 판정은 지금 구조로 불가능**하다.
3. **현행 Hexmon 이 이 점에서 강하다.** 어제 폰 근거리 테스트에서 Hexmon 은 사무실에서도
   안전모 미착용을 정확히 잡았다. 교체 판정에서 불리한 요소이므로 정직하게 기록한다.

### ★ 5차 해법 — SH17 을 통째로 뺀 것이 과했다

SH17 의 `head` 는 "머리 전체(착용 무관)" 이라 helmet 과 78.2% 겹쳐 라벨 충돌을 일으켰다.
그런데 **겹치지 않는 head 만 골라내면 그것이 곧 "안전모 안 쓴 머리"** 이고 우리 정의와 일치한다.

```
SH17 head 중
  helmet 박스와 IoU > 0.3 겹침  →  "안전모 쓴 머리" → 버린다
  겹치지 않음                    →  "미착용 머리" → 채택 ✅ (약 20% 잔존)
```

**라벨 의미 충돌은 피하면서 도메인 다양성만 가져온다.** 4차 부작용을 정확히 되돌리는 방법이다.

추가로 **E63 에 person 을 자동 라벨(pseudo-label)** 하면 E63 현장에서도 person 이 잡혀
작업자별 판정이 가능해진다. COCO 사전학습 모델로 생성한다.

```python
SH17_HEAD_FILTER   = True      # ★ helmet 과 겹치지 않는 head 만 채택
SH17_HEAD_IOU      = 0.3       #    겹침 판정 임계
E63_PERSON_PSEUDO  = True      # ★ E63·HHW train 분할에 person 자동 라벨
PSEUDO_CONF        = 0.5       #    자동 라벨 신뢰도 하한
HHW_FRACTION       = 0.45      # helmet recall 복원(4차 0.15 → R 0.433 로 하락)
SCALE              = 0.8       # 스케일 내성 보강 (설계 밴드 0.7~0.9 의 중간값)
EPOCHS             = 30        # 유지
E63_HOLDOUT_SEQ_RATIO = 0.30   # 유지
```

### 5차 노트북 구현 결정 (2026-07-30)

`ppe_yolo26_colab_v5.ipynb` 로 위 설계를 코드화했다. 판단이 필요했던 지점만 남긴다.

**① SH17 필터를 `remap` 안에 두었다** — 별도 후처리 패스를 만들지 않았다.
라벨을 읽어 통합 인덱스로 변환하는 그 자리에서 걸러야 중간 상태(충돌 라벨이 디스크에
쓰인 상태)가 존재하지 않는다. `remap(head_filter=...)` 인자 하나로 켜고, 호출부는
`s['name'] == 'sh17'` 일 때만 넘긴다 — 다른 출처는 절대 영향받지 않는다.

**② 겹치는 head 를 `helmet` 으로 바꾸지 않고 버렸다** — "안전모 쓴 머리니까 helmet 으로
쓰자"가 가능해 보이지만 하지 않았다. SH17 의 head 박스는 **머리 전체**를, 다른 출처의
helmet 은 **안전모 물체**를 가리켜 박스 정의가 다르다. 바꿔 넣으면 helmet 박스 크기 분포가
오염돼 4차가 확보한 `helmet P 0.946` 을 잃는다. 얻는 것보다 잃는 것이 크다.

**③ SH17 `helmet` 은 겹침 여부와 무관하게 전량 버렸다** — 같은 이유(박스 정의 불일치).
5차가 SH17 에서 가져오는 것은 `head` 뿐이다.

**④ 자동 라벨은 train 분할만** — val·홀드아웃에 넣으면 "COCO 자동 라벨과 얼마나 같은가"를
재는 순환이 된다. `fair_eval` 의 `person ← sh17+css` 전제도 깨진다.
`SOURCE_CLASSES['e63']` 에 `person` 을 넣지 않은 것도 같은 이유다(val e63 엔 person 정답이
없으므로 평가 대상에서 계속 빠져야 한다).

**⑤ 이미 `person` 라벨이 있는 이미지는 건너뛴다** — `HHW_MAP` 에 `person` 이 있어 HHW
일부는 이미 라벨을 갖고 있다. 그 위에 자동 라벨을 얹으면 같은 사람에 박스가 두 개 생겨
학습이 망가진다. 파일에 클래스 0 라인이 하나라도 있으면 통째로 건너뛴다(부분 중복 방지).

**⑥ `.person_pseudo_done` 마커** — 라벨 파일에 append 하는 방식이라 셀을 두 번 실행하면
박스가 두 배가 된다. 코랩은 셀 재실행이 흔하므로 마커로 막았다.
다시 돌리려면 마커를 지운다.

**⑦ 평가 참고값을 4차 실측으로 교체** — 기존 `V3` 는 head·helmet 만 전체 val 기준이라
조건이 섞여 있었다. 4차 `fair_eval` 값은 5차와 **완전히 같은 방식**으로 낸 값이므로
`R_변화` 컬럼이 그대로 의미를 갖는다.

**⑧ SH17 head 잔존률을 잘못 예측했다 (20% → 실제 94%).**

**⑨ person P 0.872 → 0.593 은 자동 라벨의 실제 대가다.**

recall 은 유지(0.841 → 0.844)하고 precision 만 떨어졌으니 person 을 남발한다.

**운영에서 person 만 conf 를 따로 높게** 잡아 완화한다.

**⑩ `fair_eval` 의 head P 하락(-0.136)은 측정 조건 변경이었다.**

### ★★★ 최중요 — ultralytics `res.path` 가 평가를 조용히 무효화했다

**오늘 같은 원인으로 세 번 막혔고, 그중 하나는 판정을 뒤집을 수 있었다.**

```
ultralytics 8.4.112 · 리스트 소스
  입력      /content/ppe3/images/val/css_-1079-_png_jpg.rf.1909….jpg
  res.path  image0.jpg        ← 입력 경로가 아니라 순번 이름
```

4차의 8.4.x 는 입력 경로를 보존했다. **버전이 올라가며 거동이 바뀌었고, 4차에서
정상 동작한 코드가 아무 오류 없이 잘못된 답을 냈다.**

| 증상 | 결과 |
|---|---|
| `person 자동 라벨 0개` (11,589장) | 라벨 경로가 `image0.txt` → 전부 skip |
| 진단 프로브도 0 | `tgt[:6]` 이 같은 시퀀스 연속 프레임 6장 — 대표성 0 |
| `미착용자 있는 장면 0장` (val 2,652장) | GT 전부 False → P·R 전부 0 |

**세 번째가 가장 위험했다.** `bare_head_eval` 은 7·8·9장이 공유하므로 그대로 돌렸으면
**5차의 판정 게이트를 "미달" 로 오판**했다. 표가 정상적으로 출력되기 때문에 눈으로 안 걸린다.

**규칙으로 굳힌다.**

1. **외부 라이브러리가 돌려주는 식별자에 의존하지 않는다.** 입력 리스트와 `zip` 으로 1:1 대응.
   `res.path`·`res.names` 처럼 편의로 제공되는 값은 버전 계약이 아니다.
2. **평가 코드는 "정답이 0건이면 멈춘다" assert 를 갖는다.** 조용히 0을 내놓는 평가는
   미달과 구별되지 않는다. `assert sum(gt) > 0` · `assert added > 0`.
3. **영상 데이터의 진단 프로브는 전체 균등 분포로 뽑는다.** `tgt[:N]` 은 같은 시퀀스의
   연속 프레임이라 대표성이 0 이다(홀드아웃을 시퀀스 단위로 나눠야 하는 것과 같은 이유).
4. **4차에서 동작한 코드라는 사실은 안전을 보장하지 않는다.** 라이브러리 버전이 바뀌면
   같은 코드가 다른 답을 낸다.

전체 수치·판정은 리포트 [14절](../../docs/ppe-ml-run-20260729.md). 여기는 **결정 근거와 교훈**만.

### 왜 이미지를 안 받았나

507 은 506.60 GB 다. 그런데 확인하려던 것은 **"안전화 미착용 박스가 발인가 사람인가"**
하나였고, 그건 **박스 좌표만으로 판정된다.** 파일 목록이 라벨(JSON)과 원천(이미지)으로
분리돼 있어 **634 MB 만 받아 끝냈다.**

**규칙 — 질문을 먼저 좁히면 받을 데이터가 1/700 이 된다.** 조끼 때 "육안으로 봤다"는
근거로 수백 GB 를 받을 뻔한 것과 같은 자리에서, 이번엔 질문이 좁아 비용이 사라졌다.

### 판정 방법 — 이름이 아니라 기하로 확인했다

`WO-07` 이 "발"이라는 것은 **어디에도 문서화돼 있지 않다.** 클래스 코드 사전이 없어서
`Raw Data Info.situation_description`(상황 코드 사전)만으로는 부위를 알 수 없었다.

대신 **부위 박스가 사람 박스 안 어디에 있는지**를 쟀다.

```
WO-04  세로 0.00 → 0.18   (UA-04 안전모 미착용)  → 머리
WO-05  세로 0.16 → 0.51   (UA-02 안전벨트 미착용) → 몸통
WO-07  세로 0.71 → 1.00   (UA-03 안전화 미착용)  → 발
```

셋이 겹치지 않고 위에서 아래로 순서대로 놓인다. **해부학이 맞으면 이름이 없어도 확정된다.**
포함률 99.8% 는 "부위가 사람 안에 있다"는 것까지 함께 증명한다.

### ★ 그래서 좋은 소식인가 — 절반만

발인 것은 맞다. 그러나 **박스 정의가 우리 것과 같다는 뜻이 아니다.**

```
507 WO-07   무릎~발 전체   사람 높이의 29% · 너비 61%(두 발 포함)
SH17 foot   발/신발 단위   (실측 필요)
```

**"발이면 우리 `foot` 으로 흡수"라는 사전 계획은 성립하지 않는다.** 이름이 같고 부위가
같아도 박스가 덮는 범위가 다르면 `helmet`↔`head` 78.2% 겹침(3절)과 같은 오염이 된다.

→ **관문이 하나 뒤로 밀렸다.** 새 관문 = SH17 `foot`·`shoes` 실측 박스 통계.

반면 `WO-04`(맨머리 23,725개)는 크기까지 맞아 **대조 없이 편입 가능**하다.

### SH17 은 어디에 있나 — 어디에도 없다

```
RAW  = /content/raw     ← SH17·CSS·HHW (Colab 임시 디스크 · 세션 종료 시 소멸)
DATA = /content/ppe3    ← 병합 데이터셋 (동일)
DRIVE= MyDrive/vitalguard-ppe   ← weights · runs · results · e63_yolo.tar 만
```

Drive 에도 맥에도 SH17 원본이 없다. 노트북의 *"나중에 하면 데이터셋 재구축 약 30분"*
경고가 이것이다. **박스 통계는 라벨 txt 만 있으면 되므로 GPU 가 필요 없다**
→ 맥에서 Kaggle CLI 로 직접 받으면 팀원 계정도 컴퓨팅 단위도 쓰지 않는다.

### ★ 도구 함정 — 성공 메시지를 출력하며 데이터를 지운다

**`aihubshell` 의 분할파일 병합이 한글 파일명에서 0바이트를 만든다.**
`printf '%q'` 이스케이프 결과로 `find -name` 을 도는데 macOS bash 3.2 는 비ASCII 를
`\355\225\234` 형태로 바꿔 **패턴이 하나도 안 맞는다** → `cat` 이 빈 입력을 받아
0바이트 zip 을 만들고, 그 다음 줄이 **원본 part 파일을 지운다.**
그리고 `병합이 완료 되었습니다` 를 출력한다.

**`res.path` 와 같은 계열이다** — 오류 없이 잘못된 결과를 내고 정상 메시지를 남긴다.
→ 직접 `curl -L` + 수동 `cat` 병합. 받은 뒤 **파일 크기를 목록의 값과 대조**한다.

zip 내부 파일명은 **CP949** 라 macOS `unzip` 이 `Illegal byte sequence` 로 죽는다.
`zipfile` 이 이미 cp437 로 디코드해 두므로 `info.orig_filename.encode('cp437').decode('cp949')`
로 역인코딩해서 읽는다.

## 2026-07-31 (이어서) — 안전화 판정 확정 · 6차 준비

수치·표는 리포트 [15절](../../docs/ppe-ml-run-20260729.md). 여기는 **판단이 갈린 지점**만.

### 판정을 두 번 미룬 것이 옳았다

`WS`(정상 작업) 발 몽타주를 먼저 봤을 때 "안전화인지 일반 운동화인지 구분 불가"로
**보류했다.** 조끼에서 축소본 육안으로 하네스를 조끼로 오독한 자리와 같았기 때문이다.

결과적으로 옳았다 — **`UA-03` 을 나란히 놓고서야** 앞의 것들이 작업화였음이 확정된다.
단독으로는 못 본다. **"판정할 수 없다"를 결론으로 내놓는 것이 답일 때가 있다.**

두 번째는 `C06 WS-13`(로프작업)이었다. 같은 현장·같은 날이라는 이유로 골랐는데
**건물 외벽에 매달린 작업이라 발이 안 보였다.** 앞서 로프작업을 제외했던 이유를
날짜 일치에 끌려 되밟았다. → **작업 유형이 부위 가시성을 결정한다.** 3.65GB 를 헛으로 썼다.

### ★ 결정적 대조는 "통제된 음성"이었다

`UA-04`(안전모 미착용 · **안전화는 착용**)가 답이었다.
같은 데이터셋·같은 제작·겹치는 현장과 날짜에서 촬영돼 **조명·현장·조건이 통제된 채
신발만 다르다.** 정상 작업(`WS`)을 찾아 헤맸는데, 정작 쓸모 있는 음성은
**다른 종류의 위반 시퀀스**에 있었다.

**규칙 — 음성 표본을 "정상" 에서만 찾지 말 것.** 통제 변수가 맞는 쪽이 낫다.

### ★★ 121 GB 를 받지 않은 근거

`Training` 과 `Validation` 의 **시퀀스 집합이 완전히 동일**했다(UA-03 23/23 · UA-04 40/40).
507 은 프레임 단위로 갈랐다. 즉 원천 121.46GB 는 **같은 영상의 다른 프레임**일 뿐이다.

**"데이터가 더 있다" 와 "다양성이 더 있다" 는 다르다.** 분할 방식을 먼저 확인하면
받을 양이 8분의 1이 된다. 이 확인은 라벨 21MB 로 끝났다.

같은 사실이 **507 자체 분할이 누수**라는 뜻이기도 하다(3차 함정 ③ 재현).
자체 train/val 을 그대로 쓰면 채점이 성립하지 않는다.

### 병합하지 않기로 한 이유 — 이름·부위가 같아도 범위가 다르면 다른 클래스다

```
SH17 foot   사람 대비 면적  1.79%   (전체 759개 = SH17 인스턴스의 0.9%)
507  WO-07  사람 대비 면적 17.70%   (32,137개 · 무릎~발)
```

`foot` R 0.079 는 모델 문제가 아니라 **759개짜리 클래스**였던 것이다.
그래서 SH17 `foot` 을 버리는 대가는 사실상 0인데도 **병합 대신 분리**를 택했다 —
분리하면 `foot`·`shoes` 쌍이 그대로 살고, 병합하면 3절의 오염이 재발한다.

### 홀드아웃을 시퀀스가 아니라 현장으로 뗀 이유

`UA-03` 의 실효 현장은 **3곳**(A03 82% · C06 13% · A04 5%)이다.
`A10` 은 `UA-03` 시퀀스가 있는데도 `WO-07` 이 하나도 없다(`SO-10` 만).

시퀀스로 떼면 같은 현장이 학습과 홀드아웃 양쪽에 남는다 —
**5차에서 배운 "홀드아웃 도메인이 결함을 가린다"를 그대로 반복하는 것**이다.
현장 하나를 통째로 예약하면 학습 현장이 줄어드는 대가를 치르지만 진짜 교차 검증이 된다.

**다만 이걸로도 부족하다.** 학습이 사실상 `A03` 단독이고 박스가 무릎~발이라
바지·양말·자세가 함께 들어간다. `UA-03` 작업자는 검정 트레이닝복 + 파란 줄무늬 양말이
반복된다 → **신발이 아니라 복장을 외울 수 있다.**
507 을 전량 받아도 해결되지 않으므로 **직접 촬영 시험지가 유일한 확인 수단**이다.

### 6차를 돌리기 전에 재봤다 — 두 가지가 조용히 망가질 참이었다

노트북을 다 만들고 나서 **"이대로 돌리면 무엇이 결과를 못 믿게 만드는가"** 를 먼저 쟀다.
둘 다 실행하기 전에는 보이지 않고, 실행하고 나면 원인 규명에 하루가 든다.

**① 507 이미지에 무엇이 라벨 없이 있는가** — v5 모델로 표본 232장을 봤다.

```
person 97.0% · head 72.4% · shoes 26.3% · helmet 13.4% · hands 9.9%
```

라벨은 `no_safety_shoes`·`head` 둘뿐이므로 나머지는 **배경으로 학습된다.**
`shoes` 가 특히 나쁘다 — `no_safety_shoes` 박스가 신발을 **물리적으로 포함**하는데
507 에서는 그 안쪽이 배경이고 SH17 에서는 같은 그림이 `shoes` 다.
**같은 화소에 정반대 지도가 들어간다.**

`person 97.0%` 는 자동 라벨이 **필수**임을 실증한다 — 없었으면 4차 E63 사고 재현이다.

**② 홀드아웃에 음성이 없다** — `C06` 273장 중 음성 16장(5.9%).
아무 데나 발사하는 모델도 `P ≈ 0.94` 가 나온다.
4·5차 안전모 게이트가 신뢰받은 이유는 **음성 600장에서 오탐 1건**이었기 때문이다.

**규칙 — 게이트를 설계할 때 양성만 세지 말고 음성 표본 수를 먼저 확인한다.**
음성이 없으면 precision 은 측정이 아니라 장식이다.

**규칙 — 새 출처를 넣기 전에 "그 이미지에 라벨 없이 무엇이 있는가" 를 모델로 재본다.**
라벨 목록만 보면 "없는 것"은 보이지 않는다. 부분 라벨의 대가는 학습 손실에서 발생하는데
`fair_eval` 은 **평가만** 보호할 뿐 학습은 보호하지 않는다.

## 2026-07-31 밤 — 6차 실행 후 교훈

수치·표는 리포트 [17절](../../docs/ppe-ml-run-20260729.md). 여기는 **판단이 틀린 지점**만.

### ★ 홀드아웃 현장을 잘못 골랐다 — 내가 앞서 배운 것을 스스로 어겼다

`C06` 을 예약 현장으로 정했다. 그런데 **불과 몇 시간 전에 같은 `C06` 을 발 검증 대상에서
제외했었다** — "로프 매달림 작업이라 사람 박스 하단이 지면이 아니라 유리면이다" 라는 이유로.

그래놓고 홀드아웃 현장으로는 그 `C06` 을 골랐다. **작업 유형이 부위 가시성을 결정한다**는
바로 그 교훈을 적어두고도 다음 결정에서 쓰지 못했다.

**규칙 — 홀드아웃을 고를 때 "학습과 무엇이 다른가"를 열거해 볼 것.**
다른 것이 하나(현장)여야 하는데 둘(현장 + 작업 유형)이면 원인 분리가 불가능해진다.

### ★★ 더 큰 문제 — 507 로는 애초에 검증이 불가능했다

`A04` 로 홀드아웃을 바꿔 재측정하려다 드러났다.

```
지상 작업   A03(82%) · A04(5%)   ← 시퀀스 해시 분할이 둘 다 train 으로 보냈다
로프 작업   C06(13%)             ← 유일한 홀드아웃인데 작업 유형이 다르다
```

**"같은 작업 유형의 다른 현장"이 507 에 존재하지 않는다.** 홀드아웃 현장을 바꿔도
A04 는 108개(5%)뿐이라 통계가 안 나온다.

**이건 설계로 고칠 수 없다.** 데이터셋의 구성 자체가 교차 검증을 허용하지 않는다.

**규칙 — 새 출처를 편입하기 전에 "무엇으로 일반화를 잴 것인가"를 먼저 정할 것.**
학습 데이터의 양이 아니라 **홀드아웃으로 뗄 수 있는 독립 표본이 있는지**가 관문이다.
507 은 32,137개라는 규모에 가려 이 점검을 건너뛰었다.

### ★ `fair_eval` 은 회귀를 희석한다

`helmet` recall 회귀가 `fair_eval` 에서는 **−0.030**, 배포 도메인 홀드아웃에서는 **−0.110** 이었다.
`fair_eval` 은 여러 출처의 평균이라 **한 도메인의 손상을 다른 도메인이 가린다.**

`R_변화 ≥ -0.05` 하나로 "회귀 없음 → 대응 C 불필요"를 판정했는데, 홀드아웃을 보고서야
뒤집혔다. **회귀 감시는 배포 도메인 홀드아웃에서도 해야 한다.**

### 원인 규명은 가설을 갈라서 측정했다

`C06` 미검출을 보고 처음 세운 가설은 **스케일**이었다(박스가 1.95배·면적 4.7배 크다).
4차 스케일 한계와 모양이 같았기 때문이다. 그런데 —

```
축소 패딩 1.5x·2.0x·2.5x  →  검출 0%   (학습 분포에 맞춰도 안 됨)
conf 0.01 무제한          →  16.7% · 신뢰도 중앙값 0.042
```

**기각.** 임계도 스케일도 아니고 **장면 자체가 학습에 없던 것**이었다(4차 GoPro 사고와 동형).
크롭을 나란히 놓으니 배경(콘크리트 vs 파란 유리)·자세(직립 vs 매달림)·신발이 전부 달랐다.

**규칙 — "모양이 같은 실패"를 같은 원인으로 단정하지 말 것.** 4차와 증상이 같았지만
원인은 달랐다. 가설마다 그것을 무효화하는 실험을 설계해야 한다.

### 잘된 것도 적어 둔다 — 하드 네거티브가 우려를 반증했다

"박스가 무릎~발이라 신발이 아니라 복장을 외울 것"이라는 우려는 **반증됐다.**
인도메인 음성 612장 중 **442장이 같은 현장(A03)의 `UA-04`**(안전모 미착용·안전화 착용)였다.
같은 조명·같은 작업복·신발만 다른 표본에서 **오탐 ≤9(≤2.0%)**.

**음성의 구성을 조사한 덕에 `FP 9` 라는 숫자가 의미를 얻었다.**
그냥 "오탐 9건"이었으면 아무 말도 못 했을 것이다.
