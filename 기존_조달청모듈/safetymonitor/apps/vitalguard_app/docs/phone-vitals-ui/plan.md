# 폰 앱 생체 표시 — 계획 (2026-08-15 수립 · 착수 전)

목적 = **워치가 수집하는 생체 데이터를 폰 앱 화면에서도 보게 한다.**
현재 폰 화면은 심박 하나만 보여주고(`90 bpm · 측정 5초 전 · 배치 #1526`), 워치 화면은
활동·이산 측정·전송 상태까지 보여준다. 그 격차를 없앤다.

> **핵심 결론 — 서버에서 받아올 필요가 없다.** 데이터는 이미 폰을 통과한다.

---

## 1. 왜 서버 왕복이 불필요한가

전제 확인이 필요했다. *"PoC 기반으로 워치 생체 데이터가 바로 서버로 가는 것으로 안다"* 는
질문이 있었는데 **실제 구조는 다르다.**

```
워치(HealthKit) ──WCSession──▶ 폰 네이티브 VitalPipeline ──HTTPS──▶ 서버
                                    ↑ 폰이 업로더다
```
워치는 서버로 직접 가지 않는다. 근거 = 08-15 실측에서 서버가 503 을 주자 **폰이** 큐를
1→41 건으로 쌓았고, 화면도 워치 `전송1525` ↔ 폰 `배치 #1526` 으로 동기다.

**`PhoneReceiver.swift:31` 이 워치 payload 의 `samples` 배열을 통째로 받는다.** 그 안에
`bpm`·`spo2`·`ae`·`hrv`·`rhr`·`whr`·`rr`·`stp`·`flt`·`pe`·`dl` 가 전부 들어 있고
이미 `spo2Count`·`aeSum` 을 세어 로그에 찍는다. **데이터는 폰 안에 있고 브리지가 심박만 통과시킨다.**

```
현재 EventChannel "vitalguard/stream"
  type:"hr"        → bpm · seq · channel          ← 여기만 열려 있다
  type:"pipeline"  → pending · uploadOk · authRejected
```

## 2. ★ 절대 어기면 안 되는 제약

**생체 데이터가 Dart 를 "경유" 하게 만들지 않는다.**

폰이 백그라운드면 iOS 는 `WCSessionDelegate` 는 깨우지만 **Flutter 엔진은 깨우지 않는다.**
수집·큐·업로드가 Dart 를 거치는 순간 **폰 강제종료·잠금 생존이 죽는다** — 이 앱의 존재 이유다
(Phase 1a 게이트에서 4분+ 무중단으로 실증한 바로 그 성질).

```
유지   네이티브가 큐·업로드를 전담 → Flutter 에는 표시용 복사본만 밀어준다 (현 구조)
금지   Flutter 가 받아서 저장·업로드에 관여
```
⟹ 이번 작업은 **`VitalBridge.emit` 의 payload 를 넓히는 것**이지 경로를 바꾸는 것이 아니다.

## 3. 표시 대상 — 넣을 것과 뺄 것

| 항목 | 넣나 | 근거 |
|---|---|---|
| 심박 + 측정 경과 | ✅ 이미 있음 | — |
| SpO₂ + 측정 시각 | ✅ | `spo2Ts` 로 측정 시각이 분리 보존됨 |
| 이산 6종(HRV·안정심박·보행심박·호흡수·MET·일광) | ✅ | 워치 화면과 동일하게 **종류별**로(0 건은 생략) |
| 걸음 · 오른층 | ✅ | 구간 증분 |
| 전송 상태(배치·큐·인증) | ✅ 이미 있음 | — |
| **활동에너지** | ❌ **뺀다** | 2026-08-15 확정 — **4배 과대**(정지 상태 288 kcal/시간). 그대로 띄우면 이상한 값을 사용자에게 보여주게 된다. [heat-activity-axis](../../../dashboard-web/docs/heat-activity-axis/checklist.md) 정리 후 재검토 |

⚠ **워치와 폰의 숫자 의미가 다른 것에 주의.** 워치 `활동 539.3 kcal` 는 **세션 누적**이고
서버로 가는 `ae` 는 **5초 증분**이다. 같은 라벨로 띄우면 헷갈린다 — 표시할 때 무엇을
보여주는지 라벨에 명시한다.

**무변경** = 워치 · 서버 · 스키마 · DB · 관제웹.

## 5. 검증 계획 (성공 기준)

- [ ] **폰 화면 값 = 워치 화면 값** — 같은 순간 두 화면을 나란히 두고 대조.
      ⚠ 이산 측정은 **종류별 건수**가 맞아야 한다(총합만 맞는 것은 08-14 에 고친 결함이다)
- [ ] **폰 화면 값 = DB 값** — 같은 배치가 서버에 도착한 값과 일치.
      세 지점(워치·폰·DB)이 맞아야 "통과시킨 것" 이 증명된다
- [ ] **★ 백그라운드 생존 회귀 0** — 폰 앱을 스와이프 종료한 뒤에도 서버 도착이 안 끊기는지.
      **이 작업의 유일한 실질 위험**이고, Phase 1a 게이트와 같은 방식으로 잰다
      (Release 빌드 필수 — debug 는 재기동이 즉사해 판정이 안 된다)
- [ ] 값이 없을 때 `--` 로 표시되는지(0 으로 표시하면 "측정했는데 0" 이 된다)

## 6. 착수 전 결정 사항

- [ ] **UI/UX 형태** — 카드 나열인가, 워치 화면처럼 한 줄 요약인가. 화면 설계가 필요하다
- [ ] **갱신 주기** — 5초마다 전부 다시 그릴지, 값이 바뀐 것만 갱신할지(배터리·시선 안정성)
- [ ] **이산 측정 표기** — 워치는 `강도26` 처럼 줄여 쓴다. 폰은 화면이 넓으니 풀어 쓸지
- [ ] **활동에너지 재검토 시점** — §3 의 ❌ 를 언제 풀지

## 7. 이 계획이 하지 않는 것

- 서버에서 데이터를 **받아오는** 경로 신설 — 불필요하다(§1). 만들면 같은 데이터의 출처가
  둘이 되고, 폰이 오프라인일 때 화면과 큐가 어긋난다.
- 워치 수집 항목 추가 — 별건이다(`motionStillSec` = [vital-absence-triage](../../../../docs/vital-absence-triage/checklist.md)).
- 관제웹 변경 — 무관하다.
