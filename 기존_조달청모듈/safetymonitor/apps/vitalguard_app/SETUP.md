## 2. 워치 타깃 추가 — ✅ 스크립트로 완료 (08-11)

원문의 Xcode GUI 절차(File → New → Target → watchOS App) 대신 **xcodeproj gem 스크립트로 자동 추가**했다. 재현이 필요하면 GUI 절차도 유효하다.

### Bundle ID 규칙 (틀리면 페어링 안 됨)

```
com.vitalguard.vitalguardApp                 ← Runner
com.vitalguard.vitalguardApp.watchkitapp     ← VitalWatch
```

### [반영 5] Info.plist 는 실파일 방식

최신 Xcode 의 워치 템플릿은 Info.plist 파일 없이 Build Settings 의 "Info.plist Values"(`GENERATE_INFOPLIST_FILE=YES`)로 키를 관리한다 — GUI 로 만들었다면 파일을 찾지 말고 빌드 설정에서 값을 확인해야 한다. 이 프로젝트는 결정론적 관리를 위해 **실파일 `ios/VitalWatch/Info.plist` + `GENERATE_INFOPLIST_FILE=NO`** 방식을 채택했다. 핵심 키는 아래와 같다.

```xml
<key>WKApplication</key><true/>
<key>WKCompanionAppBundleIdentifier</key>
<string>com.vitalguard.vitalguardApp</string>
```

## 3. Podfile — 가장 많이 깨지는 지점

**[반영 1] 원문 스니펫을 Podfile 전체로 교체하면 안 된다.** 원문에는 Flutter 표준 전문(`flutter_root` 해석 → `podhelper.rb` require → `flutter_ios_podfile_setup`)이 빠져 있어, 그대로 교체하면 `flutter_install_all_ios_pods` 미정의로 `pod install` 이 실패한다. 규칙은 하나다.

- **flutter 가 생성한 Podfile 을 그대로 두고, 워치 타깃(`target 'VitalWatch'`)을 절대 추가하지 않는다.** Flutter Pod 이 워치로 상속되면 빌드가 실패한다.
- `platform :ios, '15.0'` 주석만 해제·조정한다.

현재(플러그인 0개) 상태에서는 pod 의존성이 없어 `pod install` 자체가 불필요하다. 첫 플러그인 추가 시점에 위 규칙을 적용한다.

### Embed 검증

- Runner 타깃 → Build Phases → **Embed Watch Content** 에 `VitalWatch.app` 이 있는지 확인.
- VitalWatch 타깃 → General → Frameworks 에 **`Flutter.framework` 가 없어야** 한다. 있으면 제거한다. 심사 반려 사유다.

## 4. Capability & 권한

### VitalWatch 타깃 — ✅ 완료

- HealthKit capability = `ios/VitalWatch/VitalWatch.entitlements` (`com.apple.developer.healthkit`).
- `Info.plist` 에 `WKBackgroundModes`(`workout-processing`)·`NSHealthShareUsageDescription`·`NSHealthUpdateUsageDescription` 포함.

### Runner 타깃 — ✅ 완료

- `UIBackgroundModes` = `fetch`, `processing`.
- `BGTaskSchedulerPermittedIdentifiers` = `com.vitalguard.upload`.
- `NSHealthShareUsageDescription` 포함.

### ATS

dev 서버는 cloudflared(https)를 쓰므로 `NSAllowsArbitraryLoads` 는 넣지 않았다. HTTP 엔드포인트가 꼭 필요해지면 임시로 넣되 **운영 전환 시 반드시 제거**한다. 조달 보안 요건에 걸린다.

```

    PhoneReceiver.swift      ← Phase 0
```

## 6. 단계별 검증 게이트

각 Phase 는 아래를 통과해야 다음으로 넘어간다.

- **Phase 0** — 워치에서 보낸 HR 이 Xcode 콘솔(iOS)에 5초 간격으로 찍힘. 워치 앱을 백그라운드로 내려도 지속
- **Phase 1** — 아이폰 앱을 스와이프 종료 → 워치에서 계속 전송 → 서버 로그에 데이터 도착
- **Phase 2** — Flutter 화면에 최신 HR 과 큐 적체 수가 실시간 갱신

Phase 0/1 은 Flutter 를 건드리지 않는다. 브리지를 먼저 얹으면 장애 지점 구분이 불가능해진다.

## 7. 실기기 검증

**[반영 3]** Xcode 14 부터는 페어링된 시뮬레이터 간에도 WatchConnectivity 가 동작한다(현 툴체인 Xcode 26.6). 다만 실 심박 센서·백그라운드/강제종료 시맨틱은 시뮬레이터를 신뢰할 수 없으므로 **게이트 판정은 iPhone + Apple Watch 실기기 페어링에서만 유효**로 친다. Orca 워크트리 중 `wt-main` 하나만 실기기에 물린다.

**[반영 4] 디바이스 등록 한도** — Apple Developer 팀 `F2P5ZFP65Q` 는 100대 한도에 도달한 상태다(worker-watch-poc README 참조). 이번에 쓸 iPhone·Watch 가 이미 등록돼 있으면 통과, 새 기기면 개발자 콘솔에서 슬롯 정리가 선행돼야 한다. 서명 팀은 두 타깃 모두 빌드 설정에 넣어 두었다(`DEVELOPMENT_TEAM=F2P5ZFP65Q`, Automatic).

**★★ 같은 날 저녁, 진짜 미착용 구간이 잡혔다(18:55~19:03 KST · 옆 세션 시험).**
```
09:57Z  심박 12건 · 고유 2      ← 착용 마지막
09:58Z  심박  1건
09:59Z  심박  5건 · 고유 1      ← 30초 창이 끊기는 중
10:00Z  심박  0건  ★
10:01Z  심박  0건  ★  3분 연속 완전 NULL (행은 13·12·11 건씩 계속 도착)
10:02Z  심박  0건  ★
10:03Z  심박 10건 · 고유 3      ← 재착용
```
**수리 전이었다면 이 3분이 위조된 같은 값 36건으로 채워졌다.** 08-14 의 8,531건과 같은 형태다.
관제 화면은 `heartRateStatus(null) = idle` → `overallStatus = idle` 로 **대기**를 센다
(08-12 에 고친 false-OK 가 재발하지 않는다 — 확인함).

⚠ **다만 활동에너지는 미착용 중에도 분당 4.5~5.2 kcal 씩 쌓였다.** 워크아웃 세션이 도는 한
계속 누적되는 값이라 **심박과 같은 계열의 질문이 남는다** — 몸에 없는데 흐르는 값인가.
단정하지 않는다: 그 시험 중 워치를 손으로 다루고 있었을 수 있고(움직임이 있으면 정상 누적),
심박이 null 이라 온열 패턴 판정 자체가 안 돈다. **정지 상태로 두고 재관측할 값어치는 있다.**

⚠ **코드 주석의 "90초 뒤 연결끊김" 은 아무것도 안 보낼 때만 성립한다.** 활동에너지가 계속
들어오면 행은 생기고 `ts` 가 갱신돼 신선도 게이트를 통과한다 — 화면은 `연결됨 · 심박 —` 이 되고,
링크는 살아 있고 측정만 없는 상황이므로 **그게 정직한 표시다**(결함이 아니라 주석이 좁게 적힌 것).

### ② POST 5xx 폰측 실기기 — 큐가 자란다

서버가 저장 실패에 503 을 주면 폰이 원본을 지키는가. 상세 =
[docs/sample-loss-recovery/checklist.md](../../docs/sample-loss-recovery/checklist.md) A-3.

**★ 로컬 dev(죽은 DB)로 받지 않았다.** `.env.local` 의 `APP_JWT_SECRET` 이 프로덕션 v3 와
**다르다**(값은 안 찍고 해시로 대조). 폰 토큰에 **401** 을 내는데 401 은 300초 분기라
재려던 `default`(30초) 분기 시험이 **성립하지 않는다** — 로그는 그럴듯했을 형태다.
대신 폰↔프로덕션 사이에 로컬 프록시를 끼워 `POST /api/app/vital` 만 503 으로 바꿨다
(로그인은 통과). 이러면 **데이터 유실이 0** 이다(fail 구간분이 복귀와 함께 원래 `ts` 로 도착).

```
1건→503 · 2건→503 · … · 40건→503  →  복귀 즉시 41건→201  →  다시 1건
DB = 08:55·08:56·08:57 각 12건 온전 · 41행 = 고유 ts 41 · 중복 0
```
201 을 받고 있었다면 매번 `1건` 이다. **건수가 자라는 것 자체가 큐 유지의 증거다.**

**★ 정정** — "503 이면 30초 뒤 재시도"는 **새 데이터가 없을 때의 폴백**이다. 실제는 **5초 간격** —
`ingest()` 가 매 배치마다 `uploadLocked()` 를 부른다. 설계보다 유리하다.

### ③ ⚠ `잔량` 의 바닥이 0 이 아니다 — 08-18 오독 1순위

직접 Run 이후 워치 화면 `잔량7` 이 굳었다. **유령이라는 근거는 화면 자체에 있다** —
그 시점이 `전송2 · 큐 표시 없음 · 잔량7` 이었고, `큐`(`sentQueued + immediateFailed`)가 0 인데
잔량이 7 이면 **이번 세션이 만들 수 없는 수**다. 재설치 이전 인스턴스가 남긴 **고아 전송**이고
WatchConnectivity 데몬 큐가 앱 재설치를 넘어 들고 있다. 10분·**전송 122회** 동안 `도달` 인데도
하나도 안 빠졌다.

**데이터에는 무해하다** — 같은 구간 DB 가 12건/분·측정→전송 1~2초·옛 측정분 끼어듦 0.
조치하지 않기로 했다(데몬 큐라 앱 강제종료로 안 빠질 수 있고, 확실한 워치 재부팅은 수집이
수 분 끊긴다). **08-18 에는 절대값이 아니라 `잔량 − 7` 의 증가분을 읽는다.**

⚠ **이 관측이 시험 전제 하나를 흔든다** — `transferUserInfo` 가 **영구히 갇힐 수 있다**.
복귀 후 잔량이 안 내려가도 그것이 곧 거리 가설 기각은 아니므로 **DB 도착으로 교차 확인**한다.

### ④ VitalWatch 스킴을 공유로 (`10f194c`)

위 "아이폰 Run 의 워치 임베드 전달이 조용히 실패" 함정의 해법이 **문서에만 있었다** —

sudo 없이 `DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild …` 로 우회한다.

## ★ 재설치의 실측 비용 — 폰과 워치는 다르다 (2026-08-18)

같은 날 폰만 갈고, 두 시간 뒤 워치를 갈아 **대조군이 생겼다.**

| | 폰(Runner) 재설치 | 워치(VitalWatch) 재설치 |
|---|---|---|
| 수집 공백 | **0초** | **128초** |
| 유실 | **0건** | 그 구간 측정분(따라잡기 없음) |
| 사람 손 | 불필요 | **워치에서 [시작] 필수** |
| 흔적 | 그 분 최장지연 5.0 → 9.9초 | 재개 첫 행이 심박만·무동작 없음 |

```
17:14  12건 최장지연 5.1초
17:15  12건 최장지연 5.0초
17:16  12건 최장지연 9.9초   ← Runner 설치 17:16:49 · 앱 기동 17:16:59
17:17  12건 최장지연 5.1초
17:22  11건                  ← 워치 설치 17:23:01
17:23   0건
17:24   0건                  ← 사용자 [시작]
17:25  12건 · battery_pct 첫 도착
```

**왜 다른가** — 수집을 끊는 것은 폰이 아니라 **워치 `HKWorkoutSession`** 이다. 폰 프로세스는
실제로 죽었지만(재설치) 워치 세션이 살아 있어 측정이 이어졌고, 폰이 없던 10초는 WCSession
큐가 덮었다. 반대로 워치를 갈면 세션이 끝나고 **`HKWorkoutSession` 은 사용자 조작 없이 시작할
수 없어** 사람이 [시작] 을 눌러야 한다.

> **⚠ 종전 인식 정정.** "재설치당 10~13건 유실"(08-15)은 **워치를 건드린 재설치 한정**이었다.
> 폰 UI·Dart 변경을 워치 작업과 묶어 온 근거였는데, 그 근거가 이번 실측으로 사라졌다.
> **앞으로 폰만 바뀐 변경은 워치를 기다리지 않는다.**

### 임베드 전달 실패가 이번엔 이득이었다

`Embed Watch Content` 때문에 Runner 를 Run 하면 워치 앱도 함께 빌드되지만, **아이폰 Run 의
워치 임베드 전달은 조용히 실패한다**(08-13 함정 · 위 절). 이번에도 재현됐고, 그 증거가
데이터로 남았다 — **폰 설치 후에도 `battery_pct` 0건**이라 손목의 워치가 구 바이너리임이
확정된다. 워치를 안 건드리고 싶을 때는 이 성질에 기대도 된다.

### 공유 워킹트리에서 설치할 때

옆 세션이 워치 파일을 편집 중이면 **미검증 코드가 내 빌드에 실린다**(임베드 때문). 대기하지
않고 푸는 방법 —

```bash

rsync -a --exclude build --exclude .dart_tool "$SRC/" "$S/"
git show HEAD:"<상대 미커밋 파일>" > "$S/<상대 경로>"
# 추적 파일 전수 해시 대조로 사본이 HEAD 와 같은지 확인한 뒤 빌드
```

설치는 Xcode 없이도 된다.

```bash

xcrun devicectl list devices                      # flutter devices 가 못 봐도 여기선 보인다
flutter build ios --release                       # 자동 서명(팀 F2P5ZFP65Q)
xcrun devicectl device install app --device <UDID> build/ios/iphoneos/Runner.app
xcrun devicectl device process launch --device <UDID> --terminate-existing com.vitalguard.vitalguardApp

# ★ 워치도 CLI 로 직접 설치된다 (2026-08-19 실증 · 13초)
xcrun devicectl device install app --device <워치UUID> \
  build/ios/iphoneos/Runner.app/Watch/VitalWatch.app
xcrun devicectl device process launch --device <워치UUID> --terminate-existing \
  com.vitalguard.vitalguardApp.watchkitapp
```

★ **워치 설치에 Xcode GUI 가 필요 없다(2026-08-19).** 위 240행은 "아이폰 Run 의 워치 임베드
전달이 조용히 실패하니 스킴을 `VitalWatch` 로 바꿔 직접 Run" 이라고만 적고 있었는데, `devicectl`
이 watchOS 를 그대로 받는다. 워치가 `devicectl list devices` 에서 `connected` 여야 하고, 그러려면
**짝 폰이 USB 로 붙어 있어야 한다**(폰을 꽂으면 워치가 `unavailable` → `available (paired)` →
`connected` 로 올라온다).

⚠ **순서 = 폰 먼저, 워치 나중.** 폰이 워치의 신규 필드를 읽어 서버로 넘기는 쪽이라 워치를 먼저
갈면 새 필드가 구 폰 코드에서 조용히 버려진다.

⚠ **`xcode-select -p` 가 CommandLineTools 를 가리키면 `xcodebuild`·`xcrun devicectl` 이 막힌다.**
`sudo xcode-select -s` 가 정공이지만 sudo 가 안 되는 상황에서는 `DEVELOPER_DIR` env 로 우회된다
(위 블록 첫 줄). 우회는 그 명령에만 걸리므로 셸마다 다시 준다.

⚠ 설치 후 **앱 1회 전면 실행**은 여전히 수칙이다(미기동 시 WCSession 전달 스로틀).
⚠ `devicectl` 설치는 **서명 만료일을 늘리지 않는다.** 프로파일 갱신은 Xcode Run 이 한다.

### ⚠ 설치본 검증에 `strings` 를 쓸 때

신규 코드가 실렸는지 확인할 때 **통제군 없이는 판정할 수 없다.**

- Dart AOT 는 **비 ASCII 리터럴을 `strings` 로 못 뽑는다**(한글 0건 → 통제군 `비밀번호` 도 0건).
  ASCII 심볼(클래스명 등)로 우회한다.
- Swift fat 바이너리는 한글 리터럴이 안 잡히는 데다, **15바이트 이하 문자열은 small-string
  최적화로 코드에 인라인**돼 바이트 검색으로도 존재하지 않는다.

→ **통제군은 "원래 있던 것" 중 충분히 긴 문자열로 고른다.** 통제군도 0이면 도구 문제다(L-67).
