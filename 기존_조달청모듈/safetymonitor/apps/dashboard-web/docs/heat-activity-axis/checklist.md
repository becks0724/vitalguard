# 온열 활동 축 — 활동에너지 사용 불가 확정 + 하이브리드 결정 (2026-08-15)

온열 예방 3축(환경·생리·**활동**) 중 활동 축이 실제로 작동하는지 실측한 결과다.
환경 = [wbgt/](../wbgt/checklist.md) · 생리 = [psi/](../psi/checklist.md) · 수집 = [heat-env-inputs/](../heat-env-inputs/checklist.md).

> **결론 먼저 — 온열 ②(저활동·고심박)는 2026-08-13 배포 당일부터 발동한 적이 없고, 발동할 수도
> 없었다.** 원인은 버그가 아니라 **상시 워크아웃 세션의 구조적 대가**다. 그리고 대체 신호로
> 걸음을 단독 사용하는 것은 **사용자 결정으로 기각**됐다 — 앉아서 작업하는 사람은 걸음이 0이다.

---

## 1. 확정 사실 — 활동에너지는 저활동 판정에 쓸 수 없다

### 1-1. 판정이 구조적으로 거짓이다

```
lib/heat-pattern.ts:88
  flagged = hrAvg >= 100 && aeKcalPerMin <= HEAT_PATTERN_LOW_KCAL_PER_MIN(1.5)
```
실측(08-13 이후 · 심박 커버 ≥10 · 12건 온전한 분만 = **2,067분**)
```
분당 최소 2.40 kcal   ← 임계 1.5 보다 크다
평균     4.81
최대    52.79
임계 1.5 이하 분  0건
```
**분당 최솟값이 임계를 넘으므로 어떤 15분 창 평균도 임계 이하가 될 수 없다.** 논증 종결.
⟹ `flagged` 는 영영 false · **온열 ② 주석 + 온열 ③ "경고" 단계(38.0℃ + 이 패턴) 동반 불가**
(주의 37.8℃ 단계만 생존).

⚠ 문서에 *"주석 육안은 자연 발생 대기 — 평시엔 안 뜨는 게 정상"* 으로 적혀 있었는데
**기다려도 오지 않는다.** 재난문자 '대피' 재승격이 한 달간 죽어 있던 것과 같은 형태다.

### 1-2. 값이 상황에 반응하지 않는다

```
① 착용·활동 (심박 101)   0.401 kcal/5초 = 분당 4.82   걸음 893
② 몸에 접촉  (심박  72)   0.404          = 분당 4.84   걸음 0
③ 책상 위    (심박 없음)  0.403          = 분당 4.84   걸음 0
```
⚠ **정확한 서술은 "상수" 가 아니다.** 개별 값은 0.04~4.31 로 흔들리고(표준편차 0.11~0.15)
재착용 순간엔 0.21~0.97 까지 벌어진다. 정확히는 **평균이 상황에 반응하지 않는다**.

### 1-3. 원인 — 우리 코드가 아니다. 상시 워크아웃의 대가다

워치 델타 로직은 계약대로다(`sessionEnergyKcal − energyReportedKcal` · 음수면 기준 재설정 ·
잔여 이월). **건강 앱이 같은 값을 보여준다.**
```
건강 앱  활동 에너지 시간당 240~290 cal · 운동하기 총 472분 · 오늘 총 2,201 cal
검산     2,201 ÷ 472분 = 분당 4.66 kcal
우리 DB  분당 4.77~4.79            ← 일치
```
```
상시 HKWorkoutSession (폰 강제종료·잠금 생존의 핵심 장치)
  → 애플이 하루 7.9시간을 "운동 중" 으로 간주
    → 앉아 있어도 활동 에너지를 시간당 288 cal 로 산출
      → 우리는 그 값을 정확히 5초 증분으로 옮긴다
```
**⟹ 고칠 수 있는 버그가 아니다.** 상시 워크아웃을 포기하면 이 앱의 존재 이유가 사라진다.

⚠ **임계를 4.8 위로 올리는 것은 해법이 아니다.** 1.5 의 근거는 일반 대사 참고값
(휴식~서있기 0~1.5 · 가벼운 작업 3~5)이고 그것은 옳다. 축이 안 맞는 쪽은 워치 값이다.
임계를 맞추면 **근거 없는 숫자**가 된다.

### 1-4. 언제부터인가 — 태생적이다

```
08-13  5,535행  평균 분당 4.74     ← 온열 ① 수집 첫날
08-14  6,734행           4.79
08-15  5,382행           4.77
```
어느 시점에 망가진 것이 아니라 **처음부터 그 상태**였다.

## 2. ★ 결정 — 심박이 주(主), 걸음은 배제용 보조 (사용자 2026-08-15)

> **"온열과 걸음을 복합적으로 하이브리드 기반 — 앉아서 작업하는 사람은 걸음이 측정되지 않음."**
> **"걸음이 없다고 해서 판정 불가는 아니다 — 심박이라는 실제 생체 데이터를 수신 중이므로."**

### ★★ 구조를 뒤집었다 — 초안이 틀렸다

초안(그리고 이 트랙의 첫 제안)은 *"활동 신호가 없으면 판정 불가(null)"* 였다. **사용자 정정으로
기각한다.** 온열 ② 의 위험 신호는 **"쉬는데 심박이 안 내려옴"** 이고 그 핵심 재료는 심박이다.
심박이 살아 있으면 판정에 필요한 것은 이미 있다. **걸음은 판정의 전제가 아니라 배제 조건**이다 —
*"지금 걷고 있으니 심박이 높은 게 당연하다"* 를 걸러내는 용도.

```
심박 고 + 걸음 있음   →  걷는 중이라 높다        (정상 · 배제)
심박 고 + 걸음 없음   →  ★ 온열 의심             (앉아서 작업이든 쉬는 중이든
                                                  심박이 안 내려온 것은 사실이다)
심박 없음            →  온열 판정 대상이 아니다.  별도 판정으로 → §2-2
```

**이 구조에서는 앉아서 작업하는 사람이 배제되지 않고 오히려 잡힌다.** 잡아야 할 대상이 맞다.
초안 구조였다면 그 사람들이 통째로 판정에서 빠졌을 것이다.

### 2-2. ★★ 심박 미수신은 미착용 **또는 심정지**다 — 별도 트랙으로 분리

사용자 지적 = *"심박을 실제로 수신 못 하면 착용 불가 혹은 **심정지**를 의심할 수 있다."*

현재 구조는 둘을 **구분하지 못하고** 관제 화면은 둘 다 **"대기"** 로 센다.
**심정지를 대기로 세는 것은 이 트랙의 어떤 결함보다 나쁘다.** 08-15 에 "심박 없음 → 대기"
표시를 정직하게 만들었는데, 그 정직해진 표시가 응급을 감추고 있다.

→ **별도 트랙 = [docs/vital-absence-triage/](../../../docs/vital-absence-triage/checklist.md)**
온열보다 우선순위가 높다(사용자 판단).

### 신호별 사용 가능성 (2026-08-15 실측 · 08-13 이후 27,831행)

| 신호 | 축이 맞나 | 밀도 | 값이 없을 때의 뜻 |
|---|---|---|---|
| **심박** | ✓ 생리 — **판정의 주(主)** | 27,632 (99.3%) | **미착용 또는 심정지** (§2-2) |
| **걸음** | 보행만 — 배제용 보조 | 1,186 (4.3%) | 안 걸음 / 미수집 / 앉아서 작업 |
| **MET**(`physicalEffortMet`) | ✓ 대사율(ACGIH 표준) | 324 (1.2%) | 안 움직임 / 미기록 |
| **활동에너지** | ✗ 바닥 4.8 상수 | 촘촘 12/분 | — (§1) |
| **`motionStillSec`**(정지 지속) | ✓ **앉아서 하는 작업도 잡는다** | **0건 — 워치 미수집** | — |
| `accelMagnitudeG`·`peakRotationRadS` | 낙상 **충격 피크** 전용 | 0건 | 활동 축 용도가 아니다 |

> **⚠ 초판 정정 — 모션 필드를 혼동해 적었다.** 초판은 *"가속도(`accelMagnitudeG`)가 팔 움직임을
> 잡는 유일한 후보인데 미수집"* 이라고 썼는데 **틀렸다.** `accelMagnitudeG` 는 스키마 주석대로
> **"충격 순간의 피크"** 로 낙상 전용이다. 활동 축에 맞는 것은 **`motionStillSec`(정지 지속 초)**
> 이고, 이쪽은 **DB 컬럼도 insert 매핑(`db.ts:907`)도 이미 있는데 워치가 안 보낸다.**
> (별개로 `accelerationMagnitudeG`·`rotationRateRadS` 는 Zod 스키마에만 있고 **DB 컬럼이 없다** —
> 스키마가 받아도 저장 경로가 없다. 별건으로 §3 에 남긴다.)

**★ 그래서 필요한 것은 "가속도 수집" 이 아니라 `motionStillSec` 수집이다.**
서버 쪽은 준비돼 있으므로 **워치 전송만 추가**하면 되고, 그것 하나로 셋이 풀린다 —
ⓐ 앉아서 작업 vs 정말 쉬는 중 ⓑ 미착용 vs 심정지(§2-2) ⓒ 낙상 후 정지 확인.
⚠ 배터리 영향 확인 선행(현행 6.46%/h).

### 걸음을 배제 조건으로 쓸 때의 장치

`appendCountDelta:380` 이 **1걸음 미만이면 항목 자체를 안 실으므로** `steps IS NULL` 은
"안 걸었다" 와 "수집 안 됨" 을 겸한다. **다만 새 구조에서는 이것이 판정을 막지 않는다** —
걸음은 배제 조건이라, 불확실하면 **배제하지 않고 판정을 진행**하는 쪽이 안전하다
(놓치는 것보다 잡고 보는 것). 오탐이 문제가 되면 그때 `lookback` 을 붙인다.

## 2-3. ★★ 실측 정답 사례 (2026-08-18) — 이 트랙에 처음 생긴 정답

이 트랙의 근본 약점은 **추정을 검증할 정답이 없다는 것**이었다. 08-18 에 사용자 증언으로 처음 생겼다.

> **사용자 증언 = "많이 긴장한 상태에 흡연 및 계단 오르내리기 상태"**

같은 시각 데이터.
```
시     평균심박  걸음   계단   활동kcal        추정 심부체온
13     116.0   1449     0      306          14:05~14:15 38.00~38.02  ★경고선 이상
14     118.1   1268     0      320          14:25 최고 38.030
14:20~14:40  걸음 0 · 심박 110~116          하강 시작 → 14:45 37.886
```
**추정 심부체온이 경고선을 세 번 넘었고 경고는 0.004℃ 차이로 비켜갔다**(14:05~14:15 창 최솟값 37.996).
그런데 정답은 **온열이 아니라 긴장·흡연·계단**이었다.

### ⟹ B-1b 초안이 이 사례에서 오탐을 낸다

§2 가 정한 구조는 `걸음 없음 + 고심박 → 온열 의심` 인데, 사례의 **14:20~14:40 이 정확히 그 모양**이다
(걸음 0 · 심박 110~116). 실제로는 **계단·흡연 후 회복 국면**이었다. 즉 그대로 구현하면 오늘 경고가 났다.

원인은 셋이고 **셋 다 걸음으로는 배제되지 않는다.**

| 교란 | 심박 영향 | 배제 신호 | 상태 |
|---|---|---|---|
| **흡연(니코틴)** | +10~20 bpm · 20~30분 지속 | **없음** | 수집 항목 자체가 없다 |
| **긴장(교감신경)** | 상승 | **없음** | HRV 가 후보이나 상시 워크아웃과 배타(08-13 확정) |
| **계단** | 걸음 수 대비 부하가 훨씬 크다 | `flightsClimbed` | **신규 앱에서 0건** — 아래 2-4 |

`heat-pattern.ts` 툴팁이 이미 *"열 축적·탈수 **또는 긴장·카페인** 가능"* 이라고 적어 뒀다.
문헌 검토가 지적한 *"회복 국면이 가장 부정확한데 이 알림이 잡으려는 상황이 바로 회복 국면"* 과도 겹친다.

**⟹ 걸음 단독 배제로는 부족하다. B-1b 설계를 그대로 구현하면 안 된다.**

## 2-4. ★ 곁가지 결함 — 신규 앱이 계단을 안 보낸다 (원인 후보 확정적)

```
source=VitAlGuard-WatchVitals   계단행 816 · 합 4,767 · 마지막 08-01 13:41   ← 구 앱 시절
08-16 이후 신규 앱 구간          계단 0건 (같은 구간 걸음은 1,132건 정상)
```
**스키마·DB 컬럼·insert 매핑·워치 전송 코드가 전부 있는데 값만 0** 이다(BND-CONTRACT-01 과 달리 트리오는 온전).

읽는 경로가 구/신 앱에서 다르다.
```
구 앱   StressInputsReader.swift:178  HKStatisticsQuery 로 저장소 직접 조회
        WorkoutManager.swift:772      locationType = .unknown
신규앱  WatchStreamer.swift:643       HKLiveWorkoutBuilder.statistics(for:)  ← 워크아웃이 수집한 것만
        WatchStreamer.swift:253       locationType = **.indoor**
```
**유력 원인 = `.indoor` 워크아웃이 고도 기반 지표를 수집 대상에서 제외한다.** 걸음은 실내에서도 수집되므로
오고 계단만 빠지는 관측과 정확히 맞는다(걸음·계단은 코드 경로가 완전 대칭인데 결과만 갈린다).
⚠ **확정은 아니다** — 애플 문서 확인이나 실기기 시험이 필요하다. 다만 **처방은 원인과 무관하게 같다.**

**처방 = 구 앱처럼 워크아웃 빌더가 아니라 별도 쿼리로 읽는다.** 신규 앱은 `discreteInputs` 로 이미 같은
패턴(anchored/statistics 쿼리)을 쓰고 있으므로 계단을 그쪽으로 옮기면 워크아웃 구성과 무관해진다.
⚠ `locationType` 을 바꾸는 쪽은 권하지 않는다 — 워크아웃 구성은 폰 강제종료·잠금 생존의 핵심 장치라
건드리면 그 축이 흔들린다. **읽는 경로만 바꾸는 것이 부작용이 없다.**
