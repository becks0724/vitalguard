# 감시 공백 알림 — 결정과 근거

## A-01 · 왜 크론인가 (수신 경로로는 원리적으로 불가)

`recordAlert` 호출부가 전부 수신 경로다(`api/app/vital/store.ts:276,284,298` · cctv ingest · heat-alert).
**부재는 수신이 없어서 발생하므로 그 자리에서는 영원히 발화하지 않는다.**
`DemoDashboard.tsx` 의 `STALE_MS = 60_000` 은 클라이언트 전용이라 **누가 화면을 보고 있을 때만** 칠한다.

실제 대가 — 2026-08-18 19:01 부터 **12.9시간** 수신이 끊겼는데 **경보 0건**이었고,
사람이 워치에서 [시작] 을 눌러서야 끝났다. 아무도 감시 공백을 몰랐다.

## A-02 · 임계 10분

7일 실측 공백 분포로 정했다.

```
임계 5분  → 36건 / 7일
임계 10분 → 24건 / 7일 (하루 3.4회)
임계 30분 → 15건 / 7일   ← 08-18 의 20.9분을 놓친다
```

10분이 **잡아야 할 것을 놓치지 않는 최소 손실 지점**이다.

## A-03 · ★ 전달 단절은 오탐이 아니다 (내 판단이 뒤집힌 자리)

처음엔 "10분이면 전달 단절까지 잡혀 오탐이 난다" 고 봤다. 옆 세션이 7일 공백 전건을
복귀 지연으로 분류해 보여줬는데 **수집 정지와 전달 단절 두 모집단이 16분까지 완전히 겹친다** —
임계로는 원리적으로 못 가른다.

★ 그런데 **가를 필요가 없었다.** 이 알림의 주장은 "작업자가 위험하다" 가 아니라
**"서버가 N분째 못 받고 있다"** 이고, 그건 전달 단절에서도 참이다. 감시가 멀어 있는 것은 사실이다.

⟹ 문구를 관측 사실로 한정하면 두 원인을 가르지 않고도 옳은 알림이 된다.
원인은 **복귀한 뒤에만** 갈리므로 해제 문구에서만 말한다([A-05](#a-05)).

## A-04 · 야간은 화면 표시만 (사용자 결정 2026-08-19)

10분 초과 공백 24건 중 **7건이 야간 시작이고 길이가 600~920분**이라 퇴근으로 보인다.
push 하면 매일 밤 울려 일주일이면 무시된다.

★ **무엇이 결정이고 무엇이 우리 기본값인지 구분해 둔다.**
- 사용자 결정 = **"야간은 화면 표시만"**(push 를 근무시간으로 막는다는 것까지).
- **07~19 라는 숫자는 우리가 고른 기본값이다** — 사용자가 시각을 짚은 적 없다.
  `PUSH_WINDOW_START_HOUR`·`PUSH_WINDOW_END_HOUR` 한 곳에 두었고, 현장이 늘면 여기서 바꾼다.

⚠ **야간 교대 현장에서는 이 규칙이 틀린다.** 대안을 찾았으나 없었다 —
옆 세션이 배터리로 "충전=퇴근" 을 가를 수 있는지 재보니 9일 60분 초과 공백 13건 중
**배터리 값이 있는 것이 1건**뿐이고 그마저 평평했다(충전 아님). 원리적 한계가 더 크다 —
**부재 중에는 아무 데이터도 안 오므로 충전 여부는 복구된 뒤에야 보인다.** 실시간 판단에 못 쓴다.

★ 다만 **사후 검증 재료는 곧 생긴다** — 세션 계측(`session_auto_resumed`)이 워치에 올라가면
긴 공백 뒤 `false` 인 지점이 "사람이 [시작] 을 누른 시각" = 복귀 시각이다. 며칠 쌓이면
07~19 가정이 실제 근무 경계와 맞는지 대조할 수 있다.

⚠ 야간에 시작해 아침까지 이어지는 공백은 push 되지 않는다(자연키가 같아 재삽입이 안 된다).
화면에는 보인다 — 야간을 표시만으로 둔 결정에 포함된 결과다.

## A-05 · 복귀 사후분류 — 지표를 한 번 잘못 골랐다

복귀 직후 1분의 **최대 측정 지연**으로 원인을 가른다. 두 모집단이 깨끗이 갈린다.

```
수집 정지  0 · 2 · 3 · 7 · 10 · 11초        (그리고 47~775분짜리 긴 공백 전부 2~9초)
전달 단절  332 · 333 · 427 · 504 · 653 · 968초
```

⚠ **지표를 처음에 잘못 골랐다.** 도착 시각 기준(`received_at − ts`)으로 재니 전 구간 0~4초라
아무것도 구별하지 못했고, 그대로 갔으면 분류기 전체가 무의미했을 것이다.
옆 세션이 낸 수치를 **재현되는지 먼저 맞춰 본 덕에** 잡혔다 — 실제 지표는
`ts − heart_rate_measured_at`(측정 시각 기준)이고, 바꿔서 재니 그쪽 표와 전건 일치했다.

⟹ **남이 낸 수치를 이어받을 때는 결론이 아니라 그 수치부터 재현한다.**

복귀 직후 심박이 없으면 `null` 이고 **원인을 지어내지 않는다**(`unknown`).
실제로 08-18 20.9분 공백이 그 경우다(복귀 후 2분간 심박만 없었다).

## A-06 · 원장을 우회하지 않는다

온열 알림이 `recordAlert` 를 안 거쳐 **발동 이력을 아무도 조회할 수 없었던** 전례가 있다.
부재 알림은 문구를 직접 만들어야 해서(경과 시간·사후 판정) `notify: false` 로 통지만 끄지만
**기록은 건너뛰지 않는다.** `2026-08-19-absence-ledger.guard.test.ts` 가 기록이 통지보다
먼저 오는 것과 기록 경로에 근무시간 조건이 끼지 않는 것을 소스 불변식으로 고정한다.

`recordAlert` 는 `boolean`(새로 적혔는지)을 돌려주게 넓혔다 — 자연키 `(worker_id, type, ts)` 가
같은 공백의 재발화를 막고, 그 반환값이 곧 "이번 틱에 처음 감지했다" 이므로 통지 조건이 된다.
기존 호출부는 반환값을 무시하므로 동작 변화가 없다.

## A-07 · 해제는 새 종류가 아니라 `ack`

`alerts` 에 `ack_at`·`ack_by` 가 이미 있다. 복구를 별도 알림 종류로 만들지 않고
`ackAlert(id, "자동해제 · …")` 로 닫는다 — 스키마 변경 0, 사람이 나중에 원장에서 사유를 읽는다.
사람이 먼저 확인(ack)한 알림은 `changed === 0` 이라 자동 통지가 나가지 않는다.

`alerts.type` 은 **text 이고 CHECK 제약이 없어** 마이그레이션 없이 `absence` 를 넣을 수 있다.

## A-08 · 조회 범위는 최근 활동자로 한정

> ⚠ **정정([A-10](#a-10)) — 이 항목의 전제가 틀렸다.** 아래는 초판 설계이고, "최근 활동자"를 명부로
> 삼은 것이 곧 결함이었다. 지금은 명부가 `monitor_slot_config.slots` 이고 24시간은 **공백 상한**이다.
> 과거 서술이라 고쳐 쓰지 않고 표시만 남긴다.

`listAllWorkers()` 는 `vital_samples` 전체를 훑어 몇 달 전 사람까지 낸다.
그들에게 "10분째 수신 없음" 은 참이지만 의미가 없다 → `lastSeenByWorker(24시간)`.
한 번도 받은 적 없는 작업자도 제외한다(등록만 된 빈 슬롯이 매 틱 알림을 내면 진짜 공백과 섞인다).
— 마지막 문장(한 번도 안 받은 작업자 제외)은 지금도 유효하다.

## A-09 · 관제 표시 — 라벨만으로는 1분과 12시간이 같다

옆 세션이 잔여로 올려둔 항목. `연결끊김` 라벨 옆 수신시각이 **절대 시각**(`14:05`)이라
관리자가 경과를 스스로 계산해야 했다. 상태 칸에 경과를 함께 적고,
체온 툴팁의 `"마지막 수신 이후 60초 초과"` 고정 문구도 실제 경과로 바꿨다(12시간 끊김이 1분처럼 읽혔다).

⚠ 옆 세션 제약을 그대로 받았다 — **"수동 재개 필요" 라 단정하지 않는다.**
같은 끊김이 거리 이탈일 수 있고(자동 복구된다는 실기기 확증이 있다) 그 순간에는 서버도 못 가른다.
`absence-watch.test.ts` 가 금지어를 문구 가드로 고정한다.

## A-10 · ★ 첫 발화가 명부 구멍을 드러냈다 (2026-08-19 · 배포 당일)

등록 직후 첫 틱 응답이 `checked: 2` 였다. 그런데 **관제 화면 배정은 4명**이다.

```
명부 monitor_slot_config.slots = ["EMP-6861","EMP-admin7276","EMP-admin3470","EMP-admin0740", null×96]

EMP-6861       장우진   0.0시간    정상
EMP-admin3470  김태곤   21.0시간   ← 알림 나감
EMP-admin7276  워치PoC  17.8일     ← 대상에서 빠짐
EMP-admin0740           41.0일     ← 대상에서 빠짐
```

⟹ **알림이 `vital_samples` 를 명부처럼 쓰고 있었다.** 화면과 알림이 서로 다른 명부를 보는 상태이고,
이 레포가 반복해서 당한 false-OK 계열이다. 양방향으로 틀린다 —
① 배정 안 된 시험 기기가 붙었다 끊기면 **알림이 나가고**
② 배정됐는데 오래 꺼진 작업자는 **대상에서조차 빠진다.**

**고친 것** = 명부를 `monitor_slot_config.slots` 로 옮기고 `worker_alias` 로 접는다.
별칭 접힘은 옆 세션이 짚었고 **실측으로 확인**했다 — 별칭 7행 중 **4행이 `EMP-admin7276` 한 사람**이라
접지 않으면 최대 5명으로 갈리고, 그중 옛 ID 하나만 오래되면 **본인은 정상 수신 중인데 부재 알림이 난다**.
같은 날 별칭 쌍이 양쪽에서 수신된 이력이 5쌍 있어 **이론이 아니라 실제 위험**이다.

⚠ **24시간은 유지했고 이름만 `maxGapHours` 로 바꿨다.** 역할이 "누가 대상인가" 가 아니라
**"공백 상한"** 이다 — 41일 꺼진 기기는 사건이 아니라 상태이고, 매일 밀면 하루면 무시된다.
그런 작업자는 관제 신호등이 `대기` 로 집계해 화면에 남는다.
초안에서 반대로 **24h → 3h 축소**를 제안했다가 **철회**했다. 옆 세션과 내가 둘 다
`EMP-admin3470` 을 명명 패턴(`admin####`)만 보고 시험 계정으로 읽었는데,
**사용자가 실제 배정 작업자라고 정정**했다. 좁혔으면 실제 작업자를 숨겼을 것이다.
⟹ **계정의 성격을 ID 명명 규칙으로 단정하지 않는다**(같은 계열 오귀속이 08-16 GPS 에도 있었다).

★ 그리고 명부가 비면 `checked: 0` 이 되는데 그건 **"전원 정상" 과 구별되지 않는다** →
응답에 `roster`(배정 수)를 함께 싣는다. 이 트랙이 고치는 결함과 같은 모양이라 자기 자리에도 적용했다.

## A-11 · ★ 이름을 최근 라벨에서 골라 사람을 잘못 부를 뻔했다

명부 결함([A-10](#a-10))을 고치며 이름을 **가장 최근 샘플 라벨**에서 뽑았다. 그게 결함이었다.

**권위 있는 이름 테이블이 없다.**
```
worker_profile   worker_id · job_title · updated_at   ← 이름 컬럼 자체가 없다
t_worker         스키마만 있고 행 0
```
⟹ 작업자 이름의 유일한 출처가 **앱이 샘플에 실어 보낸 `worker_name` 문자열**인데,
워커 하나에 **시기별로 여러 라벨**이 섞여 있다.

```
                최근 라벨                    최빈 라벨
EMP-admin7276   워치PoC                ❌    전 팀원    ✅ (실제 인물)
EMP-admin0740   관리자 EMP-admin0740    ❌    김○○    ✅ (실제 인물)
EMP-admin3470   김태곤                       김태곤
EMP-6861        장우진                       장우진
```
그대로 뒀으면 알림이 `작업자 워○PoC (EMP-admin7276)` 라고 불렀다. **안전 알림이 사람을
잘못 부르는 것**이라 그냥 둘 수 없었다. `MODE() WITHIN GROUP` 으로 바꿔 프로덕션 읽기로
배정 4명 전원이 사람 이름으로 나오는 것을 확인했다.

⚠ **개명하면 옛 이름이 이길 수 있다.** 사번은 항상 맞으므로 식별은 유지된다.
⚠ 근본 해결은 **명부에 이름을 등록하는 자리를 만드는 것**이다. 지금은 그 자리가 없다.

★ 발견 경로가 남길 값이 있다 — 옆 세션이 `admin####` 명명으로 계정 성격을 단정했다가 정정했고,
나 역시 `워치PoC` 라는 **라벨을 계정 성격의 증거로 읽었다**. 둘 다 같은 형태이고
이 레포에 이미 이름이 붙어 있다 — *"라벨은 출처의 증거가 아니다"*(08-16 GPS 오귀속).
**판정 근거는 표시 문자열이 아니라 그 값을 만드는 경로다.**
