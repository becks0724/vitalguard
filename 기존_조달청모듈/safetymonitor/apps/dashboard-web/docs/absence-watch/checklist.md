# 감시 공백 알림 (absence-watch) — 체크리스트

**문제.** 경보가 전부 *샘플이 들어올 때* 발화한다. 샘플이 안 오면 발화 지점 자체가 없다.
2026-08-18 19:01 부터 **12.9시간** 수신이 끊겼는데 **경보 0건**이었고, 사람이 워치에서
[시작] 을 눌러서야 끝났다. 감시가 반나절 죽어 있는 것을 아무도 몰랐다.

**만드는 것.** 서버가 부재를 스스로 감지해 알린다. 워치 설치·재서명이 필요 없다.

## 설계 확정 (2026-08-19 · 옆 세션 조율 완료)

- **임계 10분.** 5분 36건 / 10분 24건 / 30분 15건(7일) 중 30분으로 올리면 08-18 의 20.9분을 놓친다.
- **전달 단절은 오탐이 아니다.** 옆 세션이 7일 공백 전건을 복귀 지연으로 분류했더니
  수집 정지와 전달 단절 두 모집단이 **16분까지 완전히 겹친다** — 임계로는 원리적으로 못 가른다.
  ★ 그런데 가를 필요가 없다. 이 알림의 주장은 "작업자가 위험하다" 가 아니라
  **"서버가 N분째 못 받고 있다"** 이고 그건 전달 단절에서도 참이다.
- **야간은 화면 표시만**(사용자 결정 2026-08-19). 10분 초과 공백 24건 중 7건이 야간 시작·600~920분
  길이라 퇴근으로 보이고, push 하면 매일 밤 울려 일주일이면 무시된다.
- **문구는 관측 사실만.** `수동 재개 필요` 라 단정하지 않는다 — 같은 끊김이 거리 이탈일 수 있고
  (자동 복구됨 · 시험 B 확증) 그 순간에는 서버도 못 가른다.
- **원장 필수.** 온열 알림이 `recordAlert` 를 우회해 발동 이력을 아무도 못 본 전례가 있다.

**배포 후 남는 수동 단계** — Cloud Scheduler 작업 등록(현재 `env-check` 하나뿐).
```
gcloud scheduler jobs create http absence-check --location=asia-northeast3 \
  --schedule="*/5 * * * *" --time-zone="Asia/Seoul" \
  --uri="https://vitalguard-dashboard-569797426568.asia-northeast3.run.app/api/cron/absence-check" \
  --headers="x-cron-key=$(gcloud secrets versions access latest --secret=CRON_SECRET)"
```
⚠ 5분 주기 = 임계 10분 + 최대 5분 지연. 10분 주기로 두면 최대 20분이 된다.
⚠ 헤더 값 끝의 개행이 401 을 만든 전례가 있다(`$(cat)` 은 개행을 지우지만 파일 리다이렉트는 남긴다).
