# 체감온도 산출식 교체 — 결정과 근거

2026-08-14 · 발단 = 온열 알고리즘(PSI/WBGT) 검토 중 기존 폭염 판정의 입력 출처 결함 발견.

## 왜 고치는가

법령(산업안전보건기준에 관한 규칙, 2025 개정)은 **"기상청이 측정한 체감온도"**가 31℃/33℃ 이상인 작업장소를 폭염작업으로 규정하고, 33℃ 이상이면 **매 2시간 이내 20분 이상 휴식을 의무**로 부과한다.

그런데 우리 판정 입력은 Open-Meteo 의 `apparent_temperature` 였다. 두 값은 **다른 공식**이다.

```
기상청 (2022-06-02 개정 · 여름철)
  체감온도 = -0.2442 + 0.55399·Tw + 0.45535·Ta - 0.0022·Tw² + 0.00278·Tw·Ta + 3.0
  → 풍속 항이 없다.

Open-Meteo (Steadman)
  AT = Ta + 0.348·e - 0.7·ws + 0.7·(Q/(ws+10)) - 4.25
  → 풍속 ws 가 계수 -0.7 로 값을 끌어내린다.
```

**★ 실측으로 확인한 오차 방향 — 양방향이다.** 착수 시점엔 "풍속 계수 -0.7 때문에 과소경보"로 진단했으나, 조건 매트릭스(기온 29~35 × 습도 40~85 × 풍속 0~29km/h) 실계산 결과 **지배적 방향은 반대**였다. Open-Meteo 식의 수증기압 항 `+0.348e` 가 풍속 항보다 훨씬 크게 작용해, 습한 날엔 기상청보다 최대 **+9.7℃** 높게 나온다.

| 조건 | 현행(Open-Meteo) | 기상청 | 결과 |
|---|---|---|---|
| 습·무풍 (33℃/85%/0km/h) | 43.6℃ | 35.6℃ | **과대 +8.0** |
| 오늘 광주 실측 (27.3℃/77%/2.5km/h) | 32.3℃ | 29.1℃ | **과대 +3.2** |
| 건조·강풍 (35℃/40%/29km/h) | 32.9℃ → 31주의 | 33.3℃ → **33의무** | **과소 — 법정 휴식 의무 누락** |
| 건조·강풍 (33℃/40%/29km/h) | 30.1℃ → 정상 | 31.4℃ → 31주의 | 과소 |

즉 **대부분의 여름날은 과대경보, 바람 부는 건조한 폭염일은 과소경보**다. 두 방향 모두 실재하고 둘 다 나쁘다.

- 과대 → 경보 피로. 현장이 "또 오경보"로 학습하면 진짜 위험할 때 무시한다.
- 과소 → 법이 요구하는 휴식 의무가 발동하지 않는다.

법이 지정한 값을 쓰면 양쪽이 동시에 해결된다. 이것이 수리 근거이고, 오차 방향이 한쪽이 아니라는 사실은 **오히려 근거를 강화한다**(어느 방향으로도 우연히 맞기를 기대할 수 없다).

## 이 결함이 속한 계열 (L-58)

프레이밍을 두 번 고쳐 잡았다. 최종 정의는 **표기된 근거와 실제 산출 근거가 다르다**이다.

| 사례 | 화면이 말하는 근거 | 코드가 쓰는 근거 |
|---|---|---|
| 준수율 100% | 측정된 준수율 | 무데이터 → 기본값 |
| 정상 4명 | 판정 결과 | 미판정(샘플 없음) |
| 스트레스 칩 | 심박 + HRV | 심박만 |
| **체감온도** | 법정 기준 31/33/35℃ | Steadman 식(다른 정의) |

버린 정의 2개와 이유.
- "화면이 실제보다 **안전한 쪽**으로 말한다" — 방향은 증상이지 정의가 아니다. 앞선 3건이 우연히 같은 방향이었을 뿐이고, 방향으로 정의하면 이번처럼 **과대 방향 사례를 계열에서 놓친다**.
- "화면이 **근거 없는** 값을 말한다" — 체감온도에는 근거가 있다(Steadman 실계산값). 없는 게 아니라 **다른 정의**를 쓴 것이다.

이 구별이 실질적인 이유는 처방이 하나로 모이기 때문이다. **화면이 실제 산출 근거를 말하게 하거나, 산출 근거를 표기에 맞추거나** 둘 중 하나다. "값을 보정한다"는 선택지가 아니다. 이번 건은 법령이 정의를 지정하므로 후자(기상청 식으로 교체)가 유일한 답이다.

## 채택한 공식 (교차 검증 완료)

두 독립 출처에서 계수까지 일치를 확인했다.

**여름철 (기상청 2022-06-02~)**
```
체감온도 = -0.2442 + 0.55399·Tw + 0.45535·Ta - 0.0022·Tw² + 0.00278·Tw·Ta + 3.0
```

**습구온도 Tw (Stull 2011 추정식 · atan 은 라디안)**
```
Tw = Ta·atan[0.151977·(RH + 8.313659)^0.5]
   + atan(Ta + RH) - atan(RH - 1.67633)
   + 0.00391838·RH^1.5·atan(0.023101·RH)
   - 4.686035
```

**겨울철 (JAG/TI 2001 · 기상청 채택)**
```
체감온도 = 13.12 + 0.6215·Ta - 11.37·V^0.16 + 0.3965·V^0.16·Ta     (V = km/h)
적용 조건 = 기온 ≤ 10℃ AND 풍속 ≥ 1.3 m/s
```

## 결정 1 — 구간 분기

기상청은 여름·겨울 지수를 **별개로 운영**한다(연중 연속 함수가 아니다). 두 공식 모두 자기 적용 범위 밖에서는 물리적으로 무의미하므로 분기한다.

| 조건 | 적용 | 근거 |
|---|---|---|
| Ta ≥ 25℃ | 여름철 공식 | 폭염 임계 31℃보다 충분히 아래에서 시작해 경계 누락 방지 |
| Ta ≤ 10℃ AND V ≥ 1.3 m/s | 겨울철 공식 | **기상청 공식 적용 조건 그대로** |
| 그 외 | 기온 그대로 | 두 지수 모두 부적용 구간 |

25℃ 하한만 우리 판단이다(기상청은 월 기준 5~9월 운영이라 기온 기준 경계가 없다). 월 기준을 쓰면 4월·10월 폭염일이 누락되므로 기온 기준을 택했고, 임계 31℃보다 6℃ 아래라 경계 근처에서 공식이 바뀌는 일이 없다.

## 결정 2 — 수집 시점에서 교체 (판정 시점 아님)

`app/api/weather/route.ts` 의 Open-Meteo 응답 매핑 지점에서 계산해 `apparent_temp_c` 에 저장한다.

이유. 저장·표시·판정·엑셀 내보내기가 **한 값으로 통일**된다. 판정 함수에서만 재계산하면 DB·엑셀에는 여전히 Open-Meteo 값이 남아 사고 조사 보고서와 화면이 어긋난다.

## 결정 3 — 과거 행은 소급 변경하지 않는다

`weather` 테이블에 `humidity_pct` 가 함께 저장돼 있어 기술적으로는 소급 재계산이 가능하다. 하지만 하지 않는다.

이유. 과거 행은 **그 시점에 화면이 실제로 보여준 값**이고, 사고 조사는 "그때 관제웹이 무엇을 표시했는가"를 재현해야 한다. 소급 변경하면 당시 판정 근거가 사라진다. 대신 전환 시점을 코드 주석과 이 문서에 남긴다.

⚠ 불연속 구간 = 2026-08-14 배포 이전 행은 Open-Meteo(Steadman) 기준. 사고 조사에서 그 이전 구간을 볼 때 참고.

## 미해결 · 확인 필요

- **31℃ 의 `binding` 표기** — 코드는 `legal`(법적 강제)로 두는데, 31~33℃ 를 권고로 해석하는 자료가 있다. 31℃ 가 폭염작업 법정 정의인 것은 맞아 완전한 오류는 아니나 법령 원문 대조 필요.
- **38℃ 단계 부재** — 안전보건공단 계산기 자료는 4단계(관심 31~33 / 주의 33~35 / 경고 35~38 / 위험 38+)를 쓰는데 우리는 3단계다. 출처가 앱 홍보 페이지라 신뢰도가 낮아 고용노동부 공식 지침 대조 후 판단.
- 위 두 건은 이번 수리 범위 밖(산출식 교체만). 별도 확인 후 처리.

## 검증 기준

- 풍속을 바꿔도 여름철 체감온도가 변하지 않는다 (기상청 식에 풍속 항이 없다)
- 습도·기온 단조성 · 습구온도 ≤ 기온 (물리 제약)
- 겨울철 적용 조건 경계(10℃ · 1.3m/s)에서 공식이 올바르게 갈린다
- 습도 결측·비정상 시 여름식을 쓰지 않는다
- ⚠ "기존 값보다 낮아지지 않는다"는 검증 기준은 **폐기**한다 — 실측 결과 대부분 낮아지는 것이 정상이다(과대경보 해소).
