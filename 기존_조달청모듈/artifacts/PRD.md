# PRD — VitAlGuard: 안전관리비 실집행·과다청구 검증 플랫폼

> 작성 2026-06-17 · 대회: 2026 공공조달데이터·AI 활용 창업경진대회(조달청) · 부문: **아이디어 기획 + 구현** · 마감 2026-06-19 18시.
> (이전 PRD = SafeProcure 모듈 통합 / 제품·서비스 부문 — 방향 전환으로 폐기.)

## 1. 목적 / 문제

- **문제**: 건설현장 안전관리비는 계상(예산)은 고시로 정해지지만, 그 돈이 **실제로 작업자·안전활동에 도달했는지**는 장부·사진 증빙에 의존 → 과소집행·과다청구·유령 인원 청구를 사전에 거를 수단이 없다.
- **목적**: 조달청·국세청 공공데이터 + 웨어러블 IoT로 안전관리비를 **계상→사용→실집행→증액 4단계로 교차검증**하고, 특히 **실인원 대비 과다 산정분을 자동 산출**해 조달청의 사후관리를 리스크 기반으로 강화한다.

## 2. 범위 (4축 — 구현 완료)

| 축 | 기능 | 데이터원 | 상태 |
|---|---|---|---|
| ①계상 | 계약 현장 식별 + 법정 요율로 안전관리비 계상 기준액 산정 | 조달청 계약정보(15129427) + safety-cost.ts | ✅ tsc |
| ②사용 | 세금계산서 발급처 사업자 상태조회(계속/휴업/폐업) | 국세청 15081808 (status) | ✅ tsc |
| ③실집행 | 웨어러블 출역 worker-day·실인원 집계, 계상액÷worker-day 환산 | vital_samples(SQLite) | ✅ tsc |
| ④증액 | 계약 후 증액 청구 vs 실인원 대조 → 과다 산정액 산출·판정 | 계약변경이력 + 관리자입력 + ③ | ✅ tsc |

## 3. 핵심 기능 상세

### F1. 진행 중 현장 목록 (①)
- 조달청 계약정보(체결=진행 중)로 현장 리스트. 계약금액을 안전관리비 대상액 근사로 사용 → 공사종류 분류 + 법정요율로 계상 기준액 산정. (`g2b.ts` getContracts → safety-execution.ts buildExecutionAudit)

### F2. 발급처 검증 (②)
- 사업자번호 10자리 입력 → 국세청 status API(POST) → 계속/휴업/폐업/미등록 배지. 휴·폐업처 발급 세금계산서 = 위험 신호. (`nts.ts` checkBusinessStatus → BusinessVerifyCard)

### F3. 실집행 환산 (③)
- vital_samples에서 일자별 출역인원·worker-day·distinctWorkers 집계. `계상액 ÷ worker-day = 1인·1일 명목 안전예산`. (`db.ts` auditWorkerDays)

### F4. 과다 산정 검증 (④ — 핵심)
- 입력: 청구 항목(안전모·안전화 수량·단가) + 증빙 여부.
- 산출: `과다액 = Σ max(0, 청구수량 − 실측인원) × 단가`.
- 판정: 청구/실측 비율 >1.5 의심 · >1.2 주의 · 그 외 정상 · 증빙·실측 없으면 검증불가. (`SafetyIncreaseAuditCard`)

## 4. 검증 판정 규칙 (코덱스 합의)

```
실측인원 N = 웨어러블 distinctWorkers (개인식별 → 중복 불가)
청구인원/수량 M = 세금계산서·청구서 (관리자 입력)
과다액 = Σ max(0, M − N) × 단가
인력증가율 < 10% AND 청구증가율 > 30% → 의심
청구/실측 > 1.5 → 의심 · > 1.2 → 주의
증빙 없음 / 실측 없음 → 검증불가
```

## 5. 데이터원 정직성 (과장 금지)

- 조달청 계약정보(15129427) + 국세청 사업자상태(15081808) = 실 OpenAPI.
- 안전관리비 **세목은 OpenAPI에 없음** → ②④ 청구 내역은 **관리자 입력 보강**(자동 아님).
- 웨어러블 출역 = **데모데이터**(실 현장 미착용) → "검증 로직 데모".
- 최종 적정성 판정 = 발주처·감독기관 권한. 우리는 리스크 사전 스크리닝(추정·보조).
