## ① 알림 배너 탭이 낙상 확정으로 처리됨 (최우선)

`handleFallResponseRequested` 가 `action == fallDismissActionIdentifier`("아니오")인 경우만 해제하고 **그 외 전부**(else)를 `confirmFallEmergency` 로 보냅니다.

iOS 알림에서 예/아니오 버튼을 누르지 않고 **배너를 그냥 탭해 앱을 열면** `UNNotificationDefaultActionIdentifier` 가 이 else 분기에 걸려 **실제 낙상 확정으로 전송**됩니다.

관측된 패턴(12:52~12:59 사이 5건, 약 21초 간격)이 이 구조로 설명됩니다. 알림이 반복 도착하고 그때마다 배너를 탭해 확인하려 했다면 정확히 이 결과가 나옵니다.

**수정** — 조건을 화이트리스트로 반전. `action == fallConfirmActionIdentifier` 일 때만 확정하고 배너 탭·스와이프는 판정 보류. 사실상 1줄입니다.

## ② 낙상 ML 3모델이 한 번도 동작한 적 없음

`.mlmodel` 3개(`impact`·`work_veto`·`recovery`)가 **Resources 빌드 페이즈**에 등록돼 있습니다. Xcode 의 CoreML 컴파일 룰은 **Compile Sources** 단계에서만 돌아 `.mlmodelc` 를 생성하는데, `Watch/Sources/FallMLPipeline.swift:19-22` 의 `init?()` 는 `withExtension:"mlmodelc"` 를 요구합니다.

→ **항상 nil → fail-open.** work_veto 오탐 억제가 실기기에서 작동한 적이 없고, 4명 LOSO 로 산출한 임계값(`thresholds.json`)도 쓰인 적이 없습니다.

**수정** — Xcode 에서 `.mlmodel` 3개를 Watch 타깃의 **Compile Sources** 로 이동. pbxproj 를 손으로 편집하면 `PBXBuildFile` UUID 재등록 때문에 프로젝트가 깨질 위험이 커서 **Xcode UI 작업**을 권합니다.

**검증** — 빌드 후 `Bundle.main.url(forResource:"work_veto", withExtension:"mlmodelc")` 가 nil 이 아닌지. 서버 쪽에서도 확인 가능합니다(아래 "우리 쪽 처리분" 참조).

**추가** — `Watch/Sources/MLSelfCheck.swift` 는 **호출부 0건인 데드코드**입니다. fail-open 을 탐지할 유일한 장치가 죽어 있어 같은 사고가 재발해도 알 수 없습니다. 기동 시 실제 호출하도록 배선을 권합니다.

## ③ 기본 전력모드(lowPower)가 ML 융합을 통째로 우회

`WorkoutManager.swift:245-250` 의 lowPower 분기는 `MLFusion` 을 **생성조차 하지 않습니다**(+ IMU 25Hz). 게다가 `ConnectionSettings.swift:697-708` 의 마이그레이션이 기존 balanced 사용자까지 lowPower 로 내립니다.

②를 고쳐도 이것 때문에 ML 이 돌지 않습니다. **둘 다 고쳐야 합니다.**

## ④ 워크아웃 세션 실패 시 조용한 영구 중단

`WorkoutManager.swift:758-771` — 세션이 비정상 종료되면 전부 끄고 끝입니다. 자동 재시작·서버 통보·햅틱이 없고 `scenePhase` 처리도 없습니다.

관제 화면에서 이것은 "작업 종료"와 구분되지 않습니다. **오탐보다 위험한 종류의 결함**입니다 — 작업자는 감시받고 있다고 믿는데 실제로는 아무도 보고 있지 않습니다.

**수정 제안** — 실패 시 백오프 재시작(2/4/8초 3회) + 햅틱 + 서버 통보. 초안 `audit/patches/WCH-SESSION-01.diff`.

**관련** — `VitalTransmitter.swift:441-448,478-481` 이 백로그를 `insert(at:0)` 로 넣고 `removeFirst` 로 트림해 **가장 최근 실패분(낙상·SOS)부터 버립니다.** `removeLast` 로 바꾸는 1줄 수정입니다.

## ⑤ 활동량을 하루 누적으로 전송 → 서버에서 샘플 폐기

`StressInputsReader.swift:168-187` 이 `steps`·`activeEnergyKcal`·`flightsClimbed` 를 **하루 누적**(predicate 86400초)으로 채웁니다. 서버 스키마는 **직전 60초 구간 합**을 전제해 상한(`steps≤5000`, `kcal≤200`)을 둡니다.

오후가 되면 상한을 넘겨 **샘플 전체가 거부**되고 심박·SpO₂·체온까지 함께 사라졌습니다.

**우리 쪽에서 완화 조치를 이미 배포했습니다**(2026-07-25). 이제 범위 밖 필드만 떨어지고 나머지 생체값은 살아남습니다. 다만 **활동량 값 자체는 여전히 버려지고** 스트레스 지수 판정도 왜곡됩니다.

**수정** — 창을 60초로 맞춰 주세요. Flutter 앱(`worker-phone`)은 이미 60초 구간 합을 씁니다.

- **상시 모션 2종**(`accelerationMagnitudeG`·`rotationRateRadS`)과 **ML 텔레메트리 7종**(`mlWorkVetoProb`·`mlVetoedByML` 등)이 서버 스키마에 없어 **전량 무음 폐기**되고 있었습니다. 서버에 필드를 추가해 이제 보존됩니다.

## 참고 — App Store 심사 관련 (별건)

- `PrivacyInfo.xcprivacy` 가 레포 전체에 **없습니다.** UserDefaults 등 required-reason API 를 쓰므로 제출 시 거부됩니다. 초안이 `audit/patches/` 에 있습니다.
- `APP_UPLOAD_TOKEN` 이 **UserDefaults 평문 저장**(`VitAlGuardPreviewApp.swift:28,17821`). 같은 앱의 LLM API 키는 Keychain 을 쓰고 있어(`2026-07-24-VitAlGuardAssistant.swift:63-112`) 패턴은 이미 있습니다.
- `allowsBackgroundLocationUpdates = true`(`:16536`)인데 Phone `Info.plist` 의 `UIBackgroundModes` 에 `location` 이 없습니다. Apple 사양상 **런타임 크래시**(`NSInvalidArgumentException`) 조합입니다.
- Phone 타깃 실효 배포타깃이 **26.0** 으로 오버라이드돼 있어(`project.pbxproj:600,709`) iOS 17~25 기기가 설치 대상에서 제외됩니다.
