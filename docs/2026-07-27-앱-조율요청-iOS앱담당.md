## ① `.mlmodel` 이 컴파일되지 않아 ML 이 한 번도 동작한 적 없음 · **최우선**

### 증상

`FallMLPipeline.init?()` 이 **항상 nil** 이다. 7.9 에서 새로 만든 `MLFirstShadowPipeline` 도
`guard let pipeline else { return }`(`MLFirstShadowPipeline.swift:45`)에서 즉시 빠져나가므로,
**그림자 관측이 단 한 건도 생성되지 않는다.**

### 원인

`FallMLPipeline` 은 컴파일 산출물인 `.mlmodelc` 를 요구한다.

```swift
// Watch/Sources/FallMLPipeline.swift:31-33
guard let wvURL  = Bundle.main.url(forResource: "work_veto", withExtension: "mlmodelc"),
      let impURL = Bundle.main.url(forResource: "impact",    withExtension: "mlmodelc"),
      let recURL = Bundle.main.url(forResource: "recovery",  withExtension: "mlmodelc"),
```

그런데 모델이 **Resources 빌드페이즈**에 있어 `.mlmodel` 이 그대로 복사될 뿐 컴파일되지 않는다.

```yaml
# project.yml:72-73
      - path: Watch/ML
        buildPhase: resources
```

### ⚠️ 함정 — pbxproj 를 고치면 되돌아간다

7.8 에서 XcodeGen(`project.yml`)이 도입되면서 **`project.pbxproj` 는 생성물**이 됐다.
Xcode UI 나 pbxproj 직접 편집으로 고쳐도 `xcodegen` 재실행 시 원복된다.
**반드시 `project.yml` 을 고쳐야 한다.**

### 확인 방법

수정 후 실기기에서 `MLSelfCheck.run()` 결과에 **"모델 미탑재"가 없어야** 한다.
서버 쪽으로도 확인 가능하다 — 정상 생체 샘플의 `mlFallPipelineActive` 가 `true` 로 올라온다
(이 필드는 서버가 07-27 부터 저장한다).

### 참고 — 7.9 에서 더 엄격해졌다

`recovery` 까지 필수가 됐다("부분 로드는 허용하지 않는다" 주석). **세 모델 모두** 컴파일돼야 한다.

### 영향 범위 (정정)

낙상 감지 **자체는 죽지 않는다.** `FallDetector`(규칙 기반)가 살아 있고
`WorkoutManager:289 if mlFusionEnabled` 가 ML 융합만 감싼다. 다만

- ML 오탐 억제가 무효 → 오탐이 그대로 경보로 나감
- 07-22 트랙A 에서 학습한 3모델이 실기기에서 **한 번도 쓰인 적 없음**
- 7.9 의 ML-first shadow 관측 데이터가 **0건** 축적

## ② 워치 활동량을 하루 누적으로 전송 — 오후부터 걸음수가 서버에 안 남음

### 위치

```swift
// Watch/Sources/StressInputsReader.swift:162, 168-187
func read(window: TimeInterval = 60) async -> StressInputs {
    ...
    if let daySteps = await sum(.stepCount, unit: .count(), window: 86400) { s.steps = daySteps }
```

`window: 86400`(하루 누적)을 1순위로 읽는다. 같은 패턴이 `activeEnergyKcal`·`flightsClimbed`·
`exerciseTime`·`standTime`·`moveTime` 에도 있다.

### 현재 상태

서버 스키마 상한은 `steps ≤ 5000` 이다. 상한을 넘으면 **그 필드만 스트립**된다.

- 07-25 서버 수정으로 **샘플 통째 유실은 이미 차단**됨(심박·SpO₂·체온은 계속 저장)
- 다만 **걸음수·활동량 값 자체는 오후부터 서버에 도달하지 않음**

### 요청

활동량 3종을 **60초 창**으로 전환. 함수 시그니처의 기본값(`window: TimeInterval = 60`)이
이미 60초이므로, 하루 누적 우선 분기를 제거하면 된다.

## ③ `fallPromptOutcome = "not_alerted"` — 서버 enum 에 없는 값 · **잠재 결함**

### 위치

```swift
// Watch/Sources/VitalTransmitter.swift:236
payload["fallPromptOutcome"] = isFall ? "pending" : "not_alerted"
```

서버 `VitalSampleSchema` 의 enum 은 다음 5개뿐이다.

```
"pending" | "dismissed" | "manual_sos" | "auto_escalated" | "moved_cancelled"
```

`"not_alerted"` 가 오면 **ZodError → 샘플 전량 폐기**된다.

### 현재는 무해하다

같은 함수 **215행의 `guard isFall else { return }`** 이 먼저 return 하므로 항상 `"pending"` 만 나간다.
도달 불가 코드다.

### 요청

**그 guard 를 되돌릴 계획이 있다면 먼저 알려달라.** 앱만 고치면 낙상 후보 음성 샘플이 전량 드롭된다.
둘 중 하나가 필요하다.

- 앱에서 `"not_alerted"` 제거, 또는
- 서버 enum 확장 (우리가 처리, 사전 합의 필요)

## ④ 앱 사번 폴백 제거 · **급하지 않음**

### 위치

```swift
// Phone/Sources/VitAlGuardPreviewApp.swift:14046
let employeeId = serverWorkerId.isEmpty ? vitalGuardEmployeeIdentifier(for: id) : serverWorkerId
```

### 배경

서버가 사번을 안 주면 앱이 `EMP-<로그인ID>` 로 직접 만들어 쓴다. 이 폴백이 사실상 표준이 되어
6개월치 데이터가 그 값으로 쌓였는데, 정작 서버 `users.employee_id` 는 **9명 중 8명이 비어 있었다.**
그 결과 사진 소유권 대조가 항상 실패해 **본인이 올린 사진도 못 지우는** 문제가 있었다.

### 서버는 이미 해결했다

07-27 배포로 서버가 **같은 규칙(`EMP-<username>`)으로 사번을 채운다.** 신규 가입도 자동 부여된다.
따라서 지금은 앱이 서버 값을 그대로 받고, **값이 동일해 동작 차이가 없다.**

### 요청 (정리 차원)

폴백을 제거하고 서버 값만 신뢰하도록 바꿔도 안전해졌다.

```swift
let employeeId = serverWorkerId
```

**단, 두 가지 주의사항이 있다.**

1. **서버 백필 배포(완료됨) 이후에만** 안전하다. 그 전에 했다면 사번이 빈 값이 되어
   업로드 데이터의 주인이 사라졌을 것이다
2. `vitalGuardEmployeeIdentifier` 함수 자체는 다른 곳에서도 쓰이므로(`3731`·`6941`·`12416` 등)
   **함수를 지우지 말고 이 호출부만** 바꿀 것

서버가 빈 값을 주는 경우 업로드를 막고 재로그인을 안내하면 더 안전하다(조용히 null 로 올리지 않기).

## 서버 쪽에서 이미 처리한 것 (참고)

앱 수정 없이 서버만으로 해소된 항목이다. 중복 작업하지 않도록 공유한다.

- `mlFallPipelineActive` 스키마 수용 — 앱이 보내는 값이 이제 저장된다
- 계정 사번 백필 — `users.employee_id` 9/9 채움 + 신규 가입 자동 부여
- 캘린더 사진 소유권 검증(DELETE·PATCH) — 앱 JWT 사번으로 본인 사진만
- 사진 소유자 데이터 정정 — 29/29

앱에서 사진 삭제 기능을 넣을 계획이라면, 서버 엔드포인트는 준비돼 있다.
`DELETE /api/calendar/media?id=…` 에 앱 JWT 를 Bearer 로 실으면 본인이 올린 사진만 삭제된다.
